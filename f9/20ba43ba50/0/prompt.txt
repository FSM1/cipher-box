The two new depth-3 fixtures are correctly written and correctly exposed a genuine, previously-undetected engine bug. No product or test code was changed — the working tree is clean (confirmed via `git diff --stat` and `git status --porcelain` on `packages/sdk-core`, `packages/sdk`, `tests/sdk-e2e`).

### Root cause

`collectDirtyFrontier` in `packages/sdk-core/src/rotation/engine.ts` (~line 815, calling `resolveChildKeyAndEnvelope` at ~line 664) determines whether a child edge is "dirty" by comparing `childPub.generation` (plaintext, from the child's own published IPNS envelope) against `childRef.generation` (the parent's mirrored generation) — but it does this check **after** unconditionally attempting to `unsealChildReadKey` (AEAD-decrypt) the child's `SealedChildRef.readKeySealed` with the parent's **current** readKey, with no try/catch. `resolveChildKeyAndEnvelope` bundles "fetch child's public envelope" and "decrypt the child's key" into one call, so the dirtiness check never gets a chance to run before the decrypt is attempted.

A genuinely dirty edge is, by definition, one whose ref hasn't been re-sealed to reflect the child's rotation. When the parent has **also** rotated in the same walk (the normal case — every node in a full-subtree `rotateReadFromNode` walk rotates, including every intermediate parent), the parent's current key differs from the old key the stale ref is still sealed under, so decrypting it with the current key **must** cryptographically fail. This is an ordering bug, not a crypto bug: the plaintext generation check should run first (no decryption required — `childPub.generation` is already available from `resolveAndFetchNode` alone), and the decrypt should only be attempted on a confirmed-clean edge.

This class of bug was structurally invisible to the sdk-core unit-test suite (`packages/sdk-core/src/__tests__/rotation/engine.test.ts`, `verifySubtreeClean — full-subtree recursion` describe block) because its mocks make `unsealChildReadKey` unconditionally succeed regardless of the key argument passed in — masking exactly the AEAD key-mismatch this bug produces with real crypto. The Plan 70.1-10 depth-3/multi-dirty-edge sdk-e2e fixtures are the first real-crypto test to exercise a genuinely-dirty, parent-also-rotated edge, which is exactly why Phase 70's crash-safety gate "passed vacuously" before.

### Evidence (live instrumentation, reverted after confirmation)

I temporarily added fingerprint-only (SHA-256, no key material) diagnostics around the `unsealChildReadKey` call in `resolveChildKeyAndEnvelope`, rebuilt `sdk-core`/`sdk` dist, and re-ran both failing tests individually:

- Test 5: `FAIL ipnsName=...b0zb childId=4701aa2d... childPubGen=1 childRefGen=0 ... err=Decryption failed` — this is fileA5, resolved via subA5's mirror. `childPubGen=1` (fileA5 really rotated/published) vs `childRefGen=0` (subA5's own mirror of fileA5 is stale) is precisely the dirty condition, but the decrypt attempt (using subA5's current/new key) throws before the comparison runs.
- Test 6: `FAIL ipnsName=...x85f childId=2c6e114d... childPubGen=1 childRefGen=0 ... err=Decryption failed` — same signature, one level shallower (root6's own children c1_6/c2_6), since root6 already rotated and its own D-09 batch never fired for either child before the crash.

Instrumentation was fully reverted (`git diff --stat packages/sdk-core/src/rotation/engine.ts` is empty) and dist rebuilt from clean source afterward.

### Recommended fix direction (not applied)

Restructure `collectDirtyFrontier`/`resolveChildKeyAndEnvelope` so the dirty check runs on plaintext data first:
1. Fetch `childPub` via `resolveAndFetchNode` alone (no decrypt).
2. If `childPub.generation &gt; childRef.generation` → dirty: push a `DirtyFrontierItem` **without** calling `unsealChildReadKey` at all — it's neither guaranteed to succeed nor needed, since `repairDirtyNode` (the consumer when `keyCheckpointCallbacks` is wired) already recovers the correct key via the ECIES checkpoint plane keyed by `childPub.id`, never via `item.nodeReadKey`. `DirtyFrontierItem.nodeReadKey` would need to become optional/placeholder for this path.

<result>Correct on my read of the code — there are two distinct sharing mechanisms, and `sent shares` is **not** the invite-link one.

**`sent shares`** (what the FUSE `SentSharesCache` / `GET /shares/sent` references) are **direct user-to-user shares**: the owner ECIES-wraps a folder's read key under a specific recipient's public key and creates a `Share` row (`apps/api/src/shares/shares.controller.ts`, `entities/share.entity.ts`). **Share invites** are the separate link-based flow (`share-invites.controller.ts`, `invites.controller.ts`, `entities/share-invite.entity.ts`, `AddShareInvites` migration): you mint a claimable invite (a link) for someone who isn't necessarily a known recipient yet; they later *claim* it, at which point it typically materializes into a `Share`. That's the "share via link" feature.

That's precisely the set of live grants — i.e., sent shares. An unclaimed invite link hasn't granted anyone key access yet; once claimed it becomes a `Share` and shows up in `/shares/sent`. ### Rename: you're correct — a same-folder rename does NOT rotate

`rename.rs:134-135`:
```rust
if parent != newparent
    &amp;&amp; crate::write_ops::grant_scope::run_scope_exit_gate(fs, source_ino).is_err()
```
The gate only runs when `parent != newparent`. The comment is explicit: *"A same-folder rename is NOT a scope exit — the node stays in place, so no rotation."* FUSE implements both "rename" and "move to another folder" as the same `rename` syscall, so the code has to distinguish them — and it does. Renaming `SharedFolder/FileA.txt` → `SharedFolder/FileB.txt` rotates nothing. Only a **cross-folder move** trips the gate.

(There's one extra case: if a move *overwrites* an existing shared destination, that destination's own removal is a scope-exit too — D-15d, `rename.rs:153-164`. But that's the overwritten victim leaving scope, not the rename itself.)

### Delete: it rotates because delete is a soft-delete = move OUT of the shared scope

This is the key thing your scenario is missing: **CipherBox delete is not a hard delete.** Deleting `SharedFolder/FileA.txt` moves FileA to User A's private recycle bin, and (`delete.rs:122-127`) *"the child's node/v3 read/write keys are re-sealed under the [bin plane]."* So structurally it's identical to a cross-folder move: the file object leaves the shared subtree and lands in A's private space.

Why that needs rotation: keys in CipherBox are derived **top-down through the folder key** (read chain: `parent_key` unseals each child's `readKeySealed`). B holds `SharedFolder`'s read key, so B can derive FileA's key. The shared-folder read key is the **only** revocation lever — there is no per-file revocation. The scope-exit rotation preserves the invariant *"the key a recipient holds only ever covers items currently in the shared scope."* When FileA leaves that scope, rotating `SharedFolder`'s read key is how the system enforces that B's grant no longer reaches it.

The D-07 commit-ordering in `delete.rs:94-97` confirms this is the intent: the rotation runs **before** the bin ref is sealed, precisely so the departing item is re-keyed with post-rotation material and can't be raced by a stale-key bin ref.

### The honest caveat (where I'd refute an over-strong reading)

Rotation is **forward-looking**, not a retroactive shred. It re-mints the folder key and re-seals the *remaining* children; it does **not** unpublish or re-encrypt FileA's already-published content CID (which stays pinned for bin recovery). So a recipient who *cached FileA's key before the delete* could still fetch that one old ciphertext out-of-band. What rotation guarantees is that B's held key stops matching the live tree going forward — which is the enforcement seam that makes an eventual full revocation of B sound. If your mental model was "rotation instantly destroys B's access to the deleted bytes," that part is not what it does.

### Net

- Same-folder rename → **no rotation** (you're right; code agrees).
- Private delete / private move (folder never shared) → **no rotation** (pure relink, `NoRotation`).
- Delete or cross-folder move of an item under a covering grant → **one rotation of the grant root**, because the item is leaving the shared scope and the folder key is the only revocation lever.
