### PRODUCT verdict: this is a REAL race, not test-only
`rotate_read_on_scope_exit` (crates/fuse/src/write_ops/grant_scope.rs) builds `FuseRotationDeps` over `fs.inodes`, and both pin consumers read that in-memory inode cache: `get_recipient_pubkey_pins → find_recipient_pins` (re-mint) and `reconstruct_write_body` (republish). That cache is materialized lazily (mount init / ~30s periodic metadata refresh). **In the real product flow the owner shares a folder from the web client** (which reseals the folder write-body with the new pin), then deletes inside it on their desktop mount before the next refresh → the rotation reads stale empty pins → `re_mint` fail-closes ("0 pinned") **and** `reconstruct` republishes the node pin-less, clobbering the real published pin → partial rotation → AES-GCM cascade. The fast Linux fuser mount happened to win the ~30s refresh race; slower FUSE-T (macOS) / WinFsp (Windows) do not. So this is genuine; fixing only the test would leave a real rotate-after-share gap.

### Fix (in-domain product fix — `da393f99d`)
Added `refresh_grant_root_recipient_pins` in `crates/fuse/src/write_ops/rotation_deps.rs`, called at the top of `rotate_read_on_scope_exit` **before** the rotation reads pins. It resolves + fetches + unseals the grant root's **current published** write-body (under the unchanged write key — write keys never rotate) and overwrites the inode's cached `recipient_pins` with the authoritative list. This makes both the re-mint read and the reconstruct republish see the fresh pin, deterministically, independent of the periodic-refresh timing. Best-effort: any resolve/fetch/unseal failure leaves the cache untouched and never fails the rotation itself.

I deliberately did **not** add test-side polling — the product fix makes the e2e deterministic without it. The e2e pin write (prior commit `0d9459c3d`) stays: it publishes the pin that the product refresh now reads at rotation time.
