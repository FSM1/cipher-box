## Deliberately left alone

All five items you flagged as load-bearing, untouched: the double stream-ceiling check, `onLeadershipChange`/`retireStreams`, the doubled `manifest.size != version.size`, `departed`/`endMint`, `MEDIA_WINDOW_BYTES`. No test assertion was removed.

Four findings I judged out of scope rather than rejecting:

1. **`MediaBroker` pins one engine stream per HTTP Range request, not per ticket** (`media/broker.ts:151`). `sw/pipe.ts` mints a fresh `requestId` per intercepted fetch, so a `&lt;video&gt;` re-pays `head_version` + root-manifest fetch on every Range request and every seek — for a 4 GiB file that is ~150 KB of manifest re-downloaded per seek. Pinning per *ticket* with a refcount would also give a stronger form of the #948 invariant (one version across a whole playback, not per response). **This is a behavior change, so I did not make it** — worth an issue.
2. **`RootManifest.leaf_cids: Vec&lt;Vec&lt;u8&gt;&gt;`** (`content/dag.rs:208`, not in this diff) is now long-lived state under the pin — one heap allocation per MiB of file, up to 256 streams. Every leaf CID is a fixed 36 bytes and `is_raw_leaf_cid` already enforces it, so `Box&lt;[[u8; CONTENT_CID_LEN]]&gt;` would collapse ~4096 allocations to 1 per open stream. Touches an untouched file's decode path; out of scope here.
3. **`EngineClient`'s handle-remap table** exists because the engine mints `StreamHandle` as a per-engine counter from 1. Seeding `LiveStreams.next` from the injected `Entropy` seam would make staleness self-detecting and let `EngineClient` go back to pass-through. Note that `WriteHandle` has the same property and no fence — so the codebase currently says "stream handles need a client-side table, write handles don't" with nothing expressing why. Larger than this PR.
4. **`LeaderRelay`'s `HandleKind` plumbing** — `unknownHandle`, `owners()`, `releaseHandles`, and `bind` each re-branch on the tag, and every `bind`/`release` call site re-supplies the closer. A `HandleTable` record would collapse it, but `bind`'s failure path closes a write handle via bare `abortWrite` while `release` routes it through `this.writes.run(...)`; unifying them would change behavior, so I left it.
