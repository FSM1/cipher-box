## 1. TEE worker republish route

File: `/Users/myankelev/Code/random/cipher-box/apps/tee-worker/src/routes/republish.ts` (the only route handler; helpers: `services/key-manager.ts`, `services/ipns-signer.ts`, `services/tee-keys.ts`).

**Sequence increment + re-signed record construction** (`republish.ts:78-102`):
```ts
// 3. Sign IPNS record with incremented sequence number
const newSequenceNumber = BigInt(entry.sequenceNumber) + 1n;          // :79  ← the roadmap "+ 1n"
const signedRecord = await signIpnsRecord(ipnsPrivateKey, entry.latestCid, newSequenceNumber); // :80
```
The re-signed record carries: **value/CID** = `entry.latestCid` (relay-supplied, passed as `'/ipfs/' + cid` inside `ipns-signer.ts:31`), **sequenceNumber** = `entry.sequenceNumber + 1n`, **EOL/validity** = fixed 48h (see below). There is **no `record.pubkey` field handled and no parse/verify of an incoming marshaled record** — the TEE *originates* a brand-new record from scalars rather than extending a supplied one. The returned `RepublishResult` (`:96-102`) reports `signedRecord` (base64) and `newSequenceNumber`.

So today's contract is the exact opposite of the spec's §6.4 "lease-renewer": it signs a supplied CID scalar and increments the sequence.

**Signing inputs source — schedule snapshot, NOT canonical `ipns_records`.** The TEE handler reads everything from the request body `RepublishEntry` (`republish.ts:25-32`): `encryptedIpnsKey`, `ipnsName`, `latestCid`, `sequenceNumber`, `currentEpoch`, `previousEpoch`. The relay builds that body from the **schedule snapshot row**, not the canonical record — `republish.service.ts:97-105`:
```ts
const teeEntries: RepublishEntry[] = batch.map((entry) =&gt; ({
  encryptedIpnsKey: entry.encryptedIpnsKey.toString('base64'),   // schedule col
  keyEpoch: entry.keyEpoch,                                       // schedule col
  ipnsName: entry.ipnsName,
  latestCid: entry.latestCid,                                     // schedule col (stale on content write)
  sequenceNumber: entry.sequenceNumber,                           // schedule col
  currentEpoch, previousEpoch,
}));
```
`entry` here is an `IpnsRepublishSchedule` from `getDueEntries()` (`republish.service.ts:43-52`, `scheduleRepository.find(...)`). The canonical `ipns_records` row is only touched *afterward*, on success, by `syncIpnsRecordSequence` (`republish.service.ts:158-163`, `:372-403`) — it is a write-back, never the signing source. This is precisely the §6.3 dual-source staleness the rewrite targets.

**`currentEpoch` / keyEpoch derivation — relay-supplied, not the enclave's own clock.** The TEE handler trusts `entry.currentEpoch` / `entry.previousEpoch` verbatim and feeds them straight into decryption/re-encryption (`republish.ts:71-90`). The values originate on the relay from `teeKeyStateService.getCurrentState()` (`republish.service.ts:80-87` → `currentEpoch`/`previousEpoch`). The enclave never consults its own clock or an epoch schedule. (`tee-keys.ts` derives a *keypair per epoch number* but accepts whatever epoch integer it's handed; `MIN_EPOCH`/`MAX_EPOCH` at `tee-keys.ts:18-19` are the only bound.) This is the §6.7-item-1 gap.

**Name↔key binding — ABSENT.** There is no `publicKeyFromIpnsName(ipnsName) == pubkey(decryptedKey) == record.pubkey` assertion anywhere in the TEE worker. A targeted grep for `publicKeyFromIpnsName|deriveIpnsName|pubkey|verifyIpns|parseIpnsRecord` across `apps/tee-worker/src` returns only an unrelated test hit. The handler decrypts `entry.encryptedIpnsKey`, signs `entry.latestCid` for `entry.ipnsName`, and never checks that the decrypted key actually derives to `ipnsName`. This is the §6.7-item-2 / test-18 gap.

**Tombstone / revoked-CID check — ABSENT in the TEE path.** The TEE worker does no tombstone or revocation check. The relay's `getDueEntries()` (`republish.service.ts:43-52`) selects on `status IN ('active','retrying')` and `nextRepublishAt` only — it does **not** join `ipns_records.tombstoned_at`. The only tombstone protection is reactive and downstream: `syncIpnsRecordSequence` adds `tombstonedAt: IsNull()` to its write-back UPDATE (`republish.service.ts:386-397`), and tombstoning calls `unenrollIpns` which merely *deletes the schedule row* (`ipns.service.ts:560`, `republish.service.ts:256-267`). The spec (`design …:491`) explicitly flags that schedule-row deletion alone is "not sufficient" and that the renewal CAS must also reject tombstoned names.

**IPNS key decryption flow (enclave) + EOL location.**
- Decryption: `republish.ts:67-76` base64-decodes `encryptedIpnsKey`, then `decryptWithFallback(...)` (`key-manager.ts:47-71`) tries `currentEpoch` then `previousEpoch`. Each attempt calls `decryptIpnsKey` (`key-manager.ts:23-33`) → `getKeypair(epoch)` (`tee-keys.ts:30-85`) → ECIES `unwrapKey(...)` from `@cipherbox/crypto`. The enclave private key is derived per epoch: simulator = HKDF-SHA256 from a fixed seed (`tee-keys.ts:66-71`); CVM/production = Phala `DstackClient.getKey('cipherbox/ipns-republish', 'epoch-${epoch}')` (`tee-keys.ts:47-65`). Keys are zeroed in `finally` (`key-manager.ts:30-32`) and again in the route (`republish.ts:92-94`, `:112-116`).
- Epoch upgrade/re-wrap: if `usedEpoch !== entry.currentEpoch`, `reEncryptForEpoch(ipnsPrivateKey, entry.currentEpoch)` (`republish.ts:86-90` → `key-manager.ts:84-90`) re-wraps under the relay-named `currentEpoch` pubkey and returns `upgradedEncryptedKey`/`upgradedKeyEpoch`. Note the re-wrap target epoch is **relay-chosen** (the §6.7-item-1 offline-forgery concern).
- EOL/validity: hardcoded in `ipns-signer.ts:11-12`, `TEE_RECORD_LIFETIME_MS = 48 * 60 * 60 * 1000` (48h), passed as the 4th arg to `createIpnsRecord(...)` at `ipns-signer.ts:30-36`. This is the only place lifetime is set; there is no "extend EOL on an existing record" path.

## 2. Publish path / CAS guard

The TEE renewal path does **not** itself run a compare-and-set. After the TEE returns a signed record, the relay's `RepublishService` publishes to delegated routing (`republish.service.ts:136`, `publishSignedRecord` at `:201-205`) and writes back the canonical row via `syncIpnsRecordSequence` (`:372-403`). That write-back is a forward-only/tombstone-gated UPDATE, **not** a sequence CAS:
```ts
await this.ipnsRecordRepository.update(
  { userId, ipnsName, tombstonedAt: IsNull(), sequenceNumber: LessThanOrEqual(newSequenceNumber) },
  { sequenceNumber: newSequenceNumber, signedRecord: Buffer.from(signedRecordBase64,'base64') }
); // republish.service.ts:386-397
```

The Phase-66 atomic compare-and-set lives in the **client publish path only**, `IpnsService.upsertIpnsRecord` (`/Users/myankelev/Code/random/cipher-box/apps/api/src/ipns/ipns.service.ts:379-392`):
```ts
.where(
  'ipns_name = :ipnsName AND sequence_number = :expected AND generation &lt;= CAST(:incoming AS bigint) AND tombstoned_at IS NULL',
  { ipnsName, expected: effectiveExpected, incoming: effectiveIncomingGeneration }
).execute();
// if (updateResult.affected === 0) → 409 / 410 disambiguation (ipns.service.ts:394-409)
```
This is the fused seq-CAS + generation gate + tombstone gate the spec §6.6 describes (matches the `WHERE sequenceNumber = :loaded` / `WHERE ipnsName = :n AND sequenceNumber = :expected` form). It also has an idempotent (equal-sequence) branch for the client re-sign path at `ipns.service.ts:311-317` and `:359-360`.

**Conclusion:** the relay client-publish path uses the Phase-66 CAS; the **TEE renewal path uses a different, weaker guard** (`LessThanOrEqual` write-back, not equality CAS) and routes the TEE's signed record straight to delegated routing without going through `upsertIpnsRecord`. Unifying these (TEE renewal hitting the same idempotent CAS branch) is exactly §6.6's "renewal write is guarded identically" requirement.
