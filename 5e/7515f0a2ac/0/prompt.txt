The scenario IS reachable through one path (someguy/DHT) but the binding-mismatch is caught at all client-side verifiers. The DB-cache path catches it; the network path serves the old CID but the *client* still accepts it because the old-CID record is internally self-consistent. Bottom line below.

All FUSE consumers funnel through `resolve_ipns_verified` (`crates/api-client/src/ipns.rs:169`), the single chokepoint. ### 3. Web resolve path (`apps/web`, `packages/sdk-core`)

### 4. someguy / delegated routing
Republisher pushes via `publishSignedRecord` → `delegatedRouting.publish` (`republish.service.ts:201-203`; client publish path `ipns.service.ts:125`) to someguy `PUT /routing/v1/ipns/{name}` (`delegated-routing.client.ts:48-50`). If the republisher signs the OLD CID at a forward sequence and pushes it, someguy holds an **internally self-consistent** record (sig matches its own embedded OLD CID + forward seq). Crucially: **all client checks (sig, pubKey→name, value↔cid binding, seq binding) PASS** for this record, because the binding checks only enforce internal consistency of the record — there is no comparison against the *true latest* CID. No client-side check rejects it.

### 5. Bottom line
**The stale-republished old CID is REACHABLE.** The relay's `latestCid` guard (`codec.ts:73`) only suppresses the *DB* copy; it does **not** filter the someguy/network record. Once `parseCachedRecord` returns null, `resolveRecord` falls through to `return result` (`ipns.service.ts:536-540`) and serves the old-CID network record. Every downstream verifier (Rust `bind_verified`, web `resolveIpnsRecord`) accepts it because the old record is self-consistent (valid sig over its own old CID at a high sequence) — the binding checks verify the record against *itself*, never against the true latest state. **So the republisher hazard is an exploitable read-revocation bypass, not merely an internal DB inconsistency** — the decisive code is `ipns.service.ts:506-540` (network record served whenever the DB cache is absent/discarded) combined with the fact that no verifier compares the resolved CID to an authoritative latest.

That defends record-internal consistency and DB-vs-network freshness, but it does NOT defend against a forward-sequence record pointing at an old CID — which is exactly the §4.3 M1 gap.
