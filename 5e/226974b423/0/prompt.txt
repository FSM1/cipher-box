**Branch** `fix/665-windows-unlink-barrier` · **PR #952** (DRAFT) — https://github.com/FSM1/cipher-box/pull/952 · fork base verified at `afb388752`.

## Summary

`FileStagingStore` treats op-record-before-sidecar removal ordering as a correctness property, but `fsync_dir` was `Ok(())` on non-Unix, so on Windows the ordering was never barriered. Replaced the no-op with a `metadata_log_barrier`: write a byte to a fresh `.cbtmp.` temp in the same directory and `sync_all` it, leaning on NTFS's LSN-ordered metadata log so flushing a later transaction persists the earlier directory-entry change. Pure `std::fs`, no Win32, crate stays `#![forbid(unsafe_code)]`. The barrier compiles under `cfg(any(not(unix), test))`, so the Windows algorithm is unit-tested on the Unix CI legs too.

**Key finding that widened the fix:** the issue (and the code comment) assumed `atomic_write` was still covered on Windows by `MOVEFILE_WRITE_THROUGH`. It is not — Rust std's Windows `rename` is `MoveFileExW(old, new, MOVEFILE_REPLACE_EXISTING)` only (`library/std/src/sys/fs/windows.rs`, checked against the 1.88 sources). So the rename was unbarriered too and the barrier had to cover both paths, not just unlinks.

## Dependencies concluded

No blocking prerequisite — `crates/desktop-seams` is a leaf adapter crate and the change is confined to its private `fs_util`. Historically depends on #646 (landed). Not fixable a layer down: the store holds op bytes verbatim and never parses them, so it cannot know which sidecar an op references and cannot repair the state at reopen. Relative to **#941** (engine mark-before-release, which cites this store's hard constraint 5 by name) and **#950** (cancel + orphan GC): different layer, no shared files, strictly reinforcing — #941's rule depends on the barrier this PR supplies, #950's GC is the reclaimer for the orphan this ordering deliberately leaves. The test name #941's body references is preserved.

## 2. The three `drain.rs` interaction questions

**Q1 — Double retire: impossible, by construction.** The two queues draw from disjoint CID families.

- `orphan_heads` is written at exactly one place, `drain.rs:1743`: `self.record_orphan_head(preflighted.cid())` — a **record head-envelope** CID.
- `retire_cancelled` (drain.rs:1826) retires exactly `cancels.uploaded_by(op_id)`, and `UploadCancels::confirmed` is called at exactly two places, `drain.rs:1414` (a content leaf) and `drain.rs:1441` (`staged.root_cid`) — both **content** blocks.

Nothing ever puts a head CID into `cancels`; nothing ever puts a content CID into `orphan_heads`.

There is a second, independent barrier for the same op: `record_orphan_head` fires only inside `publish_head`'s `map_err`, which is reachable only after `upload_version` succeeded, and `upload_version` returns `Err(Halt::Cancelled)` unless `enter_publish` returned true (drain.rs:1350). `enter_publish` sets `past_publish_entry` (cancel.rs:64), and `request()` refuses every subsequent cancel while that flag is set (cancel.rs:44-46). The flag is sticky across a failed attempt — `take_up` only resets `InFlight` for a *different* op (cancel.rs:94-102) — and is cleared only by `published()` (cancel.rs:69) at drain.rs:502.

And had they overlapped, it would be harmless: `retire` is idempotent server-side (net/retire.rs:13-16), so a replayed target is a no-op returning `Ok`, and `retire_orphan_heads` drains its queue on `Ok` (drain.rs:1814-1817) — no double decrement, no stale entry retrying forever.

**Q2 — The live-set guard: `retire_cancelled` has none, and I found a genuine reachable hazard. It is pre-existing on this branch, not caused by the rebase, and orthogonal to #944.**

`retire_cancelled` (drain.rs:1826-1838) has no `held`-set scan. Its intended safety is threefold: (a) `uploaded_by` returns only blocks *this session* confirmed for *this op* (cancel.rs:16-22, 85-87); (b) the publish-entry refusal above; (c) the dequeue gate at drain.rs:533.

Guard (b) is **session-scoped only** — `UploadCancels` is constructed fresh per Engine at facade.rs:1238 and is never persisted. That leaves a reachable window:

A crash between the record PUT acking and `release_staged_blocks` completing leaves an op that is **still queued** with its blocks **still staged** and its version **already published**. A `held`-set content-CID guard mirroring `record_orphan_head` would only narrow the window, not close it, since `held` is not guaranteed populated before the drain re-uploads. `pipe.ts` states its own rule twice — *"A same-origin port is still untrusted input"* and *"Vault plaintext must never reach a cache, whatever headers the tab sent"* — and then validates only **shape**. `content-type`, `x-content-type-options` and the `content-security-policy: default-src 'none'; sandbox` sandbox all originate tab-side in `packages/client/src/media/range.ts:23-45` (`safeMimeType` + `hardening`). The SW re-emits whatever pairs arrive and forces only `cache-control`.

Concrete scenario: `/stream/&lt;ticket&gt;` is a **top-level-navigable same-origin URL**. The comment at `range.ts:19-22` correctly identifies that a shared file's attacker-chosen MIME type would otherwise execute as the app itself. But the enforcement lives on the wrong side of the boundary the code declares untrusted. Exploitation today requires script execution on the origin, so this is defense-in-depth, not a live bug — but the cost of closing it is three lines, and the invariant is stated in the file that fails to enforce it.

**Fix** — force the hardening at the point the `Response` is constructed, exactly as `cache-control` already is, and clamp the type rather than trusting it:

```ts
merged.set('cache-control', 'no-store');

  merged.set('content-type', safeMimeType(merged.get('content-type') ?? ''));
  merged.set('x-content-type-options', 'nosniff');
  merged.set('content-security-policy', "default-src 'none'; sandbox");
}
```

Export `safeMimeType` from `range.ts` (it is currently module-private). `range.ts`'s copy then becomes belt-and-braces rather than the sole guard.

### [MEDIUM] Assembled plaintext is stranded unwiped on every trust-violation exit of `open_content_range`, and `content_wipe.rs` structurally cannot see it

**CONFIRMED** (static; the residue path is unreachable by the new watchdog by construction).

`crates/engine/src/content/mod.rs:244` and the two `Err` returns at `:260-265` and `:272-277`.

```rust
let mut plaintext = Vec::with_capacity(prealloc);   // :244  plain Vec, not Zeroizing
for index in leaves {
    let chunk = Zeroizing::new(open_chunk(...)?);   // :253  leaf IS wiped
    ...
    if chunk.len() as u64 != expected {
        return Err(OpenError::Trust(...));          // :261  `plaintext` drops UNWIPED
    }
    plaintext.extend_from_slice(&amp;chunk[from..to]);
}
if plaintext.len() as u64 != length {
    return Err(OpenError::Trust(...));              // :273  same
}
```

The diff correctly makes each leaf a terminal-owner `Zeroizing` (`:251-256` — and I verified the mechanics: `aead::decrypt` allocates a `Vec` of capacity `chunk+tag` and truncates in place, so the freed block genuinely carries the plaintext, and `Zeroize for Vec&lt;u8&gt;` wipes the full capacity). But the **assembly buffer** — which by the time of a mid-range reject holds every already-verified leaf's plaintext — is a bare `Vec` and is freed unwiped on both fail-closed paths. A hostile or corrupt manifest is exactly the case where an attacker wants residue left behind.

Second half: `crates/engine/tests/content_wipe.rs:34-36,50` gates the watchdog on `layout.size() == SEALED_LEN` (32). The assembly `Vec` in that test has `prealloc == length == 4`, so its deallocation is invisible to the allocator hook. The test's module doc claims *"A ranged read must not strand a leaf's plaintext in freed memory"* — true for the leaf, and the test does prove that (I ran it: `1 passed`) — but a reader will take the guarantee as broader than it is.

Related, pre-existing but now newly load-bearing: for `open_content` (full file) `prealloc = min(size, MAX_RESOLVED_RECORD_BYTES)`, so any file over that budget **reallocs repeatedly**, each growth orphaning an unwiped plaintext copy in the allocator. The ranged path happens to be exact (`prealloc == length`) so it does not grow — which is why the watchdog passes.

**Fix:**

```rust
let mut plaintext = Zeroizing::new(Vec::with_capacity(prealloc));
// ... unchanged body ...
Ok(core::mem::take(&amp;mut *plaintext))   // moves the buffer out; the empty Vec's drop is a no-op
```

`mem::take` keeps the caller as terminal owner (AGENTS.md rule 7 — no callee wiping a caller-owned buffer) while every early `Err` now wipes.

And widen the watchdog so the guarantee is actually tested: drop the `layout.size() == SEALED_LEN` filter to `layout.size() &gt;= MARKER.len()`, add a case that trips the `leaf {index} unsealed to …` reject after leaf 0 has already been appended, and assert no residue.

### [MEDIUM] Newest-port fallback answers a ticket from the wrong tab's registry, and a 404 is not retried

**CONFIRMED.** `packages/client/src/sw/pipe.ts:227-236` (`portFor`), `:210-225` (`acquirePort`), `:118-131` (`respond`).

```ts
private portFor(clientId: string): MessagePortLike | null {
  const own = this.ports.get(clientId);
  if (own) return own.port;
  let newest: PortEntry | undefined;
  for (const entry of this.ports.values()) newest = entry;   // any other client's port
  return newest?.port ?? null;
}
```

`acquirePort` short-circuits on any non-null `portFor`, so it never asks the owning client for a port when *some other* client has one. The retry loop at `:118` retries only when `head === null` (timeout) — a `head.ok === false` 404 returns immediately.

Concrete scenario, no attacker: tabs A and B are open. The SW is killed (routine — Chrome stops idle workers in ~30s; the diff's own spec exercises exactly this via `ServiceWorker.stopAllWorkers`). Both tabs get `needPort`; B answers first. A's `&lt;video&gt;` issues its next range request. `portFor('A')` finds no entry for A, falls back to B's port, B's `StreamRegistry` has never seen A's ticket → `sealed(404)`. The media element sees a hard 404 mid-playback and stops. The two-tab spec at `media.spec.ts:180-201` only covers the case where *both* tabs already hold ports, so it does not reach this.

Security framing: not a confidentiality leak — a ticket resolving in the wrong registry is a miss, and registries are per-tab. But it is an availability failure on the plaintext read path arising from a deliberate cross-client fallback, and the fallback is also the enabler for LOW-2.

**Fix:** when the request carries a real `clientId`, do not fall back to another client's port — broker to the owner:

```ts
private portFor(clientId: string): MessagePortLike | null {
  const own = this.ports.get(clientId);
  if (own) return own.port;
  if (clientId !== ANONYMOUS_CLIENT) return null;   // ask the owner instead
  let newest: PortEntry | undefined;
  for (const entry of this.ports.values()) newest = entry;
  return newest?.port ?? null;
}
```

Keep the newest-port fallback only for `ANONYMOUS_CLIENT` (top-level navigation to a ticket URL, where the browser reports no client id). If you additionally want a 404 to be recoverable, treat `status === 404` on the first of the two attempts as a re-broker trigger.

### [LOW] `downloadRange` accepts fractional offsets and silently truncates them

**CONFIRMED.** `crates/wasm/src/host.rs:386-397`.

### 1. LOW — content key left un-zeroized in freed heap after the `into_iter` refactor
`crates/engine/src/facade.rs:2545` — **CONFIRMED**, and a regression against `origin/main`.

```rust
let version_count = versions.len() as u64;
let Some(version) = versions.into_iter().next() else { … };
```

`Version` (`crates/core/src/seal/body.rs:131`) holds `content_key: SecretBytes`, whose `Drop` zeroizes (`crates/core/src/suite/secret.rs:36-40`). The 32 key bytes live inline in the `Vec&lt;Version&gt;` heap buffer. `into_iter().next()` is a `ptr::read` — a bitwise move — and `IntoIter::drop` then drops only elements `1..n` before freeing. Slot 0 is never dropped at that address, so the head version's content key stays verbatim in the freed allocation.

`origin/main` had `versions.first()` (a borrow), so the whole `Vec` dropped in place and every slot was zeroized. The refactor introduces the residue.

Scenario: every `read_content_range` — i.e. one per media seek and per buffer refill from the new SW byte pipe — strands one un-wiped copy of that file's content key. WASM linear memory is never returned to the OS, so copies accumulate across a playback session and are recoverable from a heap snapshot or `WebAssembly.Memory` dump. Not covered by the PR's own zeroize work: `content_wipe.rs`'s allocator watchdog only inspects `CHUNK + 16`-byte leaf-ciphertext blocks and cannot see a `Version`-sized allocation.

Fix: `let Some(version) = versions.first().cloned() else { … };` — `SecretBytes` is `Clone`, and keeping the `Vec` owning its elements restores in-place drop.

### 2. LOW — the pipe's newest-port fallback lets one tab's broker answer another client's request
`packages/client/src/sw/pipe.ts:239-245` — **CONFIRMED reachable, but no privilege gain.**

`portFor` falls back to the most recently adopted port for any `clientId` it holds no port for — including `''`, which every navigation and reserved-client request carries (`ANONYMOUS_CLIENT`, line 47). `waitForPort` (line 251) re-reads `portFor` on *any* adoption, so a request pending a re-broker can be resolved onto a port a different tab offered in the interim, leaking the requesting tab's ticket string to that tab's broker. A fresh client that never brokers (e.g. an iframe) can then redeem a known ticket against whichever tab brokered most recently and receive that tab's plaintext.

Why I am **not** rating this higher: every step requires an attacker-controlled same-origin script, and such a script already has strictly more power without any of this. `LeaderRelay.receive` (`leaderRelay.ts:133`) serves `cb:read` off the origin-wide, unauthenticated `BroadcastChannel` with no sender check, and `WireRead.download` (`broadcast.ts:38`) returns any node's full plaintext with no ticket at all. The port fallback confers nothing new. The owner-targeting at `pipe.ts:232-233` closes the common case correctly; only the concurrent-adoption race slips through.

Fix if you want the comment at `pipe.ts:65-69` ("one port per client") to actually hold: have `waitForPort` resolve only on an adoption whose `clientId` matches, and drop the newest-port fallback for a non-anonymous client.

### 3. LOW — the app-shell cache is never rotated, so the offline shell pins the first deploy a user installed
`packages/client/src/sw/precache.ts:12` (`APP_SHELL_CACHE` is a constant) with `precache.ts:75` (`deleteStaleCaches` explicitly excludes the live cache) and `apps/web/vite.config.ts:54` (`entryFileNames: SW_FILE`, no build stamp) — **CONFIRMED mechanism.**

`sw.js` contains no build-varying bytes (its content is a pure function of `packages/client/src/sw/**`), so a deploy that changes only app chunks leaves it byte-identical, no SW update is found, `install` never re-fires, and `precacheAppShell` never re-runs. The cache name never changes, so `deleteStaleCaches` cannot rotate it. The offline navigation fallback (`precache.ts:114`) therefore serves deploy-N's `/index.html` indefinitely, and deploy-N asset entries stay resident and claimed cache-first forever.

**Correction to how this was first reported to me:** a sub-agent rated both at MEDIUM on the claim that the app white-screens forever and that a security fix never reaches users. ### What was built

Follower read results (`snapshot`, `siweChallenge`, `download`, `downloadRange`) no longer ride the origin-wide `cipherbox-engine` `BroadcastChannel`. The follower asks where this leadership takes ports (`cb:portWanted` → `cb:portHost`), dials it through the Service Worker, names itself (`cb:portHello`), and adopts the port once the leader greets with the active leadership token. Reads then flow `cb:portRead`/`cb:portResult` over that port, with `ArrayBuffer` results **transferred**, not wrapped in a `Blob`.

A `BroadcastChannel` carries no transferables, so a Service Worker is the only cross-tab route for a `MessagePort`. The worker is a stateless forwarder — it names a client back to itself and forwards the far end of a `MessageChannel`, reading neither.
