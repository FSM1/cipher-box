## Diagnosis

The report artifact of run 35938670706 shows both grantee rows in the owner's listing. The footer shows "syncing...". So the owner pass reconciled the grantee's writes. The indicator was wrong after the data landed.

- **Mechanism 1 (found, this is the cause):** `status()` and `snapshot()` compute the staleness rung when the host reads it. A read during a pass returns `Reconciling`. After the pass, `stamp_staleness` sent `StalenessChanged` only when the rung differed from the last *event*, not from the last read. After a converged pass the rung is `Fresh` again, so no event went out. The web store reads the rung during a pass: on each `SnapshotUpdated` pull, and when `manualRefresh` resolves. So it kept `reconciling`, and no later event replaced it. A test holds the root read and reads the rung during the pass. On main it gets no event after the pass converges.
- **Mechanism 2 (found):** the manual refresh and the `Reconciling` rung had no time bound. A test shows that on main a refresh on a stalled pass stays pending past 30 s. The run gives no proof that a pass actually waited on the record deadlines.
- **Ruled out:** the lost-race loop. `Halt::LostRace` ends the drain for that pass. `UNATTRIBUTED_BUDGET` (120) limits the retries for each op. The test gave the owner no write in that window.
- **Not explained:** Playwright waited on "visible, enabled and stable" and never clicked. A rung that does not change does not change the button box. The engine harness cannot reproduce this.
- **Partial:** scope item 1 asked me to read the focus-window tick and the child resolve for a scope shared with write permission. I did not write up that read. The artifact shows the child resolve delivered both rows.

## What the PR does

- **Rung read recorded:** a host read of the rung records it as `SyncStatus::reported` (`SyncStatus::observe`). The pass that ends that rung then sends the next rung.
- **New bound:** `SyncTimingProfile::refresh_deadline` is 30 s in both profiles, one host record-request deadline. All timing comes from one clock: the pass start, which the tick loop records in `reconcile_started`.
- **Bounded rung:** `classify` shows `Reconciling` for one deadline only. After that it shows `Fresh` or `Stale` from the last success.
- **Rung changes during a pass:** `run_with_boundaries` wakes at each time `staleness::next_boundary` returns. It sends the new rung and lets the pass continue. It never cancels the pass.
- **Overdue refresh:** at the deadline, `ManualRefresh::overdue` sends the new `RefreshVerdict::Overdue` to every waiting request, and to each request filed later in that tick. `ForcedPass::landed` maps `Overdue` to `RefreshFailed`. The web command, the desktop path and the other `file_forced_pass` callers all get the bound.
- **Gates:** three Engine-harness tests in `cargo test -p cipherbox-engine`:
  - A read during the pass is replaced by an event when the pass converges.
  - A forced refresh on a stalled pass fails at the deadline, and in the same instant the host gets a rung other than `Reconciling`.
  - A refresh filed behind a stalled poll pass fails at that pass's deadline.

## Findings

### MEDIUM: a version from an unconfirmed edit can still surface at a sequence another record now holds (real, narrow)

**Location:** `crates/engine/src/sync/drain.rs` in `live_owing_record` (line 5498), in the head publish (`min_current_sequence: None` at line 6308, `Unconfirmed =&gt; Err(Halt::Attempt)` at line 6325), and in `resolved_bytes` (line 7106), which drops `tied`.

**Description:** An endpoint acknowledges the PUT of edit E at sequence N+1 but does not confirm it. The sequence floor stays at N. The version is dropped, and the user edits again. The new record Y also signs at N+1. If no endpoint serves E yet, Y confirms. The settle then reads head Y, and Y is not the base B. So the entry reads as `Published` and the settle retires E's CIDs. The background re-PUT (`spawn_background_reput`) can still put E on an endpoint that missed Y or refused it at the same sequence. `load_child_node` takes one record from a tie and ignores the others. A reader with floor N whose first endpoint serves E adopts E, and E's content is already unpinned.

The same gap applies to your case of `Edit(None)` when the node has later versions, and to a record from another writer at N+1.

**Impact:** Loss for new devices and share recipients. You need a lagging endpoint plus a refused or missed PUT at the same sequence. Honest endpoints can get there. A hostile endpoint gets there easily.

**Recommendation:**
- Record the acknowledged sequence S in the entry, for example `DroppedFrom::Edit { base, acked_seq }`, or keep a durable "acked-high" mark for each name.
- Pass `min_current_sequence = S` on the next publish of that name, so it signs strictly above E.
- In the settle, return `None` (wait) while the gated sequence is at or below S, or while `tied` is not empty. This rule does the job the head-CID check does now, and it does not depend on the base.

### LOW: the Edit rule can wait forever (leak, not loss)

**Location:** the same check at `drain.rs:5498`.

**Description:** A record above N+1 whose head is B again stands the entry down for good. A prune, a RestoreVersion, or a lazy-wave re-seal can make such a record. The stall reason says `NodeUnreadable`, which is wrong. The sequence rule above fixes this too.

<result>**Security review of commit c827c0f26**

**Summary:** The fold closes the MEDIUM loss path when the confirm returns `Unconfirmed`. That includes a record at N+1 from another writer or another device, and an Edit of a file with no version. One real loss path remains, through the `LostRace` arm. I found no new crypto or data-leak issue.

### MEDIUM (real): an acknowledged PUT that ties at its own sequence gets no mark

**Location:** `crates/engine/src/sync/drain.rs`, the `HeadPublish::Lost` arm of `publish_node`, with `net/publish.rs` `publish_pipeline`, the second confirm arm.

**Description:** When the confirm reads `observed.sequence == sequence` and the bytes are not ours, or are ours with a non-empty `tied`, the outcome is `LostRace`. At least one endpoint acknowledged E, and the code comment says "Our PUT was acked either way". No mark is written. This is the case of another writer at N+1 that races E. If the op then dead-letters before a rebased publish, E and the winner W both stand at N+1. At the settle, `loaded.tied` protects the debt only when the gated read sees both records. The republisher or a background re-PUT can show E later, after its CIDs are retired.

**Recommendation:** In the `Lost` arm, call `acknowledge(sequence)` when `observed_sequence == published_sequence`. Writing the mark for any acknowledged outcome that is not `Published` is also safe. Add a test in which the confirm reads a tie at the signed sequence and the op then dead-letters.

### LOW (real code, theoretical exploit): an unopenable mark reads as none

**Location:** `net/retire.rs` `acknowledged`.

**Description:** A failed seal open or decode returns `Ok(None)`. A partial write, a future `ACKED_V1` change, or host corruption then makes the settle go on, and the next publish can tie E again. The host can delete the key and get the same result, so this does not give an attacker more power. But corruption fails open, not closed.

**Recommendation:** Return a separate "present but unreadable" result. The settle then waits, and the publish signs above the durable floor plus the attempt count, or halts.

### LOW (theoretical): the Create empty-name rule ignores the mark

**Location:** `drain.rs` `live_owing_record`, the `Err(_) if owing == OwingRecord::Unconfirmed &amp;&amp; holds_no_record` arm.

**Description:** An acknowledged create PUT can come back after every endpoint said "none", through a background re-PUT or the republisher. The empty live set then retires E's CIDs.

**Recommendation:** Wait when a mark is held for the node.

### LOW (theoretical): a failed mark write can lose the mark

**Location:** `publish_node`, the `Unconfirmed` arm.

**Description:** If `acknowledge` fails, the halt is `Unclassified`, not `Attempt`. If the op dead-letters on a rebase before it publishes again, no mark exists, and a later local record can sign N+1 again. The loss also needs the staging store to fail right after the PUT.

**Recommendation:** Accept this and document it, or try the write again before the halt.

### INFO

- **Stale doc comment:** `Halt::Attempt` says "a retry re-signs at the same sequence". This is no longer true. Signing above the mark does not break `create_replays_a_publish`: the attempt charge is the same, and the floor stays unset after an unconfirmed create. It also does not break the attempt budget. Each unconfirmed attempt uses one extra sequence number, and the budget sets the limit.
- **Marks are never removed after a rotation or delete:** `forget_acknowledged` runs only when `acked.is_some()`. After the write name changes, the old-name mark reads as none, so it stays for good. It is kept as bookkeeping. This is a small leak: one key per node.
- **Other publishers ignore the mark:** rotation re-seal, liveness re-sign and revival can still tie E at N+1. The settle stays safe because it reads nothing at or below the mark. The tie itself is an existing issue.
- **Debt can wait a long time:** it waits until a record above the mark lands. The next edit or the EOL re-sign gives that record. This is a leak, not a loss.
- **Key metadata:** the key `cbx/ra/&lt;owner&gt;/&lt;node&gt;` shows the node id and the fact of an unconfirmed PUT. This matches the tombstone keys.

### AGENTS.md rules

- **Rule 8:** met. The encode side cannot make bytes that the decoder rejects.
- **Zeroize:** met. The body is `Zeroizing` and is owned locally.
- **Secret logging:** none.
- **Comments:** short. The only drift is the `Halt::Attempt` comment above.
- **Tracker refs:** none.

### Event `RegistryDebtUnjournaled`

The event has no payload, so it leaks no data. It is a sensible host signal. It fires on a failed expansion or a failed `owe`, and not when the root block is absent. The channel is unbounded, but the number of trimmed versions limits it.

### Recommendations

1. Write the mark on a `LostRace` at the signed sequence.
2. Make an unreadable mark fail closed.
3. Let a held mark block the Create empty-set rule.</result>
