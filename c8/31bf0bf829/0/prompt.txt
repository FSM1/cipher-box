### 2.2 `release-please.yml` mechanics
- Uses a **GitHub App token** (`create-github-app-token`, app-id `vars.RELEASE_BOT_APP_ID`, key `secrets.RELEASE_BOT_PRIVATE_KEY`) so release-PR pushes re-trigger CI.

- Post-release steps (only when `releases_created==true`): (a) **un-marks all manifest releases as `--latest=false`** (with retry) so `/releases/latest/` resolves to the desktop release marked latest by `desktop-staging-release.yml`; (b) **Cargo.lock post-merge fallback** — if the pre-merge sync raced the merge, opens a `chore/cargo-lock-sync-&lt;sha7&gt;` follow-up PR (never pushes to protected main) and best-effort auto-merges.

### 2.3 Per-PR release-target preview (bot commit mechanism)
- `pr-release-preview.yml` runs on every non-release PR. `node .github/scripts/pr-release-preview.js` analyzes PR commits and writes computed `release-as` targets into `release-please-config.json`.
- If config changed **and** the PR is same-repo (not a fork), the bot commits `chore(release): set release targets for PR #N` and `git push` onto the PR branch.
- **This commit is load-bearing:** dropping it makes release-please miss the version bump on merge. `concurrency.cancel-in-progress: false` lets a queued recompute finish so a force-push-clobbered target self-heals.

### 2.4 Tauri extra-files propagation
- `apps/desktop` component has `extra-files: ["src-tauri/tauri.conf.json", "src-tauri/Cargo.toml"]` — release-please propagates the `cipherbox-desktop` version bump into both files in addition to `apps/desktop/package.json`.

### 2.5 Cargo.lock sync (two-tier)
- **Primary (pre-merge):** `cargo-lock-release-sync.yml` runs on the `release-please--*` PR branch (unprotected), pins first-party crates (`cipherbox-api-client/core/crypto/fuse/sdk/desktop`) via `cargo update -p … --precise`, commits `chore(ci): sync Cargo.lock for released crates`, soft-pushes (tolerates lost race). Rationale: native cargo-workspace plugin is deliberately disabled (googleapis/release-please#2517 skips Cargo.lock in monorepo mode).
- **Fallback (post-merge):** the step inside `release-please.yml` (see 2.2).

### 2.6 Staging tag minting (`tag-staging.yml`)
- Manual dispatch → `resolve-main` verifies main HEAD carries a release tag (regex `^(cipher-box-v|cipherbox-.*-v|@cipherbox/)`), else fails ("Wait for release-please to merge"). → web-e2e + desktop-e2e gates run against that SHA. → `tag-staging` job requires **`staging-approval` environment** approval, computes `staging-${DATE}-release-${N}` where N is the per-day sequential counter (max existing +1), creates+pushes the tag. → `deploy` calls `deploy-staging.yml`. The `staging-` prefix avoids collision with release-please tag patterns.

### 2.7 "Release Automation Rules" from CLAUDE.md (documented failure modes, verbatim-ish)
From `/CLAUDE.md` §"Release Automation Rules":
- The `pr-release-preview.yml` workflow computes per-PR release targets and the bot pushes a `chore(release): set release targets for PR #N` commit onto the PR branch. **That commit is load-bearing: if it is dropped, release-please misses the version bump when the PR merges.**
- **"Never force-push over the bot `chore(release)` commit."** When updating an open PR branch, always `git fetch &amp;&amp; git rebase origin/&lt;branch&gt;` (or `git pull --rebase`) to preserve the bot commit — a `git push --force` clobbers it and silently drops the computed release targets.
- The preview workflow uses `concurrency.cancel-in-progress: false` as a safety-net: a queued recompute is allowed to finish so targets self-heal even if a push raced the bot. This is a backstop, not a license to force-push.
- **"Never leave a `release-as` pin in `release-please-config.json` equal to its `.release-please-manifest.json` version"** — that makes release-please re-release an already-shipped version (a self-comparing changelog loop). Remove the stale `release-as` key when this happens. **This is no longer CI-enforced, so check it manually.**

Also from §"Releases &amp; Versioning": on push to main, `release-please.yml` creates/updates the release PR; every component gets its own tag; desktop propagates version via extra-files; staging deploys triggered by `staging-*` tags minted by `tag-staging.yml` (verify release tag → E2E gates → `staging-approval` → tag → deploy).

Also §"Git Workflow" note: the husky `commit-msg` hook was replaced by an Entire CLI wrapper and **does not run commitlint locally**; PR titles are validated in CI by `pr-title.yml`.

### 9.1 pnpm workspace (`/pnpm-workspace.yaml`)

Root `Cargo.lock` is committed and load-bearing for release-please sync.

### 9.3 Version pinning
- **Node:** `node-version: '22'` hard-coded in every workflow (`ci.yml`, e2e, deploy, etc.). No `.nvmrc` and no `engines` field in any package.json. Dockerfiles: api `node:22-alpine`, tee-worker `node:20-alpine` (inconsistent), mock-ipns `node:22-alpine`.
- **pnpm:** `packageManager: "pnpm@10.33.0"` in root package.json; `pnpm/action-setup@v6.0.9` (reads packageManager) in CI; Dockerfiles `corepack prepare pnpm@10` (api/tee) / `pnpm@latest` (mock-ipns).
- **Rust:** `apps/desktop/src-tauri/rust-toolchain.toml` pins `channel = "1.88"`. **However every CI/deploy job installs `rustup default stable`** (ci.yml cargo-* jobs, desktop-e2e, deploy-staging, desktop-staging-release, cargo-lock-release-sync) — so CI effectively uses stable, not the pinned 1.88, except where cargo auto-reads the toolchain file. No root `rust-toolchain.toml`.

### 9.4 Caching strategy in CI
- **Node/pnpm:** `actions/setup-node` with `cache: 'pnpm'` (keyed on `pnpm-lock.yaml`) in all Node jobs; installs via `pnpm install --frozen-lockfile`. `landing` and `deploy-landing.yml` use `cache: 'npm'` with `cache-dependency-path: landing/package-lock.json`.
- **Cargo:** `actions/cache@55cc83…` on `~/.cargo/registry`, `~/.cargo/git`, and a target dir. Keys are per-OS+`hashFiles('Cargo.lock')` (ci.yml, desktop-e2e use root `Cargo.lock` and `target/`) or per-OS+`hashFiles('apps/desktop/src-tauri/Cargo.lock')` with `apps/desktop/src-tauri/target` (deploy-staging, desktop-staging-release). `restore-keys` fall back to `&lt;os&gt;-cargo-`. `cargo-llvm-cov` is `cargo install --locked` (uncached) in `ci.yml` `cargo-linux`.
- **Coverage artifact:** `ci.yml` `test` uploads `coverage-lcov` (7-day retention) consumed by `codecov-base.yml` on main.
