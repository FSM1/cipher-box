  - When a folder is shared, the client wraps **all descendant file &amp; subfolder keys** and sends them as `childKeys` to `/shares` POST endpoint (create-share.dto.ts)
  - These are stored in `share_keys` table with `keyType: 'file' | 'folder' | 'file-ipns' | 'folder-ipns'`
  - **Key types include `'folder-ipns'`** (types.ts:15) to allow write-share recipients to create/modify descendant subfolders (mirror of `file-ipns` for files)

- **Descendant items are NOT independently deleted when folder share is revoked:**
  - Revoking a folder share only revokes the single Share record (soft-delete via `revokedAt`)
  - ShareKey records are CASCADE-deleted when the Share is hard-deleted (completeRotation), cleaning up all nested keys at once
  - **No recursive traversal:** The server does NOT automatically revoke shares of descendant files/subfolders if they have independent shares
  - **Client responsibility:** If a descendant file/subfolder is independently shared with another user, that share must be revoked separately

- **Existing recursive handling:**
  - `reWrapForRecipients()` (share.service.ts:469-524) handles re-wrapping descendant keys after adding items to a shared folder
  - On folder modification with pending rotations, lazy key rotation (executeLazyRotation) re-wraps ALL child keys for remaining recipients
  - **No cascade revocation logic** — each share is independent; folder revocation doesn't imply descendant share revocation

---

### F. INVITE/LINK SHARES — ATTACHMENT &amp; REVOCATION

**Attachment Model:**
- Invites are **NOT attached to a specific Share record**
- Invites are **standalone records** tied only to the sharer + item (by `ipnsName`), not to a recipient until claimed
- Multiple invites can exist for the same item/sharer (e.g., three separate link-share tokens for one folder)

**Lifecycle (from share-invite.service.ts:34-223):**
1. **Create:** `createInvite(sharerId, dto)` → generate random token, store with `status: 'active'`, 7-day expiry
2. **Claim:** `claimInvite(token, claimerId, dto)` → atomic transactional create of a **new Share record** (user-to-user) with re-wrapped keys from claim DTO
3. **Post-claim:** The Share and ShareInvite have independent lifecycles; revoking the invite doesn't affect the claimed Share

**Revocation — Same or separate?**
- **Separate paths:**
  - **Invite revoke:** `ShareInviteService.revokeInvite(inviteId, sharerId)` — sets `status: 'revoked'`, prevents future claims
  - **Share revoke:** `SharesService.revokeShare(shareId, sharerId)` — sets `revokedAt`, triggers lazy rotation
  - **Already-claimed invites unaffected:** A claimed invite (which became a Share) is NOT revoked when the original invite is revoked; it's a separate Share with its own lifecycle

**Can single item have both?**
- ✅ **Yes.** A folder can have:
  - Multiple active invite links (`shareInvites` with `status: 'active'`)
  - Multiple user-to-user shares (`shares` with `revokedAt: null`)
  - Simultaneously, allowing the owner to share via link-tokens AND direct user shares

### GAPS / UNKNOWNS

1. **Bulk revoke-on-delete:** No existing endpoint or service method to revoke all shares for a file/folder in one request. Client must enumerate and call revoke per share (see soft-delete to bin requirement).

2. **Descendant share auto-revocation:** No automatic cascading revocation when a folder share is revoked. Independent shares of descendant items persist. Behavior is by design (each share is independent), but client must be aware.

3. **Share enumeration endpoint:** No server-side "list shares for this IPNS name" endpoint; client always fetches all shares and filters client-side. Could be optimized for deletion path (low-risk but not currently implemented).

4. **Invite hard-delete:** Revoked invites remain in database with `status: 'revoked'`. No cleanup / garbage collection documented.

5. **Write-share descendant creation:** When a recipient creates subfolders in a write-shared folder, the parent share includes `folder-ipns` keys allowing them to sign those subfolders.
