## 🔴 LOUD CALLOUT — Finding 20 is a real shipping write-plane clobber (now fixed)

**The bug (confirmed live):** `mergeChildren` (folder/merge.ts) is fully implemented — the "Phase-64 stub throws" docstring in registration.ts was stale. So on a 409 in `updateFolderMetadataAndPublish`, `publishWithCas` merges only the **read-body** (`SealedChildRef[]`), then `encodeAndUpload` reseals the **write-body** with the original closure value `params.writeChildren`. `decodeRemote` never even unsealed the remote write-body. Result: whenever two write-key holders (shared-write, or two devices of one owner) concurrently mutate the same folder, the loser's CAS retry **publishes a write-body missing the winner's freshly-added `WriteChildRef`** — the child stays readable but silently loses write capability. This is exactly the clobber class Phase 68.1 exists to prevent, on the concurrent-merge path. Reachable from ~8 owned call sites (createFolder/rename/delete/move/upload) + 2 bin sites, all of which pass a real writeKey.

**Fix:** `decodeRemote` now unseals the remote write-body (`unsealNode(..., params.writeKey)`); `merge` unions writeChildren by `childId` (remote wins; write plane is add-only so a union never resurrects a deleted ref); `encodeAndUpload` seals the merged set. I also made `updateFolderMetadataAndPublish` return `publishedWriteChildren` and threaded it into all 10 `adoptPublishedFolderState` sites (via `?? fallback`, mock-safe) so the in-memory mirror can't **re-drop** the merged ref on the next conflict-free publish.

**Finding 24 (related, NOT a leak, left as-is):** a *deleted* child's `WriteChildRef` is deliberately retained (write-link removal deferred to plan 68.1-02). This is chain **growth**, not data loss, and DFS never mis-traverses it — but the 68.1-02 removal should land so the write chain doesn't accumulate stale entries indefinitely.

**One latent risk worth owners' attention (finding 17, not flipped):** in *both* bin `getWriteBodyParams` and client.ts `getWriteBodyParams`, a **transient** IPNS resolve miss on an already-write-capable folder returns `writeChildren: []`, and the ensuing republish would seal an **empty** write-body — dropping the whole write chain. It's a documented D-03 fail-open and identical in both files, so I did not one-sidedly flip only the bin copy; flagging it for a holistic decision.</result>
