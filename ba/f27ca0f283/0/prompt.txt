## 1. How a file row gets its size and modified date today

**Engine**
- A folder listing can't carry file sizes. `merge_folder` (`crates/engine/src/sync/project.rs:158-203`) sets only the folder's own mtime (line 170). Its children keep whatever size/mtime they already had (191-194), and on a fresh session that's `None`.
- Size and mtime come from one place: `project_child_version` (`project.rs:211-231`). The focus leg calls it from `FolderRefresh::run_files` (`crates/engine/src/net/focus.rs:209-244`, call at 234). That happens only for rows on `FocusWindow::open_files` (`crates/engine/src/sync/tick.rs:62`).
- The snapshot copies `size`/`mtime` straight from the node meta (`facade.rs:9314`, children at 9335-9352).
- Rows get onto the queue through:
  - `queue_unprojected_children` (`tick.rs:570-587`): every file child of a folder with no size, queued as a "bulk" row.
  - `queue_focus_file` (`tick.rs:600-641`): damped by `stale_after`, capped at `MAX_FOCUS_FILES`, oldest bulk row dropped when full.

**Web**

## 3. Cold start vs warm start

I found no engine gate that skips queueing on a cold or first run:
- No first-run branch touches the focus window.
- No "projected" flag is persisted. The base is rebuilt every session from `Snapshot::new(root)` plus `project_root` (`crates/engine/src/sync/boot.rs:233-261`, installed at `facade.rs:4912-4955`), so every session starts with all file sizes `None`.
- `focus_refreshed` starts empty, so nothing is damped.
- The one leader/tab factor is the relay focus union (`packages/client/src/leaderRelay.ts:269-272`). It only forces a refresh and never sets the engine's `open_folder`.

The web does have a gate, and it hits exactly the root view:
1. `apps/web/src/vault/useFolderNavigation.ts:46` calls `store.setFocus(route.kind === 'node' ? route.id : null)`, so `/files` sends `null`.
2. `apps/web/src/engine/snapshotStore.ts:102` starts with `focus = null`, and `setFocus` returns early at `:199` when the node is unchanged. So on a fresh load at `/files`, `facade.setFocus` is never called at all.
3. Even when `null` is sent (e.g. navigating back to root, or `refocus`), `Command::SetFocus { node: None }` sets `open_folder = None` (`facade.rs:6239`). `refresh_focus_on_access(.., None)` then skips queueing (8707).
4. In the tick, `folders_in_view()` (`tick.rs:117-124`) returns nothing when `open_folder` is `None`. The web never touches `touched_folders`, so `queue_unprojected_children` never runs for the root either.
5. `null` is mapped to the root only for reads (`crates/wasm/src/host.rs:337`, `snapshot`), never for `SetFocus`. This was the same before #2122 (34895e2e0), where the old TS builder also mapped `null` to `undefined`/`None`.

So on a fresh session, the root's file rows are never resolved. Folder rows can still have a date, because a folder's own mtime is set when that folder was resolved as a navigation target (`merge_folder`, project.rs:170). That fits a user who opened some subfolders and came back to `/files`. I couldn't confirm which view the reporter was on, and that affects the folder-date part of the symptom. "Synced" is expected: the root leg reconciles and no file leg ever runs to fail. I don't see how warm vs cold would differ in the engine. The likeliest explanation is route: a warm tab more often sits on `/files/&lt;id&gt;`, where queueing works.

## Best hypothesis

`null` means "the root" to the web but "no folder open" to the engine. At `/files`, the engine's `open_folder` stays `None` (the initial `setFocus(null)` is even skipped by the dedup at `snapshotStore.ts:199`). As a result:
- `refresh_focus_on_access` never queues the root's children (`facade.rs:8707`).
- The tick's `queue_unprojected_children` loop over `folders_in_view()` (`pass.rs:669-686`) has nothing to iterate.
- Root file rows keep `size`/`mtime = None` forever, which renders as `...`.

The three fixes are intact but only work when the root is passed as `Some(root)`, which is what every Rust test does and what the web never does. This behaviour dates from #899/#971 and was never covered. Two places could close it: the engine could treat `SetFocus { node: None }` as the root in `folders_in_view`/`refresh_focus_on_access`, or the web could send `view.root` (`host.rs:337` already resolves `null` to the root for reads). A Rust test using `SetFocus { node: None }` and an end-to-end test that checks root-level cells on a cold start would pin it. I haven't changed anything.</result>

## Root cause

1. **The forced refresh runs one step behind the focus.** In `apps/web/src/engine/snapshotStore.ts`, `assertFocus` (~165-172) calls `client.reportFocus(focus)` first, and only then calls `client.facade.setFocus(focus)`. `reportFocus` goes to `LeaderRelay.reportLocalFocus` (`packages/client/src/leaderRelay.ts:271`), which calls `forceRefresh` (~689), which sends `manualRefresh` at once. The engine runs one command at a time (`Engine::command(&amp;mut self)`, `facade.rs:6027`). So `manualRefresh` runs to completion first, with the old focus (root). `SetFocus` runs after it.
2. **The navigation skips the shared folder's rows.** `SetFocus` (`facade.rs:6238`) calls `refresh_focus_on_access`. That function queues the rows (`queue_focus_file_children`). Then `scoped_to(root, …)` (~8713) removes every row whose scope is the shared folder's scope. This is intentional (`the_navigation_file_leg_leaves_a_shared_scopes_rows_to_that_scope`). The rows stay queued and are not marked as attempted.
3. **Only the tick's scope leg can paint them.** That leg is in `TickPass::refresh_focus` (`pass.rs` ~660-700). No forced pass follows the focus change, so the rows wait for the next poll tick (30 s in production).

**Why the second open paints at once.** The click back to the root sends `manualRefresh` while the engine's focus is still the shared folder. That forced pass runs the shared folder's scope leg and paints the queued rows. So the second open paints through that leftover forced pass, not through its own navigation leg.

**Hypotheses I ruled out:**
- `descendant_scope_roots` and `scope_read_seeds` are not filled late. Each pass runs `walk_scopes` (which calls `install_descendant_scopes`, `pass.rs:1568`) before `refresh_focus` (`pass.rs:200-201`). The forced pass at `/files` has therefore installed the scope, its seed and its listing before the click.
- No row is attempted under the wrong scope and then held back by the 90 s staleness stamp. I checked this with event and queue instrumentation: no abuse event, and the row is still queued after `SetFocus`.

**Another problem, not the reported defect.** If `SetFocus(shared)` runs before any pass (cold session, no refresh yet), the navigation folder leg reads the shared folder under the vault root seed. ## Proposed fix

In `refresh_focus_on_access` (`facade.rs` ~8659), run the file leg once per scope instead of only for the vault root:

- Group `queued_focus_files()` by `scope_root_of` over `focus_scope_roots(...)`.
- For each scope that is not in `unproved_scope_roots` and has both `self.scope_read_seed(&amp;scope.0)` and `self.scope_floors(&amp;scope.0)`, build a `FolderRefresh` with:
  - `scope_id: scope.0`, that scope's seed and floors;
  - `scope_root_name` from `scope_root_record_name`;
  - `plane: None` when `is_own_scope`, else `GraftedLeg`.
- Settle and remove the rows from the queue, as the root leg does now.
- Rows of a scope without a seed stay queued for the tick.

Each row is still read only under its own scope, so the AAD rule holds. The test above then passes. `the_navigation_file_leg_leaves_a_shared_scopes_rows_to_that_scope` needs to change: a scope with no seed stays queued, and a scope with a seed is attempted under its own seed.
