## Core crypto findings

### [POSITIVE] D-09 terminal-owner boundary is correct for the new key map
- Rust `RotatedNodeKey.read_key` is `Zeroizing&lt;[u8;32]&gt;` (`engine.rs:823`), inserted via `.clone()` at all three hooks (root `engine.rs:1629-1637`, BFS child `:1876-1884`, repair `:2091-2099`) — each map entry is an **independent** owned buffer that self-zeroes on drop. The engine never zeros the returned map; FUSE `refresh_rotated_inode_read_keys` copies in place and does not zero `result.rotated_nodes`. Boundary is correct.
- FUSE inode refresh overwrites in place via `copy_from_slice` (`grant_scope.rs:592`), discarding the old key. No key bytes logged (info log emits only `ipns_name` + `child_id`, both public).

### [POSITIVE, with one verified subtlety] TS map stores references, not copies — but they are never zeroed
- Unlike Rust's `.clone()`, TS `rotatedNodes.set(..., readKey: result.childReadKey)` (`engine.ts:2046, 2065, 2233`) stores the **same** `Uint8Array` that is also aliased into `ParentTrackingState.parentNewReadKey`. I traced every `.fill(0)`: teardown (`decrementPendingAndMaybeRepublish:1663`) zeros only `parentOldReadKey`, explicitly **not** `parentNewReadKey`; the BFS `finally:2373` zeros only `item.nodeReadKey` (the OLD key, a different buffer). So the stored NEW key is never zeroed and the returned map is not corrupted. **Correct today, but fragile** — a future change that zeros `parentNewReadKey` would silently zero the returned map entry (→ inode refreshed with a zero key). Recommend defensively copying (`new Uint8Array(result.childReadKey)`) at the three `set` sites to match Rust's `.clone()` and remove the aliasing hazard. Severity **LOW** (latent).

### [POSITIVE] Deep inode refresh ordering closes the stale-key bypass
- `rotate_read_on_scope_exit` calls `refresh_rotated_inode_read_keys` (`grant_scope.rs:534`) **before** returning `Ok`, and all callers run their relink/reseal only after the gate returns. Every rotated node present in the loaded inode table (Root/Folder/**File**) is refreshed by `ipns_name` with no early-return, so no intermediate node reseals under a stale pre-rotation key. Nodes not currently loaded carry no in-memory key and are re-resolved fresh. This is the T-74-04 deep-path fix and it looks sound.

### [POSITIVE] Revocation invariant upheld
- Rust `re_mint_grants_rooted_at` (`engine.rs:604-618`): `is_revoked` → `delete_grant` (no re-mint); retained → `wrap_key(new_read_key, recipient_public_key)` re-wraps under the **new** read key at the new generation. TS parity at `engine.ts:604-616`. Both use base64. FUSE source hard-codes `is_revoked: false` (`rotation_deps.rs`), which is correct because revoked shares are hard-deleted server-side and thus absent from `GET /shares/sent` — revocation by absence, not flag. `collect_sent_shares` paginates fully (`shares.rs` loop), so no page-limit truncation dropping retained recipients.

### [POSITIVE] Wire DTOs leak no plaintext / no write key
- `UpdateGrantRequest` (`shares.rs`) carries only `encryptedReadKey` (ECIES ciphertext) + `rootGeneration`; `encryptedWriteKey`/`clearEncryptedWriteKey` intentionally omitted, so `update_grant` provably cannot touch the write key (test `update_grant_patches_grant_path_with_read_key_only_body` asserts their absence). `revoke_share` sends only the share id in the path. Error messages include `share_id`/status/body but never key bytes.

### [POSITIVE] TS/Rust `RotatedNodeKey` shape parity
- Field-for-field: `ipns_name/ipnsName`, `read_key/readKey`, `generation` (u32/number), `sequence_number/sequenceNumber` (u64/bigint). No drift that could cause silent mis-decryption. Root-convenience top-level fields kept and consistent with the map's root entry.

### [POSITIVE] No new nonce/IV or key reuse
- Fresh keys minted per node via existing `rotateOne`/`mint_file_key_on_rotate`; ECIES `wrap_key` uses a fresh ephemeral per call (ecies crate). No content-encryption IV handling changed. No key reused across generations.

## Uncertain / flagged

### [UNCERTAIN – LOW] Repaired-node generation surfaced differs between engines
- Rust `repair_dirty_node` inserts the map entry with `published.generation`/`resolved.sequence_number` (`engine.rs:2094-2097`), i.e. the recovered node's already-committed generation. TS has no separate repair-insert; dirty-tail nodes flow through the BFS loop and are inserted with `result.newGeneration` (re-rotation). This reflects the pre-existing architectural difference (Rust repairs vs TS safe-double-rotates on dirty-resume), not something introduced here. The surfaced **read_key** is the node's valid current key in both, so inode decryption is correct; only the `generation` bookkeeping field could differ. I could not fully rule out a downstream AAD-generation mismatch if a caller later reseals using this surfaced `generation`. Worth a targeted parity test; flagging as uncertain rather than asserting a defect.

### [UNCERTAIN – LOW] `recipient_public_key` format assumption
- `wrap_key` requires a 65-byte uncompressed key with `0x04` prefix (`crypto/ecies.rs:22-31`). Re-mint feeds it the hex-decoded `recipient_public_key`. The system mints recipients as 65-byte uncompressed (`grant.ts:121`), so this is consistent. If any code path ever stored a compressed (33-byte) recipient key, re-mint would **fail closed** (rotation error, not a bypass). Not a defect in this diff; noting the invariant. (The test fixture uses a 33-byte `0x04…` stub that never reaches `wrap_key`, so it doesn't exercise the real constraint — see test-gap below.)

- **Wiring a no-op dependency to a real network call silently breaks tests that relied on the no-op** — 74-05's real `query_grants_rooted_at` flipped an unrelated pre-existing `delete.rs` fail-closed test red until its mock server gained a `GET /shares/sent` route; only the full-crate run caught it.
- **Plans' `read_first` repeatedly referenced harnesses/configs that didn't exist** (a WinFsp test module, a mock-HTTP harness, `tests/desktop-e2e/tsconfig.json`) — each needed a minimal additive creation before the plan's own steps were runnable.
- **A behavior fix can invalidate a pre-existing test's semantics without touching the test** — the Part A "Bob" e2e assertion encodes pre-74-05 (cut-off) behavior; left untouched and flagged as a Known Risk, with static analysis suggesting it's a false alarm (it decrypts against a stale pre-rotation key regardless of re-mint).
