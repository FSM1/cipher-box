### What shipped

`DefaultsReason::NoRecord` was derived from the per-name sequence floor alone — a mark only a *confirmed adopt* raises. A settings record leaves three durable marks; the two the sequence floor misses are the ones that matter:

- **The publish mint counter**, raised by `next_revision` ahead of everything a publish can fail at. A member whose placement save never landed still carries durable proof of the choice — the moment reverting it is cheapest.
- **The adopted body revision**, raised by a store write separate from and not atomic with the sequence floor's (both `let _ =`, and `commit_floors` is documented non-atomic). A device that took one and lost the other demonstrably adopted a record.

All three are now read on the withheld branch; any present makes a missing record `Suppressed`, which already refuses. Unreadable marks fail closed to `FloorUnreadable`. `NoRecord` → `UnprovenFirstRun`, because absence is only ever a verdict about *this device* and this is the one degraded arm that still authorises a write. No gate moved.

### Design constraint worth knowing

Refusing the unproven first run outright is not available: `publish_settings` has no production caller (#1144), so "no record" is the universal state and a blanket refusal would refuse every content write on every account. The mint-counter half is therefore dormant until a settings-save command is wired; the adopted-revision and unreadable-mark halves are live now.

## 1. Non-zero `ftruncate` resurrects deleted plaintext into the published version

`crates/fuse/src/ops.rs:517-552` — **Severity: MEDIUM**, confidence 9/10. Confirmed.

**Mechanism.** `truncate_handle` records a shrink as only `pending.len = size`. It sets `pending.base = Base::Empty` only when `size == 0` (`ops.rs:547-549`), and `SpillFile::truncate` (`spill.rs:136-149`) only retains/zero-tails blocks the spill *already holds* — on a freshly opened handle the spill is empty, so it is a no-op. `Pending` (`ops.rs:70-79`) carries no truncation floor. Later, `version_block` (`ops.rs:642-652`) resolves any block the spill does not hold by reading the pinned **pre-truncate** base version via `engine.read_stream`, which knows nothing of `pending.len`. `push_version` (`ops.rs:592-598`) then walks `0..len` with no clamp and publishes those bytes.

**Repro — two syscalls, no write needed.** File has a published 100-byte version. `open(O_RDWR)`; `ftruncate(fd, 10)` → `Pending { spill: None, len: 10, base: Version, dirty: true }`; `ftruncate(fd, 100)` → spill is `None` so the spill truncate is a no-op, `len = 100`, `base` stays `Version`; `close(fd)` → every block falls through to the base stream and the published version is byte-for-byte the original 100 bytes. The shrink is entirely undone. The shrink-then-write-past-the-cut variant yields the same for the gap region, which POSIX requires to read as zeros.

**Why security-relevant.** The resurrected plaintext is re-sealed and published as a new *live* version, so (a) a file shared after the user truncated sensitive bytes away exposes those bytes to a recipient who never held the prior version, and (b) the deleted tail is carried into every later version and into a rotated epoch's reseal. Deterministic, no race, reachable from unprivileged `ftruncate(2)`. `create` correctly sets `Base::Empty` (`ops.rs:207`), so this hits exactly the pre-existing-file case where deleted content exists.

**Fix.** Add a truncation floor to `Pending` (e.g. `zeroed_from: Option&lt;u64&gt;`, set on every shrink, raised/cleared as writes fill it). Have `version_block` return zeros — never a base read — for indices wholly at or past the floor, and zero the tail of the straddling block after the base read.

**Test gap.** `crates/fuse/tests/fuse_op_core.rs` exercises truncate only at `size == 0` (lines 986, 1068, 1094, 1115) — the one case `Base::Empty` masks. Add shrink-then-grow and shrink-then-write-past tests.

But two other things make it not-small:

1. `version_block` fetches `want = block_bytes.min(base_len - at)` and zero-fills the rest, because bytes past the floor a truncate left must read as a hole. That clamp is per-handle `Pending` state, not a property of the stream. 2. `push_version` walks the file linearly once, so inserting every base block it touches evicts the reader's hot blocks for zero reuse against a 64-block budget. The commit walk wants read-through-without-insert, which the cache doesn't offer.

So the correct fix is a semantics change on the clamp the head commit just corrected plus a new cache mode. #1168 carries both constraints and acceptance criteria; labels `v2-build` + `comp:desktop`, milestone `v2.0.0`, `parent_issue_url` → `issues/991`, `blocked_by` → `[1110]` (all verified by re-read).

## Verdict on A — half refuted, half real

**Refuted: the overwrite cannot happen.**
- `MediaPlayer.tsx:45` — `onError: () =&gt; setRefusal((held) =&gt; held ?? { recoverable: false, message: FAULT_NOTICE })`. A held refusal wins; a recoverable one is never replaced and the retry control never disappears.
- `broker.ts:441-446` — `fail()` posts `cb:media:error` to the port and calls `onFailure` on the next line, synchronously. The port message still has to reach the SW, error the response body, and surface as an element `error` event — all strictly later tasks. So a subscribed listener always hears the classified reason *before* the element's unclassifiable one.

**Real: the subscription window.** `service.ts:89-93` keeps a plain listener `Set` with no replay — a failure reported before the subscription is lost, leaving `refusal` null so only the terminal notice shows.

**Fix (minimal, no restructure):** `useEffect` → `useLayoutEffect` in `MediaPlayer.tsx:24`. Layout effects run inside the same synchronous commit that inserts the element, so no event-loop turn can deliver anything between the element getting its `src` and the listener existing. I did **not** add the reviewer's URL-scoped readiness state — withholding `src` would delay every playback for a race that needs several message round-trips to land inside one commit.
