## Commands and requests
- `emailLinkSendCode { email }` posts `POST /auth/email/link/send-code` with a Bearer token and the body `{"email": ...}`.
- `emailLink { email, code }` does two requests, as `siwe_link` does:
  1. `POST /auth/challenge/step-up` with `{"operation":"link"}`. The engine checks the challenge prefix before the identity key signs it.
  2. `POST /auth/email/link` with a Bearer token and `{"email", "code", "challenge", "challengeSignature"}`.
- Both commands accept a 201 with an empty body. A 409 becomes `ApiError::Status { message }`, and the host shows it as `"api returned status 409: Email is already linked to another account"`. This is the same mapping that `siwe_link` uses.

## Findings

### [MEDIUM] F1: A link trusts a device row that the API cannot check, so one leaked identity token becomes a permanent way into the victim's subject

**Location:** `apps/api/src/device-approval/services/account-device.service.ts:208` (`boundSubjectOf`), `apps/api/src/auth/services/auth.service.ts:267` (`linkMethod`)

**Invariant broken:** After a link, the method must reach the subject that derives this account's key. The link takes `bound` from `account_devices.identity_subject_id`. A device row proves only that the registrant once held an identity token for that subject. It does not prove that the subject derives the account's key. ADR 0058 Context says this directly: the API "cannot compute the key that a subject derives". This interim source inherits ADR 0039 E4.

**Scenario:**
1. The attacker gets an unspent identity token for victim subject S_V. The window is the one ADR 0058 Context names: "from the mint to the member's first registration, which can come days after the sign-in, or never".
2. The attacker calls `POST /auth/login` with a fresh random secp256k1 key. This makes a new account A with no device.
3. The attacker sends `POST /devices` with the leaked token. The row {A, S_V} passes `claimedElsewhere`, so `boundSubjectOf(A)` returns S_V.
4. The attacker links their own wallet W. They re-prove with A's key and sign SIWE with W. The PR writes `identity_subjects(wallet, H(W)) → S_V`.
5. From now on, every SIWE sign-in with W mints a fresh identity token whose `sub` is S_V.

The Core Kit is constructed without `disableHashedFactorKey` (`apps/web/src/auth/coreKit.ts:616`, `apps/desktop/src/auth/coreKit.ts:232`). The SDK default keeps the hashed factor on. So, while the victim has no factor policy, each such token reconstructs the victim's full TSS key. After the victim enables the policy, the route still gives the auth share.

Before this PR, the leak was single-use and lasted 300 s. After this PR, it is permanent. The victim cannot see or unlink W, because W is listed under account A.

**Recommendation:** The owner must decide the sequence. One choice: land ADR 0058 D1 (`users.identity_subject_id`, written at login under the subject lock), and gate `linkMethod` on that column, before email or wallet link ships. The other choice: record this amplification as an ADR 0058 residual next to E1. Server-side code cannot close the gap, because the server cannot connect a subject to a key. Do not try to patch it in code.

### [MEDIUM] F2: The link-code email looks the same as the sign-in-code email, so the purpose split does not stop phishing

**Location:** `apps/api/src/auth/services/mail.provider.ts:14,26-45`, `apps/api/src/auth/services/email-otp.service.ts:100`

**Invariant broken:** Item 3. A proof for one operation must not serve another. The server keeps the codes apart (`storeKey`). The person reading the email cannot tell them apart. Subject and body are both "Your CipherBox verification code". The contract helper confirms this: "A sign-in code and a link code log the same line".

**Scenario:**
1. Any account holder calls `POST /auth/email/link/send-code` for the victim's address X.
2. The phisher asks for "your CipherBox sign-in code", and the victim reads it out.
3. The phisher links X to the phisher's account. This works when X has no origin subject yet.
4. The victim's next email sign-in opens the phisher's vault. The victim uploads into it, and the phisher reads every file (account fixation).

The comment at `email-otp.service.ts:20-26` says the split stops exactly this attack. That claim is false while the email text is the same.

**Recommendation:** Pass the purpose to `MailProvider.sendVerificationCode(to, code, purpose)`. Give the link email its own subject and body, for example: "Someone signed in to CipherBox asked to add this address as a login. Do not share this code." Add a test at the `MailProvider` seam.

### [LOW] F3: A link code is not bound to the account that asked for it

**Location:** `apps/api/src/auth/services/email-otp.service.ts:201` (`storeKey`), `apps/api/src/auth/auth.controller.ts:196-197`

**Invariant broken:** A code must reach only the session that requested it.

**Scenario:** The member asks for a link code for X. An attacker sees the code, for example by shoulder-surfing or a shared inbox. The attacker spends it first from their own account. X then opens the attacker's vault, with the same fixation as F2. The member's own attempt fails with "No verification code is outstanding".

A second, smaller point: `send-code` needs only an access token. A stolen token can send link emails to any address. The limits are five per address per 15 minutes for each purpose, plus the throttle. The split also doubles each address's send budget.

**Recommendation:** Store link codes as `link:&lt;userId&gt;:&lt;address&gt;`. `request.user.userId` is already in scope at the controller, so this is a two-line change. Add a test that account B cannot spend a code that account A requested.

### [LOW] F4: When the bound subject is null, the unlink guard lets the unlink through but revokes nothing

**Location:** `apps/api/src/auth/services/auth.service.ts:350,376-377`

**Invariant broken:** After an unlink, the method must reach no key, or the unlink must refuse.

**Scenario:** The account has zero devices, or devices that carry more than one subject, so `bound` is null. The member unlinks the email that was its origin subject. The condition `isOrigin &amp;&amp; subject.subjectId === bound` is false. The display row is deleted and the subject row stays. The method keeps opening the account, but the response is a success.

The new text in `blueprint/api.md:100` ("refuses the identity the account was created through") is therefore false in this case. This is the false revocation that the `UNLINKABLE_KINDS` comment warns about.

**Recommendation:** Answer 409 when `isOrigin &amp;&amp; bound === null`, because the server cannot tell whose origin row it is. A cleaner fix is to read the ADR 0058 D1 column when it lands.

### [LOW] F5: `bound` is read outside the transaction and without the registry lock

**Location:** `apps/api/src/auth/services/auth.service.ts:267,350`

**Invariant broken:** Item 2. The write paths run under the locks that guard their inputs.

**Scenario:** A device revoke or registration commits between `boundSubjectOf` and the link transaction. The link then writes an `identity_subjects` row against a subject set that has already changed. A real attack needs F1's preconditions. Even without an attacker, the check and the write are not atomic.

**Recommendation:** Move `boundSubjectOf` inside `runLockGuardedTransaction`, read it through `manager`, and add `registryLockKey(userId)` to the `boundedAcquire` list. That is the same lock `claim()` takes.

### [INFO] F6: Nothing in the schema says a `subject_id` names an existing origin row

**Location:** `apps/api/src/migrations/1790700000000-AddIdentitySubjectSubjectId.ts`

**Invariant at risk:** `account_devices.identity_subject_id` now stores token `sub` values, which are subject ids. Its foreign key still points at `identity_subjects.id`. It holds only because an origin row has `id == subject_id`, and no code deletes origin rows. No constraint stops a link row from pointing at a missing subject. No constraint stops an origin row being deleted while link rows still point at it.

**Recommendation:** The migration is in this diff, so add the constraint here. Add `subject_id REFERENCES identity_subjects(id) ON DELETE RESTRICT`. Postgres accepts a self-reference; the backfill makes origin rows reference themselves. A `CHECK` cannot express "origin rows equal their own id", so keep that rule in `resolve`.

### [INFO] F7: The link step-up challenge does not name what is being linked

**Location:** `apps/api/src/auth/services/challenge.service.ts` (`identity-link` pool, which both link routes share)

Wallet link and email link use the same `identity-link` pool. The pool binds `publicKey` only, not the method kind or the identifier hash. Someone who captures a signed but unspent link proof can spend it on the other route, with their own SIWE message or OTP. Doing so needs XSS or a TLS break before submission, which already gives more than this.

**Recommendation:** Accept this, or bind `subject: '&lt;kind&gt;'` at mint, as unlink binds `methodId`.

### [INFO] F8: Unlink does not stop tokens or sessions that already exist

An exchange that read the link row before the unlink commits still mints a token. That token is valid for up to 300 s. A device that already rebuilt the key through the method keeps it. This matches ADR 0009 D5 ("nothing it already holds is un-shared"). Note it in the blueprint unlink line.

## Checked and holds

- **One subject per provider identity.** The unique index `(kind, identifier_hash)` holds this. `resolve` uses insert-or-ignore and then reads the row back. It now returns `subjectId` on all three paths.
- **Migration backfill.** It sets `subject_id = id`, which is correct because every existing row is an origin. It then sets `NOT NULL`, adds the index, and holds an advisory lock while it runs.
- **New rows.** `IdentitySubjectService` now mints the id through `Entropy.randomUuid()` instead of `gen_random_uuid()`. Entropy is injected, which is an improvement.
- **Hash parity.** The link and the exchange compute the same hash. Wallet: `getAddress` output, then `hashIdentifier`; this is the same bytes as the removed `hashWalletAddress`. Email: `trim().toLowerCase()` on both sides. Old `auth_methods` wallet hashes still match.
- **Token `sub` = `subject_id`.**
  - The device-registration subject lock (`device-registry-subject:&lt;sub&gt;`) keys on the same value whichever method signed in.
  - The rendezvous (`device-approval.service.ts:openSession`) maps the verified token's `subject` through `accountForIdentitySubject`, so a linked method can reach approval.
  - `claim()` stays consistent for a second device that signs in through a linked method.
  - No reader mixes `id` and `subject_id`: link and unlink read `id` only to decide whether a row is an origin.
- **Refusals write nothing.**
  - Every link refusal throws inside one transaction. It holds `auth-method:&lt;userId&gt;` and `auth-method-identifier:&lt;kind&gt;:&lt;hash&gt;`.
  - If an exchange wins the race, the `23505` error carries the named constraint. The wrapper rethrows it, the code maps it to 409, and the display row rolls back with the transaction.
  - Unlink deletes the display row and the link row in one transaction. It leaves the origin row of a different subject in place.
- **Order of proofs.** The step-up challenge is consumed and verified before the OTP is checked, so a stolen access token cannot burn OTP attempts. A 409 after a valid OTP burns the code and the challenge. That consumption is in memory with no database write, which is fail-closed.
- **Conflict messages.** Conflicts are checked only after the proof of ownership (SIWE or OTP), so the 409 text is no enumeration oracle.
- **Challenge binding.**
  - The step-up challenge is minted with `publicKey = accountKey(request)` and consumed once against the same key.
  - The engine's `step_up_challenge` checks the `cipherbox-link:v2:` prefix before it signs.
  - The `PanickingSigner` refusal test now covers `email_link`.
  - `EmailLink` signs through the same `IdentityChallengeSigner` path as `UnlinkAuthMethod`.
  - The SIWE statement split and the OTP purpose split hold on the server.
- **Linkability.** `identity_subjects` now groups a wallet hash and an email hash under one `subject_id`. `auth_methods` already grouped the same hashes under one `user_id`, and `account_devices` already joins account to subject (ADR 0058 Consequence 12). A database reader could make this join before. The PR adds no new edge. Hashes stay unsalted SHA-256 (ADR 0039 D1, pre-existing).
- **Display values.**
  - The grant `display` is the Google or email address, which is already in `email`, or `0xAbCd...1234`. The wallet form keeps 32 of 160 address bits: it confirms a guessed address but cannot recover one. The client already holds the full address.
  - Web now seals `display` with the email in the WebCrypto store (`ACCOUNT_LABELS_KEY`). The entry is bound to the subject and cleared on logout. For wallet sign-ins this is the one new place the truncated address is stored. Desktop keeps it in memory only. `auth.store` is not persisted.
  - `maskEmail` (`auth.service.ts:435`) writes the first character and the full domain into `auth_methods.identifier_display`. This is a new partial identifier at rest. The entity comment says "Plaintext identifiers are never stored". It is acceptable as display, but reword the comment to say "masked".
- **Test-mode mail.** `LoggingMailProvider` logs the address and the code. `buildMailProvider` refuses `log`, or no provider at all, unless `NODE_ENV` is `development` or `test`. Only the CI contract job reads that log (`CONTRACT_API_LOG`).
- **No key or seed material.** The diff touches no seal, KDF edge, wire format or KAT.
- **Plain strings in the engine (item 5).** The new commands take the code and the address as plain `String`. This is acceptable. ## Checked, no finding

**1. Bind integrity**

- **First-claim race (ADR 0058 E1).** An attacker who has a leaked, unspent token can still log in with a fresh key and bind the member's subject first. This is the accepted residual. The window has three shapes:
  - **New member:** the window is from the mint to the member's first login. That is seconds.
  - **Login held at the factor policy:** `recoverWithPhrase` or `adoptApprovalFactor` then calls `handOff(true)`. The 30 s margin usually holds the token back, so that login does not bind. For that exchange, the window is the full token lifetime (300 s or less). The account binds at a later plain sign-in.
  - **Account from before the deploy:** the window stays open until its next login through an exchange.

  All three shapes are inside the accepted E1 residual. Do not describe the window as "seconds" only.
- **No rewrite.** `bindSubject` in `apps/api/src/auth/services/auth.service.ts` is the only code that writes `identity_subject_id`. It writes with `update({ id, identitySubjectId: IsNull() })`. No code saves a full `User` entity, so no load-then-save path can put a stale `null` back. The `byo` change is an `update` by criteria.
- **Two accounts, one subject.** Both logins take `subjectLockKey(subject)`. The transaction uses READ COMMITTED, so the second login's `existsBy` sees the first commit and skips the write. The `UNIQUE` constraint is a second barrier.
- **One account, two subjects at the same time.** The `IS NULL` guard makes the second `UPDATE` re-check after it waits on the row lock. It then writes 0 rows.
- **Lock key.** Login and registration use the same function, now moved to `apps/api/src/common/advisory-lock.ts`. The string is still `device-registry-subject:`, so the key does not change across the deploy.

**2. Login refusal**

- A token that does not verify throws 401 before `runLockGuardedTransaction` starts. So the request writes no user row, no `auth_methods` row and no bind.
- A login without a token runs the same steps as before, now inside one transaction.
- The challenge is consumed before the token check. That was already true before the signature check. It burns only the caller's own challenge, which is bound to the caller's `publicKey`. A replay is not possible, so this is harmless.
- Non-security note: `jwtVerify` has no clock tolerance. A client clock more than 30 s behind the server can send a token that the server reads as expired, and the login is then refused with 401. This can occur only on slow held flows. It is an availability problem only.

**3. Registration**

- `spend` runs before both 409 checks, in the same transaction. A 409 rolls the spend back and writes no row.
- On success with the bound subject, the transaction commits the spend.
- `accountForIdentitySubject` no longer reads `account_devices.identity_subject_id`. It goes through `users.identity_subject_id`, then it checks that the account has at least one device. So an old row from before the bind cannot send a rendezvous to the wrong account. Such a row also blocks a re-registration under a new subject (409 "under another identity"), which is the intended result.

**F1 — Medium. After the migration, another account can bind a subject that a registration already claimed before the migration.**
- **Location:** `apps/api/src/auth/services/auth.service.ts:338` (`bindSubject`), and `apps/api/src/device-approval/services/account-device.service.ts` `claim()`, where the PR removes the `claimedElsewhere` check.
- **Invariant broken:** On `main`, an identity subject reaches at most one account (ADR 0039 D3). On `main`, the first registration made that claim in `account_devices`.
- **Scenario:**
  1. Account A registered a device under subject S before the migration. The migration does no backfill, so A is unbound.
  2. A starts a sign-in on a new device. The Core Kit login holds at the factor policy. A gets no rendezvous because A is unbound, so A starts to type the recovery phrase. The token for S stays valid for up to 300 s.
  3. The identity token goes to the Web3Auth verifier network by design (ADR 0008, `loginWithJWT`). A leak therefore needs no compromise of the client.
  4. Attacker B logs in with a new key and that token. `bindSubject` sees that no `users` row holds S, so it binds S to B. B registers a device, and the registration passes because the subject matches the bind.
  5. `accountForIdentitySubject(S)` now returns B. Each later rendezvous from A's devices goes to B, and A can never bind.
- **On `main`:** `claimedElsewhere` refused B's registration.
- **Scope:** After the bind, the mismatch 409 at `account-device.service.ts:144` stops all new rows under a different subject. The regression therefore applies only to rows that are older than the migration.
- **Effect:** No key is disclosed. A wrong factor cannot reconstruct A's key. The result is a permanent denial of service on approval, and B sees A's request metadata.
- **ADR status:** ADR 0058 E1 states a window for accounts that existed before the bind, "until its next login through an exchange". It does not state that this PR re-opens a claim that `main` had already closed.
- **Recommendation:**
  - (a) In this PR, add a refusal to `bindSubject`. Do not bind when an `account_devices` row holds this subject under a different `user_id`. This adds one query and keeps "no backfill". The column becomes a block signal, not a source for the subject-to-account mapping.

**F2 — Low. The 30 s margin compares the client clock with the server's expiry, and nothing else allows for clock skew.**
- **Location:** `packages/login/src/secret.ts:72` and `:78`; `apps/api/src/auth/services/identity-token.service.ts:136`.
- **How the check works:**
  - The client reads its injected `now()` and compares it with `expiresAt`, which is a server-clock instant from the grant body.
  - The server calls `jose.jwtVerify` with `currentDate: now` and no `clockTolerance`, so it refuses the token exactly at `exp`.
  - `CLOCK_SKEW_SECONDS` (60) sets only the `latestExpiryMs` bound.
  - So the 30 s margin is the only tolerance in the system. Its stated reason is expiry while the request is in flight. That reason covers latency. It does not cover clock skew.
- **Scenario:** The client clock is more than 30 s behind the server. A phrase recovery or an approval starts the engine more than about 270 s after the mint. The client then sends an expired token. The login answers 401, and the whole start fails with an error that does not say why.
- **Boundary:** The comparison is strict (`&lt;`). At exactly `expiresAt - 30 s` the client does not send the token. `flow.test.ts` covers this case. The comparison uses only the injected clock.
- **Recommendation:** Make the deadline relative. Add `expiresIn` to the grant body. Record `receivedAt = now()` at the exchange. Send the token only while `now() &lt; receivedAt + expiresIn - 30 s`. Do not retry the login without the token on a 401: that hides a failed bind and gives no signal.

**F4 — Info. `boundSubjectOf` (`auth.service.ts:170`) is dead code.** Only its own test calls it. It is an extra reader of the bind with no caller. Remove it in the `/simplify` pass.

**F5 — Info. The two registration 409s tell attacker B whether S was already bound.** After B logs in with a leaked token, "no bound identity subject" means that the victim bound S first. **F6 — Info. The identity token is not zeroized.** It is a `String` in Rust (`facade.rs:5327` drops it) and a string in JS. It is a 300 s bearer and not key material, so this is acceptable. `Zeroizing&lt;String&gt;` in the Rust start path would match how the secret is handled.
