## Test 1 — `full-workflow.spec.ts:1314 › 6.6.2 Restore a past version` (run 29061952925)

**Exact failure** (job 86265524185 log line 35035):
```
Error: expect(received).toBe(expected)   // line 1355
Expected: "Updated content after edit - version 2"
Received: "Edited in-browser via text editor modal - version 3"
```
The trace shows: restore-confirm clicked → details closed → editor opened → textarea read immediately. The editor showed the **pre-restore** current content (version 3).

**Root cause — missing synchronization (not stale cache).** The only "wait" between confirming the restore and reading the editor is (lines 1476-1478):
```ts
await expect(async () =&gt; {
  expect(await detailsDialog.getVersionCount()).toBe(1);
}).toPass({ timeout: 30000 });
```
Restore **swaps** current↔v1, so the past-version count is `1` **both before and after** restore. This gate passes instantly and provides **zero** wait for the restore's IPNS republish to land. I confirmed via a sub-agent that the text editor re-resolves the file **fresh from the live API on every open** (`downloadFromIpns` → `resolveIpnsRecord` → `resolveFileMetadata` → `downloadFileContent`, none cached — `packages/sdk/src/client.ts:4169`, `packages/sdk-core/src/ipns/index.ts:196`, `.../file/index.ts:373`). So there is no in-memory current-CID for restore to invalidate; the editor simply raced the just-committed/in-flight restore publish and read the old record. Given more time it reads version 2.

**Classification: (A) fixable test-timing race.**

**Fix** — full-workflow.spec.ts tail of 6.6.2 (~lines 1483-1495). The trivial `getVersionCount()===1` gate is a no-op; replace the single open→read→assert with a poll of the real end-state:
```ts
await expect
  .poll(async () =&gt; {
    await fileList.rightClickItem(editableFileName);
    await contextMenu.waitForOpen();
    await contextMenu.clickEdit();
    await textEditorDialog.waitForOpen({ timeout: 10000 });
    await textEditorDialog.waitForContentLoaded({ timeout: 30000 });
    const c = await textEditorDialog.getContent();
    await textEditorDialog.clickCancel();
    await textEditorDialog.waitForClose();
    return c;
  }, { timeout: 30000 })
  .toBe(editableFileUpdatedContent);
```
Note `textEditorDialog.waitForContentLoaded` (`text-editor-dialog.page.ts:100`) only waits for the textarea to be *visible*, not for correct content — so a single read is inherently racy.

**Latent product gap to flag separately (not what broke this test):** `useFileVersions.handleRestoreVersion` (`apps/web/src/hooks/useFileVersions.ts:58`) never refreshes the open folder listing after restore — only quota + the details dialog's own version list (`DetailsDialog.tsx:178` just bumps `metadataRefresh`). The file list won't show restored size/mtime until the 30s sync poll. Worth a ticket, but orthogonal to this flake.

## Test 2 — `writable-shares.spec.ts:533 › 8.1 Owner can navigate into subfolder created by recipient` (run 29061952925)

**Exact failure** (log line 35065):
```
TimeoutError: locator.waitFor: Timeout 30000ms exceeded.   // line 544
&gt; 544 | await bobSharedBrowser.getFolderItem(securitySubfolder).waitFor({ state: 'visible', timeout: 30000 })
```
Bob (recipient) does an `--mkdir` in a **writable shared folder**, then waits ≤30s for the folder to render in his own view. Immediately preceded by 7.2 (Bob deletes a subfolder) — so back-to-back shared-writes on the same folder IPNS.

**Root cause — tighter timeout on the highest-latency path.** A recipient mkdir in a shared folder is a full shared-write → IPNS publish → re-resolve/refresh round-trip; under 3-worker load on the shared Kubo it can exceed 30s (it *does* eventually render — slow, not broken). Critically, the whole `writable-shares` spec and the `SharedFileBrowser` page object use **bare `waitFor({timeout:30000})` with no CI floor**, while `FileListPage` waiters apply `ciFloor` → 60s on CI (`page-objects/file-browser/file-list.page.ts:10-16, 120, 130`). So the shared path — where write latency is *highest* — is held to *half* the budget of the equivalent owner path.

**Classification: (A) with a (C) tail** — a timeout-calibration miss layered on genuinely slow-but-correct shared-write IPNS latency (the exact reason the 60s floor exists).

**Fix** — bump the shared appear-waits to the 60s floor. Minimal: change the two shared-mkdir waits in `writable-shares.spec.ts` (line 544 for `securitySubfolder`, and the 8.2 `deepSubfolder` at line 597) from `timeout: 30000` → `60000`. Systemic (preferred): add a floored `waitForFolderItem(name, opts)` to `shared-file-browser.page.ts` mirroring `FileListPage`'s `ciFloor`+`waitForItemToAppear`, and route the spec's shared appear-waits (lines 65, 87, 214, 233, 544, 597 …) through it so every shared-write wait gets the same 60s CI floor.

## Test 3 — `full-workflow.spec.ts:1456 › 8.2 Delete remaining root files` (run 29062823570)

**Exact failure** (job 86268131289 log line 38444):
```
Test timeout of 90000ms exceeded.
```
Error-context DOM = **empty directory** (all files deleted). Trace confirms all 3 delete cycles ran to completion (renamed → config → editable: rightClick → Delete → confirm → wait-gone).

**Root cause — cumulative budget overflow.** 8.2 deletes 3 files sequentially via `deleteItem` (full-workflow.spec.ts:295), each doing `confirmDialog.waitForClose(15s)` + `waitForItemToDisappear({timeout:15000})` — and `ciFloor` raises that disappearance wait to a **60s cap on CI**. **Classification: (A/C boundary) — cumulative-timeout flake.** Underlying per-delete latency is irreducible live-stack (C); the fix is test-level (A).

**Fix** — pick one:

## Suite-level: should CI add `retries: 1`?

**Primary recommendation: fix all three at source first — do not reach for retries.** All three are fully diagnosable; none is Web3Auth/irreducible jitter. Two are pure timeout calibration (add the missing CI floor / raise the budget or bulk the operation), one is a genuinely absent wait. Papering these with retries would hide exactly the kind of fixable timing bug the `retries:0` philosophy is meant to surface.

**Secondary (defensible backstop, optional):** the substrate *is* a shared 2-vCPU stack whose IPNS publish/resolve latency has a fat tail under 3-worker load — that tail will keep producing occasional cumulative/timeout blips on other multi-mutation paths. A **CI-only `retries: 1`** (not 2) is a reasonable safety net *because Playwright reports retried tests as "flaky" in the run summary* — visible, not hidden. A genuinely-broken test still fails both attempts and reds the build; a transient live-stack blip passes on retry and lands in the flaky list for triage. That preserves the fix-at-source signal while cutting spurious red builds. If you adopt it: `retries: process.env.CI ? 1 : 0`, keep local at 0, and make "any test in the flaky report is a must-fix" a standing rule. I'd gate this on fixing the current three first and only add it if residual flakiness remains.

**Recommended order:** (1) land the three source fixes above; (2) re-run the dispatched suite twice; (3) add `retries:1` CI-only *only if* still flaky, with the flaky-report-triage rule.</result>
