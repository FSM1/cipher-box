## Adoption-gate finding adjudication — `crates/engine/src/gate/adoption.rs` (PR #682, HEAD `f585c973d`)

Confirmed the file exists on `origin/feat/engine-adoption-gate`. The load-bearing content gate is stage 6b: `open_read_body(candidate.envelope, reader.read_key)` (adoption.rs:445), whose AAD binds `(v,id,scope,epoch,read-body)` (aad.rs:130-139) to the reader-derived `read_key`. That gate is sound; F1–F3 concern the *auxiliary* trust checks the blueprint mandates be load-bearing.

### F1 — "Detached Structures Pass Authentication" — VERDICT: PARTIAL (real binding gap; not a standalone confidentiality bypass in this slice)

**Evidence.** adoption.rs:396-399:
```rust
for structure in &amp;candidate.structures {
    authenticate_structure(&amp;committed, structure)
        .map_err(|e| reject(GateStage::GrantSection, RejectionReason::Trust(e)))?;
}
```
`authenticate_structure` (adoption.rs:331-341) only checks `verify_structure(pseudonym, &amp;structure.input, &amp;structure.signature)`. The signature binds to `structure.input`, and `input.ciphertext_hash` is a **caller-supplied field of `StructureSigInput`** (structure.rs:44-46) — the gate never calls `over_ciphertext` to recompute it from a ciphertext present in the adopted record. Classification: `candidate.structures` is **candidate-supplied** (attacker surface — the Candidate doc, adoption.rs:259-262, defines it as "the public bytes a resolve would assemble off the record/content plane"). The gate also never cross-checks `structure.input.scope_id`/`structure.input.epoch` against `candidate.envelope.scope`/`candidate.envelope.epoch` (envelope fields at adoption.rs:277-279 are unused in stage 3). Greptile's core claim is therefore accurate: the structures are detached from the envelope, and stage 3 authenticates whatever it is handed.

**Why PARTIAL not full bypass.** In this slice stage 3's verdict is not threaded anywhere — seeds are dropped and content is gated independently by reader-derived `read_key` at stage 6b. So detached structures passing stage 3 does not by itself grant content access. But the blueprint makes stage 3 load-bearing ("any failure rejects the **whole record**", engine.md:149-153) and structure sigs bind `H(ciphertext)` precisely so a swapped ciphertext fails (core.md:127-131). Because the gate trusts the supplied hash and does not bind scope/epoch to the envelope, **cross-epoch/same-scope structure replay** (present a validly-signed structure from an old epoch alongside a current envelope) passes stage 3 today — defeating the stage's purpose the moment a resolve relies on it.

**Fix.** (1) Cross-check each `structure.input.scope_id == candidate.envelope.scope` and `structure.input.epoch == candidate.envelope.epoch` before/after the signature verify, failing closed on mismatch. (2) When the grant-section slice lands, recompute `ciphertext_hash` via `StructureSigInput::over_ciphertext(...)` from the record's *actual* sealed structure bytes (owner blob / grant blobs / ascent link / write-body / history links parsed out of `envelope.unknown["grantSection"]`), not a caller-supplied hash — and enumerate them from the record so completeness is enforced, not caller-asserted.

**Adversarial test (fails before fix, passes after).** Build a valid candidate at `epoch=2`, then replace `candidate.structures[0]` with a structure whose `input` is signed by the *same committed owner pseudonym* but over `scope_id == envelope.scope, epoch == 1` (an old but authentically-signed structure). Assert `adopt` rejects at `GrantSection`. Today it is accepted (signature verifies; no scope/epoch-to-envelope binding).

### F2 — "Candidate Supplies Ascent Authority" — VERDICT: REAL (the derive-and-verify is vacuous by input misclassification)

**Evidence.** adoption.rs:400-404:
```rust
if let Some(ascent) = &amp;candidate.ascent {
    open_ascent_link(&amp;ascent.parent_node_seed, &amp;ascent.aad, &amp;ascent.link)
        .map(drop)
        .map_err(|e| reject(GateStage::GrantSection, RejectionReason::Trust(e)))?;
}
```
`open_ascent_link` (grant.rs:488-507) re-derives `kdf::ascent_keypair(parent_node_seed)` and rejects only if `ascent_secret.public() != link.ascent_public`. Both `parent_node_seed` **and** `link` come from `AscentCheck` (adoption.rs:220-227), which lives inside **`Candidate.ascent`** (adoption.rs:275-276) — i.e., the attacker-controlled surface. A candidate producer who picks any seed and seals the link from that same seed passes the check trivially; the public-half comparison can never fail. The test fixture demonstrates exactly this: `tampered_ascent` (tests:295-312) seals the link from `parent_node_seed=[0x99;32]` and must manually corrupt `link.ascent_public[0] ^= 0xFF` to force the `ascent-link-mismatch` — there is no independent trusted seed to catch a matched (seed, link) pair.

**Blueprint clause that settles it.** engine.md:405-406: "Ancestor readers **derive** the expected ascent keypair **from the parent node seed** and reject a mismatched plaintext half." The parent node seed is reader-derived secret material (`ascent-keypair ← parent nodeSeed`, core.md:162) — it must come from **trusted reader state**, exactly like `read_key`, not from the record. Placing it in `Candidate` both violates the Candidate contract ("public bytes off the record plane") and makes the sole trust check in the ascent path a no-op.

**Fix.** Move `parent_node_seed` out of `AscentCheck`/`Candidate` and into `ReaderContext` (the reader supplies its own cached ancestor node seed). `AscentCheck` in the Candidate then carries only the network-supplied `link` (+ its `aad`); the gate calls `open_ascent_link(reader.parent_node_seed, ...)`. Now a mismatch means the published link's plaintext public half was not derived from the reader's *actual* ancestor seed — a genuine `ascent-link-mismatch`.

**Adversarial test (fails before fix, passes after).** Attacker picks `rogue_seed`, seals a link from it (uncorrupted public half), sets `AscentCheck { link, parent_node_seed: rogue_seed, aad }`. Assert `adopt` rejects at `GrantSection` with `ascent-link-mismatch`. Today it is accepted (the derive-and-verify matches the attacker's own seed). After the fix (seed sourced from `ReaderContext`), the rogue link's public half will not equal the keypair derived from the reader's real ancestor seed → rejection.

### F3 — "Seed Source Is Not Bound" — VERDICT: PARTIAL (real missing binding + unimplemented cross-check discipline; content still gated by reader-derived read_key)

**Evidence.** adoption.rs:442-446:
```rust
if let Some(blob) = &amp;reader.seed_blob {
    open_seed_blob(blob).map_err(|e| reject(GateStage::Unseal, RejectionReason::Trust(e)))?;
}
let read_body = open_read_body(&amp;candidate.envelope, reader.read_key)...
```
`open_seed_blob` (adoption.rs:346-361) opens the HPKE blob and `.map(drop)`s the payload. The blob's `enc`/`ciphertext`/`aad` are network-supplied (adoption.rs:231-233: "the envelope grant-section blob addressed to this reader"); only `enc_secret` is reader-owned. The HPKE open succeeds iff the ciphertext was sealed under exactly `blob.aad` — but `blob.aad` is presented *alongside* the ciphertext, and the gate never checks `blob.aad.scope == reader.scope_id` or `blob.aad.epoch == candidate.envelope.epoch` (AAD fields exist at aad.rs:112-123 but are never compared). Separately, `reader.read_key` (trusted, reader-derived — adoption.rs:290) opens the body with no relationship to the dropped seed. So a self-consistent blob from another scope/epoch opens fine, and the seed it yields is never checked to derive `read_key`. Greptile's claim ("neither the blob AAD nor its seed is tied to the envelope and key used below") is accurate.

**Adversarial-both-ways.** The FALSE-POSITIVE reading is "both `read_key` and `seed_blob` are `ReaderContext` = trusted, so there's no attacker in stage 6." That reading fails: the blob's ciphertext/enc/aad are network-controlled (only the secret is the reader's), so the network can present a stale/foreign blob, and nothing binds it to the envelope or to `read_key`. Conversely, this is **not** a standalone confidentiality bypass: content access is gated by `read_key` opening the AAD-bound envelope (stage 6b), and `read_key` is reader-derived — a foreign blob grants no new content. The real defect is that the seed-blob half of stage 6 is decorative (proves the reader can open *some* blob, unbound to this record) and the blueprint's mandated cross-check is absent.

**Blueprint clause.** engine.md:406-408: "Cross-check discipline: owner-blob seed vs ascent-link seed vs actual unseal — any disagreement is an attributable abuse event surfaced to the host, **never a silent failure**." The KDF chain makes this checkable and therefore required: the owner/ascent blob carries the scope/override seed, and `read_key = read_key(node_seed(scope_seed, id))` (kdf/mod.rs:229-234; fixture tests:96-98,107). The gate drops the seed instead of deriving-and-comparing.

**Fix.** (1) Before opening, assert `blob.aad.scope == reader.scope_id` and `blob.aad.epoch == candidate.envelope.epoch` (and `blob.aad.v == candidate.envelope.v`), failing closed on mismatch. (2) Do not drop the opened seed: derive `read_key` from it (`kdf::read_key(kdf::node_seed(seed, envelope.id))`) and constant-time-compare against `reader.read_key` — a disagreement is the attributable-abuse verdict the blueprint requires. This also lets `read_key` be *derived at the gate from the proven seed* rather than trusted as a bare input.

**Adversarial test (fails before fix, passes after).** Seal an owner blob under a *different* scope/epoch AAD (`scope=[0xEE;16]` or `epoch+1`) but wrapped to the reader's real enc subkey; keep the honest `read_key`/envelope. Assert `adopt` rejects at `Unseal`. Today it is accepted (the foreign blob opens under its own AAD; the seed is dropped; the honest `read_key` opens the body). A second variant: owner blob carrying a *wrong* `overrideSeed` that opens fine but does not derive `read_key` — assert rejection.

### F4 — "Missing Floor Becomes Sequence Zero" — VERDICT: FALSE-POSITIVE (the current code is more correct; the suggestion is a fail-open regression)

**Evidence.** adoption.rs:408-421:
```rust
let sequence_floor = floors.sequence_floor(name_bytes).await.map_err(GateError::Seam)?.unwrap_or(0);
if verified.sequence &lt;= sequence_floor { /* reject SequenceNotNewer */ }
```
On a fresh store the floor defaults to 0 and the gate rejects iff `sequence &lt;= 0`. The sequence convention is settled by **core.md:181: "First publish embeds sequence 1."** (matches MEMORY: "Every first IPNS publish must embed sequence 1".) Genesis is sequence **1**, not 0: `1 &lt;= 0` is false → **genesis is admitted**; `sequence == 0` is rejected, which is correct because seq 0 is never a legitimate published record. Greptile's premise ("a genesis record with `sequence == 0`… can never be adopted") is factually wrong — genesis is never 0.

**The suggestion weakens fail-closed.** Wrapping the check in `if let Some(sequence_floor)` skips the sequence comparison entirely on a fresh store, admitting *any* first-seen sequence including **0** — a record the seq-1 invariant forbids. That is a fail-open regression (engine.md:154 requires "strictly newer than the durable per-name floor"; `unwrap_or(0)` + `&lt;=` enforces `sequence &gt;= 1` on first adoption). No change needed; the current `unwrap_or(0)` is the correct fail-closed default.

**Refutation to paste.** "Genesis embeds sequence 1, not 0 (blueprint/core.md: 'First publish embeds sequence 1'). With `unwrap_or(0)` + strict `&lt;=`, a fresh store admits seq 1 and rejects seq 0 — which is correct, since seq 0 is never a legitimate record. The suggested `if let Some(sequence_floor)` would skip the check on a cold store and admit seq-0 (and any) first-seen records, a fail-open regression against engine.md's 'strictly newer than the durable per-name floor.' Current code is correct."
