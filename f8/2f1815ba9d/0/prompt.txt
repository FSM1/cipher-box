## Security confirmation on #1127

**Confirmed still live on `origin/main`.** `reseal_scope_root` (`/Users/myankelev/Code/random/cipher-box/crates/engine/src/rotation/reseal.rs`, line 333) reads `entry.recipient_enc_pk` straight from the resolved ledger and seals the override seed to it with no tag re-derivation. `enforce_committed_ledger` (`grants/ledger.rs:176`) compares `(tag, permission)` sets only.

The in-code comment at `reseal.rs:304-307` is worse than absent — it is false:

```
// Reseal trusts each entry's `recipient_enc_pk` verbatim from the committed
// ledger; the tag&lt;-&gt;enc_pk binding is enforced at resolve time.
```

No resolve path enforces that binding. The only tag re-derivation is `recipient_blinded_tag` at `grants/ledger.rs:50`, called from `grants/accept.rs:429` and `grants/invite.rs:413` — both are a party deriving **its own** tag, never a check of another row's `recipient_enc_pk` against the tag it is filed under. `self_locate` is a plain public tag compare. So a write-grantee that swaps a victim's `recipient_enc_pk` under the victim's owner-committed tag makes every subsequent honest re-seal, the owner's included, wrap the scope seed to the attacker's key. Owner authority passes at every step. This is exactly the wave-6 class: a field outside the owner's signature is trusted to identify something.

**#1129 and #1130 are the same class**, on the write plane. **#1128** (invite-claim redelivery resurrects a cut grant) is a fourth instance, newly actionable.

**Title:** `engine: two of the three re-point channels never publish, so a lagging reader has only the scope pointer`

## 3. The failure sequence and blast radius

1. Owner shares folder F read-only with Alice. `create_read_grant` (`create.rs:302,307`) files Alice's blob under `T_old = blinded_tag(ECDH(owner,alice), N_old)`.
2. Owner later downgrades Bob from write to read, or does a manual write-hygiene rotate. Either drives `rotate_scope_write`.
3. The wave mints a fresh `writeScopeSeed`; the root moves `N_old → N_new` (`rotate_write.rs:529`).
4. `reseal_root` publishes at `N_new` with `commitment.ipns_name = N_new`, owner-signed, and Alice's blob still filed under `T_old` (`net/rotation.rs:1203`, `reseal.rs:356`).
5. Alice follows the canonical scope-pointer re-point to `currentRootName = N_new`, resolves, passes the adoption gate, derives `T_new = blinded_tag(ECDH, N_new)`, and finds nothing.
6. `classify` returns `RevocationSignal` — the *definitive* "you were removed", outranking epoch lag by design (`revocation.rs:78-80`).

**Blast radius: every read-only grantee of the rotated scope, plus every write grantee that self-locates rather than deriving.** A write revoke aimed at one recipient silently reads as a mass read-revoke of the whole grant set. It is not self-healing: the tag is a pure function of the name, so every subsequent poll returns the same verdict.

**Recoverable only by owner action**, and only awkwardly — the owner must re-mint at the current name and republish. There is no client-side recovery, because after a second rotation the mint-time name is unrecoverable (`RepointObject.prev_root` carries exactly one hop, `rotate_write.rs:431`).

**Not yet exploitable in production.** `rotate_scope_write` has no facade or trigger caller (only tests and `net/rotation.rs` compose it), and `grants::revocation::classify` has no production caller at all — its only uses are the public re-export and `crates/engine/tests/grants_mailbox.rs`. This is a landed defect on an unwired path, so the cost of fixing it now is a ~15-line change in `reseal_root`, not a migration.
