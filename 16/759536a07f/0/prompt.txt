### #708 — X25519 low-order / contributory (MEDIUM)

**Root cause.** `crates/core/src/suite/x25519.rs:54-56` — `X25519Public::from_bytes` is total (doc comment at :51-53 explicitly says "the curve performs no point validation here"). `crates/core/src/suite/x25519.rs:39-41` — `diffie_hellman` drops `SharedSecret::was_contributory()`. `hpke.rs:199` (encap) and `hpke.rs:208-209` (decap, where `pk_e` is built straight from attacker-supplied `enc`) therefore both accept the all-zero DH. `kdf/mod.rs:271-278` already documents the sibling degeneracy for `blinded-tag` and points at "the contributory check on the x25519 seam" — which does not exist.

**Proposed fix (minimal-ripple; this is the load-bearing design call).**

- `x25519.rs`: make the constructor fail-closed — `X25519Public::from_bytes(bytes) -&gt; Option&lt;Self&gt;` (reject the RFC 7748 small-order encodings). Holding an `X25519Public` then *means* "not low-order", so `dhkem_encap` needs no change and **`hpke_seal` stays infallible** — no cascade into `seal_grant_blob` / `seal_owner_blob` / `seal_ascent_link` / `seal_mailbox_payload` signatures.
- `x25519.rs:39-41`: `diffie_hellman -&gt; Option&lt;SecretBytes&gt;`, `None` when `!was_contributory()` (defence in depth, and it gives the `blinded-tag` callers the seam `kdf/mod.rs:274-277` promises).
- `hpke.rs:207-214`: `dhkem_decap -&gt; Result&lt;SecretBytes, TrustViolation&gt;`; `hpke_open` (already `Result`) propagates. `dhkem_encap` unchanged.
- New `TrustViolation::HpkeNonContributory` (check `hpke-non-contributory`, class `trust`) in `error.rs` near :77-82, added to `CHECKS` at `error.rs:125`. (Alternative: reuse `HpkeOpenFailed` — no new check name, no coverage-gate entry — but it conflates a KEM-level abort with an AEAD tag failure. Recommend the new name.)

**Blast radius.** Production callers of `X25519Public::from_bytes` outside hpke: exactly one — `contact.rs:134` (maps to `Malformed::InvalidEncSubkey`, or better a new trust check; see open questions). Test callers: `kat_manifest.rs:1992, 2629, 2908, 3101`, `x25519.rs:98`, `hpke.rs:290`. `diffie_hellman` has only the two hpke call sites. Engine touches `X25519Secret` only (`gate/adoption.rs:243,254`; `tests/adoption_gate.rs`), never `X25519Public` — **fully core-local**. No wire bytes change; purely additive rejection.

**Tests.** RFC 7748 low-order-point unit table in `x25519.rs`; new hpke open-reject KAT `low-order-enc` → `hpke-non-contributory` (`kat_gen.rs:2940-2982`, `vectors/hpke/open_reject.json`); new contact reject vector `enc-subkey-low-order`; assert RFC 9180 A.1 vectors (`hpke.rs:279-320`) still pass byte-for-byte.

### #709 — aead panic + identityPk width (LOW) — **split the two halves**

**Part 1, `aead::encrypt` panic** (`suite/aead.rs:29-37`). Making it fallible cascades: `content/seal.rs:34`, `seal/mod.rs:69`, `hpke.rs:88` → `seal_read_body`, `seal_history_link`, `hpke_seal` → `seal_grant_blob`/`seal_owner_blob`/`seal_ascent_link`/`seal_mailbox_payload` → every KAT and `engine/tests/adoption_gate.rs` call site. ### #715 — unify zeroization (no severity flag)

**Root causes.** (1) `seal/body.rs:291-327` — `decode_read_body`'s transient `Value` tree carries a verbatim copy of every version's content key and drops unwiped, asymmetric with the guarded encode side (`body.rs:390-405`). (2) `seal/grant.rs:57-65` `zeroize_secret_bytes` — per-key allowlist, plain trailing statement, skipped on unwind; call sites `grant.rs:231-234`, `361`, `591`. (3) `codec/value.rs:141-152` — `zeroize_bytes` skips `Value::Text`.

**Proposed fix.**

- Promote the drop guard to `pub(crate)` and give it an **owning** variant. Note the borrow shape: `decode_read_body` does `let value = decode(...)?; let map = value.as_map()?;` — the existing borrowing `ScrubOnDrop&lt;'a&gt;(&amp;'a mut Value)` (`body.rs:400-406`) cannot wrap it (mutable guard vs. live immutable `map` borrow). Use `struct ScrubOwned(Value)` with `Drop` + a `&amp;Value` accessor and read `map` through the guard. Covers `Ok` and `Err` and panic-unwind.
- Replace all three `zeroize_secret_bytes` call sites with the guarded whole-tree pattern and **delete the helper + its per-key lists** (`grant.rs:53-65`). This is where the terminal-owner rule bites: the guard wipes only the encoder's own transient `Value::Bytes` copies materialized from `payload.*.as_bytes().to_vec()` — the caller's `SecretBytes` inputs are untouched (`value.rs:132-138` already states this invariant). Do not extend the wipe to anything the caller owns.
- Extend `Value::zeroize_bytes` to `Self::Text(s) =&gt; s.zeroize()` and update the doc comment at `value.rs:120-138` (which currently promises non-byte values are left intact) and the test at `value.rs:359-374`.

**Blast radius.** No wire bytes, no new rejects, no KAT change at all. Risk is confined to over-wiping — mitigated by the existing round-trip suites.

**Tests.** Extend the pattern at `body.rs:686,714`: a decode-side test asserting the transient tree is wiped on both `Ok` and `Err`; a panic-unwind test for each grant encode helper; `value.rs` test extended for `Text`.
