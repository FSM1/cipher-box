# Security Review — Phase 49: Shared-Folder Intra-Share Move

Date (UTC): 2026-06-18T02:53:59Z
Reviewer: Crypto/security review (agent)
Scope: `git diff origin/main...HEAD -- packages/sdk apps/web/src`
Focus: shared-folder MOVE path + key handling (crypto-sensitive surface)

## Executive Summary

The new intra-share move path is well-constructed and follows the project crypto
discipline closely. Key wrapping uses ECIES (`wrapKey`/`unwrapKey`), content stays
AES-256-GCM, all binary is `Uint8Array`, and the security-critical guard ordering
(write-capability check before any unwrap/publish) is correct. The publish ordering
(DEST → re-key → SOURCE) and the idempotent re-key give sound partial-failure
recovery, and the move-path key zeroing is correct on every exit path including the
op-throws and unwrap-throws cases.

One genuine (defense-in-depth-tier) leak exists: `enumerateSharedSubtree` unwraps a
per-subfolder AES-256 `folderKey` from `share_keys` on each DFS iteration and never
zeroes it. These are real folder keys held live in heap for the lifetime of the
process page. Everything else reviewed is either correct or a documentation nit.

Overall risk level: LOW

Finding counts: CRITICAL 0 · HIGH 0 · MEDIUM 1 · LOW 3 · INFO 2

## Findings

### [MEDIUM] enumerateSharedSubtree leaks per-iteration folderKey (no zeroing)

Location: `packages/sdk/src/client.ts:2460-2489`

Code:

```ts
const folderKey = await unwrapKey(hexToBytes(keyRecord.encryptedKey), args.vaultPrivateKey);
// ...
const meta = await sdkCore.loadFolderMetadata({ ipnsName: child.ipnsName, folderKey, ctx: this.ctx });
// folderKey is never zeroed; loop continues / function returns with it live
```

Issue: each DFS step decrypts a subfolder's AES-256 `folderKey` (recipient-wrapped
share key) and uses it only to `loadFolderMetadata`, then discards the reference
without `.fill(0)`. The project rule is explicit: "Sensitive key material MUST be
cleared after use." Unlike the move path (which zeroes everything in `finally`),
this method leaks one folder key per reachable subfolder. If `loadFolderMetadata`
throws mid-walk, the in-flight `folderKey` is also abandoned un-zeroed. Picker
enumeration walks the entire writable subtree, so a deep share leaves many plaintext
folder keys resident.

Impact: plaintext folder keys (each decrypts that folder's FolderMetadata, and
thus the file keys/IV references it lists) linger in JS heap until GC. Raises the
window for a memory-disclosure/heap-dump attacker. Not remotely exploitable on its
own; this is the same defense-in-depth zeroing the rest of the codebase honors.

Recommendation: zero each `folderKey` in a `finally` scoped to its use. `clearBytes`
is already the project helper (`@cipherbox/crypto`) and `unwrapKey`/`hexToBytes` are
already imported here:

```ts
const folderKey = await unwrapKey(hexToBytes(keyRecord.encryptedKey), args.vaultPrivateKey);
try {
  const writable = shareKeys.some((k) => k.keyType === 'folder-ipns' && k.itemId === child.id);
  result.push({ id: child.id, name: child.name, ipnsName: child.ipnsName, writable, parentId: current.id });
  const meta = await sdkCore.loadFolderMetadata({ ipnsName: child.ipnsName, folderKey, ctx: this.ctx });
  if (meta?.metadata?.children) {
    stack.push({ id: child.id, ipnsName: child.ipnsName, children: meta.metadata.children });
  }
} finally {
  clearBytes(folderKey);
}
```

(Import `clearBytes` — it is already in the `@cipherbox/crypto` import line at
`client.ts:22` alongside `unwrapKey`, `hexToBytes`.)

References: project rule "Clear sensitive data from memory after use"; the move
path's own `finally` zeroing at `client.ts:2387-2392` is the in-repo precedent.

### [LOW] Double-zero of fileIpnsPrivateKey is benign but undocumented

Location: `packages/sdk/src/client.ts:2389` ↔ `packages/sdk-core/src/file/index.ts:372`

Issue: on the file-move re-key path, the same `fileIpnsPrivateKey` buffer is zeroed
twice — once inside `updateFileMetadata`'s `finally` (`file/index.ts:372`, reached
via `reencryptFileMetadataForFolderChange`), then again in the client `finally`
(`client.ts:2389`). This is correct and safe (`fill(0)` on an already-zeroed buffer
is idempotent), and on the idempotent already-re-keyed path `updateFileMetadata` is
never called so the client `finally` is the only thing that clears it. No bug — but
the double-ownership is subtle and the client-side comment doesn't call it out.

Impact: none (correctness is fine). Risk is only future-maintenance: a refactor that
assumes single ownership could regress.

Recommendation: optional — add a one-line comment at `client.ts:2389` noting that on
the re-key path `updateFileMetadata` may have already zeroed this buffer, and the
client `finally` is the authoritative clear for the no-re-key / folder-item / early
paths. `reencrypt.ts:44-47` already documents the inverse direction; mirror it here.

### [LOW] Batch move re-fetches share keys per item (extra unwrap churn, minor TOCTOU)

Location: `apps/web/src/hooks/useSharedWriteOps.ts:218-249`, `packages/sdk/src/client.ts:2314`

Issue: `batchMoveItemsHandler` loops `moveInSharedFolder` per item, and each call
independently invokes `getShareKeysFn` (`fetchShareKeys`) and re-unwraps the dest
folder/ipns keys. Functionally correct and the per-item presence-guard re-runs each
iteration (good — picks up a mid-batch revocation), but it multiplies network round
trips and key unwraps, and there is a benign TOCTOU window: write access could be
revoked between the picker enumeration and a later item in the batch. The per-item
guard + the 403 revocation guard (`withRevocationGuard`) both catch this, so the
worst case is a clean mid-batch failure that stops the loop and keeps the selection.

Impact: informational/perf. No security regression — revocation is caught, and a
stale-key unwrap that no longer matches simply fails closed.

Recommendation: acceptable as-is (matches the owner `handleMoveItems` pattern). If
optimizing later, hoist a single `getShareKeysFn` fetch per batch and pass the
resolved key set down; keep the per-item presence assertion against that set.

### [LOW] reencrypt re-key path does not unpin the pruned/old FileMetadata CID

Location: `packages/sdk/src/reencrypt.ts:77-85`

Issue: `reencryptFileMetadataForFolderChange` calls `updateFileMetadata({ updates: {} })`
to re-seal under the dest key. `updateFileMetadata` returns `prunedCids`, but the
re-key wrapper discards them (it returns `void`). The old source-key-encrypted
metadata CID is left pinned. The `updateSharedFile` path explicitly unpins pruned
CIDs (`shared-write.ts:485-489`); the move re-key path does not. This is a storage/
refcount hygiene gap, not a confidentiality break — the orphaned CID is ciphertext
under a key the recipient still holds, and Phase-42 guarded-unpin would gate any
attempt anyway.

Impact: minor storage leak (dangling pinned ciphertext blob per moved file). No
plaintext or key exposure.

Recommendation: pre-existing behavior shared with the owner move path (reencrypt is
reused, not new in P49) — out of scope to change here, but worth a tracked todo:
surface `prunedCids` from the re-key and fire best-effort `unpinFromIpfs` like the
edit path does. Confirm parity with the owner `moveItem` caller before changing.

### [INFO] Self-move / cycle guards correctly precede key declaration

Location: `packages/sdk/src/client.ts:2310-2331`

The `destFolderId === itemId` self-move guard (2310) and the dest `folder` /
`folder-ipns` presence guards (2321, 2326) all throw BEFORE `destFolderKey` /
`destIpnsPrivateKey` / `fileIpnsPrivateKey` are declared (2329-2331) and before the
`try`. There is nothing unwrapped to zero on those early-throw paths — correct per
threat #5. Descendant-of-self is additionally excluded at the picker
(`SharedMoveDialog.tsx:113-128` walks `parentId` to disable the moved folder's whole
subtree). Defense-in-depth is layered correctly.

### [INFO] No key material in logs or error messages

Location: new code across `shared-write.ts`, `reencrypt.ts`, `client.ts` move/enumerate

All `console.warn`/`throw` sites in the new code log only generic strings or the
`err` object from non-crypto callbacks (`addShareKeysFn`, IPFS). No `privateKey`,
`folderKey`, `fileKey`, hex key string, or plaintext is interpolated into any log or
thrown message. The wrong-key decrypt path uses `.code === 'DECRYPTION_FAILED'`
(`reencrypt.ts:29-31`) rather than message-matching — correct padding-oracle hygiene.

## Compliance Checklist (project crypto rules)

- [x] ECIES for key wrapping — `wrapKey`/`unwrapKey` throughout; share keys recipient-wrapped, FilePointer/FolderEntry owner-wrapped
- [x] AES-256-GCM for content — unchanged; re-key re-seals FileMetadata, content key untouched
- [x] Web Crypto API only — via `@cipherbox/crypto`; no JS crypto libs introduced
- [x] Uint8Array for all binary — keys, IPNS keys, folder keys all `Uint8Array`
- [x] Never store/log/transmit unencrypted privateKey — no key bytes in logs/errors/transit; `vaultPrivateKey` passed by reference web→SDK, never serialized
- [x] Server zero-knowledge — server only ever sees recipient-wrapped `share_keys` ciphertext + IPFS ciphertext
- [~] Clear sensitive key material after use (`finally`) — move path: YES; enumerate path: NO (MEDIUM finding). Single gap.
- [x] IPNS keys resolved from `share_keys` file-ipns/folder-ipns, never owner-wrapped — confirmed for move (`client.ts:2355`) and enumerate write-cap (`client.ts:2465`)
- [x] caller owns `vaultPrivateKey` zeroing — SDK never zeroes it (test asserts at `enumerate-shared-subtree.test.ts:287`)
- [x] folderNav clones SDK-owned buffers to avoid use-after-zero on `client.destroy()` — `useFolderNavigation.ts:264-265`
