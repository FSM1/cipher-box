6. Add a new subsection under the Staging section documenting the critical operational constraint from the research:

   ```markdown
   **CRITICAL: CVM Identity Preservation**

   The Phala Cloud CVM derives deterministic keys from its `app_id`. If the CVM is deleted and recreated (instead of updated), the `app_id` changes, causing `getKey()` to derive different keys for all epochs. This makes all existing ECIES-encrypted IPNS keys undecryptable.

   - Always UPDATE the CVM: `phala deploy -n cipherbox-tee-staging --wait`
   - NEVER delete and recreate the CVM
   - If accidentally deleted: all staging IPNS republish entries must be re-enrolled with the new CVM public key
   ```

7. Add a note about the migration from simulator to CVM:

   **Migration Note (Phase 35):**

   The staging TEE was migrated from a local Docker simulator (`TEE_MODE=simulator`, HKDF-based keys) to a Phala Cloud CVM (`TEE_MODE=cvm`, hardware-backed keys). Because CVM key derivation produces entirely different keys than the simulator, all existing staging IPNS republish schedule entries need to be re-enrolled with the new CVM public key. For staging, the simplest approach is to wipe the `ipns_republish_schedule` table and let clients re-enroll on next publish.
