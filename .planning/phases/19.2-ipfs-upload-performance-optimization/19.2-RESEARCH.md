# Phase 19.2: IPFS Upload Performance Optimization - Research

**Researched:** 2026-03-23
**Domain:** IPFS Kubo pinning performance, NestJS API concurrency, Docker infrastructure tuning
**Confidence:** HIGH

## Summary

The upload bottleneck is well-understood from Phase 19 baselines: each `uploadFile` SDK call makes 5 sequential API calls, 3 of which are `POST /ipfs/upload` (pin operations). Each pin takes ~1.73s mean, totaling ~5.4s server-side per upload. Kubo IPFS pinning consumes ~95% of the upload endpoint latency. IPNS publishing is negligible (~100-140ms, DB upsert only).

There are three independent optimization levers, ordered by expected impact and implementation complexity. Lever 1 (concurrent pins at the SDK/API orchestration level) is the highest-impact, lowest-risk change since it requires no Kubo configuration changes. Lever 2 (Kubo datastore backend swap from flatfs to pebbleds) targets per-pin latency but requires Docker volume recreation and data migration. Lever 3 (multi-file batch add to Kubo in a single HTTP request) is the most complex but could eliminate per-request overhead for metadata pins.

**Primary recommendation:** Deploy concurrent pin orchestration (Lever 1) together with the pebbleds datastore swap (Lever 2). Validated testing showed concurrent pins alone regress under high concurrency — pebbleds is required to handle the doubled write load. Only pursue batch add (Lever 3) if the combined Lever 1+2 improvement is insufficient.

## Architecture Patterns

### Current Upload Flow (5 Sequential API Calls)

```
SDK client.uploadFile()
  |
  v
1. sdkCore.uploadFile()
   |-> addToIpfs(ciphertext)         -> POST /ipfs/upload  -> Kubo api/v0/add  [~1.73s]
   |-> createFileMetadata()
       |-> addToIpfs(encryptedMeta)  -> POST /ipfs/upload  -> Kubo api/v0/add  [~1.73s]
  |
  v
2. sdkCore.batchPublishIpnsRecords() -> POST /ipns/publish-batch              [~0.11s]
  |
  v
3. sdkCore.updateFolderMetadataAndPublish()
   |-> addToIpfs(folderMeta)         -> POST /ipfs/upload  -> Kubo api/v0/add  [~1.73s]
   |-> createAndPublishIpnsRecord()  -> POST /ipns/publish                     [~0.14s]
                                                              Total: ~5.44s
```

### Dependency Analysis of the 5 Calls

| Step | Operation                  | Depends On                                                    | Independent?        |
| ---- | -------------------------- | ------------------------------------------------------------- | ------------------- |
| 1a   | Pin ciphertext             | Nothing                                                       | YES                 |
| 1b   | Pin file metadata          | Needs CID from step 1a (cid is embedded in FileMetadata)      | NO -- depends on 1a |
| 2    | Publish file IPNS record   | Needs metadata CID from step 1b                               | Sequential after 1b |
| 3a   | Pin folder metadata        | Needs FilePointer (which needs fileMetaIpnsName from step 1b) | Sequential after 1b |
| 3b   | Publish folder IPNS record | Needs CID from step 3a                                        | Sequential after 3a |

**Key insight:** Steps 1a and 1b are NOT independent -- the file metadata contains the CID from step 1a. However, steps 2 and 3a ARE partially independent: the IPNS batch publish (step 2) and the folder metadata pin (step 3a) could execute concurrently since they don't depend on each other's results.

### Revised Understanding of Parallelization Opportunity

Looking more carefully at the code:

1. `sdkCore.uploadFile()` (steps 1a + 1b) -- sequential, CID dependency
2. `sdkCore.batchPublishIpnsRecords()` (step 2) -- needs fileMetaIpnsName from step 1b
3. `sdkCore.updateFolderMetadataAndPublish()` (steps 3a + 3b) -- needs FilePointer from step 1b

Steps 2 and 3 are currently sequential in `client.uploadFile()` (lines 612-621 of client.ts). They CAN be parallelized:

```typescript
// Current (sequential):
await sdkCore.batchPublishIpnsRecords([uploadResult.ipnsRecord], this.ctx);
const { newSequenceNumber } = await sdkCore.updateFolderMetadataAndPublish({...});

// Optimized (concurrent):
const [_, { newSequenceNumber }] = await Promise.all([
  sdkCore.batchPublishIpnsRecords([uploadResult.ipnsRecord], this.ctx),
  sdkCore.updateFolderMetadataAndPublish({...}),
]);
```

This saves one pin duration (~1.73s) because `updateFolderMetadataAndPublish` internally does a pin + IPNS publish, and we overlap it with the IPNS batch publish.

**Expected savings:** ~1.73s (one pin) off the total ~5.44s = ~3.71s target, which aligns with the success criteria target of ~3.5s at p50.

### Pattern 1: Concurrent Pin + IPNS Publish at SDK Level

**What:** Parallelize the file IPNS batch publish and folder metadata update in `CipherBoxClient.uploadFile()`.

**When to use:** Always -- these two operations have no data dependencies between them.

**Implementation location:** `packages/sdk/src/client.ts`, `uploadFile()` method, lines 611-621.

```typescript
// In CipherBoxClient.uploadFile():
// BEFORE: sequential
await sdkCore.batchPublishIpnsRecords([uploadResult.ipnsRecord], this.ctx);
const { newSequenceNumber } = await sdkCore.updateFolderMetadataAndPublish({...});

// AFTER: concurrent with prioritized failure handling
const [batchResult, folderResult] = await Promise.allSettled([
  sdkCore.batchPublishIpnsRecords([uploadResult.ipnsRecord], this.ctx),
  sdkCore.updateFolderMetadataAndPublish({
    children: updatedChildren,
    folderKey: folder.folderKey,
    ipnsPrivateKey: folder.ipnsKeypair.privateKey,
    ipnsName: folderIpnsName,
    sequenceNumber: folder.sequenceNumber,
    ctx: this.ctx,
  }),
]);
if (folderResult.status === 'rejected') throw folderResult.reason;
if (batchResult.status === 'rejected') {
  console.warn('[SDK] File IPNS batch publish failed:', batchResult.reason);
}
const { newSequenceNumber } = folderResult.value;
```

### Pattern 2: Kubo Datastore Backend Swap (flatfs -> pebbleds)

**What:** Replace the default flatfs block storage with pebbleds (PebbleDB) for faster write throughput.

**When to use:** When per-pin latency is the bottleneck and concurrent load causes filesystem contention.

**Why pebbleds:** LSM-tree based datastores like Pebble have very fast write performance (blocks streamed to disk) compared to flatfs (one file per block, filesystem metadata overhead). Pebble is the modern replacement for deprecated badgerds. Badgerds is explicitly deprecated in Kubo and will be removed.

**Trade-offs:**

- Pebbleds uses more memory than flatfs
- Read amplification for lookups (blocks need index lookup)
- Requires Docker volume recreation (cannot convert in-place)

**Implementation:** Requires Docker compose changes + Kubo init with `--profile pebbleds`.

### Pattern 3: Multi-File Batch Add via Kubo API

**What:** Send multiple files in a single `POST /api/v0/add` request using multipart form-data, reducing per-request overhead.

**When to use:** When multiple small metadata blobs need pinning (file metadata + folder metadata are both small JSON).

**Implementation complexity:** HIGH -- requires changes to the `LocalProvider.pinFile()` interface to support batching, plus a new `pinFiles()` method or endpoint.

### Anti-Patterns to Avoid

- **Don't batch the ciphertext pin with metadata pins:** The ciphertext pin is large (user file data). Batching it with small metadata would not help and could increase memory pressure. Keep large files as individual pins.
- **Don't add a new batch pin API endpoint:** The existing upload endpoint already does pin + quota tracking atomically. Adding a batch endpoint would complicate quota accounting and error rollback. Instead, parallelize at the SDK orchestration level.
- **Don't switch to badgerds:** It's explicitly deprecated and scheduled for removal from Kubo. Use pebbleds if changing datastores.
- **Don't modify the `addToIpfs` → `POST /ipfs/upload` contract for batching:** The quota tracking per-pin in the API controller makes batching at the API level complex. Parallelization at the SDK level is cleaner.

## Don't Hand-Roll

| Problem                 | Don't Build                     | Use Instead                                   | Why                                                                                               |
| ----------------------- | ------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------- |

## Common Pitfalls

### Pitfall 1: Promise.all Error Handling in Upload

**What goes wrong:** If the file IPNS publish fails and the folder metadata publish succeeds (or vice versa) in the Promise.all, the system is in an inconsistent state.
**Why it happens:** Promise.all rejects on first failure, leaving the other promise's side effects in an unknown state.
**How to avoid:** Use Promise.allSettled instead of Promise.all, then apply failure prioritization explicitly: treat folder metadata publish failure as critical (throw), and treat file IPNS batch publish failure as non-critical (warn + emit event + rely on subsequent publish cycles or TEE republishing).
**Warning signs:** Partial upload state -- file IPNS record exists but folder doesn't reference it, or folder references a file whose IPNS record doesn't exist yet.

### Pitfall 2: Kubo Concurrent Pin Contention at High Load

**What goes wrong:** Under high concurrency (50+ clients), parallel pins from multiple uploads compete for Kubo's datastore write lock, potentially increasing per-pin latency rather than decreasing it.
**Why it happens:** Flatfs writes one file per block, and filesystem metadata operations (create, fsync) serialize under the OS. Even with concurrent HTTP requests, Kubo serializes writes internally.
**How to avoid:** Benchmark before and after on the actual deployment. If per-pin latency increases under parallel pins, the net effect may be neutral. The pebbleds datastore handles concurrent writes better due to LSM-tree batching.
**Warning signs:** Pin p50 increasing while total upload time stays the same or gets worse.

### Pitfall 3: Docker Volume Migration for Datastore Change

**What goes wrong:** Changing Kubo's datastore backend requires a fresh IPFS repo. Existing pinned data is lost.
**Why it happens:** Kubo datastores are not interchangeable; each has a different on-disk format.
**How to avoid:** For the local dev/test infrastructure, this is acceptable -- the data is ephemeral test data. For staging, the user will manually redeploy the docker stack (as stated in the phase context). Document the migration steps clearly.
**Warning signs:** Kubo fails to start after config change because the existing volume has flatfs data.

### Pitfall 4: IPFS_PROFILE=server Overriding Datastore Config

**What goes wrong:** The staging docker-compose sets `IPFS_PROFILE: server` which may override manual datastore configuration.
**Why it happens:** Kubo profiles are applied at init time and configure multiple settings including the datastore.
**How to avoid:** When switching to pebbleds, use `IPFS_PROFILE: server,pebbleds` (comma-separated profiles) or apply pebbleds after server profile. Verify the resulting config with `ipfs config Datastore.Spec`.
**Warning signs:** After setting pebbleds, `ipfs config show` still shows flatfs.

### Pitfall 5: Measuring the Wrong Thing

**What goes wrong:** Client-side latency improvements don't match server-side improvements because the load test SDK overhead or network latency masks the savings.
**Why it happens:** The load test measures end-to-end SDK operation time, which includes HTTP overhead, JSON serialization, and client-side crypto.
**How to avoid:** Use BOTH Prometheus server-side histograms (pin duration, endpoint duration) AND the load test client-side metrics. Compare both before/after.
**Warning signs:** Server-side pin p50 drops but load test uploadFile p50 doesn't change.

## State of the Art

| Old Approach                       | Current Approach                     | When Changed        | Impact                                                                   |
| ---------------------------------- | ------------------------------------ | ------------------- | ------------------------------------------------------------------------ |
| badgerds datastore                 | pebbleds datastore                   | Kubo v0.35+ (2025)  | badgerds deprecated, pebbleds is the modern LSM-tree alternative         |
| flatfs (one file per block)        | flatfs with atomic batch ops         | Kubo v0.40.0 (2026) | Batch operations use less memory, block data written to disk immediately |
| Kubo pin tracking in single object | Same (architectural limitation)      | Unchanged           | Pin tracking remains a performance bottleneck under high pin counts      |
| Sequential SDK API calls           | Can be parallelized with Promise.all | This phase          | Saves ~1.73s per upload by overlapping independent operations            |

**Deprecated/outdated:**

- **badgerds:** Explicitly deprecated in Kubo, will be removed in a future release. Use pebbleds instead.
- **delegated-ipfs.dev for pinning:** Already replaced by self-hosted Someguy in Phase 19 for IPNS routing. Pinning goes through local Kubo only.

## Open Questions

1. **pebbleds write performance vs flatfs under CipherBox's workload profile**
   - What we know: Kubo docs say pebbleds has "very fast write performance" due to LSM-tree. Flatfs was rewritten in v0.40.0 with atomic batch ops.
   - What's unclear: No public benchmarks comparing pebbleds vs flatfs v0.40.0 under this specific workload (many small pin operations, moderate concurrency).
   - Recommendation: Deploy Lever 1 (concurrent pins) and Lever 2 (pebbleds) together. Validated testing showed concurrent pins alone regress at 50+ clients — pebbleds is required for net benefit.

2. **Kubo internal pin concurrency limits**
   - What we know: Baselines show "Kubo pin mean stays flat (~1.6s)" even at 200 clients, suggesting Kubo handles concurrency well internally. The "knee at ~50 clients" is queuing, not Kubo degradation.
   - What's unclear: Whether making 2 concurrent pin requests per upload (instead of 1) from the API will hit Kubo's internal write locks.
   - Recommendation: This is an empirical question. Implement and benchmark.

3. **IPFS_PROFILE interaction with pebbleds**
   - What we know: `IPFS_PROFILE=server` is set on staging. Kubo supports comma-separated profiles at init.
   - What's unclear: Whether `server,pebbleds` correctly applies both profiles or if one overrides the other's datastore config.
   - Recommendation: Test on local infra first. Verify with `ipfs config Datastore.Spec` after init.
