<objective>
Deliver SC#3: `restoreFromBin` to a different parent re-homes the `WriteChildRef` under the destination write scope (reusing the shipped 68.1-31 `moveItem` re-homing pattern), and close the bin-path write-body growth gap by dropping the lingering ref on permanent delete.

Structural gap (RESEARCH Pattern 2): `restoreFromBin` today only loads the TARGET folder (`requireFolder(targetFolderIpnsName)`) — it never loads the ORIGINAL parent, so it structurally cannot re-home. `BinEntry.originalParentIpnsName` is captured at `addToBin` time, so the source folder can be resolved. The fix adds that load, extends `binOps.restoreFromBin` to accept the source `FolderState` and perform the unseal/reseal/drop, and publishes dest-before-source.

This plan also carries the permanent-delete half of the Open Question 1 decision (resolved in Plan 03): soft-delete RETAINS the WriteChildRef; permanent removal DROPS it. Because dropping requires the same original-parent load this plan introduces for re-homing, `permanentDeleteFromBin` gets the drop here (plumbing reuse), which is why this plan also lists SC#1.

Purpose: A restored file is write-capable in its new home; the bin path does not leak write-body growth.
Output: re-homing on restore-to-different-parent, permanent-delete drop, and a live sdk-e2e regression.
</objective>

|----------|-------------|
| bin restore → two folders' write scopes | The moved write key crosses from the source write scope to the destination write scope; a crash mid-publish must not orphan write capability |
| SDK → original parent resolve | The original parent may have been deleted/moved since soft-delete; its resolve is untrusted |

| T-72-05-02 | Information Disclosure | unsealed moved write key | medium | mitigate | D-09 finally zeroes the borrowed unseal result; nulled before ownership transfer |
