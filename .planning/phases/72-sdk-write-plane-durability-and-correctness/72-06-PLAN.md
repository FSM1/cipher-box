Deliver SC#4 (reframed per RESEARCH Critical Finding 1) plus the standalone zeroize hygiene todo — both localized to `client.ts`.

SC#4 reframe (LOCKED): the `SealedChildRef.size`/`modifiedAt` display mirror the todo describes was REVERTED in Phase 68.2-12 (`SealedChildRef` is frozen to `{name, ipnsName, generation, versionFloor, readKeySealed}` — no size/modifiedAt field exists to refresh). The ACTUAL staleness is `listingCache` (keyed by parent ipnsName, invalidated only on a parent sequence bump). Since `replaceFile`/`restoreFileVersion`/`deleteFileVersion` publish only the file's own IPNS record (parent sequence unchanged), the cache survives the edit and the next `folder:updated` emission serves a stale `ResolvedChild[]`. The fix is the shipped one-liner from the shared-path sibling `updateSharedFile` (68.2-02): `this.listingCache.delete(folderIpnsName)` before the `resolveListingChildren` + emit in `maybeRepublishFolderForFileMigration`, gated behind the locked "did size/mtime actually change" check. Do NOT reintroduce mirror fields on SealedChildRef (violates NODE-03 frozen-field invariant).

Zeroize (todo 2026-07-10): in `updateSharedSingleFile`, both keys are unwrapped BEFORE the `try` that owns the `finally` cleanup; if the second `unwrapKey` throws, the first key lingers un-zeroed. Move both `unwrapKey` calls inside the `try`, null-init before.

Purpose: Fresh listing after an in-place edit; no un-zeroed key material on the unwrap error path.
Output: Gated cache invalidation + the zeroize fix + two unit tests.
