<objective>
Wire the real node/v3 root-key lifecycle into the desktop vault commands, replacing 69-20's placeholder. Today `initialize_vault` mints ONE random `root_folder_key`, ECIES-wraps it into a v2 blob, and fabricates the node/v3 read/write keys with `derive_root_node_keys` (the `^0xA5` bridge); `fetch_and_decrypt_vault` requires a v2 blob and recovers only that single key (research §Q3). A web-created v3 vault is unreadable, and the desktop's fake keys never match a real vault.

This plan makes the desktop read/write the SAME persisted v3 blob the web does (research recommended approach (a)):
- **initialize_vault**: generate TWO independent random 32-byte keys (`root_read_key`, `root_write_key`); ECIES-wrap BOTH under the user public key; `serialize_vault_blob_v3` (69-21) -> publish to the vault-key IPNS; seal the empty root Node under THOSE SAME two keys via `build_empty_root_published_node` (the 69-20 helper, now fed real keys) -> publish at seq 1. DELETE `derive_root_node_keys` (the bridge). Root Ed25519 IPNS keypair stays HKDF-derived.
- **fetch_and_decrypt_vault**: `deserialize_vault_blob_v3` (69-21) -> ECIES-unwrap both -> land into `state.sdk.root_read_key`/`root_write_key` (69-22). Keep populating `root_folder_key` (= root_read_key) transitionally so the still-bridged mount stays green until 69-24. Root IPNS key stays HKDF-derived.

The server stays zero-knowledge (only `{ owner_public_key, root_ipns_name }`); both keys live only ECIES-wrapped in the v3 blob.

Purpose: SC-04 — real root-key recovery replaces the placeholder bridge; a v3 vault created on desktop or web opens on either.
Output: node/v3 init + recovery in vault.rs, `derive_root_node_keys` gone, an init->recover round-trip unit test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| two random root keys (memory) -> ECIES v3 blob -> IPFS/IPNS | The only at-rest form is ECIES-wrapped under the user pubkey; plaintext keys never leave memory |
| persisted v3 blob (untrusted IPFS) -> resolve_ipns_verified -> deserialize + unwrap | A tampered blob/record must be rejected before key material is trusted (D-09 chokepoint) |
| /vault/init (server) | Zero-knowledge boundary: server sees only owner_public_key + root_ipns_name, never key material |
| root Ed25519 IPNS seed -> sealed write-body | The signing seed lives inside the sealed root node (under root_write_key), never in the v3 blob |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-69-23-01 | Information Disclosure | A root key persisted in plaintext (server or IPFS) | high | mitigate | Both keys ECIES-wrapped under the user secp256k1 pubkey (wrap_key) before the ONLY at-rest write (the v3 blob); /vault/init body carries no key columns (zero-knowledge, CLAUDE.md #6) |
| T-69-23-02 | Spoofing / Tampering | A tampered vault-key blob or IPNS record injects attacker keys | high | mitigate | Recovery routes through resolve_ipns_verified (D-09 verified chokepoint, kept); deserialize_vault_blob_v3 bounds-checks; unwrap_key fails closed on a non-matching ECIES envelope |
| T-69-23-03 | Elevation | Create/recover key mismatch (bridge remnants) -> a fresh vault is unreadable, or fake `^0xA5` keys leak into the real path | high | mitigate | derive_root_node_keys DELETED; init seals the root under the SAME two random keys it wraps into the blob; init->recover round-trip test proves agreement |
| T-69-23-04 | Information Disclosure | Root keys zeroed before their ECIES wrap or root seal completes (or not zeroed after) | medium | mitigate | Zeroizing wrappers preserved; keys borrowed into wrap_key/seal, dropped/zeroed only after both the blob and the root node are produced (D-09 terminal owner) |
| T-69-23-SC | Tampering | cargo installs | high | mitigate | N/A — zero new crates (apps/desktop already deps cipherbox-core/crypto/sdk/api-client) |
</threat_model>
