<objective>
Give the Rust SDK KeyState the node/v3 two-key root slots the desktop recovery (69-23) fills and the mount (69-24) consumes. Today `crates/sdk/src/state.rs` KeyState holds only the legacy single `root_folder_key` (one random AES key); there are no `root_read_key`/`root_write_key` fields, which is why the desktop mount has to fabricate them with the `^0xA5` bridge (research §Q3 gap).

This plan ADDITIVELY:
- adds `root_read_key: RwLock<Option<Zeroizing<Vec<u8>>>>` and `root_write_key: RwLock<Option<Zeroizing<Vec<u8>>>>` to KeyState (two independent random 32-byte keys — the node/v3 model),
- initializes both to None in `new()`,
- zeroizes both in `clear()` (mirroring the root_folder_key block),
- extends the three existing KeyState unit tests to cover them.

`root_folder_key` is KEPT (not replaced) so the still-bridged mount stays workspace-green until 69-24 flips it. AppState (apps/desktop/src-tauri/src/state.rs) needs NO struct change — it wraps `Arc<KeyState>` and its clear_keys() already delegates to KeyState::clear(); the desktop reads the new keys via `state.sdk.root_read_key`/`root_write_key`.

Purpose: SC-04 — the in-memory landing slots for the recovered node/v3 root read/write keys.
Output: KeyState with `root_read_key`/`root_write_key` (Zeroizing) + zeroization on clear.
</objective>
