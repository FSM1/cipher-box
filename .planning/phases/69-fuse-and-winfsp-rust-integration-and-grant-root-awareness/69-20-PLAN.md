<objective>
P4b (SC-04, wave 7): migrate vault-creation off the legacy folder model onto node/v3, the second (and last) live consumer blocking the 69-10 delete. Today `initialize_vault` (apps/desktop/src-tauri/src/commands/vault.rs:145-188) seals an empty `FolderMetadata{version:"v2", children:[]}` via `cipherbox_core::folder::encrypt_folder_metadata`, wraps it in the legacy `{iv, data}` IPFS envelope, uploads it, and publishes the root folder IPNS record at sequence 1.

This plan replaces ONLY that folder-metadata publish with an empty node/v3 **ROOT node** emit:

- Build `Node::Root { id: generate_uuid_v4(), generation: 0, created_at, modified_at, children: vec![] }` and `NodeWriteBody { ipns_private_key: <root IPNS signing seed>, write_children: vec![] }`.
- `seal_published_node(&root_node, &root_read_key, &root_write_key, Some(&write_body))` → `encode_published_node(..)` → the sealed node/v3 envelope bytes.
- Upload the envelope to IPFS and publish the root IPNS record at **sequence 1**, reusing the EXISTING `create_ipns_record(seq=1)` + `marshal_ipns_record` + `IpnsPublishRequest{ expected_sequence_number: None }` + `publish_ipns` tail already in `initialize_vault` (the same seq-1 idiom as `emit.rs::publish_first`).

**Root read/write keys — mount-consistent bridge.** The freshly-published root must be readable and writable at first mount, so create derives the root read/write keys the SAME way the mount does today (apps/desktop/src-tauri/src/fuse/mod.rs:192-205, the phase-63 placeholder bridge): `root_read_key = root_folder_key[..32]` and `root_write_key = root_read_key XOR 0xA5`. The root IPNS keypair stays HKDF-derived (`derive_vault_ipns_keypair`) — identical at create and mount. Real node/v3 root-key persistence/recovery (server-side `rootReadKey`/`rootWriteKey` minted at registration, recovered at login) is the separate **phase-63 desktop-runtime** work; this plan documents the coupling and stays consistent with the placeholder until phase-63 lands (accepted residual, D-06 desktop-e2e deferred).

**Why not `build_folder_emission(is_root=true)`.** `cipherbox_sdk::build_folder_emission` MINTS a fresh random Ed25519 keypair + random readKey/writeKey — vault-creation instead needs the HKDF-derived root IPNS keypair and the bridge-derived root read/write keys so create and mount agree. So this plan composes the `crates/core::node` seal path DIRECTLY (the same primitives `build_folder_emission` itself calls), not the minting wrapper.

**Kept unchanged:** the v2 vault-KEY-blob publish (`serialize_vault_blob_v2` + `ecies::wrap_key(root_folder_key, public_key)`) — ECIES is retained for the vault-root wrap only (NODE-06). The `/vault/init` registration tail is unchanged.

**Boundary:** `cargo check --workspace` green. A practical creation correctness test: a pure `build_empty_root_published_node` helper is unit-tested (seals+encodes → decodes to schema `node/v3`, kind `root`, generation 0, empty children; the read-body unseals under `root_read_key`, the write-body under `root_write_key` — AAD-bound / KAT-consistent). Full new-user creation is desktop-e2e territory (deferred to phase-63 root-key recovery, D-06 — documented, not overclaimed).

Purpose: SC-04 — remove the vault-creation consumer of the legacy folder model.
Output: `initialize_vault` publishes an empty node/v3 root node at seq 1 with mount-consistent keys; a unit-tested pure root-emit helper.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| new-user root_folder_key → root read/write keys (bridge) → sealed root node | The create-time key derivation must match the mount bridge or the first mount cannot open the root |
| root IPNS keypair (HKDF) → first publish (seq 1) | The strict IPNS gate rejects a first publish with seq != 1 |
| root_folder_key → v2 ECIES vault-key blob (kept) | The one retained ECIES wrap; must not be confused with the node/v3 symmetric root seal |
