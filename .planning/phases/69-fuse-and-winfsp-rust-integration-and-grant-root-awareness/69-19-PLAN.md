<objective>
P4a (SC-04, wave 7): migrate the recycle-bin subsystem off the legacy folder-model types onto node/v3, so 69-10 can delete `FolderMetadata`/`FileMetadata`/`FilePointer`/`FolderEntry`. Today `crates/core/src/bin.rs` is one of the last two live consumers of the legacy types: `BinEntry.file_pointer: Option<FilePointer>` + `BinEntry.folder_entry: Option<FolderEntry>` (and `original_folder_key_encrypted`, a re-encrypt-on-restore keeper from the old parent-key model). The FUSE delete path (`delete.rs`) and the WinFsp path (`platform/windows/write_ops.rs`) populate those fields at delete time.

This plan:

- **Reshapes `BinEntry`** (bin.rs): DROP `file_pointer`/`folder_entry`/`original_folder_key_encrypted`; ADD node/v3 restore data sufficient to re-splice a deleted node back into a parent — `child_published_node: String` (b64 `encode_published_node`, a re-upload keeper), `child_ref: SealedChildRef` (read plane, keyed by ipnsName), and `write_child_ref: WriteChildRef` (write plane, D-07, keyed by childId UUID). `original_folder_key_encrypted` is DROPPED: node/v3 restore re-splices the sealed child ref rather than re-encrypting a `FileMetadata` under a new parent key (SC#2-consistent — each node self-seals under its own readKey). `version_cids`/`content_cid`/`content_size`/`item_type`/`original_parent_ipns_name`/`original_path` are KEPT.
- **KEEPS the ECIES bin envelope** (`encrypt_bin_metadata`/`decrypt_bin_metadata`): the whole `RecycleBinMetadata` blob is still ECIES-wrapped under the user's secp256k1 public key — a user-level keeper (like the vault-root wrap), NOT a node-to-node key hop. Only the BinEntry CONTENTS change.
- **Migrates the FUSE delete bin-write** (`delete.rs` handle_unlink + handle_rmdir): capture the D-07 dual refs from the inode's node/v3 keys — `WriteChildRef.child_id = uuid_from_ino(child_ino)` (write plane), `SealedChildRef.ipns_name = child ipns_name` (read plane), both sealed under the PARENT inode's read_key/write_key — never conflated.
- **Edits the WinFsp bin-write** (`platform/windows/write_ops.rs`, `#[cfg(feature="winfsp")]`) for correctness against the new shape (best-effort; the WinFsp build is NOT compiled by the default `cargo check --workspace` — its verification is 69-14's `Cargo Check & Test (Windows)` CI on the user's Windows box, per D-06).
- **Verifies `metadata.rs::spawn_bin_entry_publish`** consumes the reshaped entry unchanged (it pushes the entry into `RecycleBinMetadata.entries` and ECIES-wraps the blob; no legacy-field references to drop).

**No live restore command exists in the Rust desktop today** — the bin is write-only (delete → bin). This plan lands the node/v3 restore DATA + a pure re-splice round-trip test proving the captured `SealedChildRef`/`WriteChildRef` are restore-sufficient (re-splice into a fresh parent node body → the child is recovered). The live FUSE/Tauri restore command is future work (no restore consumer on this branch); this plan does not fabricate one.

**Boundary:** the reshape touches a cross-crate type (core→fuse), so an intermediate state may be RED until the fuse consumer updates in the SAME plan. The PLAN boundary is `cargo check --workspace` (default fuse) green + `cargo test -p cipherbox-core bin` + `cargo test -p cipherbox-fuse delete` green. `--features winfsp` may be RED (the WinFsp bin-write edit is verified by 69-14 CI), documented, not a regression.

Purpose: SC-04 — remove the recycle-bin consumer of the legacy folder-model types.
Output: reshaped `BinEntry` on node/v3; FUSE delete bin-write captures the D-07 dual refs; WinFsp bin-write edited for 69-14.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deleted node's inode keys → captured BinEntry restore data | The child's readKey/writeKey are re-sealed under the PARENT keys into the bin; the whole entry is then ECIES-wrapped to the user |
| write plane (WriteChildRef.childId = uuid_from_ino) vs read plane (SealedChildRef.ipnsName = k51) | Two distinct key spaces that must never be conflated (D-07) |
| RecycleBinMetadata blob → ECIES(user publicKey) | The bin envelope is user-key ECIES (kept), NOT a node-to-node hop |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-69-19-01 | Tampering / DoS | Conflating WriteChildRef.childId (uuid_from_ino) with SealedChildRef.ipnsName in the bin-write breaks a future rotateWriteFromNode on restore | high | mitigate | D-07 dual ref via build_child_refs; child_id = uuid_from_ino (write), ipns_name = k51 (read); test asserts child_id != ipns_name; SECURITY-REVIEW marker + write_ops flagged |
| T-69-19-02 | Information Disclosure | Minted/inode key material leaked or an inode-owned key zeroed prematurely during capture, corrupting the parent seal | high | mitigate | Terminal-owner (D-09): capture borrows inode keys, never zeros them; build_child_refs borrows; no key logged |
| T-69-19-03 | Tampering | A leftover dual-format/serde-alias path lets a legacy file_pointer/folder_entry entry deserialize, weakening the single-codec guarantee | medium | mitigate | D-04 clean flag-day: no serde alias, no From<FilePointer/FolderEntry> bridge; grep gate empty; no prod vaults to migrate |
| T-69-19-04 | Spoofing | The ECIES bin envelope weakened or swapped for a node-to-node symmetric hop | high | mitigate | encrypt_bin_metadata/decrypt_bin_metadata ECIES-under-user-key KEPT verbatim; grep shows ECIES only there; round-trip test green |
| T-69-19-SC | Tampering | cargo installs | high | mitigate | N/A — zero new crates (crates/fuse already deps cipherbox-sdk + cipherbox-core) |
