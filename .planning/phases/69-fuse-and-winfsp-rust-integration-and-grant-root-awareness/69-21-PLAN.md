<objective>
Add the Rust `vault-blob-v3` codec — the missing half of the node/v3 root-key model. The web already mints two independent random 32-byte root keys (`rootReadKey`, `rootWriteKey`), ECIES-wraps both under the user's secp256k1 public key, and packs them into a v3 blob `0x03 | u16_BE(readLen) | ECIES(rootReadKey) | u16_BE(writeLen) | ECIES(rootWriteKey)` (packages/core/src/vault/blob.ts). Rust `crates/core/src/vault_blob.rs` has only the legacy v2 single-key envelope, so a web-created v3 vault is literally unreadable on desktop and vice-versa (research §Q4 gap).

This plan lands, ADDITIVELY (v2 untouched):
- `BLOB_V3_VERSION = 0x03`, `serialize_vault_blob_v3(enc_read, enc_write) -> Result<Vec<u8>, String>`, and `deserialize_vault_blob_v3(blob) -> Result<(Vec<u8>, Vec<u8>), String>` byte-matching blob.ts.
- A cross-language KAT test loading the frozen `tests/vectors/vault-v3-blob.json` and asserting byte-identical serialize output + a full round-trip (D-04 clean-cutover conformance — the vault-v3 envelope must conform to the shipped vector, not a re-invented layout).

The codec is pure envelope byte-manipulation — no ECIES/AES here; the caller (69-23) supplies the already-wrapped key bytes. v2 stays because the live desktop vault path (69-20) still consumes it until 69-23 flips init/recovery to v3.

Purpose: SC-04 — the byte contract that lets a desktop and a web client open the SAME persisted v3 vault blob (research recommended approach (a)).
Output: `serialize_vault_blob_v3` / `deserialize_vault_blob_v3` + a KAT-driven cross-language test.
</objective>

| web-minted v3 blob <-> desktop-minted v3 blob | Byte-identity of the envelope is what makes the two clients mutually openable (recommended approach (a)) |
| caller-supplied ECIES key bytes -> envelope | The codec treats key bytes as opaque; it must not interpret, log, or transform them |
