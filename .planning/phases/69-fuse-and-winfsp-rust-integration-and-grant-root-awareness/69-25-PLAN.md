<objective>
Make the desktop-e2e round-trip actually validate the node/v3 flip, then hand the orchestrator a runnable recipe. Today the verifier `packages/sdk-core/scripts/verify-filepointer.mts` reads `vaultKeyBlob.rootFolderKey` (retired in v3 — `loadVaultKeyBlob` now returns `{ rootReadKey, rootWriteKey }`, so the field is `undefined`; tsx runs no typecheck so it silently mis-verifies), and traverses children with the legacy FolderEntry/FilePointer shape rather than node/v3 SealedChildRef (research §Q5). So the FUSE-local I/O tests are meaningful but the API round-trip / content-decrypt path does NOT exercise a real v3 vault.

This plan:
- migrates the three e2e helpers (`verify-filepointer.mts`, `edit-filepointer.mts`, `rename-folder.mts`) onto the node/v3 read chain: `loadVaultKeyBlob` -> `{ rootReadKey }`; `loadFolderMetadata({ folderKey: rootReadKey })` -> root Node with `children: SealedChildRef[]`; unseal the target child's `readKeySealed` under the parent readKey (`unsealChildReadKey`, mirroring `navigate.ts`); `resolveFileMetadata(child.ipnsName, fileReadKey, ctx)` -> `NodeContent`; `downloadFileContent({ fileKey: content.fileKey, fileIv, encryptionMode, ctx })` (raw fileKey — the v3 model stores it un-wrapped).
- documents the exact LOCAL run recipe so the orchestrator can execute the desktop-e2e run.

Boundary: the three helpers TYPECHECK/BUILD clean against the node/v3 SDK types; the recipe is captured. This plan does NOT run e2e (the orchestrator does, after this lands) and does NOT claim the flip is validated — necessary, not sufficient.

Purpose: SC-05 — the desktop-e2e round-trip becomes a meaningful node/v3 gate; the run is made executable.
Output: three node/v3-migrated helpers + a documented LOCAL run recipe.
</objective>
