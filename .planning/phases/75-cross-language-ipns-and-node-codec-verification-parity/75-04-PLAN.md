<objective>
Turn the node-codec KAT from an opaque-string round-trip into a real encoding lock: pick fileIv sample values that are valid base64 but invalid hex, add an expected decoded-length field, and add a base64-decode-and-assert step to both the Rust and TS KAT consumers so a hex-vs-base64 divergence (the Phase 69 desktop-e2e "Decryption failed" root cause) can never round-trip through the tests undetected again.

Purpose: RESEARCH Pattern 3 / Pitfall 1 — today's fileIv sample "000102030405060708090a0b" is coincidentally valid as BOTH hex and base64, and neither KAT consumer ever decodes fileIv to bytes, so a hex-encoded regression passes the KAT trivially. Just changing the sample is insufficient; a NEW decode-and-assert path is required.
Output: A KAT where a hex-encoded file_iv fails on both languages.
</objective>

## Trust Boundaries

| Boundary | Description |

| Rust mount ↔ TS reader wire format | NodeContent.file_iv is written by one language and decoded by the other; an encoding mismatch is a silent total decryption failure (Phase 69 incident) |
| shared vector ↔ both KAT consumers | node-codec.json is the frozen oracle that must pin the fileIv encoding, not merely carry it |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-75-09 | Tampering | KAT that round-trips fileIv without decoding it (SC2 root cause) | high | mitigate | Add explicit base64-decode-and-assert-length steps in both languages against an encoding-unambiguous sample so a hex regression fails the KAT |
| T-75-10 | Tampering | encoding-ambiguous sample value (valid as both hex and base64) | high | mitigate | Replace every fileIv sample with base64 that is invalid as hex; verify the property programmatically, never hand-derive |
| T-75-11 | Tampering | hand-edited expected_read_body_hex diverging from the codec | medium | mitigate | Any wire-byte change to expected_read_body_hex regenerated from the canonical codec, never hand-authored |
</threat_model>
