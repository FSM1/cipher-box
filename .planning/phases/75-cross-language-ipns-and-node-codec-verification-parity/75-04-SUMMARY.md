# Phase 75 Plan 04: node-codec KAT fileIv Encoding Lock Summary

**Node-codec KAT hardened with a real base64-decode-and-assert-length step so a hex-encoded `file_iv` regression now fails on both Rust and TypeScript, closing the Phase 69 "opaque-string round-trip" blind spot.**

## Accomplishments

- Replaced all four file-kind `fileIv` samples in `tests/vectors/node-codec.json` with base64 values that are programmatically verified to be invalid as hex (GCM 12-byte samples contain a non-hex character; CTR 16-byte samples naturally end in `==` padding), and added a pinned `expected_file_iv_len_bytes` (12/16) alongside each.
- Regenerated `expected_read_body_hex` for the two affected body vectors by actually running the canonical TS `encodeReadBody` codec against the new fileIv values (via `tsx`), never hand-derived — per RESEARCH.md's explicit anti-pattern warning.
- Added a new Rust test (`node_codec_kat_file_iv_is_base64_not_hex`) that base64-decodes `content.fileIv` and every `versions[].fileIv` for each file-kind vector and asserts the decoded length matches `expected_file_iv_len_bytes`.
- Added a mirrored TS `describe` block ("fileIv Encoding Lock") using a local helper that mirrors `decode.ts`'s private `base64ToUint8Array` (not the test file's `fromHex` helper), asserting the same invariant off the same shared `VECTORS` import.
- Confirmed (via a standalone hex-shape check) that every new fileIv sample fails a naive hex-decode attempt — the encoding lock is real, not just a new sample value round-tripping through an unchanged opaque-string test.

## Decisions Made

- `expected_file_iv_len_bytes` is only present on the two file-kind body vectors (index 1 GCM, index 2 CTR) — folder/root vectors (index 0, 3) have no `content` object at all, so making the field mandatory on every body vector (as the plan's literal wording and its illustrative verify script implied) would have made the verify script crash on `b.node.content.fileIv` for those two vectors. Implemented as `Option<usize>` in Rust (`#[serde(default)]`) and detected via `typeof` filtering in TS, with both new tests asserting a non-vacuous minimum of 2 vectors exercised. This is a Rule 1 (bug-avoidance) deviation from the plan's illustrative script, not from its intent — SC2's actual requirement ("a hex-encoded file_iv fails the node-codec KAT") is fully met for every vector that carries a fileIv.
- Used `tsx` to invoke the real `encodeReadBody` codec (rather than hand-deriving the new `expected_read_body_hex`) to comply with RESEARCH.md Pattern 3 / Anti-Pattern: "Any changed expected_read_body_hex... regenerated from the codec, never hand-edited."
