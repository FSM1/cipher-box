<objective>
Recover the per-operation IPNS signature-verification CPU cost on the API publish path with a safe, measured short-circuit (D-11): a short-TTL in-process cache keyed by the full `(ipnsName, sequenceNumber, signatureV2-bytes)` triple that lets a repeated submission of an already-verified signed record skip the redundant Ed25519 `verifyIpnsRecordSignature`. Externally-sourced / DHT records and any not-previously-verified input are ALWAYS fully verified. Deliver a measured cost recovery in `docs/CAPACITY.md` §1.5.

Purpose: D-11 mandates a measurement before committing to a mechanism. This plan measures first (Task 1), then implements the cache only if/where the measurement shows recoverable cost. It touches `ipns.service.ts` (shared with Plan 05), so it sequences after Plan 05 in Wave 3.

IMPORTANT FINDING (verify before implementing): The TEE republish path (apps/api/src/republish/republish.service.ts) publishes via `publishSignedRecord` + `syncFolderIpnsSequence` and does NOT call `publishRecord`/`upsertFolderIpns`/`verifyIpnsRecordSignature` — so the TEE re-sign cycle does NOT currently pay the verify cost. The recoverable cost is on the client `publishRecord` path only. Do NOT add a `skipSigVerify` bypass to the TEE path (RESEARCH assumption A3 is moot — confirm by reading republish.service.ts before designing the short-circuit).
Output: A benchmark harness, a measured §1.5 entry, and (if the measurement justifies it) a safe verified-record cache wired into publishRecord.
</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
| -------- | ----------- |
| client publish → verify anchor | The cache decides whether to skip verification; an incorrect predicate would skip verifying an untrusted record |
| DHT/someguy resolve → client | DHT records are externally sourced; the cache must NEVER mark them authoritative |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --------- | -------- | --------- | ----------- | --------------- |
| T-60-20 | Tampering | cache short-circuit skipping verification of an untrusted record | mitigate | Cache populated ONLY on a successful server-side publish-verify; resolve/DHT never populate it; key is the full (ipnsName, seq, signatureV2-bytes) triple, never CID alone (D-11 invariant) |
| T-60-21 | Spoofing | CID-collision cache poisoning | mitigate | Full-triple key includes the signatureV2 bytes; a forged record with a different signature is a cache miss → full verify |
| T-60-22 | Elevation | TEE skipSigVerify bypass weakening the anchor | accept→avoid | The TEE path does not hit verifyIpnsRecordSignature (confirmed in republish.service.ts); no bypass is added, so the anchor is never weakened |
| T-60-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages introduced (60-RESEARCH Package Legitimacy Audit: none); no install task in this plan |

</threat_model>
