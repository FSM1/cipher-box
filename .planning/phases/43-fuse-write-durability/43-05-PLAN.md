<objective>
Close the foundational replay-correctness gaps (CR-01, CR-02, CR-03) plus replay-ordering and nesting warnings (WR-01, WR-02) and the journal durability/permission warnings (WR-03 partial, WR-09). This plan owns the journal schema (`crates/sdk/src/queue.rs`) and the replay core (`crates/fuse/src/lib.rs`). Subsequent gap plans (43-06 fuser write-side, 43-07 Windows) populate the new journal field; 43-08 wires the daemon.

The root defect: the parent folder IPNS private key was never journaled, so replay could not sign and publish the parent IPNS record. It returned Ok without a commit (journal entry removed, data orphaned), unpinned the live parent CID, and recorded a phantom publish. Additionally the journaled ECIES-wrapped file/child IPNS keys were misinterpreted as raw 32-byte keys.

Per the project key-derivation architecture: folder IPNS keys are randomly generated (`generate_ed25519_keypair`, not HKDF-derivable), so re-derivation at replay is impossible for folders. The correct, zero-knowledge-preserving fix is to journal the USER-ECIES-wrapped parent IPNS private key (the same wrapped form already stored everywhere in folder metadata) and unwrap it at replay with the user's private key — never persist raw key material, never journal the TEE-wrapped form.

Purpose: make replay actually complete a confirmed remote commit so the original UAT orphan bug closes and no new data-loss risk (live-CID unpin) is introduced.
Output: updated journal schema with `parent_ipns_key_hex`; corrected replay that publishes, unwraps keys, orders deterministically, and resolves nested parents.
</objective>
