## Summary

Phase 62 is a pure TypeScript codec implementation phase with no new external dependencies. The seal primitive (`sealAesGcmAad`/`buildNodeAad`) and its frozen AAD byte encoding shipped in Phase 61 and are consumed here unchanged. The implementation work is: define the `Node`/`SealedChildRef`/`PublishedNode` TypeScript types; write encode/decode functions (`JSON.stringify ↔ JSON.parse` with validation, per D-03); write seal/unseal functions that compose the Phase 61 primitive; freeze golden vectors for all three node kinds; redesign the vault blob to carry two ECIES-wrapped keys (v3 hard-cut); and bring `packages/sdk-core`, `packages/sdk`, and `apps/web` to compile-only (stub any real behavior with `throw new Error('not implemented — phase NN')`).

The keystone nature means nothing downstream typechecks until `packages/core dist/` is rebuilt — the fan-out of retired types (`FolderMetadata`, `FileMetadata`, `FilePointer`, `FolderEntry`, `encryptedRootFolderKey`) through sdk-core / sdk / web is broad but the changes are mechanical: delete the old type references, import `Node`/`SealedChildRef`, stub any call site that needs real new logic. The hardest part of the phase is the golden-vector freeze (freeze-first discipline from Phase 61): body bytes must be IV-independent (encode only, no seal), and the full-envelope vector uses fixed-key / fixed-IV to lock the entire AEAD flow.

**Primary recommendation:** Implement `node/types.ts` → `node/encode.ts` → `node/decode.ts` → `node/seal.ts` in that order (types first drives everything else), freeze vectors before wiring consumers, then do the vault v3 blob redesign, then the consumer compile-gate sweep.

### Pattern 1: JSON Codec (mirrors `encryptFolderMetadata`)

The node read-body and write-body are JSON-serialized exactly like `encryptFolderMetadata`. The encode step is the same; the seal step swaps `encryptAesGcm` for `sealAesGcmAad`. [VERIFIED: `packages/core/src/folder/metadata.ts`]

```typescript
// Source: packages/core/src/folder/metadata.ts (pattern to mirror)
// In node/encode.ts — encodeReadBody(node: Node): Uint8Array
function encodeReadBody(node: Node): Uint8Array {
  const readBody = {
    schema: 'node/v3',
    children: node.kind !== 'file' ? node.children : undefined,
    content: node.kind === 'file' ? node.content : undefined,
    createdAt: node.createdAt,
    modifiedAt: node.modifiedAt,
  };
  // D-03: JSON wire format — same as encryptFolderMetadata
  return new TextEncoder().encode(JSON.stringify(readBody));
}

// In node/seal.ts — sealReadBody
async function sealReadBody(
  node: Node,
  readKey: Uint8Array,
  kindByte: number,
): Promise<string> {  // returns base64
  const plaintext = encodeReadBody(node);
  const aad = buildNodeAad(node.id, kindByte, node.generation, 0x01); // role=body
  const sealed = await sealAesGcmAad(plaintext, readKey, aad);
  // [SECURITY: MEDIUM-08] chunked base64 for large bodies
  return uint8ArrayToBase64(sealed);
}
```

### Pattern 2: `SealedChildRef.readKeySealed` — child-readkey role

```typescript
// Source: design §2.6 + ADR 0003 (role 0x02)
// In node/seal.ts — sealChildReadKey
async function sealChildReadKey(
  childReadKey: Uint8Array,   // 32 bytes — caller owns, never zeroed here (D-09)
  parentReadKey: Uint8Array,
  childId: string,
  childKind: 'folder' | 'file',
  childGeneration: number,
): Promise<string> {  // base64
  const kindByte = childKind === 'folder' ? 0x01 : 0x02;
  const aad = buildNodeAad(childId, kindByte, childGeneration, 0x02); // role=child-readkey
  const sealed = await sealAesGcmAad(childReadKey, parentReadKey, aad);
  return uint8ArrayToBase64(sealed);
}
```

### Pattern 3: Content self-seal — role `0x03 content`

```typescript
// Source: design §2.9 + ADR 0003 (role 0x03)
// In node/seal.ts — sealContent (file nodes only)
async function sealContent(
  content: NodeContent,       // plaintext content object (fileKey as raw Uint8Array)
  fileNodeReadKey: Uint8Array,
  nodeId: string,
  generation: number,
): Promise<string> {  // base64
  // content.fileKey is raw 32B inside sealed body — NOT ECIES hex (semantic type change, D-07)
  const plaintext = new TextEncoder().encode(JSON.stringify(serializeContent(content)));
  const aad = buildNodeAad(nodeId, 0x02 /* file */, generation, 0x03); // role=content
  const sealed = await sealAesGcmAad(plaintext, fileNodeReadKey, aad);
  return uint8ArrayToBase64(sealed);
}
```

### Pattern 4: Vault blob v3 (mirrors v2 layout, adds second key)

```typescript
// Source: packages/core/src/vault/blob.ts (v2 pattern)
// D-05: 0x03 | u16_BE(readLen) | ecies(readKey) | u16_BE(writeLen) | ecies(writeKey)
export const BLOB_V3_VERSION = 0x03;

export function serializeVaultBlobV3(
  encryptedRootReadKey: Uint8Array,   // ECIES(rootReadKey) ~129 bytes
  encryptedRootWriteKey: Uint8Array,  // ECIES(rootWriteKey) ~129 bytes
): Uint8Array {
  const readLen = encryptedRootReadKey.length;
  const writeLen = encryptedRootWriteKey.length;
  // 1 (version) + 2 (readLen) + readLen + 2 (writeLen) + writeLen
  const result = new Uint8Array(1 + 2 + readLen + 2 + writeLen);
  result[0] = BLOB_V3_VERSION;
  result[1] = (readLen >> 8) & 0xff;
  result[2] = readLen & 0xff;
  result.set(encryptedRootReadKey, 3);
  const writeOffset = 3 + readLen;
  result[writeOffset] = (writeLen >> 8) & 0xff;
  result[writeOffset + 1] = writeLen & 0xff;
  result.set(encryptedRootWriteKey, writeOffset + 2);
  return result;
}
```

### Pattern 5: Runtime decode validation (mirrors `validateFolderMetadata`)

Validation in `node/decode.ts` must match the `validateFolderMetadata` pattern: check all required fields, throw `CryptoError('Invalid node format', 'DECRYPTION_FAILED')` on any violation. The `generation` range check (0 ≤ generation ≤ 0xffffffff, integer) mirrors the `buildNodeAad` validation in Phase 61 (fail-closed, D-08). [VERIFIED: `packages/core/src/folder/metadata.ts` + `packages/crypto/src/aes/seal.ts`]

### Anti-Patterns to Avoid

- **Barrel-only implementation:** All codec logic must live in named files (`encode.ts`, `decode.ts`, `seal.ts`), not in `node/index.ts`. The vitest coverage config excludes `src/**/index.ts` barrels — code in a barrel is invisible to coverage. [VERIFIED: `packages/core/vitest.config.ts` line `exclude: ['src/**/index.ts']`]
- **IV-dependent body bytes in golden vectors:** The PRIMARY LOCK vector asserts only the encode output (body bytes before AEAD). The FULL-SEAL LOCK uses a fixed IV injected via a test-only helper — never use a random IV for the fixed-IV vector. Do not confuse the two.
- **Zeroing caller-owned key material in the codec:** `sealChildReadKey` receives the child's `readKey` from the caller; the codec must not zero it after sealing — the caller may reuse it. Only zero keys the codec minted itself (D-09, zeroization terminal-owner rule). [VERIFIED: project memory — zeroization landmine from `Phase-51-04`]
- **`fileKey` as ECIES hex string:** In v3, `content.fileKey` is a raw 32-byte key inside the sealed body (`Uint8Array` in memory, included as a `number[]` or base64 field in the JSON-serialized content). It is NOT an ECIES-wrapped hex string. Documenting this semantic type change in `METADATA_SCHEMAS.md` is an explicit requirement (D-07, NODE-02).
- **Stubbing with empty functions instead of `throw`:** Consumer stubs must be `throw new Error('not implemented — phase NN')`, not `return undefined` or empty functions. An empty stub can silently pass type checks while hiding a real missing behavior path from reviewers.
- **Forgetting `pnpm build` in `packages/core` before consumer typecheck:** sdk-core/sdk/web check the built `dist/`, not source. A dist rebuild must be the first step in the consumer compile-gate task. [VERIFIED: project memory — cross-package dist staleness]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| AAD-bound seal | Custom AES-GCM + AAD wiring | `sealAesGcmAad` / `unsealAesGcmAad` from `@cipherbox/crypto` | Already frozen in Phase 61; reimplementing risks diverging from the KAT-locked encoding |
| AAD byte construction | Custom concatenation | `buildNodeAad` from `@cipherbox/crypto` | The 45-byte layout is KAT-frozen in `tests/vectors/crypto/node-aad.json`; any hand-roll risks drift |
| ECIES key wrapping for vault blob | Custom key-wrap | `wrapKey` / `unwrapKey` from `@cipherbox/crypto` | Existing ECIES functions used by current vault `initializeVault` / `decryptVaultKeys` |
| Base64 encoding of large sealed blobs | `btoa(String.fromCharCode(...blob))` | `uint8ArrayToBase64` (chunked helper) from `folder/metadata.ts` | The spread-based pattern fails on large Uint8Arrays (MEDIUM-08 note) |
| Generation range validation | Custom guard | Mirror `buildNodeAad`'s `!Number.isInteger(generation) || generation < 0 || generation > 0xffffffff` | Reuse the exact guard from Phase 61 for consistency; the KAT relies on the same range |

**Key insight:** The codec is composition of Phase 61 primitives. Any reimplementation of `buildNodeAad` or `sealAesGcmAad` risks producing different bytes and silently breaking AEAD for all Nodes until Phase 69 Rust asserts the KAT.

## Common Pitfalls

### Pitfall 1: AAD Byte-Encoding Drift (carried from PITFALLS.md)
**What goes wrong:** If any call to `buildNodeAad` in `node/seal.ts` passes the wrong role byte or wrong kind byte, every Node sealed in this phase fails to unseal in Phase 69 Rust or in any cross-language scenario.
**Why it happens:** The four roles (`0x01 body`, `0x02 child-readkey`, `0x03 content`, `0x04 child-writekey`) are easy to confuse. The `readSealed` body and `writeSealed` body both use role `0x01 body` but with different keys — distinguishable only by the key, not the role byte. The `content` seal for file nodes uses role `0x03`.
**How to avoid:** The golden-vector FULL-SEAL LOCK asserts exact ciphertext bytes for a fixed key/IV. If the wrong role byte is used, the ciphertext differs from the vector and the test fails immediately. Freeze vectors before wiring consumers.
**Warning signs:** Golden-vector full-seal test fails with a ciphertext mismatch. [VERIFIED: PITFALLS.md Pitfall 1]

### Pitfall 2: Coverage-Barrel Pitfall
**What goes wrong:** `vitest.config.ts` excludes `src/**/index.ts` from coverage. Codec logic placed in `node/index.ts` (even partially) is never counted toward coverage and silently goes untestedby the coverage gate.
**Why it happens:** The barrel exclusion is intentional (Phase 61 C-02 discovery). Developers familiar with index-as-module patterns may put logic there.
**How to avoid:** `node/index.ts` must be a re-export-only file. All encode/decode/seal/unseal logic lives in `encode.ts` / `decode.ts` / `seal.ts`. [VERIFIED: `packages/core/vitest.config.ts` exclude list]

### Pitfall 3: Consumer Test Suite Breakage Masking
**What goes wrong:** Skipping tests with `describe.skip` per D-02 is correct, but tests that still reference deleted types without being skipped will fail typecheck before the skip is even evaluated, blocking CI.
**Why it happens:** A test file imports `FolderMetadata` from `@cipherbox/core`. After `folder/` is deleted from core and the export removed from `index.ts`, the import is a compile error — `tsc` fails before vitest runs.
**How to avoid:** Update imports in consumer test files (change `FolderMetadata` → `Node` or a stub type) AND wrap the test body in `describe.skip`. If the test is purely behavioral and can't compile at all even with stubs, move the entire test file to a `__skip__/` subfolder (or use a `.ts.todo` extension) and note the restore path.
**Warning signs:** TypeScript build fails on test files despite `describe.skip` being present.

### Pitfall 4: `content.fileKey` Type Confusion
**What goes wrong:** `content.fileKey` in the new schema is a raw 32-byte key inside the sealed body. If code accidentally treats it as the legacy ECIES-encrypted hex string (`fileKeyEncrypted`) — e.g., by passing it to `unwrapKey` — the result is garbage or a CryptoError.
**Why it happens:** The old `FileMetadata.fileKeyEncrypted` was a hex string (ECIES output ~129 bytes). The new `content.fileKey` is raw AES key material. The field name similarity masks the semantic type change.
**How to avoid:** Document the type change in `METADATA_SCHEMAS.md` (D-07 requirement). Use `Uint8Array` in the in-memory type for `content.fileKey`, never `string`. The JSON-serialized form inside the sealed body can be `number[]` or base64 — keep it explicit in the types. [VERIFIED: design §2.3 + §2.9]

### Pitfall 5: Vault `init.ts` Two-Key Adaptation
**What goes wrong:** `initializeVault` currently returns `{ rootFolderKey, rootIpnsKeypair }`. After v3, it must also manage `rootWriteKey`. If `vault/init.ts` is not updated alongside `vault/blob.ts`, the type changes in blob.ts break init.ts at compile time, blocking the overall typecheck gate.
**Why it happens:** The vault module has three files (`blob.ts`, `types.ts`, `init.ts`) and all three must be updated atomically. The `encryptedRootFolderKey` field is present in `EncryptedVaultKeys` (types.ts) and referenced by `encryptVaultKeys` / `decryptVaultKeys` (init.ts) and `serializeVaultBlobV2` (blob.ts).
**How to avoid:** Update all three files in a single task: (1) `vault/types.ts` — rename/restructure, (2) `vault/blob.ts` — v3 hard-cut, (3) `vault/init.ts` — two-key wrap/unwrap. Add `vault/init.ts` to the scope explicitly in the plan. [VERIFIED: `packages/core/src/vault/` directory structure]

### Known Threat Patterns for This Phase

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| AAD transplant — relay moves a child's sealed `readKeySealed` to a different parent | Tampering | `buildNodeAad(childId, childKind, childGeneration, role=child-readkey)` binds the blob to the specific child identity; replaying under a different `childId` fails AEAD authentication |
| Stale-generation replay — relay serves a pre-rotation sealed body | Tampering | `generation` is plaintext on the envelope AND folded into AAD; a lower-generation body sealed under the new `readKey` fails authentication; the Phase 66 server-side generation gate is defence-in-depth |
| Key material leak via logging | Information Disclosure | `Uint8Array` key material must never be passed to `JSON.stringify` or `console.log`; codec returns raw `Uint8Array` to caller per D-09 |
| Content self-seal semantic confusion (`fileKey` treated as ECIES) | Tampering | Type system enforcement: `content.fileKey` must be `Uint8Array` in-memory; documented as semantic type change in METADATA_SCHEMAS.md |
| Coverage-barrel silencing of security-critical validation | Tampering (via omission) | vitest.config.ts excludes barrels; all validation code must be in named files |

## Open Questions

1. **`BinEntry` adaptation scope**
   - What we know: `BinEntry` imports `FilePointer` and `FolderEntry` as the types for `filePointer?` and `folderEntry?` fields. After those types are deleted, `BinEntry` must either import `Node` or use a stub type.
   - What's unclear: The bin restore path in Phase 65 will convert `BinEntry` to use Node-based references properly. For this phase we need compile-only: should `filePointer?` and `folderEntry?` be typed as `Node` now (anticipating Phase 65), or as `unknown` with a TODO?
   - Recommendation: Use `Node` for the type (it's the correct future type) but stub any behavioral code in `bin/encrypt.ts` / `bin/schema.ts` with `throw new Error('not implemented — phase 65')`.

2. **`vault/init.ts` two-key shape**
   - What we know: `initializeVault` generates `rootFolderKey` + `rootIpnsKeypair`. Under v3, it needs `rootReadKey` (random 32B, replaces `rootFolderKey`) + `rootWriteKey` (random 32B, new) + `rootIpnsKeypair` (unchanged — Ed25519 key is write-plane).
   - What's unclear: Is `rootWriteKey` derived from or independent of the Ed25519 key? The design (§2.2) says write-body is sealed under a separate `writeKey`; the Ed25519 key lives INSIDE the sealed write-body. So `writeKey` is a fresh random AES key, independent of the Ed25519 keypair.
   - Recommendation: `rootWriteKey = generateFileKey()` (independent random 32B AES key). `rootIpnsKeypair` unchanged. `VaultInit` gains `rootWriteKey: Uint8Array`.
