<objective>
Bind every resolved IPNS record to its signed CBOR-embedded cid/sequence and route
all Rust FUSE resolve sites through a single verified chokepoint, with symmetric CBOR
binding on the JS side. Closes the CID/sequence-swap gap (D-07/D-08) and makes all
~9 Rust resolve sites safe-by-default (D-01), with scoped fail-closed posture (D-02),
the security-boundary folder-key descent kept hard fail-closed (D-03), legacy records
still allowed (D-04), and a unified Rust↔JS posture (D-05).

Purpose: Today only 1 of 9 Rust resolve sites verifies, and neither language decodes
the signed CBOR `data` to bind the embedded cid/sequence back to the response. A
malicious/MITM server can present a genuinely-signed record alongside a swapped cid
and both sides accept it. This plan removes that tamper surface as defense-in-depth.

Output: New `decode_ipns_cbor_data` helper (cipherbox-core), new `resolve_ipns_verified`
wrapper (cipherbox-fuse), 8 unverified FUSE sites rerouted through it, replay.rs sole
verified site converted to the wrapper (D-03 behavior preserved), and CBOR binding added
to the sdk-core `resolveIpnsRecord` chokepoint.
</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
| -------- | ----------- |
| IPNS resolve provider → FUSE/sdk-core | The delegated routing provider / CipherBox API returns a resolve response (cid, sequenceNumber, signatureV2, data, pubKey). The provider is semi-trusted; a malicious or MITM'd response is the adversary here. |
| Signed CBOR `data` ↔ response top-level fields | The Ed25519 signature covers the CBOR `data` only. The top-level `cid`/`sequenceNumber` fields are NOT covered by the signature and can be tampered independently. |
