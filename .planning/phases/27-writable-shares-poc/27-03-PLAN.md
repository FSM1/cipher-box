1. **Extend return type** -- Add these fields to `UseSharedNavigationReturn`:
   - `permission: 'read' | 'write' | null` -- current share's permission (null when at top-level list)
   - `ipnsPrivateKey: Uint8Array | null` -- unwrapped IPNS private key for write shares (null for read-only)
   - `ipnsName: string | null` -- current folder's IPNS name (needed for write operations)
   - `currentSequenceNumber: string | null` -- latest known sequence number for conflict detection
   - `uploadFile: (file: File) => Promise<void>` -- upload handler for write shares
   - `createFolder: (name: string) => Promise<void>` -- mkdir handler for write shares
   - `renameItem: (item: FolderChild, newName: string) => Promise<void>` -- rename handler
   - `deleteItem: (item: FolderChild) => Promise<void>` -- delete handler

2. **IPNS key unwrapping** -- When `navigateToShare` is called and the share has `permission === 'write'` and `encryptedIpnsKey`:
   - Get the user's private key from auth store: `const { privateKey } = useAuthStore.getState();`
   - Unwrap: `const ipnsPrivKey = await unwrapKey(hexToBytes(share.encryptedIpnsKey), privateKey);`
   - Store in a ref (`ipnsPrivateKeyRef = useRef<Uint8Array | null>(null)`) and expose via return value
   - On unmount or navigation away: zero the key `ipnsPrivateKeyRef.current?.fill(0); ipnsPrivateKeyRef.current = null;`
   - For read-only shares: `ipnsPrivateKey` remains null

3. **30s sync polling for write shares** -- Add a `useEffect` with `setInterval`:
   - Only activate when `currentView === 'folder'` AND `permission === 'write'` AND the shared folder is currently viewed
   - Poll interval: 30000ms (30s, matching owner's multi-device sync)
   - On each tick: re-resolve the folder's IPNS record, re-decrypt metadata, update `folderChildren` state
   - The IPNS resolve already happens in `navigateToShare`/`navigateToSubfolder` -- extract that logic into a reusable `refreshFolderContents()` function
   - Clear interval on unmount, view change, or navigation away
   - Cleanup: `return () => clearInterval(intervalRef.current);`
   - Do NOT poll for read-only shares (no need, they only view)

4. **Write operation handlers** -- Implement the four write handlers using sdk-core functions:
   - Each handler must use `withConflictRetry` from `folder-helpers.ts`
   - Each handler receives the IPNS private key from the ref, folderKey from state, and ipnsName from state
   - **uploadFile**: Call the same upload flow as the owner's FileBrowser (look at `useFolderMutations.ts` for the pattern), but parameterized with the share's keys. The upload flow is: encrypt file content, upload to IPFS, add FilePointer to folder metadata, encrypt metadata, sign IPNS record with ipnsPrivateKey, publish via API.
   - **createFolder**: Generate random Ed25519 keypair for the subfolder (same as existing `createSubfolder` in sdk-core). Use the share's folderKey to encrypt the subfolder entry. Sign with share's IPNS key. Publish via API. The subfolder is created under the owner's namespace (sequence number coordination through the owner's FolderIpns row).
   - **renameItem**: Update the item's name in folder metadata, re-encrypt, sign with IPNS key, publish.
   - **deleteItem**: Move item to recycle bin. Per CONTEXT.md, deleted items go to the OWNER's recycle bin. This means the delete operation updates the shared folder's metadata (removing the item) but the recycle bin entry is created under the owner's bin IPNS name. For the PoC, simply remove the item from the shared folder's metadata and publish. The recycle bin integration is complex and can be a stub that just removes the entry (document this as a PoC limitation).
   - All handlers should call `refreshFolderContents()` after success to update the view.

5. **Silent revocation handling**:
   - During polling, if the share's permission changes from 'write' to 'read' (detected by re-fetching the received shares or from the IPNS publish returning 403):
   - Zero the IPNS private key ref
   - Set permission state to 'read'
   - The UI will reactively hide write actions (SharedFileBrowser reads permission from the hook)
   - If a write operation receives a 403 from the server: catch it, zero IPNS key, set permission to 'read', show error message `> write access revoked -- folder is now read-only` via the hook's error state
