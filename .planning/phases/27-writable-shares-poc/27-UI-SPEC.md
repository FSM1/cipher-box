## Component Inventory

### New Components

#### 1. Permission Toggle (`share-permission-selector`)

Location: Inside ShareDialog, between pubkey input and share button.

```
// permission
[ READ-ONLY ]  [ READ-WRITE ]
```

**Structure:**

- Label: `// permission` -- monospace, `--font-size-xs`, `--font-weight-semibold`, uppercase, `--color-text-secondary`, `letter-spacing: 0.05em`
- Container: `display: flex; gap: 0;` -- buttons adjacent with no gap (terminal toggle feel)
- Each button: `role="radio"`, `aria-checked`, grouped under `role="radiogroup" aria-label="Permission level"`
- Active state: `color: var(--color-green-primary); border-color: var(--color-green-primary); background-color: var(--color-green-darker);`
- Inactive state: `color: var(--color-text-muted); border-color: var(--color-border-dim); background: transparent;`
- Button padding: `2px 8px` (matches `share-revoke-btn` compact pattern)
- Font: `--font-family-mono`, `--font-size-xs`, `--font-weight-semibold`, `letter-spacing: 0.05em`
- Focus: `:focus-visible { outline: 1px solid var(--color-green-primary); outline-offset: 1px; }`
- Keyboard: ArrowLeft/ArrowRight to switch between options (standard radiogroup pattern)

Default selection: `READ-ONLY` (safe default per CONTEXT.md).

#### 2. `[RW]` Badge (`shared-rw-badge`)

Location: Replaces `[RO]` badge in SharedFileBrowser rows for write-permission shares.

**Structure:**

- Text: `[RW]`
- Font: `var(--font-family-mono)`, `0.65rem` (matches existing `shared-ro-badge`)
- Color: `var(--color-green-primary)` (NOT `--color-text-dim` like `[RO]` -- the green signals active write capability)
- Opacity: `0.9` (slightly more prominent than `[RO]` at `0.7`)
- `margin-left: var(--spacing-xs); user-select: none;`

Contrast with `[RO]` badge:

- `[RO]`: `color: var(--color-text-dim); opacity: 0.7;` -- dim, passive
- `[RW]`: `color: var(--color-green-primary); opacity: 0.9;` -- bright green, active

#### 3. Recipient Permission Display

Location: In share recipients list within ShareDialog, alongside each truncated pubkey.

**Structure:**

- After pubkey text, before revoke button: inline permission label
- Text: `[read]` or `[write]`
- Font: `--font-family-mono`, `--font-size-xs`
- Color for `[read]`: `var(--color-text-muted)` -- dim, expected default
- Color for `[write]`: `var(--color-green-primary)` -- bright, signals elevated permission
- `margin-left: var(--spacing-xs); flex-shrink: 0;`

#### 4. Permission Upgrade/Downgrade Controls

Location: In share recipients list, between permission label and revoke button.

**Structure:**

- Single button per recipient showing opposite action: `--upgrade` or `--downgrade`
- `--upgrade` button: `color: var(--color-green-primary); border-color: var(--color-green-dim);` (follows `share-submit-btn` pattern)
- `--downgrade` button: `color: var(--color-warning); border-color: var(--color-warning-dim);` (orange/amber signals reduced access, not destructive)
- Padding: `2px 8px` (matches revoke button)
- Font: `--font-family-mono`, `--font-size-xs`
- Hover: background tint matching the button color at 10% opacity
- Downgrade confirmation: Inline `confirm? [y] [n]` pattern identical to existing revoke confirm

#### 5. Write Toolbar for Shared Folders

Location: In SharedFileBrowser toolbar area, visible only when `permission === 'write'`.

**Structure:**

- Reuses existing `file-browser-actions` container pattern
- Upload button: `class="toolbar-btn toolbar-btn--primary"`, label: `--upload`
- New folder button: `class="toolbar-btn toolbar-btn--primary"`, label: `--mkdir`
- Matches exactly the owner's FileBrowser toolbar button styles -- no visual distinction between owned and write-shared folders (write-share recipients are full collaborators)

### Modified Components

#### 1. ShareDialog (`ShareDialog.tsx`)

Changes:

- Add permission toggle after pubkey input section, before share button
- Recipient list entries show `[read]` / `[write]` label + upgrade/downgrade button
- Share button label changes contextually: `--share` (unchanged)
- Progress text unchanged: `> re-wrapping keys...` (also wraps IPNS key for write shares)

#### 2. SharedFileBrowser (`SharedFileBrowser.tsx`)

Changes:

- `SharedListRow`: Conditional badge -- `[RW]` for write shares, `[RO]` for read-only
- `SharedFolderRow`: Same conditional badge
- Folder view toolbar: Conditionally render upload zone and `--mkdir` button when write-permitted
- Context menu: Pass `readOnly={permission !== 'write'}` instead of always `readOnly`
- When write-permitted, context menu shows: Download, Preview, Edit, Rename, Move, Delete, Details
- When read-only, context menu shows: Download, Preview, Details, Hide (unchanged from current behavior)

#### 3. ContextMenu (`ContextMenu.tsx`)

No structural changes needed. The existing `readOnly` prop already gates write actions (rename, move, delete, share). The `onShare` action remains hidden for shared folders (no re-sharing in PoC per CONTEXT.md).

## Interaction Contract

### Permission Toggle Behavior

1. Default to `READ-ONLY` on dialog open
2. Toggle is a radio group -- only one selected at a time
3. ArrowLeft/ArrowRight keyboard navigation between options
4. Selection persists during the share creation flow (reset on dialog close)
5. When `READ-WRITE` selected, the share submission wraps IPNS key in addition to folder key

### Write Actions in Shared Folders

1. Upload: Standard drag-drop or `--upload` button. Uses shared folder's IPNS key for publish.
2. Create folder: `--mkdir` button. Creates subfolder with new random Ed25519 keypair. Enrolls with TEE under owner's userId.
3. Rename: Via context menu. Publishes updated metadata using shared IPNS key.
4. Delete: Via context menu. Moves item to owner's recycle bin (per CONTEXT.md).
5. All write operations use `withConflictRetry` -- 409 triggers re-sync then retry.

### Permission Upgrade/Downgrade

1. Owner clicks `--upgrade` on a read-only recipient in the recipients list
2. Inline confirmation: not required (upgrade is non-destructive, safe to perform)
3. API wraps and delivers IPNS key to recipient
4. Recipient sees `[RW]` and write actions on next 30s sync poll

Downgrade flow:

1. Owner clicks `--downgrade` on a write recipient
2. Inline confirmation: `confirm? [y] [n]` (same pattern as revoke, since this removes capability)
3. API nulls the IPNS key and sets permission to `read`
4. Server immediately rejects future publishes from this recipient
5. Recipient sees `[RO]` badge and write actions disappear on next sync poll (silent transition per CONTEXT.md)

### Silent Revocation Transition

When a write-share is downgraded or revoked:

- No error dialog shown to recipient
- Badge changes from `[RW]` to `[RO]` on next sync
- Write toolbar disappears, context menu reverts to read-only
- If recipient had an in-progress write operation, it receives a server-side 403 -- handle with: `> write access revoked -- folder is now read-only`

### Sync Polling for Write Shares

- Add 30s IPNS polling for the currently-viewed shared folder (not all shared folders)
- Same sync banner as multi-device: `// metadata updated -- refreshing...`
- Existing `withConflictRetry` handles 409 identically to multi-device sync

## State Mapping

| UI State                          | Visual Treatment                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------- |
| Read-only share (default)         | `[RO]` badge (dim), no write toolbar, read-only context menu                          |
| Write share                       | `[RW]` badge (green), write toolbar visible, full context menu                        |
| Permission toggle: read selected  | `[ READ-ONLY ]` button: green text+border, dark green bg. Other button: muted.        |
| Permission toggle: write selected | `[ READ-WRITE ]` button: green text+border, dark green bg. Other button: muted.       |
| Sharing in progress               | Submit button shows `...`, input disabled, progress text animates                     |
| Upgrade in progress               | `--upgrade` button shows `...`, disabled                                              |
| Downgrade confirming              | `confirm? [y] [n]` inline (replaces `--downgrade` button)                             |
| Downgrade in progress             | `[y]` button shows `...`, both confirm buttons disabled                               |
| Write operation conflict (409)    | Sync banner appears, operation retries automatically, resolves silently               |
| Write access revoked mid-session  | Badge transitions `[RW]` to `[RO]`, toolbar disappears, no error unless mid-operation |
| Write operation after revocation  | Error message: `> write access revoked -- folder is now read-only`                    |
