<objective>
Close the shared-folder consolidation that 48-04 left open: the SDK must own
shared-folder REFRESH (background re-resolve), not just write. Today the web 30s
poller (`useSharedNavigation.refreshFolderContents`) resolves IPNS, fetches IPFS,
and decrypts inline, then writes the projection refs directly — the exact
parallel data path 48-04 eliminated for writes, but still live for polling.

Add `client.refreshSharedFolder(shareId)` (the shared analog of the owned path's
`loadFolder`/`ensureFolderLoaded`): re-resolve the share's IPNS record via
`sdkCore.loadFolderMetadata`, apply the REQ-1 sequence-guard (never clobber
fresher in-memory state with a stale IPNS snapshot), adopt into
`sharedFolderTree`, and emit `sharedFolder:updated`. Repoint the web poller
through it and delete the hook's inline resolve.

Purpose: the SDK becomes the single source of truth for shared-folder state on
BOTH paths (write and poll). The desync-risk note in 48-04-SUMMARY ("poll-then-
write relies on CAS rather than a fresh seed") is eliminated — a poll now adopts
into `sharedFolderTree`, so the next write publishes against fresh state.
Output: one new SDK client method (+ index export + TDD test) and a slimmed web
poller fed by the existing projection subscription.
</objective>

<background>
The owned path already has this shape — the consumer never resolves IPNS itself:

- `client.loadFolder(ipnsName, folderKey, ipnsKeypair)` (client.ts ~370): calls
  `sdkCore.loadFolderMetadata({ ipnsName, folderKey, ctx })`, applies the #489
  sequence-guard (`existing.sequenceNumber >= result.sequenceNumber` → keep
  existing, emit, return), adopts into `folderTree`, emits `folder:loaded`.
- The folder store's `subscribeToSdk` projects the emitted children/sequence.

The shared path got the WRITE half in 48-03 (`uploadToSharedFolder` … +
`adoptSharedFolderResult` → emit `sharedFolder:updated`) and 48-04 wired the web
write hook + the `sharedFolder:updated` projection subscription. But the REFRESH
half is missing: `getSharedFolderState` is only a synchronous snapshot read, and
nothing re-resolves a shared folder's IPNS in the background. The web poller is
the only puller of remote shared changes, and it does so OUT of the SDK.

This plan adds the missing refresh method (reusing `sdkCore.loadFolderMetadata`
and the existing `adoptSharedFolderResult` emit shape) and routes the poller
through it.

CRITICAL: the web app + web typecheck consume the BUILT `@cipherbox/sdk` dist.
Rebuild it before web checks: `pnpm --filter @cipherbox/sdk-core build &&
pnpm --filter @cipherbox/sdk build`. Otherwise web tsc reports `refreshSharedFolder`
as missing.
</background>

| Boundary | Description |
| -------- | ----------- |
| web ref ↔ SDK shared state | Refs remain write-only-by-event on BOTH write and poll paths |
| poll vs in-memory freshness | A background poll must never overwrite fresher just-written in-memory state (sequence-as-clock, #489) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --------- | -------- | --------- | ----------- | --------------- |
| T-48-12 | Tampering | poll-then-write ordering | mitigate | refreshSharedFolder applies the #489 sequence-guard — a stale IPNS resolve re-emits existing state instead of clobbering; closes the 48-04 residual desync note (Task 1 guard, asserted Task 1b + UAT step 3) |
| T-48-13 | Tampering | poll ref writes | mitigate | Poller routes through the SDK and the projection subscription is the sole ref writer — no inline resolve, no direct ref writes from the poll path (Task 3, asserted Task 4) |
| T-48-14 | Information Disclosure | shared folderKey reuse on refresh | accept | refreshSharedFolder reuses the folderKey already cloned into sharedFolderTree (48-03); no new key material is unwrapped or exposed on the poll path |

</threat_model>
