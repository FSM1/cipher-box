    1. Create `invites.controller.ts` as a SEPARATE controller (not on SharesController) because the public GET endpoint must NOT have JwtAuthGuard:

       Endpoints:
       a. `GET /invites/:token` — **NO AUTH** — returns `{ status: 'active' | 'expired' | 'claimed' | 'revoked' }` only. Opaque — no file name, no sharer identity before auth. Uses `@ApiTags('invites')`.
       b. `POST /invites/:token/claim` — **WITH JwtAuthGuard + ThrottlerGuard** — accepts ClaimInviteDto (re-wrapped keys from client), creates Share + ShareKey records via existing SharesService.createShare() pattern, returns `{ shareId }`.
       c. `POST /shares/invites` — **WITH JwtAuthGuard + ThrottlerGuard** — accepts CreateInviteDto, generates token, creates ShareInvite, returns invite details + token.
       d. `GET /shares/invites` — **WITH JwtAuthGuard** — query param `ipnsName` (required), returns sharer's active invites for that item.
       e. `DELETE /shares/invites/:inviteId` — **WITH JwtAuthGuard** — revokes an invite (sets status='revoked'). Only the sharer can revoke.

       For endpoints c, d, e: Use a second controller class `ShareInvitesController` at path `shares/invites` WITH `@UseGuards(JwtAuthGuard, ThrottlerGuard)` at class level, or put them on the same InvitesController with per-method guards. The key constraint: GET /invites/:token must be unauthenticated.

       Recommended approach: Single `InvitesController` with NO class-level guard. Apply `@UseGuards(JwtAuthGuard, ThrottlerGuard)` per-method on c/d/e and the claim endpoint. Leave the public GET without guards.

       Import `RequestWithUser` interface matching the pattern in shares.controller.ts.
