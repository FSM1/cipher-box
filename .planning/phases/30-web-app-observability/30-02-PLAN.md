# Plan 30-02: FaroErrorBoundary and Fallback UI

<objective>
Wrap the route tree in App.tsx with FaroErrorBoundary from @grafana/faro-react so that unhandled React render errors are captured by Faro and users see a recovery UI instead of a white screen. The fallback UI follows CipherBox's terminal/cipher aesthetic with a reload button.
</objective>

## Background

Currently, the web app has no ErrorBoundary at all — confirmed by grep. Unhandled render errors crash to a blank white screen with no user recourse and no error telemetry. The FaroErrorBoundary component from @grafana/faro-react automatically reports caught errors to Faro while displaying a fallback component. Errors flow through the Phase 28 logger via the Faro transport (wired in Plan 30-04), maintaining a single error path.

## must_haves

- FaroErrorBoundary wraps the route tree in App.tsx
- ErrorFallback component displays a user-friendly "Something went wrong" message
- ErrorFallback includes a "Reload" button that calls `window.location.reload()`
- ErrorFallback matches the CipherBox dark/terminal visual style
- When Faro is not initialized (local dev), the boundary still catches errors gracefully

```typescript
export function ErrorFallback() {
  return (
    <div className="error-fallback">
      <div className="error-fallback__container">
        <div className="error-fallback__icon">{'// ERROR'}</div>
        <h1 className="error-fallback__title">Something went wrong</h1>
        <p className="error-fallback__message">
          An unexpected error occurred. Your encrypted data is safe — this is a display issue only.
        </p>
        <button
          className="error-fallback__reload"
          onClick={() => window.location.reload()}
          type="button"
        >
          {'> RELOAD'}
        </button>
      </div>
    </div>
  );
}
```

Key design decisions:

- Reassures user that "encrypted data is safe" — critical for a zero-knowledge app
- Uses `{'// ERROR'}` with JSX expression to avoid Biome `noCommentText` rule (per CLAUDE.md)
- Uses `type="button"` on the button element
- Terminal aesthetic: monospace font, green accent, dark background
- No state or hooks — pure presentational component that works even when React state is corrupted

<action>
Update `apps/web/src/App.tsx` to wrap the route tree with FaroErrorBoundary:

```typescript
import { FaroErrorBoundary } from '@grafana/faro-react';
import { AppRoutes } from './routes';
import { ErrorFallback } from './components/ErrorFallback';
import './App.css';

function App() {
  return (
    <FaroErrorBoundary fallback={<ErrorFallback />}>
      <AppRoutes />
    </FaroErrorBoundary>
  );
}

export default App;
```

Key points:

- FaroErrorBoundary is placed inside App (which is inside QueryClientProvider, CoreKitProvider, etc. in main.tsx) so it catches route-level errors
- When Faro is not initialized (no VITE_FARO_URL), FaroErrorBoundary still works as a standard React ErrorBoundary — it just doesn't report to Faro
- ErrorFallback is a plain component (not a render function) since FaroErrorBoundary accepts a ReactNode fallback
- Check the actual FaroErrorBoundary API — it may accept `fallback` as a ReactNode or as a render function `(error: Error, resetError: () => void) => ReactNode`. If the latter, adjust:
  ```typescript
  <FaroErrorBoundary fallback={(error, resetError) => <ErrorFallback />}>
  ```
  </action>
