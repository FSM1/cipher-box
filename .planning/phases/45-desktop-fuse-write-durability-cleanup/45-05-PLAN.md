<objective>
Reduce repeated work in replay: (#20) reuse the shared `publish_file_metadata` instead of the duplicated inline publish steps in `replay_upload_entry`, and (#15) memoize `resolve_folder_key` so N journal entries sharing one parent folder do one BFS instead of N. Both are behavior-preserving refactors of the same replay functions, so they ship together. The Plan-01 safety-net tests (T-45-06/07) plus the existing replay tests are the oracle.

Purpose: `replay_upload_entry` currently re-implements steps 3–10 of file publishing (encrypt, upload, IPNS record, TEE wrap, publish) that already live in `publish_file_metadata`; and each replay entry re-runs the full root→parent BFS. Both are pure efficiency/duplication wins with identical observable behavior.
Output: `replay_upload_entry` calls `publish_file_metadata` after ECIES-unwrapping the key and deciding `is_first_publish`; `replay_for_vault` owns a `HashMap<String, Vec<u8>>` folder-key cache seeded with the root key; `replay_mkdir_entry` + `replay_upload_entry` take `&mut` that cache and look up via `resolve_folder_key_cached`.
</objective>
