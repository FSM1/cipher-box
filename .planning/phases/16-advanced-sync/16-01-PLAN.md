<objective>
Add optimistic concurrency control to IPNS folder publish endpoints.

Purpose: Prevent silent overwrites when two devices modify the same folder concurrently. The second publish detects the sequence number mismatch and fails with 409, letting the client re-sync and retry.

Output: Modified API DTOs, service, controller, and unit tests. After this plan, clients can send `expectedSequenceNumber` and receive 409 Conflict on mismatch.
</objective>

  <action>
    1. **DTO changes** (`publish.dto.ts`):
       - Add `expectedSequenceNumber` optional field to `PublishIpnsDto`:
         ```typescript
         @ApiProperty({
           description: 'Expected sequence number for conflict detection. When present, the API validates against the stored value and rejects with 409 if mismatched. Omit for backward-compatible unconditional publish.',
           required: false,
           example: '5',
         })
         @IsOptional()
         @IsString()
         @Matches(/^\d+$/, { message: 'expectedSequenceNumber must be a numeric string' })
         expectedSequenceNumber?: string;
         ```
       - Add the same field to `PublishIpnsEntryDto` (batch entry).

    2. **Service changes** (`ipns.service.ts`):
       - Add `expectedSequenceNumber?: string` parameter to `upsertFolderIpns` method signature.
       - Import `ConflictException` from `@nestjs/common`.
       - **Before** the existing update logic (before `existing.latestCid = metadataCid`), add conflict check:
         ```typescript
         if (expectedSequenceNumber !== undefined && existing) {
           const expected = BigInt(expectedSequenceNumber);
           const current = BigInt(existing.sequenceNumber);
           if (expected !== current) {
             throw new ConflictException({
               statusCode: 409,
               message: 'Sequence number mismatch: folder was modified by another device',
               currentSequenceNumber: existing.sequenceNumber,
               expectedSequenceNumber,
             });
           }
         }
         ```
       - Thread `expectedSequenceNumber` through the call chain:
         - In `publishRecord`: pass `dto.expectedSequenceNumber` to `upsertFolderIpns`.
         - In `publishBatch`: For batch processing, implement "validate folder records first" strategy:
           a. Separate records into folder records (with `expectedSequenceNumber`) and other records.
           b. For any folder record that has `expectedSequenceNumber`, validate it FIRST by calling `upsertFolderIpns`. If any folder record throws `ConflictException`, re-throw it to fail the entire batch with 409.
           c. Process remaining records normally with `Promise.allSettled`.
           Note: The simplest approach is to just pass `entry.expectedSequenceNumber` to `upsertFolderIpns` in the existing batch processing. If a folder record conflicts, the `ConflictException` will be thrown from inside the `Promise.allSettled` mapper. Catch that specific exception type in the batch processing loop: if any settled result has a `ConflictException`, throw it to fail the entire batch. This avoids restructuring the batch logic.

    3. **Controller changes** (`ipns.controller.ts`):
       - Add `@ApiResponse({ status: 409, description: 'Conflict - expectedSequenceNumber does not match current server sequence number' })` to both `publishRecord` and `publishBatch` endpoints.
       - In `publishBatch`, wrap the service call in a try/catch that re-throws `ConflictException` directly (NestJS will serialize it as 409 automatically, but ensure the batch endpoint properly propagates it).

    **IMPORTANT - DB-level atomicity consideration:** The research identified a TOCTOU risk with application-level read-compare-write. However, since the `upsertFolderIpns` method already does a read (getFolderIpns) followed by a save, and the per-folder publish lock on the desktop client + the sequential nature of single-user API requests make true simultaneous DB writes extremely unlikely, the application-level check is sufficient for v1. A future optimization could use TypeORM QueryBuilder with a `WHERE sequence_number = :expected` conditional update.

    **Backward compatibility:** When `expectedSequenceNumber` is undefined, the existing behavior is preserved unchanged. Per-file IPNS publishes will not send this field. TEE republishes will not send this field.
