       ```typescript
       /**
        * Detect HTTP 409 Conflict errors from the API.
        * Used for IPNS publish conflict detection (sequence number mismatch).
        */
       export function isConflictError(error: unknown): boolean {
         if (!error || typeof error !== 'object') return false;
         // Orval-generated client throws errors with status property
         const e = error as Record<string, unknown>;
         if (e.status === 409) return true;
         // Fallback: check nested response
         if (typeof e.response === 'object' && e.response !== null) {
           const resp = e.response as Record<string, unknown>;
           if (resp.status === 409) return true;
         }
         return false;
       }

       /**
        * Extract the current server sequence number from a 409 conflict error.
        */
       export function getConflictSequenceNumber(error: unknown): string | undefined {
         if (!error || typeof error !== 'object') return undefined;
         const e = error as Record<string, unknown>;
         // Check for currentSequenceNumber in error body/data
         if (typeof e.data === 'object' && e.data !== null) {
           return (e.data as Record<string, unknown>).currentSequenceNumber as string | undefined;
         }
         return undefined;
       }
       ```

       **IMPORTANT:** Check how Orval-generated client surfaces HTTP errors. Look at the generated `apps/web/src/api/ipns/ipns.ts` to see the error shape. The `isConflictError` function must match the actual error structure. The Orval custom instance (`apps/web/src/api/custom-instance.ts` or similar) likely wraps errors. Inspect that file and adjust the detection logic accordingly.

    **Part B -- checkAndRotateIfNeeded conflict handling (Pitfall 7 from Research):**

    `checkAndRotateIfNeeded` in `folder.service.ts` (line ~967) calls `updateFolderMetadata` internally at line ~1015. Since `updateFolderMetadata` will now throw on 409 (the error propagates from the API), this caller needs explicit handling.

    **Current call chain:** `checkAndRotateIfNeeded` is called during post-upload re-wrapping as a fire-and-forget operation. If `updateFolderMetadata` throws `ConflictException` (409), the error will propagate up. The fire-and-forget caller swallows errors (logs but doesn't crash).

    **Required changes in `checkAndRotateIfNeeded`:**
    1. Wrap the `updateFolderMetadata` call in a try/catch for conflict errors:
       ```typescript
       import { isConflictError } from '../lib/errors';

       try {
         await updateFolderMetadata({
           folderId: folderNode.id,
           children: currentMetadata.children ?? [],
           folderKey: newFolderKey,
           ipnsPrivateKey: folderNode.ipnsPrivateKey,
           ipnsName: folderNode.ipnsName,
           sequenceNumber: resolved.sequenceNumber,
         });
       } catch (err) {
         if (isConflictError(err)) {
           // Key rotation already committed (share keys re-wrapped, revoked shares deleted).
           // The metadata re-encryption failed due to conflict. On next sync, the folder will
           // be re-read with fresh metadata. The next checkAndRotateIfNeeded call will detect
           // the pending rotation again and retry the re-encryption.
           console.warn(
             `[share] Conflict during lazy rotation metadata publish for ${folderNode.ipnsName}. ` +
             'Will retry on next sync cycle.'
           );
           // Return the new key -- rotation was committed, only the metadata publish failed.
           // The caller should still use the new key for encrypting the file being uploaded.
           return { folderKey: newFolderKey, rotated: true };
         }
         throw err; // Re-throw non-conflict errors
       }
       ```
    2. Add a comment explaining that this is safe because:
       - The share key rotation (re-wrap + delete) was already committed to the server
       - The metadata re-encryption is idempotent -- it will be retried on next sync
       - The caller (post-upload) still needs the new key to encrypt file content correctly

    **Part C -- Subfolder publish re-sync path:**

    When a SUBFOLDER publish gets 409 (not the root folder), the retry needs to resolve and reload that specific subfolder's metadata, not just the root. The re-sync path for a subfolder conflict is:

    1. Resolve the subfolder's IPNS name: call `resolveIpnsRecord(subfolderIpnsName)` to get the fresh CID and sequenceNumber
    2. Fetch the encrypted metadata blob from IPFS via the fresh CID
    3. Decrypt with the subfolder's `folderKey` (available from `useFolderStore.getState()` since subfolder keys are cached when navigating into them)
    4. Update the folder store with the fresh children and sequenceNumber for that subfolder
    5. Re-apply the local mutation (add/remove/rename child) onto the fresh children array
    6. Call `updateFolderMetadata` again with the merged children and the fresh sequenceNumber

    This path is used whenever a mutation handler in `useFolderMutations.ts` operates on a subfolder (the `parentFolderIpnsName` could be any folder, not just root). The `resolveIpnsRecord` + `fetchAndDecryptMetadata` functions already exist in `folder.service.ts` and handle both root and subfolder IPNS names identically. The hooks just need to call them with the correct `ipnsName` for the folder being mutated.

    **1. Hooks layer -- handle 409 with re-sync + retry:**

    In `useFolderMutations.ts`, create a shared conflict handler:
    ```typescript
    import { isConflictError } from '../lib/errors';
    import { useSyncStore } from '../stores/sync.store';

    // Inside the hook, create a reusable conflict handler:
    const handleConflictRetry = useCallback(async (
      operation: () => Promise<void>,
      folderIpnsName: string,
    ) => {
      try {
        await operation();
      } catch (err) {
        if (!isConflictError(err)) throw err;

        // 1. Show conflict status
        useSyncStore.getState().setConflict('Folder updated by another device, re-syncing...');

        // 2. Re-sync: resolve IPNS for the SPECIFIC folder (may be root or subfolder),
        //    fetch & decrypt metadata, update store.
        //    Full re-sync path for any folder:
        //    a. resolveIpnsRecord(folderIpnsName) -> get fresh CID + sequenceNumber
        //    b. fetchAndDecryptMetadata(freshCid, folderKey) -> get remote children
        //    c. Update folder store with fresh children + sequenceNumber
        const resolved = await resolveIpnsRecord(folderIpnsName);
        if (resolved) {
          // Get the folder key from the store (cached when folder was navigated to)
          const freshState = useFolderStore.getState();
          const folderNode = freshState.findFolderByIpnsName(folderIpnsName);
          if (folderNode) {
            const remoteMetadata = await fetchAndDecryptMetadata(resolved.cid, folderNode.folderKey);
            // Update the store with fresh remote state
            freshState.updateFolderChildren(folderIpnsName, remoteMetadata.children ?? [], resolved.sequenceNumber);
          }
        }

        // 3. Add random jitter (100-500ms) before retry to break symmetry
        await new Promise(r => setTimeout(r, 100 + Math.random() * 400));

        // 4. Retry ONCE with fresh state
        try {
          await operation();
          useSyncStore.getState().clearConflict();
        } catch (retryErr) {
          useSyncStore.getState().clearConflict();
          if (isConflictError(retryErr)) {
            throw new Error('Conflict persists after re-sync. Please try again.');
          }
          throw retryErr;
        }
      }
    }, []);
    ```

    **CRITICAL -- Stale closure prevention:** The `operation` callback MUST re-read folder state from `useFolderStore.getState()` (not from the closure). Each mutation handler (handleCreate, handleRename, handleMove, handleDelete, handleDeleteItems) should be wrapped so that:
    - The first attempt uses the current state from the hook
    - The retry re-reads fresh state from `useFolderStore.getState()` after re-sync

    The exact implementation approach: In each mutation handler that calls `updateFolderMetadata` or batch publish, wrap the call in a try/catch for conflict errors. On conflict:
    1. Call sync to refresh the store (using the specific folderIpnsName, not hardcoded root)
    2. Re-read parent folder from `useFolderStore.getState()`
    3. Rebuild the operation with fresh children/sequenceNumber
    4. Retry once

    **Apply to these mutation handlers:**
    - `handleCreate` (creates subfolder)
    - `handleRename` (renames item)
    - `handleMove` / `handleMoveItems` (move item between folders)
    - `handleDelete` / `handleDeleteItems` (delete item)

    In `useFileOperations.ts`:
    - `handleAddFile` / `handleAddFiles`: These use `addFileToFolder`/`addFilesToFolder` which do batch publish. Wrap with similar conflict handling. On conflict, re-sync parent folder (using the folder's ipnsName, which may be a subfolder), rebuild the batch with fresh children list, retry.
    - `handleUpdateFile`: This publishes only the file IPNS record (not folder). NO conflict detection needed here.

    **2. Sync store -- add conflict status:**

    In `sync.store.ts`:
    - Extend `SyncStatus` type: `type SyncStatus = 'idle' | 'syncing' | 'success' | 'error' | 'conflict';`
    - Add `conflictMessage: string | null` to state
    - Add `setConflict: (message: string) => void` action that sets `status: 'conflict'` and `conflictMessage`
    - Add `clearConflict: () => void` action that sets `status: 'success'` and clears `conflictMessage`

    **3. SyncIndicator -- show conflict state:**

    In `SyncIndicator.tsx`:
    - Add a `'conflict'` case to both `getIcon()` and `getTitle()`:
      - Icon: spinning circle with a different color (amber/yellow) to distinguish from normal sync
      - Title: Read `conflictMessage` from sync store, or fallback to "Resolving conflict..."
    - Add CSS class `sync-indicator-icon--conflict` with amber color styling (add to `App.css` or relevant stylesheet)
    - The conflict state is transient: set when conflict detected, cleared after retry succeeds or fails. Auto-clear after 5 seconds if the clearConflict was not called (safety fallback).
