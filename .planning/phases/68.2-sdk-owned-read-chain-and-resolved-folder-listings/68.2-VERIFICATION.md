### What Changed Since the Prior (human_needed) Pass

The prior pass left exactly one item open: truth #5's e2e behavioral proof, which it could not independently execute because no live app stack was running (it had already source-confirmed the `forceResolve`/`reresolveFolderInPlace`/`doReresolveFolderInPlace` mechanism and re-run the SDK unit suite 338/338). The orchestrator has since stood up a FRESH-container stack (fresh Postgres + CORS-configured Kubo v0.42.0 + someguy + mock-ipns-routing + API on :3000) and executed the specs. The SC#5 acceptance (`shared-folder-desync.spec.ts` step 3.1) passes 4/4 — upgrading truth #5 from ⚠️ PRESENT_BEHAVIOR_UNVERIFIED to ✓ VERIFIED.

That fresh-stack triage also surfaced **two web-layer regressions** (VERIFICATION gaps introduced by earlier 68.2 plans, NOT a reopening of SDK-READ-01..04 — all four remain satisfied; both fixes are web-only with zero SDK change). Both are now closed in gap-closure round 2 and **independently confirmed in current source** by this verifier:

- **Regression A (Plan 68.2-15):** After the 68.2-11 kind-cache removal, `isFileRef(bareSealedChildRef)` always returned `false` (folder-safe default), which broke download affordances *and* the download logic itself (`handleDownload`/`handleBatchDownload` filtered every selected file out). Fixed via a new `isFileRefResolved(ref, resolvedByIpnsName)` classifier in `apps/web/src/utils/fileTypes.ts` (L167) that reads `ResolvedChild.kind` inline and classifies a bare `SealedChildRef` against the SDK-resolved listing keyed by `ipnsName`. Threaded to all download-gating sites (`useFileBrowserActions.ts` L414/L479, `FileBrowser.tsx`, `SelectionActionBar.tsx`, `ContextMenu.tsx`, `SharedFileBrowser.tsx`). Verified by `batch-download.spec.ts` 5/5.
- **Regression B (Plan 68.2-16):** Post-upload refresh (`onUploadComplete` → `handleSync`) only resynced root, so an upload into a subfolder never appeared until the 30s poll. Fixed by calling the already-exported `invalidateOpenFolder()` (immediate gated re-resolve of the currently-open folder) on upload complete — `FileBrowser.tsx` L162 — before the best-effort root `handleSync()`, and forcing `{ forceResolve: true }` on both legs of `handleSync` (`useFileBrowserActions.ts` L154/L156) and `resyncFolder` (the post-409 CAS re-sync, `folder-helpers.ts` L33/L34). No SDK change — `forceResolve`/`invalidateOpenFolder` already existed. Verified by `writable-shares.spec.ts` 29/29 (and the desync spec stayed 4/4).

Commits: `0577a34b3` (fix), `edc6d2fec` (docs). Prior SDK unit suite remains 338/338 with no regressions.
