## Accepted Risks Log

- **T-68.2-06 (low, Info Disclosure — `ResolvedChild` size/modifiedAt).** `ResolvedChild`
  exposes only display metadata (name/kind/size/modifiedAt/sequence) derived from the
  parent's sealed read-body. It reveals nothing beyond what any legitimate `readKey`
  holder already derives (ba3e0229a rationale). It carries no key material — verified: the
  `ResolvedChild` type (`packages/sdk/src/folder-listing.ts:36-43`) has no
  `readKey`/`readKeySealed`/`writeKey`/`privateKey` field. Accepted.
- **T-68.2-14-02 (low, Info Disclosure — in-place folderTree update).** The re-resolve
  mutates the single SDK-owned `FolderState` in place rather than spawning a second cache
  (SC#3), so there is no divergent stale copy to leak. Accepted.

## CipherBox Security Invariants (CLAUDE.md)

All invariants hold across the phase's touched surface:

- **No `privateKey` in local/sessionStorage** — grep over `apps/web/src` for
  `(local|session)Storage.(set|get)Item` with any key field: zero hits.
- **No key logging** — no `console.*` of `privateKey`/`readKey`/`writeKey`/`folderKey`/
  `ipnsPrivateKey` in the touched SDK files (`client.ts`, `folder-listing.ts`).
- **ECIES wrap + AES-256-GCM, zero-knowledge server, TEE-only IPNS decryption** — unchanged
  by this phase; it moves the read chain into the SDK facade and reverts additive display
  fields. No new server call carries plaintext or unencrypted keys; the download path still
  routes crypto through `SealedChildRef.readKeySealed` via the SDK (e.g. `client.ts:437`,
  `:818`, `:963`, `:1159`, `:1469`). The gap-closure fixes (Plans 15/16 —
  `utils/fileTypes.ts` `isFileRefResolved` kind classification, post-upload
  `invalidateOpenFolder`) are display/refresh-only; `fileTypes.ts` imports `SealedChildRef`
  as `import type` and touches no key material.

## Advisory (hardening, non-blocking)

The D-07 web/SDK boundary (T-68.2-04) is enforced by a **manual** two-step grep gate, not by
an automated CI/ESLint rule. It returns zero violations at HEAD (verified), so the declared
mitigation is present. However, there is no `no-restricted-imports` rule or CI job pinning it,
so a future `apps/web` change could silently reintroduce a runtime `@cipherbox/sdk-core`/
`@cipherbox/core` value import or a raw-IPFS call without failing CI. Recommend promoting the
grep gate to an ESLint `no-restricted-imports` boundary rule or a dedicated CI check. This does
not affect the current disposition (mitigation present); tracked as hardening only.
