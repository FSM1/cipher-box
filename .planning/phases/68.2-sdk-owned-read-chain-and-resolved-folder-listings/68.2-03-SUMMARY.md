# Phase 68.2 Plan 03: SDK Write-Path and IPFS-Transport Facade Mediation Summary

**Added `client.uploadBytes`/`downloadBytes`/`unpin` (progress-preserving raw IPFS-transport facade methods) and `client.getFolderMetadata` (gated folder-metadata read facade), plus re-exported the four pure structural utils (`getDepth`, `isDescendantOf`, `calculateSubtreeDepth`, `selectEncryptionMode`) from `@cipherbox/sdk`, closing the last facade gaps the cutover wave needs to route every web write-path/raw-IPFS call through the SDK (D-07).**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2 (TDD: RED test + GREEN implementation per task)
- **Files modified:** 5 (2 created, 3 modified — 2 new test files; `client.ts` and `index.ts` modified, `folder-metadata-facade.test.ts` also asserts the `index.ts` re-exports)

## Accomplishments

- `client.uploadBytes(encryptedData, onProgress?)` wraps `sdkCore.addToIpfs`, forwarding `onProgress` verbatim so the web's upload-progress UI keeps working after the cutover (RESEARCH Open Q2)
- `client.downloadBytes(cid, onProgress?)` wraps `sdkCore.fetchFromIpfs`, forwarding `onProgress` (loaded/total) for download-progress UI
- `client.unpin(cid)` wraps `sdkCore.unpinFromIpfs` for direct unpin calls (e.g. cleanup after a superseded config/registry blob publish)
- `client.getFolderMetadata(ipnsName)` returns a folder's decoded `Node` (the mediated replacement for the web's direct `sdkCore.fetchAndDecryptMetadata` call in `useFileBrowserActions.ts`/`folder-helpers.ts`) by delegating entirely to the Plan-01-gated `ensureFolderLoaded` — confirmed no gate bypass via a spy-based unit test
- `packages/sdk/src/index.ts` re-exports `getDepth`, `isDescendantOf`, `calculateSubtreeDepth`, `selectEncryptionMode`, and the `TreeNode` type from `@cipherbox/sdk-core`, so `MoveDialog.tsx`, `useFolderMutations.ts`, and `streaming-crypto.service.ts` can import these pure, no-crypto/no-IO utils from the facade instead of `sdk-core` directly

## Decisions Made

- `uploadBytes`/`downloadBytes`/`unpin` are new, standalone facade methods rather than extensions to the existing private `pinWithMode` — they mediate the web's direct raw-IPFS-transport call sites (BYO-pinning config blobs, device-registry blobs per RESEARCH's `@cipherbox/core` runtime call-site table) which are orthogonal to `pinWithMode`'s file-metadata-orchestration role inside `uploadFile`/`uploadFiles`
- `getFolderMetadata` returns the full decrypted `Node` (matching `sdkCore.fetchAndDecryptMetadata`'s current return shape) rather than a narrowed projection — `listFolder` (Plan 02) remains the entrypoint for resolved-children-only consumers; `getFolderMetadata` is for consumers that need the folder's own metadata fields (`id`, `generation`, `writeBody`, etc.)
- Pure-util re-exports are direct pass-throughs from `@cipherbox/sdk-core`'s existing barrel exports, not re-implementations — `@cipherbox/sdk` already depends on `@cipherbox/sdk-core`, so this is a zero-cost, zero-logic public-surface addition
- Neither task's caller-supplied buffers (`encryptedData` in `uploadBytes`) are zeroed by the facade (D-09: caller remains terminal owner)
