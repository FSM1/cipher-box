# Phase 68.2 Plan 12: Revert Interim Mirror + Document ResolvedChild Summary

**Reverted the ba3e0229a SealedChildRef.size/modifiedAt display mirror (restoring the frozen NODE-03 five-field schema), documented ResolvedChild as its replacement, fixed two pre-existing e2e-blocking bugs along the way, and root-caused (but did not fix) a deeper `ensureFolderLoaded` staleness bug that keeps the SC#5 desync test red.**

## Accomplishments

- `SealedChildRef` is back to exactly its NODE-03 five fields (`name`, `ipnsName`, `generation`, `versionFloor`, `readKeySealed`) across `packages/core`'s codec, `sdk-core`'s `addFilePointerToFolder`, and all 5 SDK write call sites (folder create, single upload, batch upload, `createSharedSubfolder`, `uploadToSharedFolder`).
- `docs/METADATA_SCHEMAS.md` now documents `ResolvedChild` as the canonical, in-memory, per-folder-load resolved display carrier, replacing the retired mirror in the schema reference.

- `core` (including the node-codec golden-vector KAT), `sdk-core`, and `sdk` unit suites are all green; `sdk-core`+`sdk` dist rebuilt; `apps/web` typechecks with 0 errors.

## Issues Encountered

**Full local `web-e2e` suite is NOT green; the SC#5 desync spec is root-caused but NOT fixed.**

Two full local runs of `pnpm --filter @cipherbox/web-e2e test` (213 specs) were executed, with the local dev stack (Postgres/Redis/Kubo/mock-ipns-routing/API/vite, all already running) restarted fresh (vite `--force`, sdk-core/sdk dist rebuilt) between runs per the project's documented local-full-suite recipe. Both runs showed a similar tally: ~16 failed / ~40 passed / ~157 cascade-skipped (this suite is `describe.serial`, so one early failure skips the rest of its file).

Investigation (targeted isolated re-runs of `shared-folder-desync.spec.ts`, Playwright trace/DOM-snapshot inspection, and source-level tracing) found and fixed two of the contributing bugs (see Deviations #2/#3 above), which measurably improved the isolated desync spec: step "2.1 Grantee uploads a file into the shared folder" went from timing out to passing in under 300ms.

However, the desync spec's actual target assertion — step "3.1 Owner sees the grantee upload without writing, size/modifiedAt from the resolved listing" — still fails: the owner's folder view renders "EMPTY DIRECTORY" instead of the grantee's uploaded file. Root cause, confirmed at the source level:

- `CipherBoxClient.ensureFolderLoaded` (`packages/sdk/src/client.ts:1549`) short-circuits on any already-present `folderTree` entry (`if (existing) { ...; return existing; }`) and performs ONLY `recoverWriteKeyIfNeeded` (write-key recovery) — it never re-resolves the folder's IPNS record from the network to check for a newer sequence number.
- `listFolder` (line 862) calls `ensureFolderLoaded` first, then `resolveListingChildren`, which checks its own `listingCache` against `folder.sequenceNumber` — but that field is itself stale for the same reason, so the cache check is a no-op comparison against itself.
- Net effect: once the OWNER has loaded a folder once (e.g. at creation time), any subsequent navigation into that SAME folder returns the in-memory snapshot from the FIRST load, even after another party (the grantee, in this repro) publishes a new sequence number with additional children. There is no "nav-triggered re-resolve" (D-03) actually implemented for the already-loaded case — only a genuinely cold (never-loaded) folder gets a live network resolve.

This is the exact "desync bug class" SC#5/SDK-READ-03 set out to close, and it is confirmed still open. It predates this plan (Plans 02/09/11 built `ResolvedChild`/the projection-only store, but the underlying `ensureFolderLoaded` caching contract was not changed to add a live re-resolve trigger) and is NOT caused by this plan's mirror revert — the failure occurs at "does the item appear at all," entirely independent of the `size`/`modifiedAt` fields removed in Task 2.

**Recommendation:** file a dedicated gap-closure plan against `CipherBoxClient.ensureFolderLoaded`/`listFolder` to add an explicit, deliberate live-resolve-on-navigation path (distinct from the cached fast path used by write-mutation chokepoints, where re-resolving on every call would be wasteful/risky against `RotationHighWater`/`enforceResolved` semantics). This is an architectural decision (cache invalidation contract, not a targeted bug patch) and should not be made unilaterally inside an executor session.

**Other observed failures (not individually root-caused):** the remaining ~14 first-failures across the two full runs (`batch-download`, `bin-restore-after-reload`, `conflict-detection`, `full-workflow` 2.1, `invite-link-workflow` 1.2, `media-preview`, `move-restore-content`, `recovery.spec.ts`, `recycle-bin` TC02, `rotation-durability`, `share-itemname-encrypted`, `shared-folder-move`, `sharing-workflow`, `streaming-playback`, `writable-shares`) were NOT individually traced to root cause given time constraints. Several plausibly share the `ensureFolderLoaded` staleness root cause above (any spec that creates an item and immediately re-navigates/re-reads it); others may be independent flakes in a multi-day-uptime local stack (`docker ps` showed containers up 3-5 days; the API log showed frequent Postgres `duplicate key value violates unique constraint "UQ_ipns_records_ipns_name"` errors and a stale TEE-worker 404, both symptomatic of long-lived local state rather than this plan's changes). CI (fresh containers per run) should be treated as the authoritative confirmation for these, per this plan's own infra-gating guidance.
