# Phase 68.2 Plan 04: SDK Vault-Bootstrap, Device-Registry, and BYO-Pinning Facade Summary

**Added `client.bootstrapVaultKeys`/`serializeVault`/`deserializeVault`/`publishEmptyRootNode` (auth-bootstrap crypto), `client.deriveRegistryIpnsKeypair`/`encryptRegistry`/`decryptRegistry` (device-registry crypto), and `client.testConnection`/`resolveConfigBlob`/`publishConfigBlob` (BYO-pinning config-blob passthrough, deliberately un-gated) — closing the three off-path pockets D-07's full-boundary scope requires alongside the folder-listing read chain.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2 (TDD: RED test + GREEN implementation per task)
- **Files modified:** 4 (2 created test files; `client.ts` and `index.ts` modified)

## Accomplishments

- `client.bootstrapVaultKeys(userPrivateKey)` mints a new user's `VaultInit` (rootReadKey/rootWriteKey/rootIpnsKeypair) via `@cipherbox/core`'s `initializeVault`
- `client.serializeVault(vault, userPublicKey)` / `client.deserializeVault(blobBytes, userPrivateKey)` mediate the exact ECIES-wrap-then-serialize and deserialize-then-unwrap sequences `useAuth.ts` performs today for the v3 vault key blob, verified with a real round-trip unit test
- `client.publishEmptyRootNode(params)` wraps `sdkCore.publishEmptyRootNode` with `this.ctx` injected, giving `useAuth.ts` a facade entrypoint for the root-Node publish it currently calls directly from `@cipherbox/sdk-core`
- `client.deriveRegistryIpnsKeypair`/`encryptRegistry`/`decryptRegistry` mediate `device-registry.service.ts`'s registry crypto, also verified with a real encrypt/decrypt round-trip
- `client.testConnection`/`resolveConfigBlob`/`publishConfigBlob` give `ConnectionTest.tsx`/`StorageTab.tsx` a facade entrypoint for the BYO-pinning config-blob operations — explicitly NOT routed through the ROT-07 `rotationHighWater.enforceResolved` gate, since the config blob is a user-configured settings entry rather than a rotation-governed node
- `packages/sdk/src/index.ts` re-exports `VaultInit`, `DeviceRegistry` (from `@cipherbox/core`) and `ConnectionTestResult` (from `@cipherbox/sdk-core`) so consumers can type these facade calls without importing either package directly

## Decisions Made

- `serializeVault`/`deserializeVault` are combined two-step facade calls (matching `useAuth.ts`'s exact current sequences) rather than exposing every underlying primitive (`encryptVaultKeys`, `serializeVaultBlobV3`, `deserializeVaultBlobV3`) as separate one-to-one methods — this keeps the facade surface minimal while still calling each named `@cipherbox/core` primitive internally
- `bootstrapVaultKeys`/`deriveRegistryIpnsKeypair` do not zero anything on success — the caller becomes the terminal owner of the freshly minted key material (D-09), matching the underlying core primitives' own contract
- `deserializeVault` zeroes the already-unwrapped `rootReadKey` if the paired `unwrapKey` call for `rootWriteKey` fails, closing a T-68.2-09 information-disclosure gap (an orphaned live key buffer) that the underlying primitives alone don't address when composed sequentially
- `resolveConfigBlob`/`publishConfigBlob` are named generically (not BYO-prefixed) since the config-blob shape applies to any user-configured settings entry, and both deliberately skip `rotationHighWater.enforceResolved` per 68.2-PATTERNS' "No Analog Found" BYO passthrough guidance
- Config-blob fetch/add (raw IPFS bytes) reuse the existing `downloadBytes`/`uploadBytes` facade methods from Plan 03 rather than adding config-blob-specific duplicates — no new capability is needed for those two operations
- Test suites mock `@cipherbox/crypto`'s `wrapKey`/`unwrapKey` with a deterministic invertible fake (prefix-tag + copy), following the precedent in `client-write-descriptor.test.ts`, since `@noble/secp256k1` is not a declared dependency of `@cipherbox/sdk`
