# Phase 68.2: SDK-Owned Read Chain and Resolved Folder Listings - Research

**Researched:** 2026-07-06
**Domain:** TypeScript monorepo boundary enforcement (web -> SDK facade), IPNS read-chain gating, folder-listing resolution

## Summary

This phase is a **boundary-enforcement and consolidation** refactor, not new-library integration. All facts below come from live grep/`git show` against the current tree (branch `feat/sdk-owned-read-chain-and-resolved-folder-listings`), not training knowledge — no `[ASSUMED]` tags apply except where explicitly marked.

The single most important finding, not visible from CONTEXT.md's blast-radius estimate: **the SDK's own internal read/navigate path (`ensureFolderLoaded` / `dfsFindFolder` / `resolvePublishedNode` in `packages/sdk/src/client.ts`) currently calls `sdkCore.resolveIpnsRecord` with ZERO ROT-07 gating.** The *only* place `RotationHighWater.enforceResolved` is wired into `client.ts` today is the pre-publish write-side check (`reconcileFolderSequence`, line ~1086). The ROT-07 read-side gate that actually exists in production today lives entirely in the web layer's `apps/web/src/services/ipns.service.ts` `resolveIpnsRecord()` wrapper (which calls `enforceResolved` from `rotation-state.service.ts`) and is invoked ad hoc by `kind-cache.ts`, `file-metadata.service.ts`, `useSharedNavigationActions.ts`, `StorageTab.tsx`, `useAuth.ts`, etc. Deleting `ipns.service.ts` per SC#1 **removes the only read-side ROT-07 gate that exists today** unless the SDK's internal navigate path is gated as part of this phase. This must be treated as a first-class task, not a side effect of "moving files."

The second major finding: shared-folder navigation (`useSharedNavigationActions.ts`, 912 lines) duplicates the ENTIRE read chain in the web layer — raw `unsealNode`/`unsealChildReadKey` (`@cipherbox/core`), raw `resolveIpnsRecord`/`fetchFromIpfs`/`navigateReadChain` (`@cipherbox/sdk-core`) — and has **no ROT-07 gating at all** beyond a single soft check (`share.rootGeneration !== undefined && rootPublished.generation > share.rootGeneration`). This is the largest single file the D-07 boundary rewire must collapse, and it's also the SC#5 desync bug's home (owner/grantee visibility of a shared folder's live children).

Corrected blast-radius numbers (see full inventory below): **9 files** have runtime (non-type) `@cipherbox/sdk-core` imports needing rewiring (not ~15 — the ~15 figure counted the 2 files being deleted outright plus 4 files that are actually type-only), **20 files** touch raw IPFS/IPNS (`lib/api/ipfs.ts`, `fetchFromIpfs`/`addToIpfs`/`resolveIpnsRecord`) needing rewiring (close to the ~19 estimate), and of the 53 files importing `@cipherbox/core`, only **7** have runtime (non-type) imports — the rest are legitimately type-only and must NOT be touched by the D-07 grep gate.

**Primary recommendation:** (1) Add `enforceResolved` gating inside `client.ts`'s internal read path (`resolvePublishedNode`, used by both `dfsFindFolder`/`ensureFolderLoaded` and any new listing facade) BEFORE deleting `ipns.service.ts`, so ROT-07 read coverage is never dropped mid-cutover. (2) Build `listFolder`/`listSharedFolder` as thin wrappers that call the now-gated internal resolve + a per-child kind/size/modifiedAt resolution loop, returning `ResolvedChild[]` and emitting `folder:updated` with the new shape (the event plumbing already exists in `folder.store.ts` — only the payload type changes). (3) Do the `ba3e0229a` mirror revert LAST, exactly as D-08 specifies, using the precise 13-file/hunk list below.

### Pattern 1: Gate-first resolve (close the ROT-07 read-path gap)
**What:** Every IPNS resolve on the read path — not just the pre-publish reconcile check — passes through `RotationHighWater.enforceResolved` before its result is trusted.
**When to use:** Any new `resolvePublishedNode`-style helper inside `client.ts`, and inside any new `listFolder`/`listSharedFolder` facade method.
**Example (the EXISTING gate pattern to replicate, from `client.ts:1063-1092`):**
```typescript
// Source: packages/sdk/src/client.ts (reconcileFolderSequence, current write-path-only gate)
if (this.config.rotationHighWater) {
  if (!resolved.signatureVerified) {
    throw new Error(`... refusing to gate durable floors on it`);
  }
  const nodeGeneration = this.folderTree.get(ipnsName)?.nodeGeneration ?? 0;
  await this.config.rotationHighWater.enforceResolved({
    nodeId: ipnsName,
    seq: Number(resolved.sequenceNumber),
    generation: nodeGeneration,
    versionFloor: Number(expectedSequence),
  });
}
```
Note the generation-source subtlety already established elsewhere in the same file (`dfsFindFolder`): the `generation` passed to `enforceResolved` for a CHILD node must be `childRef.generation` (the parent's `SealedChildRef` mirror), never the child's own envelope generation. The current write-path gate uses the in-memory `folderTree` node's own `nodeGeneration` because it's reconciling the SAME node being republished; a new read-path gate resolving a not-yet-loaded child must use the parent-mirror value instead — do not copy the write-path gate verbatim.

### Anti-Patterns to Avoid
- **Gating only the new facade method, not the internal DFS walk:** `ensureFolderLoaded`/`dfsFindFolder` are called from many existing write-path call sites (`createFolder`, `moveItem`, etc.) via `resolvePublishedNode`. If the gate is bolted onto a NEW `listFolder` method without also gating `resolvePublishedNode` itself, most navigation still resolves ungated and SC#1's "gated read chain lives in the SDK" claim is false.
- **Treating `@cipherbox/core`'s 53 import sites as a single number:** grep gates that fire on `grep -rl '@cipherbox/core' apps/web/src` will false-positive on 46 legitimate type-only files. See the exact grep gate command below.
- **Reverting the `ba3e0229a` mirror before `ResolvedChild` renders correctly:** D-08 explicitly orders this last; the size/modifiedAt display fields in `FileListItem.tsx`/`SharedFolderRow.tsx`/`FileDetails.tsx`/`FolderDetails.tsx` read `item.size`/`item.modifiedAt` off whatever object they're handed — if the revert lands before the components are repointed to `ResolvedChild`, size/date silently regress to `—`/absent for a window.

## Common Pitfalls

### Pitfall 1: `navigateReadChain` cannot render an intermediate folder
**What goes wrong:** `navigateReadChain` (sdk-core) is designed to walk from a grant root to a FILE leaf; it forces `kind: 'file'` at the end of its path. `useSharedNavigationActions.ts`'s own doc comment confirms this (68.1-05 decision, STATE.md): *"navigateReadChain cannot render an intermediate folder (forces kind:'file' leaf) — folder nav uses a parallel low-level web-layer walk reusing the same sdk-core/core primitives."*
**Why it happens:** The primitive was built (Phase 63) for the single-file-download use case (READ-02), not general folder browsing.
**How to avoid:** Either (a) extend `navigateReadChain` with a "stop at folder" mode, or (b) hoist the web's existing intermediate-folder walk (the `fetchPublishedNode` + `unsealChildReadKey` + `unsealNode` loop already written in `useSharedNavigationActions.ts` lines 127-136, 347-467) into `packages/sdk` verbatim as `listSharedFolder`'s implementation, now with the ROT-07 gate added. Given D-08's "reuse, don't reinvent" spirit and the size of `navigateReadChain`'s existing test surface, (b) is lower-risk — moving already-working code rather than modifying a primitive with existing callers (`downloadSharedFile`, `loadSharedFileContent`).
**Warning signs:** A `listSharedFolder` implementation that calls `navigateReadChain` with a non-empty `path` and expects a `children` array back — it doesn't return one; it returns `{ status, content }` for a leaf.

### Pitfall 2: Deleting `ipns.service.ts` drops the only working ROT-07 read gate
**What goes wrong:** As detailed in the Summary, `client.ts`'s internal navigate path is currently ungated. If `ipns.service.ts` is deleted (SC#1) before an equivalent gate is added inside `client.ts`, the app silently loses ALL read-side anti-rollback protection — a regression from ROT-07/Phase 68's shipped guarantee, not a neutral refactor.
**Why it happens:** The web-layer gate was bolted on as the pragmatic 68.1 stopgap ("symmetric with the read-path gate in apps/web ipns.service" — client.ts:1064 comment) precisely because the SDK-internal equivalent didn't exist yet.
**How to avoid:** Sequence the plan so the SDK-internal gate lands and is unit-tested (via `fakeRotationHighWater`) BEFORE the web service deletion task. Add a regression test asserting `sdkCore.resolveIpnsRecord`/`resolvePublishedNode` call sites inside `client.ts`'s read path are gated (e.g., a spy asserting `enforceResolved` is called once per resolve during `ensureFolderLoaded`).
**Warning signs:** A plan wave that deletes `ipns.service.ts` in the same task as adding `listFolder`, without a preceding task that gates `resolvePublishedNode`.

### Pitfall 3: `versionFloor`/`generation` context is only available from the PARENT's `SealedChildRef`, not from the child's own record
**What goes wrong:** A gated resolve needs `{ generation, versionFloor }` context to call `enforceResolved`. This context lives on the PARENT's `SealedChildRef` entry for the child being resolved — it is NOT retrievable from the child's own IPNS record. A `listFolder(ipnsName)` facade signature that only takes an `ipnsName` with no parent context cannot gate a COLD (not-yet-cached) child correctly on first contact.
**Why it happens:** This is the same generation-source rule already enforced elsewhere (`dfsFindFolder`'s explicit comment: "childRef.generation (parent mirror), NEVER childResolved.published.generation"). It applies equally to any new gated listing wrapper.
**How to avoid:** For the folder ALREADY in `folderTree` (the common "list the folder I'm standing in" case), the gate can source `generation` from `folderTree.get(ipnsName)?.nodeGeneration` (mirroring the existing write-path gate). For a COLD folder reached via `ensureFolderLoaded`'s DFS walk, the gate must use the traversal-time `childRef.generation`/`childRef.versionFloor`, exactly as `dfsFindFolder` already does for the unseal step — just add the `enforceResolved` call alongside the existing unseal call in that same loop (client.ts:854-905).
**Warning signs:** A `listFolder` implementation that resolves the target folder directly (bypassing `dfsFindFolder`'s per-hop context) and has no `generation`/`versionFloor` value to gate with.

### Pitfall 4: `file-metadata.service.ts` contains pure helpers that are NOT part of the read chain
**What goes wrong:** `resolveFileMetadata` (the read-chain duplicate, lines 62-100) is what SC#1 wants deleted. But the same file also exports `shouldCreateVersion`, `computeRestoreVersionUpdate`, `computeDeleteVersionUpdate` (lines 115-192) — pure, no-network transforms over `VersionEntry[]` used by the WRITE path (version restore/delete UI flows). These have no runtime `@cipherbox/core`/`@cipherbox/sdk-core` imports beyond types and must be relocated (e.g., to a new `apps/web/src/lib/version-transforms.ts`) rather than deleted, or write-path version restore/delete UI breaks.
**Why it happens:** The file's name suggests it's entirely "metadata service" (read-chain), but it accreted pure write-path helper functions during 68.1-12.
**How to avoid:** Explicit plan task: "extract the 3 pure version-transform functions from file-metadata.service.ts into a non-service module BEFORE deleting the file."
**Warning signs:** Grepping for `resolveFileMetadata` shows 0 remaining callers but `shouldCreateVersion`/`computeRestoreVersionUpdate`/`computeDeleteVersionUpdate` still have live callers elsewhere in `apps/web/src`.

### Pitfall 5: The D-07 grep gate must not fire on inline `type` modifiers
**What goes wrong:** A naive gate like `grep -rn "from '@cipherbox/sdk-core'" apps/web/src | grep -v "import type"` still misses/mis-classifies lines using inline modifiers, e.g. `import { type ConnectionTestResult, type PinningMode } from '@cipherbox/sdk-core';` — this line does NOT start with `import type` but contains zero runtime symbols. Verified live example: `apps/web/src/components/settings/StorageTab.tsx:2`.
**Why it happens:** TypeScript supports three type-only import syntaxes: `import type { X }`, `import { type X }`, and inline mixed `import { type X, Y }` (Y is runtime, X is not). A single regex cannot distinguish "all identifiers on this line have the `type` keyword" from "some do, some don't" without parsing the import specifier list.
**How to avoid:** Use a two-step gate: (1) `grep -rn "from '@cipherbox/sdk-core'\|from '@cipherbox/core'" apps/web/src --include='*.ts' --include='*.tsx'` to enumerate every import line, then (2) for each line, strip the import to its specifier list and assert every specifier token is prefixed with `type ` OR the whole import starts with `import type`. In practice, a small Node/ts-morph script is more reliable than a regex; if the plan must ship a pure-shell gate, this approximation is acceptable and was manually verified to work on the current tree: `grep -rnE "from '@cipherbox/(sdk-core|core)'" apps/web/src --include='*.ts' --include='*.tsx' | grep -vE "^\S+:import type \{" | grep -vE "^\S+:import \{( *type [A-Za-z0-9_]+,?)+ *\} from '@cipherbox/(sdk-core|core)';?$"` — this correctly excludes `StorageTab.tsx:2`, `useSharedNavigation.ts:13`, `file-metadata.service.ts:23`, and the 3 sdk-core-type-only service files (`owner-reconcile.service.ts`, `rotation-driver.service.ts`, `encrypt-worker.service.ts`) while retaining every genuine runtime import site found below. Verify this exact command against the tree at plan time (line numbers/imports may have shifted since this research).
**Warning signs:** A grep gate that reports 0 violations even though `useAuth.ts` still calls `initializeVault`/`encryptVaultKeys` from `@cipherbox/core` at runtime.

### Pitfall 6: `size`/`modifiedAt` mirror populated at 3+ write call sites, not 1
**What goes wrong:** The `ba3e0229a` mirror is written in THREE places in `packages/sdk/src/client.ts` (folder create ~line 1512, single upload ~line 2103, batch upload ~line 2399) plus TWO places in `packages/sdk/src/share/shared-write.ts` (`createSharedSubfolder`, `uploadToSharedFolder`) plus the `addFilePointerToFolder` primitive in `packages/sdk-core/src/folder/metadata-ops.ts`. A revert that only touches `packages/core/src/node/{types,encode,decode}.ts` (the type/codec) leaves 5 dead call sites passing `size`/`modifiedAt` params that no longer exist on the type, which will be a compile error (good — TypeScript will catch this) but the plan must budget for cleaning up all 5, not just the type definition.
**Why it happens:** The commit touched 13 files; only 3 are core/type files, the rest are call sites and consumers.
**How to avoid:** Use the exact file list in "Code Examples > Mirror Revert Footprint" below rather than reverting via `git revert ba3e0229a` (a straight revert will conflict with everything written on top of these files since 2026-07-04, including 68.1 gap-closure commits) — a manual, targeted removal of the added fields/params is safer.
**Warning signs:** `pnpm --filter @cipherbox/sdk typecheck` failing with "Object literal may only specify known properties" after the `packages/core` type change but before the `client.ts`/`shared-write.ts`/`metadata-ops.ts` call sites are cleaned up — expected mid-revert, must be resolved before the wave completes.

## Open Questions

1. **Does `listSharedFolder` wrap an extended `navigateReadChain`, or hoist the existing web-layer walk?**
   - What we know: `navigateReadChain` cannot stop at an intermediate folder today (Pitfall 1); the web has a working (if duplicated) implementation that does.
   - What's unclear: Whether extending the shared sdk-core primitive is worth the risk to its existing callers (`downloadSharedFile`, `loadSharedFileContent`) vs. moving already-proven code.
   - Recommendation: Default to hoisting the existing web-layer walk into `packages/sdk` (lower blast radius on a primitive with existing production callers), gate it with `enforceResolved`, and revisit unifying with `navigateReadChain` as a later cleanup if duplication becomes a maintenance burden.

2. **How does the SDK reconcile its two IPFS-transport implementations (`lib/api/ipfs.ts`'s api-client-based wrapper with upload-progress callbacks vs. sdk-core's direct-axios `addToIpfs`/`fetchFromIpfs`)?**
   - What we know: Both exist today, both work, they differ in transport client (`@cipherbox/api-client` generated functions vs. raw axios) and in whether progress callbacks are supported.
   - What's unclear: Whether the SDK's write-mediation facade (D-07's write-path scope) needs to preserve `apps/web`'s upload/download progress bars, which currently depend on `lib/api/ipfs.ts`'s `onProgress` parameter threading through `addToIpfs`/`fetchFromIpfs`.
   - Recommendation: Verify `packages/sdk-core/src/ipfs/index.ts`'s `addToIpfs`/`fetchFromIpfs` signatures already support progress callbacks (some sdk-core call sites pass `onProgress`, e.g. `download/index.ts:40`) before assuming this is a straight swap; if progress plumbing is missing from the sdk-core path web currently doesn't use, that's an additive task, not a pure deletion.

3. **Is `ConnectionTest.tsx`/`StorageTab.tsx` (BYO-pinning settings UI) in scope for this phase's D-07 write-path mediation?**
   - What we know: These files have both runtime `sdk-core` (`testConnection`) and raw-IPFS/IPNS (`addToIpfs`, `fetchFromIpfs`, `resolveIpnsRecord`, `createAndPublishIpnsRecord`) call sites for a BYO-config IPNS blob that is orthogonal to the folder-listing read chain.
   - What's unclear: Whether the phase's SC#1 grep-gate acceptance criterion is meant to cover ALL of `apps/web/src`, including these settings-only flows, or whether they're a known deferred pocket.
   - Recommendation: CONTEXT.md's D-07 text is unambiguous ("no raw IPFS/IPNS access ... apps/web/src") with no carve-out — treat these as in-scope, but flag explicitly in the plan since they add ~2 more files' worth of rewiring (config-blob resolve/publish, not folder listing) that the roofline success-criteria wording doesn't obviously anticipate.

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| IPNS rollback (relay/attacker serves a stale signed record with a lower sequence/generation) | Tampering | `RotationHighWater.enforceResolved` durable monotonic-max floor (ROT-07) — MUST cover every read-path resolve post-phase, not just pre-publish reconcile (this phase's core gap to close) |
| Unverified-signature record silently bumping a durable floor | Tampering / Elevation of Privilege | Existing fail-closed check (`if (!resolved.signatureVerified) throw`) in both the write-path gate and the web's `ipns.service.ts` — must be replicated in the new SDK-internal read gate, not dropped |
| Generation-source confusion (using a child's own envelope generation instead of the parent's `SealedChildRef.generation` mirror) | Tampering | The generation-source rule is already documented and enforced in `dfsFindFolder`; any new gated-resolve code must follow the identical rule (Pitfall 3) |
| AAD transplant across the read/write chains during the mirror revert | Tampering | Out of scope for THIS revert (only additive display fields `size`/`modifiedAt` are removed, not AAD-bound fields) — CRYPTO-03 test coverage is unaffected |
