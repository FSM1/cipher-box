# Phase 68.2 Plan 08: Shared-Folder Navigation Cutover onto client.listSharedFolder Summary

**Gutted `useSharedNavigationActions.ts`'s duplicated web-layer read-chain walk (raw `unsealNode`/`unsealChildReadKey` + `navigateReadChain`/`resolveIpnsRecord`/`fetchFromIpfs`) in favor of four new SDK facade methods (`resolveShareRoot`, `descendSharedChild`, `downloadSharedFile`, `resolveNodeIdentity`) added this plan, and wired `SharedFolderRow` to a new `resolvedChildren: ResolvedChild[]` display projection via a dual-prop pattern that keeps `SealedChildRef` as the write-op identity carrier.**

## Performance

- **Duration:** ~90 min
- **Tasks:** 2 (plus 4 SDK facade-addition deviations required to complete them)
- **Files modified:** 11 (4 new SDK test files, `client.ts`, 5 web files modified)

## Accomplishments

- `client.resolveShareRoot` hoists `navigateToShare`'s raw-crypto bootstrap (ONE ECIES unwrap of `readDescriptorRef` + resolve/unseal the root Node) into the SDK, returning a `revoked`/`behind-retry`/`ok` discriminated result
- `client.descendSharedChild` hoists `navigateToSubfolder`'s per-hop descent (gated-resolve + `unsealChildReadKey` + `unsealNode`) into the SDK, returning the RAW `SealedChildRef[]` children the web still needs for nav-stack/write-op identity
- `client.downloadSharedFile` moves the full grant-to-leaf walk (wraps `sdk-core`'s unchanged `navigateReadChain`) + IPFS fetch + AES decrypt entirely into the SDK, replacing the web's direct `navigateReadChain`/`fetchFromIpfs`/`decryptAesGcm`/`decryptAesCtr` orchestration in both `downloadSharedFile` and `loadSharedFileContent`
- `client.resolveNodeIdentity` resolves a node's plaintext `id`/`kind` (NODE-03, no readKey needed) for `useSharedWriteOps.ts`'s `deleteFromSharedFolder` childNodeId lookup
- `useSharedNavigationActions.ts` no longer imports `navigateReadChain`/`resolveIpnsRecord`/`fetchFromIpfs` (sdk-core) or `unsealNode`/`unsealChildReadKey` (core) at runtime; the web-side soft `rootGeneration` check is dropped (the SDK's ROT-07 floor gate supersedes it)
- `useSharedNavigation.ts` drops the `kind-cache` `resolveKinds()` population entirely and adds a new `resolvedChildren: ResolvedChild[]` projection (via `client.listSharedFolder` for the current seeded depth, cached in-SDK)
- `useSharedWriteOps.ts` no longer imports `resolveIpnsRecord`/`fetchFromIpfs` at runtime
- `SharedFolderRow` gets a new optional `resolved?: ResolvedChild` prop driving `kind`/`size`/`modifiedAt` display (falls back to the legacy `SealedChildRef` mirrors/kind-cache only while the resolved listing is still loading); `SharedFileBrowser.tsx` wires it via a minimal `resolvedByIpnsName` map

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Added `client.downloadSharedFile`, `client.resolveShareRoot`, `client.descendSharedChild` facades to `packages/sdk/src/client.ts`**
- **Found during:** Task 1 planning (before writing any web code)
- **Issue:** The plan's `<artifacts_this_phase_produces>` states this plan "CREATES no new symbols (rewire-only)" and references "the existing/extended `client.downloadSharedFile` facade" and `client.listSharedFolder`, but no `client.downloadSharedFile` existed anywhere in `packages/sdk/src/client.ts`, and `client.listSharedFolder` (Plan 02) explicitly requires a pre-seeded `sharedFolderTree` entry — it cannot bootstrap a share from the top-level list (Plan 02's own SUMMARY documents this limitation) nor descend one hop while also recovering the raw `SealedChildRef[]` + readKey the web needs for nav-stack/write-op identity. Without new facades, `navigateToShare`/`navigateToSubfolder`/`downloadSharedFile`/`loadSharedFileContent` could not be rewired off `unsealNode`/`unsealChildReadKey`/`navigateReadChain`/`resolveIpnsRecord`/`fetchFromIpfs` — the plan's own must_haves would be unreachable.
- **Fix:** Added three new `client.ts` methods, each a verbatim hoist of the raw-crypto portion previously inline in the web hook: `resolveShareRoot` (share-entry bootstrap), `descendSharedChild` (one read-chain hop), `downloadSharedFile` (wraps `sdk-core`'s UNCHANGED `navigateReadChain` — per 68.2-RESEARCH.md's explicit guidance not to modify that primitive, since it has other existing callers — plus the fetch+decrypt orchestration). `downloadSharedFile` returns a `revoked`/`behind-retry`/`ok` discriminated result rather than throwing, matching `navigateReadChain`'s own contract.
- **Files modified:** `packages/sdk/src/client.ts`, plus 3 new test files (`download-shared-file.test.ts`, `resolve-share-root.test.ts`, `descend-shared-child.test.ts`)
- **Verification:** `pnpm --filter @cipherbox/sdk test` — 334/334 pass (13 new tests across the 3 files, 0 regressions); `tsc --noEmit -p tsconfig.build.json` exits 0
- **Committed in:** `b5c021267`, `269b5010b`

**2. [Rule 2 - Missing Critical] Added `client.resolveNodeIdentity` facade**
- **Found during:** Task 2 (rewiring `useSharedWriteOps.ts`)
- **Issue:** `useSharedWriteOps.ts`'s `resolveChildNodeId` (used by `deleteFromSharedFolder`) directly called `sdk-core`'s `resolveIpnsRecord`/`fetchFromIpfs` to read a node's plaintext `id` field (NODE-03: `id`/`kind` are plaintext on the envelope, no decryption needed) — no existing SDK facade exposed this.
- **Fix:** Added `client.resolveNodeIdentity(ipnsName)`, a thin wrapper around the existing private `resolvePublishedNode` returning `{nodeId, kind} | null`.
- **Files modified:** `packages/sdk/src/client.ts`, `packages/sdk/src/__tests__/resolve-node-identity.test.ts` (new)
- **Verification:** `pnpm --filter @cipherbox/sdk test` — 334/334 pass; `grep -n "resolveIpnsRecord|fetchFromIpfs" apps/web/src/hooks/useSharedWriteOps.ts` returns nothing
- **Committed in:** `203bc3bf4`

**3. [Rule 4-adjacent, resolved via established precedent] `SharedFolderRow.item` kept as `SealedChildRef` instead of a straight swap to `ResolvedChild`**
- **Found during:** Task 2 (repointing `SharedFolderRow`'s display fields)
- **Issue:** The plan's Task 2 action literally says "Repoint SharedFolderRow's prop type from SealedChildRef to ResolvedChild." Tracing every consumer of `SharedFolderRow`'s `item` prop through `SharedFileBrowser.tsx` (not in this plan's `files_modified`, and flagged in STATE.md's 68.2-06 blocker as unowned by any of the 12 phase-68.2 plans) showed `item` is also passed directly to `ContextMenu`, `DetailsDialog`, `TextEditorDialog`, `ImagePreviewDialog`, `PdfPreviewDialog`, `AudioPlayerDialog`, `VideoPlayerDialog`, `SharedMoveDialog`, and every write-op call (`renameItem`/`deleteItem`/`moveItem`/`updateSharedFile`) — several of which (`updateSharedFile`'s `filePointer`) genuinely require `SealedChildRef.readKeySealed` for crypto, and none of which are owned by this plan. A straight type swap would have broken every one of those out-of-scope components' compile.
- **Fix:** Added a NEW optional `resolved?: ResolvedChild` prop instead (dual-prop pattern), mirroring `FileListItem.tsx`'s already-established owned-folder pattern from Plan 06 (documented in STATE.md's key-decisions for 68.2-06) for the exact same underlying tension. `isFolder`/`size`/`date` now read from `resolved ?? item` (via `isFileRef`'s existing union support) / `resolved?.size` / `resolved?.modifiedAt`, satisfying the plan's actual truth ("SharedFolderRow renders kind/size/modifiedAt from ResolvedChild") without the blast radius.
- **Files modified:** `apps/web/src/components/file-browser/SharedFolderRow.tsx`, `apps/web/src/components/file-browser/SharedFileBrowser.tsx` (minimal additive wire only — one `useMemo` + one prop)
- **Verification:** `pnpm --filter @cipherbox/web exec tsc -b --force` — byte-identical 18-error pre-existing baseline before/after (confirmed via `git stash` comparison), zero errors from any of this plan's 6 touched files; `pnpm --filter @cipherbox/web exec eslint` clean
- **Committed in:** `a49a0e992`
