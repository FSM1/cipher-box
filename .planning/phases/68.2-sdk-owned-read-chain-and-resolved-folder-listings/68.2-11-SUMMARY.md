# Phase 68.2 Plan 11: SDK Read-Chain Deletion + D-07 Boundary Gate Summary

## Accomplishments

- Added `client.resolveFileMetadata(fileRef, folderKey)` to `packages/sdk/src/client.ts` (Rule 2) — the read-only counterpart to the existing `downloadFromIpns`, sharing its exact resolve/unseal steps (resolve the file's `PublishedNode`, recover the file's own readKey via `unsealChildReadKey` under the parent's `folderKey`, delegate to `sdkCore.resolveFileMetadata`), zeroing the internally-minted `fileReadKey` on every exit path.
- Migrated all 9 real (non-test) importers of the doomed `file-metadata.service.ts` onto the new facade: `TextEditorDialog.tsx`, `DetailsDialog.tsx`, `useStreamingPreview.ts`, `useFileVersions.ts`, `useFileOperations.ts`, and `download.service.ts` (a 9th importer the orchestrator's audit had not listed, found via a fresh grep sweep per Task 1's "rewire before deleting" instruction).
- Migrated `TextEditorDialog.tsx`'s raw `addToIpfs`/`unpinFromIpfs` calls to `client.uploadBytes`/`client.unpin`, and `useFileVersions.ts`/`useFileOperations.ts`'s `unpinFromIpfs` to `client.unpin`.
- Closed the `FileList.tsx`/`FileBrowser.tsx` ownership gap STATE.md flagged as a blocker: repointed `FileList` from the dead `kind-cache`-backed `toResolvedChildView` adapter to a `resolvedByIpnsName` lookup into the folder store's real `children: ResolvedChild[]` (mirroring the `SharedFileBrowser`/`SharedFolderRow` pattern from Plan 08), with `FileBrowser.tsx` now passing `currentFolder?.children` as the new `resolvedChildren` prop.
- Simplified `fileTypes.ts`'s `isFileRef` SealedChildRef fallback branch from a `kind-cache` lookup to a hardcoded `false` (folder-safe) — behavior-preserving, since `resolveKinds` was never wired into any render path and the cache was a permanent miss in production.
- Deleted `apps/web/src/services/ipns.service.ts`, `file-metadata.service.ts`, `lib/kind-cache.ts`, `hooks/useFileSize.ts` (dead, zero importers even before this plan), and their re-exports from `services/index.ts`.
- Ran the allowlist-free D-07 grep gate (Gate A: `sdk-core`/`core` runtime imports via the two-step Pitfall-5 pipeline; Gate B: raw IPFS call sites) — found `lib/api/ipfs.ts` had zero remaining apps/web importers once the migration completed, deleted it, and re-ran the gate to `GATE_CLEAN`.
- Rebuilt `sdk-core`/`sdk` dist and ran the full `sdk`/`sdk-core`/`core` vitest suites plus `apps/web` typecheck (`tsc -b --force`) — all green, no fixes needed.

## Decisions Made

- `client.resolveFileMetadata` deliberately mirrors `downloadFromIpns`'s existing (ungated) resolve pattern rather than adding a new ROT-07 gate at the web-native call site — the critical_constraints explicitly forbid re-adding web-side gating since Plan 01 already covers the SDK-internal read path, and `downloadFromIpns` (used for actual file downloads) already establishes this exact accepted pattern.
- `FileList.tsx`'s `toResolvedChildView` fallback (used only for an in-flight-sync-race miss) still builds a folder-safe stub from raw `SealedChildRef` fields rather than throwing, matching the existing defensive style used elsewhere in this cutover.
- `isFileRef`'s hardcoded `false` fallback (replacing the kind-cache lookup) is verified behavior-identical: `resolveKinds`/`clearKindCache` had zero call sites anywhere in the codebase before this plan, so `getKind()` always returned `undefined` in production.
