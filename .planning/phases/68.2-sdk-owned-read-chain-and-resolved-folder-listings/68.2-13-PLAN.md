<objective>
Fix the cache-invalidation contract at the root of SDK-READ-03 / SC#5: add an explicit, deliberate live-resolve-on-navigation path to `CipherBoxClient.ensureFolderLoaded` / `listFolder`, distinct from the cached fast path that internal write-mutation chokepoints rely on.

Today `ensureFolderLoaded` (client.ts ~L1549) short-circuits on any already-loaded `folderTree` entry and returns it verbatim without re-resolving from the network; `resolveListingChildren` (~L828) then compares the incoming `sequenceNumber` against the SAME stale `folder.sequenceNumber` the short-circuit just returned — a no-op comparison against itself. An owner who loaded a shared-out folder once never sees a grantee's later upload without writing first (the exact desync bug class this phase exists to close).

Purpose: Make an already-loaded folder re-resolve its own IPNS record from network truth on nav/poll intent, GATED through the existing ROT-07 durable anti-rollback gate (D-04/D-05), updating the single source of truth (`folderTree`) in place — while leaving the cheap cached path intact for write chokepoints.

Output: A `forceResolve` option on `ensureFolderLoaded`/`listFolder` backed by a gated in-place re-resolve, proven by a new deterministic Node unit test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IPNS relay -> SDK read path | A malicious/compromised relay can serve a stale, rolled-back, or forged IPNS record during the new re-resolve. |
| SDK folderTree (single source of truth) -> web projection | The in-place update mutates the sole folder-state owner; a bad update would corrupt every projection. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-68.2-13-01 | Tampering | forceResolve re-resolve in ensureFolderLoaded | high | mitigate | The re-resolve is a GATED re-resolve — it routes through `RotationHighWater.enforceResolved` exactly like dfsFindFolder; a below-floor seq rejects with SequenceRegressionError. Test 2 proves the gate is invoked and rejects; the re-resolve is never a raw bypass (D-05). |
| T-68.2-13-02 | Spoofing | resolvePublishedNode on re-resolve | high | mitigate | Fail closed on `!signatureVerified` BEFORE any floor mutation (mirrors 68.2-01); an unverified record throws and never updates folderTree. |
