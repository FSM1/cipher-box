# Phase 68.2 Plan 05: Shared-Folder Desync Regression Spec (SC#5) Summary

**Authored `tests/web-e2e/tests/shared-folder-desync.spec.ts`, a permanent two-account (owner + grantee) Playwright regression spec proving the owner sees a grantee's write-share upload into a shared folder without writing first, with the new file's size/modifiedAt asserted to render from the resolved listing rather than the pre-fix SealedChildRef mirror's em-dash/epoch placeholders — the deterministic SC#5 proof, intentionally expected-red until the Phase 68.2 web cutover (Plans 06-11) lands.**

## Performance

- **Duration:** ~15 min
- **Tasks:** 1
- **Files modified:** 1 (new spec file)

## Accomplishments

- New spec `tests/web-e2e/tests/shared-folder-desync.spec.ts` with 3 sequential tests (`describe.serial`):
  1. Account setup (owner, grantee) via `multi-account-wallet.ts`
  2. Owner creates a folder and shares it with the grantee using write permission (mirrors `writable-shares.spec.ts`'s `[ READ-WRITE ]` flow)
  3. Grantee navigates to `~/shared`, enters the folder, and uploads a file — the owner never writes
  4. Owner navigates into the same folder for the first time (nav-triggered re-resolve, D-03) and asserts the grantee's file is visible with formatted size (not `'—'`) and a real date (not containing `'1970'`)
- Confirmed the assertion targets are grounded in the actual current source: `FileListItem.tsx`'s `sizeDisplay`/`dateDisplay` fall back to the em-dash (`'—'`) when `item.size`/`item.modifiedAt` are absent from the `SealedChildRef` mirror — exactly the pre-fix desync symptom this spec proves is closed post-cutover
- Verified the spec is discoverable by Playwright's runner without standing up the local web-e2e stack: `npx playwright test --list` found all 4 tests; `--list` does not invoke `webServer` startup

## Decisions Made

- Write-permission share (not read-only), since the grantee must upload a file into the folder — the owner's read-only visibility of that upload is exactly the SC#5 desync surface
- Direct `.file-list-item-size`/`.file-list-item-date` locator queries used instead of `FileListPage.getFileItem`/`getFolderItem` (which filter on a literal hyphen `'-'` in size text, while the current `FileListItem.tsx` em-dash placeholder is `'—'` — a pre-existing, unrelated selector mismatch in those helpers, out of this plan's scope to fix) — the direct-locator approach avoids coupling this new spec to that quirk while still landing on the exact same DOM elements
- Spec left un-skipped and un-fixme'd per the plan's explicit instruction: it is a genuine, permanent regression test that is expected to fail today (RED) and is expected to turn green only once Plans 06-11 rewire `folder.store.ts` into a pure `ResolvedChild[]` projection
