## Freshness policy (the desync fix — SC#5)

**Notes:** Nav-resolve leg is the deterministic SC#5 fix; poll leg keeps an open folder live.

## Anti-rollback gate reuse (Gate / boundary)

| Option | Description | Selected |
|--------|-------------|----------|
| Reuse `RotationHighWater` as the single gated entrypoint | Route the read-listing resolve through existing `RotationHighWater.enforceResolved`; raw sdk-core resolve internal-only; no new abstraction. | ✓ (via follow-up) |
| Introduce a distinct `DurableFloorStore` | New adapter per roadmap wording; risk of two floor stores drifting. | |
| You decide | Defer to researcher. | |

**User's choice:** "Other" — freeform architectural directive: *"Ideally the web ui should not be doing any raw resolves or ipfs/ipns accesses or any calls to sdk-core. the entire reason for the existence of the sdk is to mediate this."*
**Notes:** Reframed the gate question into a boundary principle. Two plain-text follow-ups resolved it:
1. Confirmed reuse of the existing `RotationHighWater`/`HighWaterStore` seam as the "DurableFloorStore" (no new abstraction); user added that `HighWaterStore` must be mocked/injected for Node.js SDK unit tests.
2. On boundary scope, user directed that the **write path be included in this phase too** — "phase 69 is entirely Rust/Desktop side and should not be conflated with the current TS code (web + sdk)." Orchestrator clarified (accepted, subject to user review) that the boundary targets **runtime** sdk-core/core calls + raw IPFS/IPNS; **type-only imports remain allowed** to avoid a ~54-file no-op churn.
