# Phase 68.2 Plan 13: Gated Live-Resolve-on-Navigation for Already-Loaded Folders Summary

**Adds a gated `forceResolve` re-resolve path to `CipherBoxClient.ensureFolderLoaded`/`listFolder` that closes the SDK-READ-03 self-referential cache-clock gap, proven by a new deterministic Node unit test (`folder-reresolve.test.ts`).**

## Performance

- **Duration:** ~8 min

- **Completed:** 2026-07-06T08:55Z
- **Tasks:** 2 (TDD RED/GREEN)
- **Files modified:** 2 (1 new test file, 1 modified source file)

## Accomplishments

- Root-caused gap closed: `ensureFolderLoaded` no longer unconditionally short-circuits an already-loaded `folderTree` entry. `{ forceResolve: true }` routes to a new gated in-place re-resolve (`reresolveFolderInPlace` / `doReresolveFolderInPlace`) that genuinely re-resolves the folder's own IPNS record from the network.
- The re-resolve is GATED exactly like `dfsFindFolder`'s per-hop gate and `ensureRootFolderState`'s root gate: fail-closed on `!signatureVerified` BEFORE any floor mutation, `Number.MAX_SAFE_INTEGER` overflow guard, then `RotationHighWater.enforceResolved` sourced from `existing.nodeGeneration` (never the freshly relay-served envelope generation). A below-floor resolve still rejects with `SequenceRegressionError` and leaves the stored `FolderState` untouched — Plan 01's guarantee is not weakened.
- `FolderState` is updated in place (single source of truth, D-09/SC#3) — `sequenceNumber`/`children`/`metadata`/`nodeGeneration`/`lastLoadedAt` all advance from the newly-unsealed node, with `writeKey`/`ipnsKeypair`/`nodeId` preserved. No second cache or store was introduced.
- `listFolder(ipnsName, { forceResolve: true })` threads `opts` into `ensureFolderLoaded` so the advanced sequence flows into `resolveListingChildren`'s cache check, which now compares against network truth instead of the stale value the old short-circuit returned — a newly-appeared child correctly surfaces in the resolved `ResolvedChild[]`.
- Concurrent `forceResolve` calls for the same `ipnsName` dedupe to a single network resolve via a `reresolveInFlight` map, registered synchronously so two calls issued back-to-back (e.g. a nav re-resolve racing the 30s poll leg) share one in-flight promise.
- The no-opts cached fast path used by internal write-mutation chokepoints (`requireFolder`, etc.) is byte-for-byte unchanged.

## Decisions Made

- `generation` for the re-resolve gate call is sourced from `existing.nodeGeneration` (locally-trusted, previously-gate-validated), never the freshly relay-served envelope's own `generation` field — matches the Pitfall 3 / D-04 rule enforced everywhere else in the read path (`dfsFindFolder`, `gatedResolveChild`, `ensureRootFolderState`).
- `versionFloor: 0` on the gate call, mirroring `ensureRootFolderState`'s own root-resolve gate — the seqFloor is already established for an already-loaded node, so this value is structurally never consulted (only the cold-device first-contact branch reads it).
- A null resolve (structurally unresolvable / transient network miss) or a resolved sequence `<= existing.sequenceNumber` (#489 sequence-as-clock guard) both return `existing` unchanged without re-unsealing — the re-resolve never blows away a loaded view on a stale-lagging or failed read.
- Dedup is implemented as two private methods (`reresolveFolderInPlace` wraps `doReresolveFolderInPlace`) rather than one, so the in-flight map registration happens synchronously in the outer method before the inner method's first `await` — this is what makes `Promise.all([forceResolve, forceResolve])` observe the same in-flight promise instead of racing two independent network resolves.
