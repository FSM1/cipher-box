# Phase 68.2 Plan 01: SDK Internal Read-Path ROT-07 Gate Summary

**Gated the SDK's internal navigate path (ensureFolderLoaded -> dfsFindFolder -> resolvePublishedNode) through RotationHighWater.enforceResolved, closing the "SDK exists but the actual anti-rollback gate lives only in apps/web" gap before any web-service deletion.**

## Performance

- **Duration:** ~25 min
- **Tasks:** 2 (TDD: RED test, GREEN implementation)
- **Files modified:** 2 (1 created, 1 modified)

## Accomplishments

- `resolvePublishedNode` now threads `signatureVerified` from `sdkCore.resolveIpnsRecord` (previously silently discarded)
- `dfsFindFolder`'s per-hop child loop gates every not-yet-cached child resolve through `RotationHighWater.enforceResolved` before trusting it for `unsealChildReadKey`/`unsealChildWriteKey`, sourcing `generation` from `childRef.generation` (the PARENT's `SealedChildRef` mirror) — never the child's own envelope `generation`
- `ensureRootFolderState`'s root resolve is gated the same way, sourcing `generation` from the in-memory `folderTree` entry (mirroring the existing write-path gate, since the root has no parent `SealedChildRef`)
- Both gate sites fail closed on `signatureVerified === false` BEFORE calling `enforceResolved` (no floor mutation on an unverified record) and guard `Number.MAX_SAFE_INTEGER` overflow before `Number()` conversion, matching the existing `reconcileFolderSequence` write-path gate
- New unit test file `folder-listing-gate.test.ts` proves all three behaviors with a `fakeRotationHighWater` (reused verbatim from `client-rotation.test.ts`)

## Task Commits

Each task was committed atomically (TDD RED/GREEN):

1. **Task 1: RED — failing gate test for the internal read path** - `bb42f50ef` (test)
2. **Task 2: GREEN — gate resolvePublishedNode + dfsFindFolder + ensureFolderLoaded root resolve** - `9cb17ac4b` (feat)

_Both tasks landed as separate commits per the plan's TDD requirement — no REFACTOR commit was needed (no cleanup pass required after GREEN)._

## Files Created/Modified

- `packages/sdk/src/__tests__/folder-listing-gate.test.ts` - New unit test proving below-floor rejection, single-invocation gating with correct generation sourcing, and fail-closed unverified-signature handling
- `packages/sdk/src/client.ts` - `resolvePublishedNode` return type gains `signatureVerified`; `dfsFindFolder`'s per-hop child loop and `ensureRootFolderState`'s root resolve both gate through `this.config.rotationHighWater.enforceResolved(...)`

## Decisions Made

- `resolvePublishedNode`'s return type grows a `signatureVerified` field rather than introducing a new method — every other call site (moveItem's FLAG-63-U2 re-seal, `getWriteBodyParams`, etc.) is unaffected since they only destructure `published`/`sequenceNumber`
- Root resolve gate passes `versionFloor: 0` since the root has no parent `SealedChildRef` to source an owner-vouched cold-device floor from — it is the client's own self-bootstrapped node, not an external grant
- `getWriteBodyParams` (write-internal-only resolve) intentionally left ungated per D-05 — this plan's scope is the read path only

## Deviations from Plan

None - plan executed exactly as written. The `<action>` for Task 2 specified gating `resolvePublishedNode`, `dfsFindFolder`, and `ensureFolderLoaded`'s root resolve with the exact generation-sourcing rules (parent mirror for children, in-memory `folderTree` for root) and fail-closed signature handling — implemented as specified, verified against both the new test file and the full existing `client-rotation.test.ts` suite plus the full `@cipherbox/sdk` test suite (296/296 passing).

## Issues Encountered

- Initial test draft mocked `deriveEd25519PublicKey` on the `@cipherbox/core` module; the real import in `client.ts` sources it from `@cipherbox/crypto`. Fixed by moving the mock to a dedicated `vi.mock('@cipherbox/crypto', ...)` block before running the RED test — this surfaced during the RED run itself (a `CryptoError: Invalid private key size` from the real `deriveEd25519PublicKey` running unmocked) and was corrected before the RED commit landed, so the committed RED run cleanly demonstrates the three intended gate-behavior failures rather than an unrelated mock-wiring bug.
