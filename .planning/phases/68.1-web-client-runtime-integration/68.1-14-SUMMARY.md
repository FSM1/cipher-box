# Phase 68.1 Plan 14: Kind Cache Render-Path Wiring (D-02) Summary

**`resolveKinds(children)` now runs on every owned and shared folder-load/navigation render path — the D-02 kind cache built in 68.1-04 goes from unreachable dead code to actually populated at runtime, so uploaded/shared files stop defaulting to folder rows.**

## Accomplishments

- `useFolderNavigation.navigateTo` now `await resolveKinds(state.children)` after `ensureFolderLoaded` resolves and BEFORE the `FolderNode` lands in the store via `setFolder`, with the existing stale-nav-target guard re-checked after the new await.
- `folder.store.ts`'s `subscribeToSdk` handles `folder:loaded`/`folder:updated` (root initial load + every resync, which never flow through `navigateTo`) by populating the cache best-effort after the existing synchronous `updateFolderChildren`/`updateFolderSequence` calls, then re-invoking `updateFolderChildren` once the resolve settles so rows flip from folder-safe to resolved — guarded against the folder having been removed mid-resolve, never throws out of the subscription handler.
- All four `useSharedNavigationActions.ts` handlers that list children (`navigateToShare`, `navigateToSubfolder`, `navigateUp`, `navigateToBreadcrumb`) now `await resolveKinds(children)` immediately before `setFolderChildren(children)` — placed after the existing behind-retry/revoked handling in the two fresh-fetch handlers so a stale/revoked navigation never populates for a level it will not render.
- `useSharedNavigation.ts`'s `subscribeSharedFolderProjection` callback (the `sharedFolder:updated` projection) populates the cache best-effort after its synchronous `setFolderChildren`/`setCurrentSequenceNumber` calls, re-setting the same children reference once resolved — guarded by a captured-then-rechecked active `shareId` so a stale resolve never re-renders an abandoned share.
- `downloadSharedFile` (lists no children) intentionally left unwired, per the plan.

## Decisions Made

- **Two different wiring patterns by call-site shape**, both explicitly sanctioned by the plan text ("immediately before (or right after) setFolderChildren(children)"):
  - **Blocking/before-setter** for user-triggered navigation (`navigateTo`, `navigateToShare`, `navigateToSubfolder`): the cache populates before the folder lands in the store, so the very first render already reads the resolved kind — no flicker.
  - **Non-blocking/after-setter with follow-up re-render** for synchronous event/subscription paths (`folder:loaded`/`folder:updated`, `sharedFolder:updated`): these are SDK-driven events, not user actions — blocking them on a network resolve would delay the authoritative sync signal, so the existing synchronous update fires first (folder-safe render) and a best-effort resolve triggers exactly one follow-up re-render.
- `navigateUp`/`navigateToBreadcrumb` also call `resolveKinds` on their nav-stack children even though those children were already resolved during the original descent (same array reference, so the call is a memoized no-op in the common case) — kept for defense-in-depth per the plan's explicit "for each handler that lists children" instruction, covering an edge case where the cache was cleared mid-session (e.g. a logout/login between descent and ascent).
- The shared projection callback snapshots `currentShareIdRef.current` before the `resolveKinds` await and re-checks it after settling, mirroring the shareId filter already applied one layer up in `subscribeSharedFolderProjection` — prevents a stale resolve for an abandoned share from re-rendering the wrong folder.
