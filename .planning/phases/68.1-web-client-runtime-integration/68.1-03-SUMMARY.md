## Accomplishments

- New-user branch of `initializeOrLoadVault` no longer throws: after publishing the v3 vault key blob, it publishes an empty `kind:'root'` Node (write-body carrying the root IPNS signing key) via `publishEmptyRootNode`, registers the vault via `vaultApi.initVault({ ownerPublicKey, rootIpnsName })`, and calls `setVaultKeys` with the full key set
- `publishEmptyRootNode` is invoked with a locally-built `SdkContext` (apiUrl + getAccessToken + shared apiAxios instance), since it runs before `initSdkClient` constructs the app's SDK client
- Both the existing-user and new-user branches now pass `rootWriteKey: vaultState.rootWriteKey!` into the `initSdkClient` config alongside `rootFolderKey`, unblocking `ensureFolderLoaded`'s DFS write-chain recovery for both login paths
- Removed both `TODO(phase 63)` markers and the throwing stub at the former `useAuth.ts:210`

## Decisions Made

- `publishEmptyRootNode` derives `rootIpnsName` internally (via `deriveIpnsName(rootIpnsKeypair.publicKey)`) and returns it in its result -- `useAuth.ts` consumes the returned name rather than duplicating the derivation call inline, avoiding a redundant Ed25519-to-IPNS-name computation
- New-user `publishEmptyRootNode` call omits `teeKeys` (stays `undefined`) -- a brand-new user has no TEE enrollment state yet; `teeKeys` is only populated from `existingVault.teeKeys` on the returning-user path
