## Accomplishments

- **createFolder retry-on-stale + folder-store id desync (root cause of "create a folder inside a folder appears to silently fail")**: `client.createFolder` was the only folder mutation not wrapped in `runWithFailureUx`, so a `ReconcileStaleError` (common right after a sibling mutation bumps the parent's sequence) failed closed instead of retrying. Separately — and this was the dominant root cause blocking ~15 of the 17 originally-failing spec groups per the orchestrator's hint — `useFolderMutations.handleCreate` stored the newly-created folder under its write-body UUID instead of its `ipnsName`, creating an orphan duplicate store entry. The SDK's `folder:updated` event subscription (which resolves the target by `f.ipnsName === event.ipnsName`) could then match the orphan instead of the entry `FileBrowser` actually renders from, silently dropping the child list update whenever a folder was created *inside* a folder created earlier in the same session.
- **File/folder details-dialog fields restored**: `FileDetails`' IPNS row was relabeled `"File IPNS"` during the refactor (test expects `"File Metadata IPNS"`) and `FolderDetails` dropped the `"Folder Key"`/`"IPNS Private Key"` redacted rows entirely (replaced by an unrelated `"Read Key Sealed"` row). Both restored — the folder-key data was already available on `DetailsDialog`'s `folderStoreEntry`, just not threaded through.
- **Kind-cache wiring in `FileListItem`/`ContextMenu`**: both components had hardcoded `phase-63` stub booleans (`isFolder = true`, `isFile = false`) despite the kind cache (D-02, populated by `folder.store.ts`'s `subscribeToSdk` on every `folder:updated`/`loaded` event) already being live and used elsewhere. This meant every file rendered with the `[DIR]` icon and was double-click-navigable as an (empty) folder, and the single-item Preview/Edit/Download context-menu options never appeared for **any** item. Fixed both to read `isFileRef(item)`. This directly fixed the user-reported "uploaded PDF is picked up as a folder" bug and the media-preview/streaming-playback specs' "browser crashed" failures (they were hanging 180s waiting for a Preview menu item that could never exist, then Playwright force-closed the browser on global timeout).
- **Batch-download UI wiring**: `handleBatchDownload`/`handleDownload` (`useFileBrowserActions.ts`) were complete, working implementations with no UI trigger — `SelectionActionBar` received `onDownload` as a prop but never rendered a button for it, and `ContextMenu`'s batch-download menu item was unconditionally wired to `undefined`. Wired both to the existing handlers.
- Rebuilt `sdk-core`/`sdk` dist after each debug-instrumentation cycle; final dist is clean (no leftover instrumentation — verified via `grep -rn TEMPDBG`).

## Known Gaps (surfaced, NOT fixed — exceed "small wiring fix" scope)

### GAP-1: `resolveFileMetadata` AEAD "Decryption failed" for CTR/streaming video and immediately-post-upload batch-download

**Symptom:** Video preview (`VideoPlayerDialog` → `useStreamingPreview` → `resolveFileMetadata`) shows `"> Decryption failed"` in the modal instead of a player. Batch-download of freshly-uploaded text files also throws `CryptoError: Decryption failed` at `unsealNode`/`decryptAesGcmAad` inside `resolveFileMetadata`. Single PDF/image preview (`useFilePreview` → `downloadFileFromIpns` → `resolveFileMetadata`, same call chain) succeeds for the SAME test session's PDF fixture.

**What's confirmed:** The failure is inside `apps/web/src/services/file-metadata.service.ts`'s `resolveFileMetadata` — specifically the `unsealChildReadKey`/`unsealNode` step recovering the file's own `NodeContent`, an AEAD authentication failure (wrong key or wrong AAD, not a missing-data error). It reproduces consistently for: (a) the large/CTR-mode video fixture in `streaming-playback.spec.ts`/`media-preview.spec.ts`, and (b) files downloaded via the batch-download UI in `batch-download.spec.ts` shortly after upload. It does NOT reproduce for the PDF/image fixtures in the same test sessions, nor for `full-workflow.spec.ts`'s text-editor read/write round-trip (which uses a related but distinct `resolveFileMetadata`-adjacent path and passed in earlier full-suite runs).

**Suspected root cause (unconfirmed):** A stale/incorrect `SealedChildRef.generation` (the AAD input to `unsealChildReadKey`) for specific files — most plausibly from a race in the folder-children merge during rapid or batched uploads (`uploadFiles`'s parallel pipeline, or a large-file upload racing a smaller sibling's upload+republish in the same test). Both failing scenarios involve either large/slow uploads (video) or multiple files uploaded to the same folder in quick succession (batch-download's 3 text files) — the common thread not yet isolated.

**Why not fixed here:** Confirming and fixing an AEAD/generation mismatch requires careful side-by-side comparison of the exact `childId`/`kind`/`generation` triad used at seal time (upload) vs unseal time (read), ideally with fresh instrumentation and a minimal non-parallel repro — genuinely new debugging work, not a wiring fix, and a wrong guess here risks a real crypto correctness regression.

**Recommended next step:** A dedicated debugging session, ideally starting from a MINIMAL repro (upload exactly one file, wait for its own folder republish to complete, then immediately try to read it) to determine whether the race is upload-count-dependent or file-size-dependent.

### GAP-2: Cold-reload multi-level IPNS DFS times out (`full-workflow.spec.ts` 3.8)

**Symptom:** After `page.reload()` (test 3.7, which passes and correctly re-resolves root's children), navigating into a subfolder that itself has real nested children (`workspace` → `documents`) times out with `"[Nav] Failed to load subfolder: Error: Folder not loaded — IPNS propagation timed out"` after `ensureFolderLoaded`'s 3-retry/2s-backoff budget is exhausted. The app correctly reverts to the parent view (no crash, no data loss) — this is a UX/timing gap, not a correctness bug.

**What's confirmed:** Root's own IPNS record resolves correctly post-reload (the file list shows the exact right 5 root-level items). The failure is specifically resolving `workspace`'s own IPNS record — repeated `GET /ipns/resolve` 404s during `ensureFolderLoaded`'s DFS walk. This scenario was UNREACHABLE before this plan's GAP-fix-1 (folder-store id desync) — nested folder creation always failed before, so `full-workflow.spec.ts` never previously reached a reload with real multi-level content to navigate.

**Suspected root cause (unconfirmed):** Either (a) genuine IPNS propagation lag in the local Kubo/mock-ipns-routing stack when many records were published in quick succession across tests 2.1-3.6 before the reload, exceeding `ensureFolderLoaded`'s fixed 3-retry/2s budget, or (b) a real bug where `workspace`'s IPNS record ends up in a bad state from one of its several republishes during nested-child-creation (tests 2.2-2.6) racing with concurrent uploads into its descendants (tests 3.3-3.6). Distinguishing these requires either a longer retry budget (to test hypothesis a) or direct inspection of `workspace`'s actual on-chain IPNS sequence history (to test hypothesis b) — both genuinely new investigation, not scoped for this plan.

**Recommended next step:** Re-run `full-workflow.spec.ts` 3.7-3.8 in isolation with the retry budget temporarily bumped (e.g. 8 retries / 3s) to distinguish infra propagation lag from a real publish-sequence bug; if the longer budget fixes it, the fix is a `MAX_RETRIES`/`RETRY_DELAY_MS` tuning change in `useFolderNavigation.ts` (genuinely small); if not, this needs the same forensic treatment as GAP-1.
