# Phase 68.1 Plan 20: SHARE-WRITE-KEY Recipient Wiring + Fail-Closed fetchShareKeys Summary

**Recipients with a write grant now recover a real shared-root writeKey on navigation entry (unwrapped from `writeDescriptorRef`) instead of a zero buffer, `share.service.ts` has no remaining reachable throw, and `moveInSharedFolder` resolves destination keys from a one-hop write-chain walk instead of the nonexistent `share_keys` endpoint — closing the write-permission half of SHARE-WRITE-KEY (WEB-03) that 68.1-18 left on the owner-create side only.**

## Accomplishments

- `share.service.ts`: `fetchShareKeys` and `fetchPendingRotations` return `[]` instead of throwing — there is no per-child `share_keys` fan-out or pending-rotations endpoint under the descriptor-ref grant model, so every existing caller's empty-array fallback path (`useSharedNavigation.ts`, `useSharedWriteOps.ts`, `SharedMoveDialog.tsx`, `TextEditorDialog.tsx`, `checkPendingRotation`) is now exercised instead of crashing. `createShare` (zero live callers anywhere) removed entirely. `updateSharePermission` (still called from `ShareDialog.tsx`'s `handleUpgrade`/`handleDowngradeConfirm`, out of this plan's scope) converted from an unconditional throw to a fail-closed no-op with a comment pointing at 68.1-19's `updateGrant` migration.
- `ReceivedShare` (`share.store.ts`) gained an optional `writeDescriptorRef` field, populated by `share.service.ts`'s `toReceivedShare` from the DTO's existing `writeDescriptorRef` — the grant row already carried this on the wire, it just was never surfaced to the web store.
- `useSharedNavigationActions.ts`: `navigateToShare` unwraps `share.writeDescriptorRef` (when present — write grants only) with the vault private key via a new `resolveSharedRootWriteKey` helper, and passes the recovered shared-root writeKey to `seedActiveSharedFolder`, replacing the SDK's zero-buffer default. `navigateUp`/`navigateToBreadcrumb` do the same re-derivation, but ONLY when the depth they are restoring is the share ROOT (`target.ipnsName === share.ipnsName`) — a subfolder restore keeps the zero-buffer default untouched, since a subfolder's own writeKey is sealed inside its parent's write-body (out of the grant's descriptor, and out of this plan's stated scope). The unwrapped buffer is zeroed in a `finally` after each `seedActiveSharedFolder` call (D-09).
- `client.ts`: `moveInSharedFolder` no longer depends on `getShareKeysFn` returning a real per-child fan-out. When it returns empty (now always, since `fetchShareKeys` is fail-closed), the method unseals the currently active shared folder's own write-body (its `writeKey` was seeded by the above navigation change) and walks one hop to the destination's `WriteChildRef`, mirroring `updateSharedFile`'s existing inline write-chain pattern (68.1-08). The legacy `share_keys` branch is kept for backward compatibility. dest-before-src publish order and full key zeroing (`destFolderKey`/`destWriteKey`/`destIpnsPrivateKey`) are preserved. A destination that is NOT a direct child of the source folder's write-body fails closed with a precise, documented error rather than falling back to a zero/guessed key.

## Known Gaps (surfaced, NOT fixed — exceeds this plan's scope)

### GAP-7: `enumerateSharedSubtree` (shared-move destination picker) is now also fail-closed-empty, not just `moveInSharedFolder`

**Symptom:** `SharedMoveDialog.tsx`'s destination picker calls `getSdkClient().enumerateSharedSubtree(shareId, { getShareKeysFn: fetchShareKeys, ... })`. Since `fetchShareKeys` now always returns `[]` (Task 1), `enumerateSharedSubtree`'s internal `folderKeyMap`/`writableSet` (built entirely from `share_keys` entries) are always empty, so its DFS `continue`s on every child and returns an empty result — the picker UI shows "No writable folders available" for every write-shared folder, regardless of actual write access.

**Why not fixed here:** `enumerateSharedSubtree` is architecturally the SAME kind of `share_keys`-based enumeration this plan's Task 1 intentionally retired (no live server-side fan-out exists). Fixing it "properly" requires a write-tree DFS equivalent of the write-chain walk this plan added to `moveInSharedFolder` — recursively unsealing each folder's own write-body to discover its writable children, rather than a single flat `share_keys` list. That is a materially larger SDK feature (a new traversal primitive), not a contained fix within `moveInSharedFolder`'s destination-key resolution, and this plan's `must_haves.truths` scoped the write-chain requirement specifically to move's *key resolution*, not the picker's enumeration.

**Confirmed:** `enumerateSharedSubtree` was ALREADY non-functional before this plan (Task 1's predecessor state had `fetchShareKeys` throw synchronously, which `SharedMoveDialog.tsx`'s `.catch()` turned into "Failed to load folder tree") — this plan changes the FAILURE MODE (empty list vs. error message) but does not newly break a previously-working picker.

**Recommended next step:** A dedicated follow-up plan should add a write-body DFS enumeration (walking `writeChildren` recursively from the seeded root writeKey, symmetric to `enumerateSharedSubtree`'s existing read-chain DFS) so the picker can show real writable destinations, and so `moveInSharedFolder`'s one-hop limitation (see `key-decisions`) can be lifted for genuinely nested destinations.
