# Phase 68.1 Plan 09: Owned File Write-Chain Client Wiring Summary

**`uploadFile` rewired onto the v3 file-Node chain (parent SealedChildRef + WriteChildRef from `fileReadKey`/`fileWriteKey`/`fileNodeId`), and `replaceFile`/`restoreFileVersion`/`deleteFileVersion`/`downloadFromIpns` implemented via a new client-side write-chain walk (`resolveFileWriteChainKeys`) and `sdk-core updateFileMetadata`/`resolveFileMetadata`/`downloadFileContent` — no `client.ts` stub throws remain.**

## Accomplishments

- `uploadFile` seals the v3 file Node's own `fileReadKey` (not the content `fileKey`) into the parent read-body via `addFilePointerToFolder`, and — when the parent already carries a real write-body — inserts a `WriteChildRef` for `fileWriteKey` via `sealChildWriteKey`, publishing both through the existing `Promise.allSettled` critical/non-critical batch-publish + folder-publish pattern (BYO pinFn override and duplicate-name guard preserved verbatim). Zeroes `fileReadKey`/`fileWriteKey` in `finally` (D-09 — this call site is their terminal owner).
- New private `resolveFileWriteChainKeys(folder, fileId)` walks an owned file's write chain: looks up the `SealedChildRef` by `ipnsName`, resolves the file's `PublishedNode` for its plaintext `id`/`kind`, unseals `fileReadKey` from the parent read-body and `fileWriteKey` from the parent write-body's matching `WriteChildRef` (by node UUID), then unseals the file's own current Node to recover `nodeGeneration`/`originalCreatedAt`. Returns the derived keys raw to the caller (ownership-transfer pattern: nulled locals on success, zeroed in `finally` only on a failure path).
- New private `maybeRepublishFolderForFileMigration` implements the "conditional folder publish only on `migratedIpnsPrivateKeyEncrypted`" behavior described in all three methods' JSDoc — since v3's `SealedChildRef` has no field to bump for a per-file migration marker, this instead threads the migrated key into the **parent folder's own** IPNS record TEE re-enrollment via `updateFolderMetadataAndPublish`'s existing `encryptedIpnsPrivateKey` param, republishing the folder's unchanged children. Always emits `folder:updated` from the current folderTree snapshot.
- `replaceFile`, `restoreFileVersion`, `deleteFileVersion` all now: `requireFolder` → `resolveFileWriteChainKeys` → `sdkCore.updateFileMetadata` (caller's pre-resolved `fileIpnsPrivateKey`/`currentMetadata`/`updates` per locked decision 2, plus the resolved write-chain fields) → `maybeRepublishFolderForFileMigration` → zero the derived keys. `deleteFileVersion` always publishes with `createVersion: false` and surfaces the caller's `deletedCid` alongside `prunedCids`.
- `downloadFromIpns` resolves `NodeContent` via `sdkCore.resolveFileMetadata` then decrypts via `sdkCore.downloadFileContent` (raw fileKey, GCM/CTR per `encryptionMode`), zeroing the recovered `fileKey` in `finally` (T-68.1-09-04) without touching the caller-owned `folderKey` parameter (D-09).
- Exported `downloadFileContent` and `UpdateFileContentParams` from the `sdk-core` barrel (`packages/sdk-core/src/index.ts`) — both existed in `file/index.ts` since 68.1-07 but were never re-exported, blocking Task 2/3's typed `client.ts` call sites.

## Decisions Made

- **`fileId` convention confirmed as `SealedChildRef.ipnsName`**, not the file Node's own UUID — matches the existing `deleteFromFolder`/`renameInFolder` `childId` convention used everywhere else in `client.ts`. `resolveFileWriteChainKeys` derives the node UUID internally from the resolved `PublishedNode`'s plaintext `id` field.
- **`migratedIpnsPrivateKeyEncrypted` reinterpreted for v3**: the pre-v3 JSDoc on all three methods described "bump the FilePointer's `modifiedAt` + `ipnsPrivateKeyEncrypted`" — fields that no longer exist on `SealedChildRef` under NODE-03's frozen 5-field set. Reinterpreted as a lazy migration of the **parent folder's own** TEE-wrapped IPNS key, persisted via `updateFolderMetadataAndPublish`'s pre-existing `encryptedIpnsPrivateKey` param (folder TEE re-enrollment) — the only structurally valid sink for this parameter under the v3 model. Documented as an assumption in the code; 68.1-13 or a dedicated TEE-migration plan is the natural place to confirm end-to-end.
- **`downloadFromIpns`'s `folderKey` parameter is actually the file Node's own `fileReadKey`**, not the parent folder's readKey — the plan preserved this exact signature verbatim (legacy naming carryover), so the parameter name was kept and documented inline rather than renamed.
- **`deleteFileVersion` always passes `createVersion: false`** to `updateFileMetadata` — deleting a past version prunes `currentMetadata.versions` (caller-resolved) without changing the live content descriptor, so folding a NEW version entry would be incorrect; the plan's own param type for this method omits `createVersion` entirely, confirming this reading.
- **Uploaded files without a real parent writeKey (legacy zero-fallback) upload read-only** (no `WriteChildRef` inserted) rather than throwing — matches `getWriteBodyParams`' existing preservation-only contract at every other owned call site (renameItem/deleteItem/uploadFile pre-existing pattern), rather than adopting `createFolder`'s (68.1-02) stricter fail-closed-on-no-writeKey behavior. Given this milestone is greenfield (no pre-v3 folders survive), this branch is effectively dead in practice but kept for defensive consistency.
