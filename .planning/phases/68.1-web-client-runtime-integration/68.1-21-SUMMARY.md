# Phase 68.1 Plan 21: GAP-4/GAP-5 Web-E2E Triage Summary

**Fixed the D-05 stale-record-rejection toast by making ReconcileStaleError direction-aware (network-behind-local now rejects immediately instead of retrying for 30s), and corrected the share-itemname-backfill seed helper's POST shape to the current CreateShareDto — while surfacing a new, deeper finding that the REQ-4 legacy-itemName-backfill feature the latter spec exercises is now structurally dead code (its `item_name` column was dropped, not renamed, by the node/v3 schema cutover).**

## Performance

## Accomplishments

- **GAP-4 fixed**: `ReconcileStaleError` now carries `localSequence`/`networkSequence`. `useMutationFailureUx`'s retry loop only retries when the network sequence is AHEAD of local (a genuine concurrent update elsewhere — SC#3/D-04); a network sequence BEHIND local is a stale/relay-replayed record and now gets the immediate D-05 `role="alert"` toast ("Stale data from server rejected.") via the same classifier path real folder mutations already use, never a 30s retry-then-exhaustion.
- **GAP-4 root cause identified**: the durable ROT-07 anti-rollback floor (`rotation-high-water.ts`) is bumped *pre-publish* using the just-resolved sequence, one step behind the client's own subsequent publish. A relay replay of the record from immediately before that publish therefore lands EXACTLY ON the floor (not below it), sailing through `enforceResolved` untouched and falling to the plain `ReconcileStaleError` equality check — which previously retried uniformly regardless of direction.
- **GAP-5 seed-shape fixed**: `share-itemname-backfill.spec.ts`'s legacy-seed helper now POSTs `recipientPublicKey`/`readDescriptorRef`/`rootNodeId`/`rootIpnsName` (matching the current `CreateShareDto`) instead of the retired `itemType`/`ipnsName`/`itemName`/`encryptedKey` shape, which 400'd under the API's `whitelist:true`/`forbidNonWhitelisted:true` `ValidationPipe`.
- **New Known Gap surfaced**: migration `1750000000000-ApiSchemaCutover` dropped the `shares` table's plaintext `item_name` column entirely — it was never renamed, just removed. `apps/web/src/services/share.service.ts`'s `toSentShare`/`toReceivedShare` now hardcode `itemName: ''` because the DTO no longer returns it, which means `shouldBackfill()` (`Boolean(row.itemName)`) is permanently `false` in production. The REQ-4 lazy-backfill feature this whole spec file exercises is currently unreachable dead code. Documented for a follow-up plan rather than fixed here (see Known Gaps).

## Known Gaps (surfaced, NOT fixed — exceeds this plan's "small wiring fix" scope)

### GAP-6: REQ-4 lazy-itemName-backfill feature is dead code post node/v3 schema cutover

**Symptom:** Even after this plan's GAP-5 seed-shape fix makes `POST /shares` return 2xx, `share-itemname-backfill.spec.ts` test 2's own `expect(seeded?.itemName).toBe(legacyItemName)` assertion (and tests 3, 5, 6's related plaintext-fallback/backfill assertions) will still fail, because the API can no longer return an `itemName` field at all.

**What's confirmed:**
- `apps/api/src/migrations/1750000000000-ApiSchemaCutover.ts` (a greenfield "node/v3 model" cutover) `DROP`s and recreates the `shares` table without any `item_name` column — only `item_name_encrypted bytea` survives (see the migration's own column-list comment at line 35, which already omits `item_name`).
- `apps/api/src/shares/entities/share.entity.ts` and `apps/api/src/shares/dto/create-share.dto.ts` confirm: no `itemName`/`item_name` field exists anywhere in the current schema or DTO surface — only `itemNameEncrypted`.
- `packages/api-client/src/models/sentShareResponseDto.ts` (generated from the live OpenAPI spec) confirms the response DTO has no `itemName` field.
- `apps/web/src/services/share.service.ts`'s `toSentShare`/`toReceivedShare` (lines 116, 132) hardcode `itemName: ''` — presumably patched to satisfy TypeScript after the DTO's `itemName` field was removed, rather than as a deliberate design choice.
- `shouldBackfill()` (line 89-93) is `if (!hasRecipientPubKey) return false; if (row.itemNameEncrypted) return false; return Boolean(row.itemName);` — since `row.itemName` is *always* `''` from the hardcoded mapping above, this predicate is now **permanently `false`** in production. `backfillSentShareItemNames` (called from `fetchAllSentShares` on every sent-shares load) therefore can never actually backfill anything — it is unreachable dead code.

**Why not fixed here:** Two possible resolutions exist, both out of this gap-closure plan's scope:
1. **Retire the feature + spec.** If no share row can ever have had a plaintext `item_name` (the column is gone, and it was dropped in a *greenfield* migration per the migration's own comment — "D-01 waiver — staging DB wiped on each deploy" — meaning there is no historical data to migrate either), then the entire REQ-4 lazy-backfill mechanism (`decryptItemName`'s plaintext-fallback branch, `shouldBackfill`, `backfillSentShareItemNames`, the `PATCH /shares/:id/item-name` client call, and this whole spec file) is vestigial and could be deleted.
2. **Redesign for the current schema.** If a "recipient doesn't yet have a decryptable display name" state should still exist (e.g. a share created without `itemNameEncrypted` at all — the DTO still marks it `@IsOptional`), the intended UX for that state needs a fresh design (what does the recipient see when `itemNameEncrypted` is null AND there's no plaintext fallback? Does the frontend derive the name by resolving the actual shared content via the read descriptor instead?) — this is a genuine product/security design decision, not a wiring fix, and reintroducing ANY plaintext name storage server-side would violate CLAUDE.md's zero-knowledge server rule.

**Recommended next step:** A dedicated follow-up plan (not 68.1-22, which is the exit-gate full-suite confirmation pass) should decide between the two options above. Until then, `share-itemname-backfill.spec.ts` will continue to fail from test 2 onward even with this plan's seed-shape fix applied — that failure is now an accurate signal of the real gap (dead backfill feature), not a wiring bug.
