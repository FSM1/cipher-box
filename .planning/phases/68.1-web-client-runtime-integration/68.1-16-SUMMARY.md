# Phase 68.1 Plan 16: createFolder TEE Enrollment + Bin-Restore Hardening Summary

**client.createFolder now enrolls new subfolders in TEE republish on first IPNS publish (encryptedIpnsPrivateKey/keyEpoch, ECIES-wrapped via wrapKey), closing the durable-registration gap behind the "logout to login makes subfolder navigation dead" repro; restoreFromBin now warns instead of silently re-linking a dead child record.**

## Accomplishments
- `client.createFolder`'s first IPNS publish (client.ts, previously the one owned first-publish call site omitting TEE enrollment) now computes `encryptedIpnsPrivateKey`/`keyEpoch` from `this.config.teeKeys` and passes them into `createAndPublishIpnsRecord`, mirroring `createSubfolder` (registration.ts:85-109) exactly
- Fail-closed guards (`teeKeys.currentPublicKey` missing/empty, `teeKeys.currentEpoch` not a positive integer) run BEFORE the `addToIpfs` upload, so malformed config never orphans an IPFS blob
- Confirmed (read-only, no code change) that the per-file mint path already enrolls: `createFileMetadata` (sdk-core/src/file/index.ts) has its own enrollment block, and `uploadFile`/`uploadFiles` in client.ts already thread `teeKeys: this.config.teeKeys` through (3 call sites total)
- Hardened `restoreFromBin`: after re-linking a restored `SealedChildRef` into the target parent, verifies the restored child's OWN IPNS record still resolves and emits a non-throwing `console.warn` if it does not — instead of silently presenting a dead, non-navigable folder as a successful restore
- Documented in code why `restoreFromBin` cannot re-mint the child's own record: bin entries never carry the child's `ipnsPrivateKey` by design (only `nodeReadKey` for re-sealing the parent link), so re-signing is structurally impossible there

## Decisions Made
- Enrollment block placed after `sealNode` (pure local crypto, no side effect) but strictly before the `addToIpfs` call — matches the "fail closed before any IPFS side effect" invariant used by `createSubfolder`/`publishEmptyRootNode`/`createFileMetadata`
- `restoreFromBin`'s resolve-check wraps `resolveIpnsRecord` in its own try/catch and never throws on either a null resolve or a resolve error — a warning is the correct signal because the re-link itself already succeeded and should not be rolled back for a downstream record-availability issue
- Did not add a dedicated unit test for the bin-restore warn path (out of Task 2's `<action>` scope, which only names it as a source-level hardening + SUMMARY documentation item); relied on the full existing `bin.test.ts` suite (21 tests) passing unchanged as a regression guard
