<objective>
Close the deep-shared-write gap (WEB-03) documented in `68.1-29-SUMMARY.md`: a recipient with a write grant cannot write inside a NESTED subfolder of a write-shared tree because the web seeds `SharedFolderState.writeKey` only at the share root (`resolveSharedRootWriteKey`, 68.1-20 scope boundary). Descending into a subfolder re-seeds that depth with a zero writeKey, so `uploadToSharedFolder`/`createSharedSubfolder` fail GCM auth on the subfolder's own write-body — writable-shares 8.2 times out at 30s and 8.3+ cascade-skip.

The fix mirrors the OWNED-tree recovery `dfsFindFolder` already ships (client.ts:820-894) and the read-side descent `enumerateSharedSubtree` (68.1-27) walks: during shared-subtree descent, derive each nested folder's writeKey from its parent's write-body chain — find the child's `WriteChildRef.writeKeySealed` (keyed by the child node UUID `childId`) in the parent's unsealed write-body, unseal it under the parent writeKey with the AAD triad (childId / child kind / childRef.generation), validate it against the child's own write-body, and seed it into the recipient's shared folder state.

The subfolder's own `ipnsPrivateKey` does NOT need separate recovery: `buildSharedWriteContextFromState` (client.ts:3452) derives the publish key from inside the unsealed write-body (`unsealParentWriteBody`, shared-write.ts:202), so seeding a real `writeKey` is the ONLY change required for a subfolder write to publish under the subfolder's own IPNS key.

Purpose: recipients gain genuine deep-tree write access (upload/mkdir/rename at any depth), completing WEB-03's recipient write flows.
Output: one new SDK resolver + its unit suite, one web navigation wiring change, confirmed green by a single-file live re-run of `writable-shares.spec.ts`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| recipient browser -> shared write-body chain | The recipient unseals parent/child write-bodies client-side to recover per-subfolder writeKeys; a wrong or over-broad recovery could grant unintended write capability. |
| in-memory key buffers -> logs / lingering heap | Recovered writeKeys are 32-byte AES secrets that must not leak via logs or un-zeroed buffers. |
| write plane (UUID childId) vs read plane (ipnsName) | Conflating the two identifier spaces could seal/unseal against the wrong node. |
