<objective>
Close the D-02 wiring gap: the kind cache (`resolveKinds`/`getKind`/`setKind` in `apps/web/src/lib/kind-cache.ts`) and the cache-backed `isFileRef`/`isFilePointer` guards are built in 68.1-04, but no task ever calls `resolveKinds(children)` on a folder-load / navigation render path. Without this the cache stays permanently empty, every child defaults to "folder" (the folder-safe miss default), files are never recognized (no preview/download/streaming/file context menu), and every file-touching web-e2e spec fails — breaking WEB-01 and cascading through the exit gate.

This plan invokes `resolveKinds(children)` on EVERY owned and shared folder-load / navigation render path before the file browser lists children, and ensures the list re-renders once the cache is populated (so a row that first rendered folder-safe flips to a file row).

Purpose: make the D-02 kind cache actually load, so file-vs-folder discrimination works at runtime.
Output: `resolveKinds` invoked on the owned nav hook + owned folder-store subscription and on the shared nav handlers + shared projection subscription.

## Why this is a separate plan (not folded into 04 or 05)

- The owned render path (`useFolderNavigation.ts` + `folder.store.ts`) is owned by no existing plan; 68.1-04's blast-radius text already asserts "the owned folder-load / navigation path calls resolveKinds(children)" but ships no task doing it. This plan is that task.
- `resolveKinds` is defined in 68.1-04 (wave 3); the shared nav handlers are wired in 68.1-05 (wave 2). Wiring both render paths must run in a wave at or after both — wave 4 — so `resolveKinds` exists and both nav paths are already implemented. Folding into 04 would overload it (8 files / 3 tasks) and folding the shared side into 05 would force 05 past wave 2. A dedicated wave-4 plan keeps every existing plan and wave unchanged.
</objective>
