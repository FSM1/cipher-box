# Phase 68.1 Plan 05: Shared-Folder Read Navigation Summary

**All five shared-folder navigation handlers (navigateToShare, navigateToSubfolder, navigateUp, navigateToBreadcrumb, downloadSharedFile) wired to the Node v3 read-chain, including single-file-share and write-permission edge cases.**

## Performance

- **Duration:** ~40 min
- **Started:** 2026-07-02T13:04:00Z
- **Completed:** 2026-07-02T13:44:00Z
- **Tasks:** 2 (combined into one commit — see Deviations)
- **Files modified:** 1

## Accomplishments

- `navigateToShare(shareId)` ECIES-unwraps `readDescriptorRef` (hex-decoded), resolves + unseals the share root Node, and either renders its children (folder root) or switches to `currentView: 'file'` for single-file shares
- `navigateToSubfolder(folderId, folderName)` derives the child readKey via `unsealChildReadKey` using the parent-mirror `childRef.generation` (never the child's own envelope generation), unseals the child Node, and pushes the pre-descent state onto the nav stack
- `navigateUp()` / `navigateToBreadcrumb(crumbIndex)` restore prior levels entirely from the in-memory nav stack (no network round-trip), zero every discarded folderKey, and re-seed the SDK's `sharedFolderTree` for the restored depth
- `downloadSharedFile(item)` walks the full grant-to-leaf chain via sdk-core's `navigateReadChain` (bridging the hex `readDescriptorRef` to its base64 contract), fetches the CID, and decrypts with the leaf's raw fileKey (base64 iv, GCM/CTR by `encryptionMode`), zeroing the fileKey after use
- Write-permission folders resolve their IPNS signing key via the existing `getShareKeys` `folder-ipns` fan-out (unchanged mechanism, reused not reinvented)
- All `'behind-retry'` / `'revoked'` `NavigateResult` discriminants surface as user-facing `setError` messages rather than unhandled throws

## Decisions Made

- Custom low-level read-chain walk in the web layer for folder navigation (Task 1) since `navigateReadChain` cannot render an intermediate folder (it hard-requires the walked-to node be `kind: 'file'`) — see `key-decisions` in frontmatter for full rationale
- `downloadSharedFile` (Task 2) does use `navigateReadChain` directly, bridging the hex `readDescriptorRef` DTO format to the base64 format `navigateReadChain` expects
- Single-file shares detected via `rootNode.kind === 'file'` in `navigateToShare`, switching to `currentView: 'file'` to activate `SharedFileBrowser.tsx`'s pre-existing (previously unreachable) download effect
- `writeKey` for `NodeWriteBody` unsealing left at the zero-placeholder default; `ipnsPrivateKey` for write shares resolved via the existing `getShareKeys` `folder-ipns` mechanism

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] hex/base64 encoding mismatch for `readDescriptorRef` passed to `navigateReadChain`**

- **Found during:** Task 2 (`downloadSharedFile`)
- **Issue:** `ReceivedShare.readDescriptorRef` (web) is hex-encoded (API DTO contract — `apps/api/src/shares/shares.service.ts` does `Buffer.from(dto.readDescriptorRef, 'hex')` on write and `.toString('hex')` on read), but sdk-core's `navigateReadChain` internally calls `base64ToBytes(params.readDescriptorRef)` matching its own `issueReadGrant`'s `bytesToBase64(wrapped)` output — a real format divergence that would silently corrupt the ECIES unwrap if passed through unmodified
- **Fix:** Added a local `bytesToBase64` helper; `downloadSharedFile` hex-decodes `share.readDescriptorRef` then re-encodes to base64 before calling `navigateReadChain`
- **Files modified:** apps/web/src/hooks/useSharedNavigationActions.ts
- **Verification:** `pnpm --filter @cipherbox/web exec tsc -b` clean; logic traced against `packages/sdk-core/src/share/navigate.ts` and `apps/api/src/shares/shares.service.ts`
- **Committed in:** d5791f499

**2. [Rule 3 - Blocking] `navigateReadChain` unusable for folder rendering (Task 1)**

- **Found during:** Task 1 (`navigateToShare`/`navigateToSubfolder`)
- **Issue:** The plan's `key_links` names `navigateReadChain` as the primitive for shared folder navigation, but the function hard-requires the walked-to node be `kind: 'file'` (throws `'revoked'` otherwise) — it cannot be used to render a folder's children, only to reach a file leaf
- **Fix:** Implemented a parallel low-level walk directly in the web hook, reusing the same exported building blocks `navigateReadChain` itself uses internally (`resolveIpnsRecord`, `fetchFromIpfs` from sdk-core; `unsealNode`, `unsealChildReadKey` from core; `unwrapKey` from crypto) via a new local `fetchPublishedNode` helper mirroring sdk-core's own (non-exported) helper of the same name
- **Files modified:** apps/web/src/hooks/useSharedNavigationActions.ts
- **Verification:** `pnpm --filter @cipherbox/web exec tsc -b` clean; algorithm cross-checked step-by-step against `navigateReadChain`'s own documented steps 1-5 (ECIES unwrap, resolve+fetch, behind-retry check, unseal, generation-source-rule hop)
- **Committed in:** d5791f499

**3. [Rule 2 - Missing Critical] Single-file share routing**

- **Found during:** Task 1 (`navigateToShare`)
- **Issue:** `SharedFileBrowser.tsx` already contains an effect (lines 417-446, pre-existing, not part of this plan's file scope) that fires on `currentView === 'file'` and downloads a synthetically-constructed root-referencing `SealedChildRef` — but nothing in the codebase ever set `currentView` to `'file'`, since `navigateToShare` unconditionally threw. Without detecting `rootNode.kind === 'file'`, a single-file share would either crash (treating a file Node as a folder, `.children` undefined) or silently render as an empty folder
- **Fix:** `navigateToShare` checks `rootNode.kind === 'file'` after unsealing the root and switches to `currentView: 'file'` (zeroing the now-unneeded root readKey) instead of the folder path; `downloadSharedFile` special-cases `p.currentView === 'file'` to use an empty `path: []` (root IS the leaf) matching `navigateReadChain`'s documented root-is-leaf contract
- **Files modified:** apps/web/src/hooks/useSharedNavigationActions.ts
- **Verification:** `pnpm --filter @cipherbox/web exec tsc -b` clean; traced against `SharedFileBrowser.tsx`'s existing effect and synthetic-ref construction (`ipnsName: shareItem.share.ipnsName`, matching `rootIpnsName`)
- **Committed in:** d5791f499
