# Phase 68.1 Plan 06: Owned File Preview + Streaming Summary

**`useFilePreview` now resolves+downloads owned files via `resolveFileMetadata`/`downloadFileFromIpns` into a Blob object URL, `useStreamingPreview` registers CTR media with the existing `decrypt-sw.ts` Service Worker for ranged streamed decryption, and `DetailsDialog`'s stale phase-63 comments are gone — no throwing/error stubs remain in any file this plan touched.**

## Accomplishments

- `useFilePreview` (`apps/web/src/hooks/useFilePreview.ts`) replaced the error-string stub with a real flow: on `open`+`item`+`folderKey`, calls `downloadFileFromIpns({ fileRef: item, folderKey })` (68.1-04), wraps the decrypted `Uint8Array` in a `Blob` (never `.buffer`, per apps/web/CLAUDE.md), and exposes an object URL revoked on close and on unmount. `loading` is now a real state (previously hard-coded `false`).
- `DetailsDialog` (`apps/web/src/components/file-browser/DetailsDialog.tsx`) had its two stale `TODO(phase 63)` comments removed/rewritten — the file's `resolveFileMetadata` wiring already landed in 68.1-04; the remaining comments now accurately describe that the folderStore-membership heuristic is intentionally left standing until 68.1-14 wires real `Node.kind` discrimination (`resolveKinds`).
- `useStreamingPreview` (`apps/web/src/hooks/useStreamingPreview.ts`) fully implemented: resolves `NodeContent` via `resolveFileMetadata`, and when `encryptionMode === 'CTR'` converts the raw fileKey + base64 iv to the hex contract `decrypt-sw.ts` expects, registers the stream (`registerStream`), and exposes `/decrypt-stream/{ipnsName}` as `streamUrl`. Non-CTR files resolve with `isCtr: false` so callers fall back to the GCM blob-URL path (`useFilePreview`), matching the existing caller gating in `AudioPlayerDialog`/`VideoPlayerDialog`. Listens for the SW's `fetch-progress`/`fetch-complete`/`fetch-error` postMessages (scoped to the active registration) to drive `decryptProgress`. `handleDownload` now decrypts the full file via `downloadFileFromIpns` and triggers a browser download instead of throwing. Stream registration is torn down both when the previewed item changes and on unmount, preventing stale SW registry entries.

## Decisions Made

- **`useFilePreview` ignores `shareId` for the download path.** `folderKey` passed in by the caller is already the correct readKey for the `SealedChildRef` being previewed — owned or shared — matching the precedent 68.1-04 established for `DetailsDialog`'s `resolveFileMetadata` call (no shareId-specific branching there either). `shareId` stays in the prop type for caller API compatibility (all 4 preview dialogs pass it) but is unused inside the hook.
- **`useStreamingPreview` re-resolves `NodeContent` independently rather than sharing a resolve-once cache with `useFilePreview`.** Matches the existing caller pattern already in place: `AudioPlayerDialog`/`VideoPlayerDialog` gate `open` on both hooks specifically to avoid a redundant blob fetch while the CTR check resolves (see their own "Gate on !streaming.loading" comments, unmodified by this plan). Introducing a shared cache was out of this plan's 2-file scope.
- **Raw fileKey is zeroed immediately after hex conversion, before `registerStream`, not "when the stream terminates."** The hook's own `resolveFileMetadata` call is the terminal owner of that unsealed key material (D-09) — holding decrypted key bytes in memory longer than necessary (until stream teardown, which could be minutes later) is worse practice than zeroing as soon as the hex string needed by the SW contract has been derived.
- **`DetailsDialog`'s `isFolderHeuristic` (folderStore membership) left functionally unchanged.** Replacing it with real `Node.kind` discrimination via `kind-cache.ts`'s `resolveKinds` is explicitly owned by 68.1-14 (per 68.1-04's SUMMARY "Next Phase Readiness"); this plan's task only called for removing the stale phase-63 comments referencing it, not rewiring the heuristic itself.
