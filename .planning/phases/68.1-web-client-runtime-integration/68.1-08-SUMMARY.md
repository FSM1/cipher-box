# Phase 68.1 Plan 08: Shared File Update + Intra-Share Move Client Wrappers Summary

**`client.updateSharedFile` walks the shared write-chain (parent write-body → WriteChildRef → child write-body) to resolve file keys before republishing, and `client.moveInSharedFolder` resolves destination keys from `share_keys` + the moved item's readKey via the read-chain before delegating to the fully-implemented `shareOps.moveInSharedFolder` (dest-before-src publish).**

## Accomplishments

- `updateSharedFile(shareId, { filePointer, newContent, getFileIpnsKeyFn })` unseals the parent shared folder's write-body, walks its `writeChildren` to find the file's `WriteChildRef` (matched by UUID, never `ipnsName`), recovers the file's `writeKey`, then unseals the file's own current node to obtain `ipnsPrivateKey` + `originalCreatedAt` + `originalVersions` — all forwarded to `shareOps.updateSharedFile` along with a freshly-derived `fileReadKey`. `getFileIpnsKeyFn` is retained as a fallback for `fileIpnsPrivateKey` only, per the existing signature. Emits a file-only `sharedFolder:updated` (unchanged children/sequence) mirroring `refreshSharedFolder`'s pattern. All derived keys are zeroed in `finally`.
- `moveInSharedFolder(shareId, { itemId, destFolderId, destIpnsName, vaultPrivateKey, getShareKeysFn })` validates presence of both `share_keys` `folder` and `folder-ipns` entries for the destination BEFORE any unwrap (T-49-01 fail-closed guard), unwraps `destFolderKey`/`destIpnsPrivateKey` via `unwrapKey`, loads fresh destination children via `loadFolderMetadata` (never a cached ref), resolves the moved item's UUID/kind (plaintext on its `PublishedNode` envelope) and re-derives its `readKey` under the source folder's key, then builds src/dest `SharedWriteContext`s and delegates to `shareOps.moveInSharedFolder` (publishes destination before source). Adopts only the SOURCE result into `sharedFolderTree`.
- Extracted `buildSharedWriteContextWithOverrides` from `buildSharedWriteContextFromState` (behavior-preserving) so both the current shared-folder state and the one-off destination context in `moveInSharedFolder` share the same `addToIpfsFn` (BYO-pinning-aware)/`publishNodeFn` seams.
- Both stub throws (`not implemented — phase 65 (write-chain: updateSharedFile)` and `not implemented — phase 63 (navigation: moveInSharedFolder)`) removed; plan's `<verification>` grep assertions both pass.

## Decisions Made

- `getFileIpnsKeyFn` is a fallback ONLY for `fileIpnsPrivateKey`, never for `fileWriteKey` — the write-chain walk is the sole source of a real AES writeKey; if no `WriteChildRef` exists for the file, the operation fails closed (a write-body republish cannot happen without a writeKey, regardless of what the fallback callback returns).
- `moveInSharedFolder`'s destination key resolution is a direct adaptation of the pre-refactor Phase-49 implementation (`share_keys` `folder` + `folder-ipns` entries, ECIES-unwrapped via `vaultPrivateKey`) — the `folder-ipns`-wrapped 32 bytes are now passed as `SharedWriteContext.writeKey` since the new write-body model has no separate `ipnsPrivateKey` field on the context. This is a documented assumption (not independently verifiable from static analysis) that `68.1-13`'s web-e2e move spec must confirm: if `folder-ipns` no longer wraps a value compatible with the destination's actual write-body seal, the operation fails closed with an AEAD auth error inside `shareOps.moveInSharedFolder`'s internal `unsealParentWriteBody` call rather than corrupting state.
- `moveInSharedFolder` reuses the CID `loadFolderMetadata` already resolved (`destMeta.cid`) to fetch the destination's raw `PublishedNode` via `fetchFromIpfs`, avoiding a second `resolveIpnsRecord` round trip for the same content-addressed data.

## Issues Encountered
