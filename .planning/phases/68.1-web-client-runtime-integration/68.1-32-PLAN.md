Close the last undispositioned WEB-03 failure before phase 68.1 exit: writable-shares.spec.ts test 10.3 ("Bob opens the write-shared file and can edit it"). A recipient of a DIRECT single-FILE share (root `kind: 'file'`) currently cannot open the file in the text editor — `SharedFileBrowser.tsx`'s auto-open effect synthesizes a `SealedChildRef` with `readKeySealed: ''` (a pre-existing `// TODO(phase 63)` stub) and `navigateToShare` sets `folderKey: null` for a single-file root, so `TextEditorDialog`'s shared-load path (`downloadFileFromIpns({ fileRef, folderKey })`) recovers nothing and the textarea loads empty. This plan wires the single-file-share editor route to the already-proven node/v3 read-chain (READ) and adds the missing single-file WRITE seam (SDK), mirroring 68.1-29's `a6db25594` (shared text-file read via the node/v3 chain) and 68.1-30's `resolveSharedSubfolderWriteKey` (one-hop write-chain, validate-before-trust, fail-closed, terminal-owner zeroing).

|----------|-------------|
| recipient browser → CipherBox API | Untrusted relay for IPNS resolve + IPFS fetch/publish; server is zero-knowledge, never sees plaintext or unwrapped keys |
