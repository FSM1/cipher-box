<domain>
## Phase Boundary

Wire the v2.0 web app + `CipherBoxClient` runtime to the already-shipped `node/v3` read-chain (Phase 63) and write-chain (Phase 65) primitives, replacing all 46 `not implemented — phase 63/65` stubs so the app runs end-to-end. The exit gate is the **full `tests/web-e2e` Playwright suite passing** — the first runtime validation of Phases 62–68 since Milestone 4 began.

In scope: web hooks/services/components + `client.ts` wrappers for login/root-init, navigation, owned+shared file read (metadata/download/preview/streaming), owned+shared file write (upload/create/replace/update/versions), delete→bin re-link, move, and sharing (grant/upgrade/invite create+claim); plus building the **owned file write-chain in sdk-core** (`createFileMetadata`/`updateFileMetadata`, copied from `shared-write.ts`).

Out of scope: FUSE/WinFsp clients (Phase 69); Tier-3 capability layer; any new codec/crypto design or change to the frozen `SealedChildRef`/`Node` read schema.
</domain>

<decisions>
## Implementation Decisions

### Scope + approach (locked)
- **D-01**: This phase is runtime **wiring to existing sdk-core primitives**, not a re-design. The ONE genuine build is the owned-file write-chain in `packages/sdk-core/src/file/index.ts` (`createFileMetadata`, `updateFileMetadata`) — implemented by copying `shared-write.ts` `uploadToSharedFolder`/`updateSharedFile`. No new codec, no crypto changes, frozen read schema unchanged.
- **D-04 (sequencing)**: Read-chain wiring lands before write within the phase — many `phase 65`-labelled stubs depend on read-chain subtree walks / key resolution. Plan waves: read foundation (`ensureFolderLoaded`, root-init, nav, owned read) → owned file write-chain (sdk-core build) → owned+shared write wiring (versions, bin collect, share/invite, shared write ops) → web-e2e enablement/triage.
- **D-05**: Delete `packages/sdk/src/reencrypt.ts` (obsolete — no callers; content self-seal removes re-encrypt-on-move). Do not implement it.
- **D-06**: ZERO `apps/web/src/*.spec.ts` files (SC#5 doctrine) — hoist testable logic to SDK (Vitest), prove web behavior via web-e2e Playwright only.
- **D-07 (exit gate)**: The full `tests/web-e2e` suite (all specs) passes locally against the standard stack; a subset pass is not acceptance.
- **D-09 (zeroization)**: Follow the terminal-owner rule — zero minted/derived keys on success + in catch/finally; never zero caller-supplied buffers (see `shared-write.ts` `didDeriveWriteKey`).

### Open design decisions — planner MUST resolve each with a recommendation (for user review in the plan)
- **D-02 (kind discrimination)**: `SealedChildRef` has no `kind`, so the file browser can't distinguish file vs folder without a per-child network hop (`fileTypes.ts:137,145` throw). Choose and justify: lazy-resolve+cache kind (no schema change), resolve+cache at folder-load, or carry kind in in-memory `FolderState` at create time. The frozen read schema must NOT change.
- **D-03 (owned FolderState write model)**: owned `FolderState` (`types.ts:164`) is read-chain-only (no `writeKey`/`publishedNode`) while shared `SharedFolderState` (`types.ts:205`) carries the write-body model. Owned file write needs one resolved: extend the owned model to the write-body model (clean copy of shared, wider blast radius) vs thread the file `ipnsPrivateKey`/writeKey read-chain-only. Pick, justify, and scope the blast radius.

### Claude's Discretion
- Wave/plan decomposition and granularity (respecting D-04 sequencing and shared-file serialization in `client.ts`).
- Which quick-win wirings to batch (e.g. `useSharedWriteOps.renameItemHandler` is trivial — client method exists).
</decisions>
