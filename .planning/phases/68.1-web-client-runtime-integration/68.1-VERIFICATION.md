### Root cause: cross-device write-plane clobber (conflict-detection 219; suspected shared root for writable-shares 3.2 / sharing-workflow 7.3)

Evidence-backed chain, high confidence:

1. The cold-load path (`ensureFolderLoaded` DFS) never populates `FolderState.writeKey` — it stays zeroed after a fresh login.
2. `getWriteBodyParams` (client.ts:669) fail-opens to `{}` on a zero writeKey, so a second device's upload publishes a folder record with **no write-body at all** (D-03 zero-key fallback) — silently erasing every WriteChildRef from the wire. This is the same `ensureFolderLoaded` under-wiring class as the known ROT-07 gap.
3. Pre-`814ea642d`, device A never noticed: its stale local `metadata.writeBody` mirror still held the WriteChildRef, so saves passed while the wire was already clobbered. The new network refresh (correctly) adopts the fresh record; the wiped write plane surfaces; `getWriteBodyParams` falls through to the on-wire record (`writeSealed` absent → `[]`) and the editor save fails closed with "not write-capable".

`814ea642d` exposed this pre-existing defect; reverting it would re-hide, not fix. The fix is to wire write-plane recovery into the cold-load path (unseal child writeKeys from the parent write-body chain during DFS; root uses `internalRootWriteKey`), and to make `refreshFolderStateFromNetwork` preserve the local `metadata.writeBody` when it unseals without a writeKey (never adopt a write-plane-less view over a populated mirror).
