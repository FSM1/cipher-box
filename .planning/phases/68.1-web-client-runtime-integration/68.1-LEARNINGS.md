# Phase 68.1 — Learnings

Durable, codebase-specific learnings mined from Phase 68.1 (web client runtime
integration onto the node/v3 read+write chain). Sourced from the round-3
VERIFICATION, the SECURED-107/107 SECURITY register, the VALIDATION audit,
`deferred-items.md`, the ship-phase follow-up todos, and the ship-pass commit arc
(`origin/main..HEAD`). All entries dated 2026-07-04.

The phase wired the v2.0 web app end-to-end (login/root-init, navigation,
upload/download/preview/stream, versions/bin, sharing) across 33 plans plus
gap-closure rounds. The dominant defect class throughout was the **v2→v3
write-plane clobber**: a fresh device or concurrent writer publishing a record
that erases another writer's `WriteChildRef`.

---

## Decisions

### 2026-07-04 — Fix-now vs defer is decided at the exit gate, per-residual

At the 68.1-29 exit gate the human dispositioned each residual failure individually
rather than blanket-deferring. `writable-shares` 10.3 (single-file-share editor)
and 10.4 (owner kind-cache read-back race) were chosen to FIX (executed as 68.1-32 /
68.1-33), while two others were deferred with recorded overrides. When closing a
phase, drive each open spec to an explicit fix/defer decision — do not fold a
fixable gap into a deferral bucket. The two recorded overrides live in the
VERIFICATION frontmatter (`overrides:`), which is the audit-of-record for "SC#5
passed modulo deferrals."

### 2026-07-04 — recovery.spec.ts and rotation SC-4 were deferred; the code mitigation for SC-4 still shipped

`recovery.html` only parses legacy v2 vault blobs; the app has produced node/v3
since Phase 62, so `recovery.spec.ts` cannot pass and porting the tool is its own
feature plan (todo `2026-07-03-port-recovery-tool-to-v3-vault-format.md`). The
rotation-durability SC-4 relay-replay assertion is deferred because the simulation
is unreachable past the API's DB-canonical resolve — but note the *code* mitigation
(durable floor `enforceResolved` at ipns.service.ts:224 + the D-05 "Stale data from
server rejected." toast) IS present and exercised by SC-1..3. A deferred *test* is
not the same as an absent mitigation; keep them distinct in the security register.

### 2026-07-04 — GAP-6: dead plaintext-name backfill removed; owner display uses create-time projection

The plaintext item-name backfill endpoint (`shouldBackfill`/`updateItemName`) was
deleted rather than kept as a compat path. Item names are `itemNameEncrypted`
end-to-end; the owner cannot decrypt a recipient-wrapped name, so the owner-side
display intentionally uses a create-time projection (accepted risk AR-68.1-08). When
a zero-knowledge constraint makes a field un-recoverable on one side, project it at
write time — don't reach for a server-side plaintext mirror.

## Lessons

### 2026-07-04 — CAS-merge / 409 must merge BOTH planes, or it silently drops a concurrent writer

This is the headline lesson and the exact residual instance of the milestone's core
defect that the ship pass caught (commit `bdd0ecb3e`). On a 409 conflict,
`publishWithCas` merged only the read-body and resealed the write-body from the
**stale closure `writeChildren`** — `decodeRemote` never unsealed the remote
write-body. Result: a concurrent writer's `WriteChildRef` was dropped, so the child
stayed readable but lost write capability. The fix: `decodeRemote` now unseals the
remote write-body, and the merge **unions `writeChildren` by `childId` (add-only,
remote wins)**.

Rule for this codebase: any CAS/409 conflict merge, network-refresh adoption, or
republish path must reconcile the write-body by unioning `WriteChildRef`s keyed on
node UUID — never reseal the write-body from an in-memory closure that predates the
conflict. Grep the write plane for reseal sites whenever you touch publish logic.

### 2026-07-04 — getWriteBodyParams D-03 fail-open can seal an EMPTY write-body on a transient resolve miss

Distinct from the intended read-only-device fallback (zero writeKey → no write-body).
Here the device HAS the writeKey, but a transient IPNS resolve miss returns
`writeChildren: []`; if the folder then republishes it seals an empty write-body,
dropping the entire write chain. The bug is duplicated verbatim in
`client.ts:669` and `bin/index.ts:72`, so it must be decided and fixed
**holistically in both** (flipping one diverges them). Options captured in todo
`2026-07-04-getwritebodyparams-transient-resolve-miss-drops-write-chain.md`:
fail-closed (throw/retry when a real writeKey is present but the resolve missed), or
preserve the last-known local `writeChildren` mirror (mirroring the 68.1-23
network-refresh preservation at client.ts:1121-1128). Still open.

### 2026-07-04 — D-09: a callee must never zero a caller-owned buffer; zero only at the terminal owner

Reaffirmed across the phase and re-hit during ship (`7f2f827cf`). Recovered keys are
cloned from tree-owned buffers via `new Uint8Array(...)` (e.g. client.ts:974) and the
tree-owned SOURCE is never zeroed; `vaultPrivateKey` / `recipientPrivateKey` are
caller-owned and the SDK never zeroes them. Minted/derived keys are `fill(0)`-ed in a
`finally` at the function that owns them (download.service.ts:135, file/index.ts:527,
client.ts:3979). Getting this wrong is not theoretical — a prior milestone's
over-zeroing broke 48/89 E2E tests. When adding a write/read path, ask "who minted
this buffer?" and only zero if the answer is "this function."

### 2026-07-04 — CI does NOT run apps/web unit tests — web `.test.ts` files can rot silently

`ci.yml`'s unit-test job covers api, crypto, core, sdk-core, sdk, api-client only;
`@cipherbox/web` is gated exclusively by Playwright web-e2e. A broken web `.test.ts`
never turns CI red. Concretely, `apps/web/src/services/__tests__/ipns.service.test.ts`
is byte-identical to origin/main and crashes at module-load (incomplete
`@cipherbox/api-client` mock missing `createAxiosInstance`), so a SECURITY-relevant
IPNS-signature fail-closed contract has zero protection today (todo
`2026-07-04-fix-broken-ipns-service-unit-test-mock.md`). Implication for this repo:
keep security-critical logic in a CI-covered package (SDK / sdk-core with Vitest);
do not rely on an `apps/web` unit test to gate anything. Zustand store logic
(`folder.store.test.ts`) is the one web unit surface that IS covered via the web
vitest `include`, but the include is `*.test.ts` only — `.spec.ts` is silently
skipped.

### 2026-07-04 — Rebuild sdk-core/sdk dist BEFORE typechecking a consumer

`apps/web`'s `tsc -b` checks the BUILT `packages/*/dist`, not source. After any
sdk/sdk-core API change you must rebuild those dists first or the web typecheck reads
a stale surface and either false-passes or false-fails. The VALIDATION sampling map
codifies this: "tsc -b for web-only wiring (sdk-core/sdk dist rebuilt first)." Same
applies before running sdk-e2e, which imports built dist.

### 2026-07-04 — The v2→v3 cutover silently dropped behavior that the v2 path had

`createFolder` had lost the duplicate-sibling-name check that `uploadFile` kept — the
cutover dropped it for folders while files retained it (fixed in `3f2c55207`). When
wiring a v3 path that replaces a v2 one, diff the two paths for guards/validation the
old path enforced and the new one silently lost. Parity gaps between sibling
operations (folder vs file, single vs batch) are a recurring source of these.

## Patterns

### 2026-07-04 — Write plane keyed by node UUID (`childId`), read plane keyed by `ipnsName`

The single most load-bearing identifier discipline in the write chain. `WriteChildRef`
is looked up by `wc.childId === child.published.id` (the node UUID), never by the
ipnsName param; `SealedChildRef` is keyed by `ipnsName`. Conflating the two seals or
unseals against the wrong node. Any shared-write delete/move/update must thread BOTH:
the child node UUID in the write body and the ipnsName in the read body. `moveItem`
returns a `movedRef` (a `SealedChildRef` keyed by ipnsName, with no `id` field) —
callers that expect an `id` will break.

### 2026-07-04 — sdk-e2e v2→v3 modernization pattern (restoring the cross-package publish gate)

The ship pass un-quarantined 11 D-01 stub-era suites to 100/101 green (`23c384296`).
The mechanical shape of the port, reusable for the remaining work and any new suite:

- Read plane is keyed by `ipnsName` (not the v2 numeric/`id` key).
- Fixtures must publish a real root Node with a **seeded writeKey** (mirror the
  68.1-25 web-e2e `createTestAccount`); a v2-style vault with no write capability
  trips the v3 write-capability gate on every mutation (`client.ts:1391` "has no
  writeKey — cannot mint an owned subfolder").
- `createFolder` self-registers — do NOT call `registerFolder` again afterward; the
  redundant `registerFolder` zeroed the writeKeys and broke subsequent writes.
- First publish embeds sequence baseline `1` (strict gate rejects seq≠1).
- Use current share/invite DTOs and the `movedRef` return shape.

Expect real per-suite rework, not a mechanical un-skip. sdk-e2e is the only suite
exercising a real client→API IPNS round-trip, so restoring breadth here is the true
cross-package gate (todo `2026-07-03-reenable-quarantined-sdk-e2e-suites-on-v3.md`).

### 2026-07-04 — Kind cache is fire-and-forget with a folder-safe default; warm it in EVERY projection sink

`SealedChildRef` carries no `kind` field (NODE-03); the UI reads a memoized kind cache
(`kind-cache.ts`) whose miss defaults folder-safe (renders `[DIR]`, hides the file-only
"Edit" affordance). Because the resolve is fire-and-forget (D-02), a reload-then-open
within a single test races the async settle. The 68.1-33 fix warms the cache
(`await resolveKinds(...)`) before projecting children in ALL THREE owner-side sinks —
`folder.store.ts` `subscribeToSdk`, `useFileBrowserActions.ts:145` `handleSync`, and
`folder-helpers.ts:35` `resyncFolder` — using a hybrid: sync fast-path when
`allKindsCached`, await-on-miss with a post-await sequence guard. If you add a fourth
inserter that bypasses the SDK event, it must warm the kind cache too or file rows
mis-render as folders.

### 2026-07-04 — Folder state lives in BOTH the Zustand store and the SDK folderTree; guard against blanking

Projected state must never be blanked or rewound by a stale/empty/out-of-order event.
The store uses a sequence-aware empty-over-populated guard (folder.store.ts:228-238;
IPNS `sequenceNumber` is the clock). Reconcile the SDK `folderTree` before sdk-core
mutations, and preserve the local write-body mirror when refreshing from the network
without a real writeKey (client.ts:1121-1128). A synchronous store fast-path still
needs the stale-sequence guard (added in `7f2f827cf`).

### 2026-07-04 — Single-file-share write seam is grant-descriptor-keyed with no parent write chain

`updateSharedSingleFile` (client.ts:3891) recovers readKey/writeKey directly from the
ECIES grant descriptors (no parent write chain to walk), validates-before-trust
(`unsealNode` never caught), and publishes to the file's OWN IPNS at
`fileSequenceNumber + 1n`. Transport seams (`buildWriteTransportSeams`, client.ts:3580)
are shared with the folder write path. The web wiring is null-`folderKey`-tolerant
(`TextEditorDialog.onLoadSharedFileContent`) and gated on `currentView === 'file'` in
`SharedFileBrowser`. This is the template for any "leaf resource shared directly, no
containing folder" write.

## Surprises

### 2026-07-04 — A "redact preview" helper was rendering RAW private-key bytes

CodeRabbit caught `redactKeyPreview` rendering raw private-key bytes in the folder
details UI; it now renders a hashed device id (`7f2f827cf`). The function whose whole
job was to hide key material was leaking the exact bytes. When reviewing any
preview/redact/summary helper that touches key material, verify it hashes/truncates
rather than passing bytes through.

### 2026-07-04 — Rotation SC-4's relay-replay test is unreachable past the API's DB-canonical resolve

The e2e simulation can't reach the client's fail-closed gate because the API resolves
IPNS from its DB-canonical record and short-circuits the replayed stale record before
the client ever sees it. The mitigation code exists and passes SC-1..3; only the
adversarial *simulation* is blocked, and unblocking it needs an apps/api architectural
decision or a test redesign (todo
`2026-07-03-rotation-durability-sc4-relay-replay-unreachable.md`). Lesson: a
server-side canonicalization layer can make a client-side adversarial test
structurally unreachable — verify the threat at the layer that actually enforces it.

### 2026-07-04 — Deletes RETAIN the removed child's WriteChildRef by design (unbounded write-body growth)

The 68.1-02 write-body-preservation design keeps a deleted child's `WriteChildRef` in
the parent's write chain (write-link removal was deferred). It is not data loss and not
a mis-traversal risk (DFS only consults write refs for children whose read-body is
still present), but the sealed write-body accumulates dead entries over a vault's
lifetime. Removal should drop the `WriteChildRef` in the same CAS publish that removes
the read-plane `SealedChildRef`, keyed by `childId` (todo
`2026-07-04-delete-should-drop-writechildref-not-just-retain.md`).

### 2026-07-04 — The Web3Auth Core Kit login hang is a recurring external flake — isolate before diagnosing

The setup/login test intermittently hangs (0ms `loginViaWallet`, Core Kit / Torus init
hang), which cascade-skips the rest of a suite and looks like a code regression. It is
not — a single-file re-run always isolates the real residual (as it did for
rotation-durability in the closing run). When an in-suite setup-hook failure appears,
re-run that spec file in isolation before treating it as a code defect; the retry is
gated on a narrow error signature in `wallet-login-helpers.ts:94-116`.

### 2026-07-04 — Wave-parallel execution leaves self-documented copy-paste that needs a DESIGNED primitive, not a mechanical extract

The write-chain hop walk (find WriteChildRef by UUID → unsealChildWriteKey under parent
mirror generation → unsealNode validate-before-trust) appears at 7 sites with
**divergent fail-open/fail-closed choices**; the "is a real non-zero 32-byte writeKey"
predicate is spelled 4 different ways; the TEE enrollment gate is triplicated verbatim
in sdk-core; `bin/index.ts` copies `getWriteBodyParams`/`adoptPublishedFolderState`
from `client.ts`. These cannot be de-duped by a mechanical extract because the
fail-open/fail-closed behavior legitimately differs per site — the dedup needs a
designed `walkChildWriteKey` primitive with an explicit mode parameter, and zeroization
ownership must stay with the terminal owner (D-09). Captured in todo
`2026-07-03-dedupe-sdk-write-plane-helpers.md` as a high-blast-radius, gate-with-web-e2e
refactor.
