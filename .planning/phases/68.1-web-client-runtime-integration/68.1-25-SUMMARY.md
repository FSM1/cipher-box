# Phase 68.1 Plan 25: Test-Infra Hardening — Core Kit Login Retry + sdk-e2e D-06 nodeId Fix Summary

**Bounded exponential-backoff retry around the Web3Auth Core Kit/Torus login flake in `loginViaWallet`, plus `createTestAccount` now publishing a real root Node via `publishEmptyRootNode` so the D-06 nodeId guard no longer masks `recovery.spec.ts`.**

## Performance

- **Duration:** ~25 min (includes a from-scratch `pnpm install` + full package dist rebuild in the fresh worktree)
- **Tasks:** 2
- **Files modified:** 2

## Accomplishments

- `loginViaWallet` (tests/web-e2e/utils/wallet-login-helpers.ts) now retries a narrowly-detected transient Web3Auth Core Kit / Torus DKG quorum failure up to 3 times with exponential backoff (2s, 4s, 8s), re-navigating to the login page each attempt via its own existing `page.goto('/')`. The retry gate requires BOTH still-on-login-page AND a visible `[role="alert"]` banner matching the known failure copy ("Failed to get vault keypair from Core Kit" / raw Torus "Unable to resolve enough promises… invalid public key result") — any other failure, or exhausted retries, re-throws the original error unmodified so real regressions are not masked. The `{ outcome }` return contract and success/requiredShare detection are unchanged. `multi-account-wallet.ts`'s `createWalletTestAccount` delegates to `loginViaWallet`, so both call paths are covered by a single fix.
- `createTestAccount` (tests/sdk-e2e/src/fixtures/test-harness.ts) now publishes a real, empty `kind:'root'` Node via `publishEmptyRootNode` (mirroring `useAuth.ts`'s new-user flow exactly: no `teeKeys`, matching the brand-new-user path per decision 68.1-03) instead of only registering the root in-memory via `registerFolder(rootIpnsName, vault.rootReadKey, vault.rootIpnsKeypair, [], 0n)`. The published Node's `nodeId`, first-publish `sequenceNumber` (1n), and `vault.rootWriteKey` are threaded into `client.registerFolder(...)`, so subsequent root-folder publishes (e.g. `uploadFile` to the root, exercised by `recovery.spec.ts`) carry the required `nodeId`/`nodeGeneration` and no longer trip `registration.ts:221`'s "nodeId is required — do not omit (D-06)" guard.
- Investigated whether `recovery.spec.ts`'s original "v2-blob residual" persists beneath the now-fixed nodeId error, per the plan's instruction. It does — see Deviations/Issues below.

## Files Created/Modified

## Decisions Made

- Retry detection is deliberately narrow (still-on-login-page AND matching error-banner text) rather than a blanket "retry any failure" — this was an explicit acceptance criterion to avoid masking real login regressions.
- Reused `attemptWalletLogin`'s existing `page.goto('/')` as the retry's "reload" mechanism rather than adding a separate `page.reload()` call — functionally equivalent (full navigation) and keeps the single-attempt logic in one place.
- `createTestAccount` derives `rootIpnsName` from `publishEmptyRootNode`'s return value (removing the standalone `deriveIpnsName` call and its now-unused import), mirroring the exact pattern `useAuth.ts` established under decision 68.1-03.
- Left `apps/web/public/recovery.html` untouched — migrating it to the v3 vault-blob format and node/v3 metadata schema is a production-code architectural change well outside this test-infra-only plan's `files_modified` scope, and is a pre-existing gap dating to Phase 24 (predates the entire v2.0 milestone).

## Issues Encountered

**`recovery.spec.ts`'s underlying v2-blob residual is confirmed to persist beneath the (now-fixed) nodeId error — still-expected-residual, not fixed by this plan.**

Per the plan's Task 2 instruction, I investigated whether the original v2-blob issue survives underneath the D-06 nodeId throw now that the harness publishes a real root Node. It does:

- `apps/web/public/recovery.html` hard-codes `BLOB_V2_VERSION` detection (`detectBlobVersion`) and calls `deserializeVaultBlobV2` — it rejects any vault key blob that isn't the legacy single-key v2 format with `'The vault blob at this IPNS name is not v2 format. Recovery cannot proceed.'`
- It also rejects any folder/file metadata whose `version !== 'v2'` ("only v2 supported").
- The harness (via `publishVaultKeyBlob`, unchanged by this plan) already produces v3 blobs (`serializeVaultBlobV3`, two ECIES-wrapped keys), and the live app has produced `node/v3` metadata exclusively since Phase 62 (no dual-codec bridge, per PROJECT.md's greenfield decision).
- `git log` confirms `recovery.html` was last touched by commit `392ccc940` ("fix(e2e): fix IPNS record parsing...") predating Phase 62's node/v3 cutover — this is not something introduced or masked by the D-06 nodeId bug; it's an independent, pre-existing production-code gap.

**Disposition for the exit gate: still-expected-residual, NOT fixed by 68.1-25.** `recovery.spec.ts` ("recovers vault files via IPFS-direct v2 blob path") will continue to fail at the `detectBlobVersion(blobBytes) !== 2` check in `recovery.html`, now that the D-06 nodeId error no longer masks it. Fixing this requires migrating `recovery.html` to parse v3 vault blobs and `node/v3` metadata (a production-code feature task, out of scope for `files_modified: [tests/web-e2e/utils/wallet-login-helpers.ts, tests/sdk-e2e/src/fixtures/test-harness.ts]`). Recommend a follow-up gap-closure plan scoped to `apps/web/public/recovery.html`.
