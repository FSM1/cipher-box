# Phase 68.1 Plan 17: GAP-1 AEAD Decrypt Root Cause + Fix Summary

**uploadFiles' addFilePointerToFolder call was sealing the file's content-encryption key (`fileKey`) into the parent folder's `SealedChildRef.readKeySealed` instead of the file Node's own `fileReadKey` -- a stale field name left over from before 68.1-07 split the two keys apart, hit on every upload since the web app's drop-zone always calls the batch `uploadFiles` path -- fixed at the seal site, confirmed by 3 previously-failing/at-risk e2e specs now passing (16/16).**

## Accomplishments

- **Root-caused GAP-1** (68.1-13's unresolved "resolveFileMetadata AEAD Decryption failed" gap) to a confirmed, deterministic wrong-key bug in `packages/sdk/src/client.ts`'s `uploadFiles` method, NOT the AAD-triad/generation-race the plan's `must_haves` hypothesized. Runtime diagnostics proved the AAD triad (`childId`/`kind`/`generation`) matches perfectly between seal-time and read-time in every failing case -- the actual divergence is which 32-byte key gets wrapped as the child's readKey.
- **Diagnosed the mechanism precisely:** `uploadFile` (client.ts's single-shot upload path, rewired correctly in 68.1-09's `cbf975f9e`) passes `uploadResult.fileReadKey` to `addFilePointerToFolder`'s `childReadKey` param. `uploadFiles` (the batch path -- confirmed via `apps/web/src/hooks/useDropUpload.ts` to be the ONLY path the web app's drop-zone ever calls, for both single-file and multi-file drops) still passed `uploadResult.fileKey` -- a field that existed pre-node/v3 (before 68.1-07 minted `fileReadKey` as a second, independent key) and was never updated when 68.1-09 fixed the sibling call site. `sealChildReadKey`/`unsealChildReadKey` (role 0x02) faithfully seal/unseal whatever value is handed to them under a matching AAD, so this step never errors -- the wrong key silently propagates and only surfaces as a hard AEAD failure one step later, in `unsealNode`'s role-0x01 body-unseal, because the recovered "readKey" doesn't match what `sealNode` actually used at creation time.
- **Fixed the one-line divergence** at the seal site (`success.uploadResult.fileKey` → `success.uploadResult.fileReadKey`), matching the plan's explicit "read-time must match seal-time" direction. `resolveFileMetadata`/`unsealChildReadKey`/`unsealNode` (the read side) were not modified.
- **Closed an adjacent zeroization gap** discovered while touching the call site: `uploadFiles`' cleanup only cleared `fileKey`, leaving `fileReadKey` (now consumed here) and `fileWriteKey` (unused by this batch path) unzeroed in memory. Both now cleared, matching `uploadFile`'s existing terminal-owner contract.
- **Verified via 3 scoped e2e runs** against the live local stack (no full-suite run, per plan's verification section): `streaming-playback.spec.ts` (6/6, was 1 failing), `batch-download.spec.ts` (5/5), and `media-preview.spec.ts` (5/5, regression check).
