## Known Gaps (surfaced, NOT fixed — exceeds this plan's "app-side classification/UX only" scope)

### GAP-7: rotation-durability.spec.ts SC-4's relay-replay attack vector cannot manifest under the current DB-canonical resolve architecture

**Symptom:** SC-4 ("rejects a relay-replayed stale record fail-closed via a genuine UI mutation, with the D-05 toast, and does not apply it") fails at its very first assertion (the D-05 toast never appears) because the rename mutation it drives succeeds normally, silently renaming the target item — the "stale" replay has zero effect on the outcome.

**What's confirmed (live repro + code trace):**
- `apps/api/src/ipns/ipns.controller.ts`'s `GET /ipns/resolve` delegates to `IpnsService::resolveRecord(ipnsName)`.
- `IpnsService::resolveRecord()` (lines 673-701) always prefers the DB-cached record over the network (delegated-routing) record whenever `dbSeq >= networkSeq` — this is a deliberate, documented design choice ("the DB-cached record is the authoritative, fully-signed record the owner published ... prefer the DB record whenever it is at the same or a higher sequence").
- `IpnsService::publishRecord()` (lines 112-124) writes the DB row **synchronously** as part of every publish; the push to the delegated-routing service (the mock relay SC-4 tampers with) is fire-and-forget and unawaited.
- SC-4's own "bump" mutation (step 2 of the test — a real create+rename) publishes through this exact path, so by the time step 3 replays the earlier-captured stale bytes into the mock relay, the DB row for `rootIpnsName` is already strictly ahead of those bytes, by construction (a "stale" record is by definition older than the client's own most recent publish, and the DB row always reflects that most recent publish synchronously).
- Consequently, in step 4's resolve, `networkSeq` (the replayed value) is always `< dbSeq`, so the API returns `cachedResult` (the correct, un-stale, DB record) and the network record — the only thing SC-4 actually tampered with — is discarded before it ever reaches the SDK client, `reconcileFolderSequence`, or `rotationHighWater.enforceResolved`.
- The rename mutation therefore succeeds using the correct current sequence, exactly as if no replay had happened — confirmed by the live repro's page snapshot showing the item successfully renamed to `...-rejected`.

**Why not fixed here:** Three possible resolutions exist, none of which fit this gap-closure plan's "app-side classification/UX only" scope, nor the sibling 68.1-27 plan's "SDK client.ts" scope — all three require either an `apps/api` (backend) change or a security-relevant test-design decision:

1. **Redesign SC-4's attack simulation to target genuine DB-level staleness** rather than relay-only staleness — e.g. a test-only mechanism to directly seed the DB row (or the `rotationHighWater` store) with an older record, simulating "the backend itself served a stale/rolled-back record" (a compromised DB restore, a multi-region replication lag, or a malicious/buggy backend) rather than "a colluding/lagging relay." This is the scenario the client-side `rotationHighWater`/`enforceResolved` defense-in-depth layer actually protects against, given the DB-canonical architecture — but it requires new, security-sensitive test infrastructure (any endpoint or mechanism that lets a test directly manipulate another row's DB state needs careful scoping to test-only builds).
2. **Change `apps/api`'s resolve-preference policy** so a genuinely-network-observed regression is NOT silently absorbed by DB preference — e.g. surface the discrepancy to the client instead of always serving the DB record. This would be a deliberate architectural change to the "DB-canonical resolve with generation + seq-floor as anti-rollback authority" design PROJECT.md documents as an intentional v2.0 milestone goal, and doing so purely to satisfy a test (rather than a real threat-model gap) needs explicit product/security sign-off — the current DB-preference behavior is arguably the CORRECT and SAFER outcome (no rollback occurs; the client always ends up with the true current state), and weakening it could reintroduce real staleness risk elsewhere.
3. **Retire or retarget SC-4.** If DB-canonical resolve genuinely closes the T-68-101 "colluding/lagging relay" threat vector as designed (this investigation strongly suggests it does — the relay can never win against a DB row this same client keeps synchronously current), then SC-4 as literally specified may be testing an attack that structurally cannot succeed anymore, and the client-side `rotationHighWater` floor's actual value lies in different scenarios (e.g. a genuinely stale/rolled-back DB, or a completely different client/device that hasn't yet observed the bump) that would need a different test design entirely.

**Recommended next step:** A dedicated follow-up plan (not 68.1-29, the exit-gate full-suite confirmation pass) should decide between the three options above — this is a product/security architecture decision requiring human sign-off, not a wiring fix. Until then, `rotation-durability.spec.ts` SC-4 will continue to fail — 68.1-29 should route this failure to GAP-7 rather than treating it as a regression or re-attempting a classification fix.
