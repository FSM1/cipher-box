## Accomplishments

- `createFileMetadata` mints fresh fileReadKey/fileWriteKey/Ed25519 keypair, builds a v3 file Node (`NodeContent` with raw fileKey + base64 iv, write-body carrying the file's own ipnsPrivateKey), seals it, uploads to IPFS, and builds (but does not publish) the file's first IPNS record with sequenceNumber hard-wired to `1n`. Returns fileReadKey/fileWriteKey/fileNodeId raw to the caller (terminal owner, D-09); the minted Ed25519 private key never leaves the function raw — zeroed once consumed.
- `resolveFileMetadata` resolves the file IPNS name, fetches the PublishedNode, and unseals content under the file readKey (read-only, fails closed on a missing record or non-file node).
- `downloadFileContent` fetches a CID and decrypts with a raw (non-ECIES-wrapped) fileKey for both AES-256-GCM and AES-256-CTR, decoding the base64 iv — mirrors the web layer's `downloadSharedFile` pattern.
- `updateFileMetadata` rebuilds the file Node preserving id/generation/createdAt, optionally folds the superseded content descriptor into version history via `capVersions` (an adapter reusing the existing `mergeVersions` dedupe/sort/cap algorithm unmodified), and republishes directly (single-shot, no CAS retry) at `fileSequenceNumber+1`.
- `registration.ts` `addFileToFolder`/`addFilesToFolder` seal the new file's readKey into the parent's read-body (`sealChildReadKey`) and writeKey into the parent's write-body (`sealChildWriteKey`), republish the parent via the write-body-aware `updateFolderMetadataAndPublish` (68.1-01), and batch-publish the file IPNS record(s) concurrently. `replaceFileInFolder` is a thin delegate to `updateFileMetadata` (parent untouched — folder republish not needed for a content-only replace).
- `upload/index.ts` `uploadFile` now threads the raw fileKey + iv into `createFileMetadata` and surfaces `fileNodeId`/`fileReadKey`/`fileWriteKey` on `UploadResult` additively (existing `fileKey` field preserved for compat until 68.1-09 rewires callers).

## Decisions Made

- createFileMetadata builds the file's first IPNS record locally (create+sign+marshal) but does NOT publish it over the network — the caller batch-publishes it, matching the pre-existing `UploadResult.ipnsRecord` contract client.ts already wires via `batchPublishIpnsRecords([uploadResult.ipnsRecord])`.
- updateFileMetadata is a single-shot direct republish (`createAndPublishIpnsRecord` once at `fileSequenceNumber+1`), not a CAS-retry-with-merge flow — mirrors `shared-write.ts` `updateSharedFile`; the legacy CAS+merge conflict-resolution behavior tested in the quarantined `file.test.ts` `describe.skip` block is explicitly out of scope for this plan.
- `ipnsPrivateKeyEncrypted` changed from required to optional (both `createFileMetadata`'s return and `UploadResult`) to match `createSubfolder`'s fail-closed `teeKeys`-optional convention — the pre-existing stub's required-but-sometimes-undefined field was a latent bug.
- `addFileToFolder`/`addFilesToFolder`/`replaceFileInFolder` signatures were fully redesigned from the phase-65-era stubs rather than preserved verbatim — a repo-wide grep confirmed zero live callers (only comments/quarantined `describe.skip` blocks referenced them), so there was no compatibility surface to protect.
- `capVersions` reuses the existing `mergeVersions` dedupe/sort/cap algorithm unmodified by mapping v3 `VersionEntry` (`createdAt`) to the legacy `FileVersionEntry` shape (`timestamp`) for the call, then resolving the returned cids back to their original `VersionEntry` objects via a cid lookup — keeps `mergeVersions` itself untouched per the plan's explicit instruction.
