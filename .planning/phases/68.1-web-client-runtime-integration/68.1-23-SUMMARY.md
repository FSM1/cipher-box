# Phase 68.1 Plan 23: Write-Plane Cold-Load Recovery + Refresh Mirror Preservation Summary

**Fixed the cross-device write-plane clobber root cause: `ensureFolderLoaded`/`requireFolder` now recover a real writeKey for read-only-seeded folder entries reachable from a write-capable root, and `refreshFolderStateFromNetwork` never replaces a populated local `metadata.writeBody` with an absent one.**

## Accomplishments

- `refreshFolderStateFromNetwork` (client.ts) now preserves an already-populated `folder.metadata.writeBody` when it unseals a network-ahead record without a real writeKey, instead of wholesale-replacing `folder.metadata` with a write-body-less node — closing the D-03 zero-key clobber a second device's bump could trigger.
- `ensureFolderLoaded` (and, by extension, `requireFolder`, the mutation chokepoint every folderTree-dependent call site routes through) now detects a read-only-seeded `FolderState` entry (zero writeKey, e.g. `registerFolder`/`loadFolder` invoked without a `writeKey` argument — the web-layer's parallel `navigateReadChain` walk from 68.1-05) and, when self-bootstrap material is configured, re-runs the existing DFS write-chain recovery to adopt a real writeKey + populated `metadata.writeBody` onto that entry, preserving its existing readKey/ipnsKeypair/sequenceNumber/children.
- `requireFolder` was simplified to always route through `ensureFolderLoaded` (dropping the `folderTree.get() ?? ensureFolderLoaded()` short-circuit) so the recovery check fires for already-loaded entries too, not just cache misses.
- 5-test scoped Vitest suite (`client-write-plane-recovery.test.ts`) locks both invariants plus the anti-rollback guard and two recovery no-op paths (already-real writeKey; no root write material configured).

## Decisions Made

- `recoverWriteKeyIfNeeded` adopts ONLY the write-plane fields (`writeKey`, `metadata.writeBody`) from the DFS-recovered `FolderState` onto the pre-existing entry, explicitly restoring the original `folderKey`/`ipnsKeypair` afterward — `dfsFindFolder`'s own `folderTree.set()` calls would otherwise wholesale-replace the entry with the freshly network-recovered view, which is stronger than what the plan called for (D-09: never replace a caller/folderTree-owned read-plane view with a network re-walk).
- `requireFolder` now always calls `ensureFolderLoaded` rather than short-circuiting on an already-present `folderTree` entry, so the new recovery check reliably fires for both cache-miss loads and already-loaded read-only entries — this is the only way `requireFolder`'s call sites (the primary mutation chokepoint) benefit from the fix, since the plan explicitly named "ensureFolderLoaded / requireFolder" as the two entry points.
- The write-body preservation fix in `refreshFolderStateFromNetwork` only applies when `realWriteKey === undefined` (this device has no write material for the folder); when a real writeKey is present, the freshly-unsealed write-body from the network continues to be trusted as-is — unchanged from pre-68.1-23 behavior for write-capable devices.
