# Phase 68.1 Plan 02: Owned Subfolder Create + Bin-Relink Subtree Collectors Summary

**createFolder mints an owned subfolder write-body and threads it onto the parent's write-body via WriteChildRef, and the bin-relink IPNS collectors now walk the read-chain (with best-effort skip-on-unreadable-descendant) instead of throwing — obsolete reencrypt.ts removed.**

## Performance

- **Files modified:** 2 (1 modified, 1 deleted)

## Accomplishments

- `createFolder(parentIpnsName, name)` adapts `createSharedSubfolder`'s build path to the owned (non-share) chain: mints child readKey + writeKey + Ed25519 keypair, builds a `kind:'folder'` Node with a write-body (`ipnsPrivateKey` + empty `writeChildren`), seals and publishes at seq 1n, then seals a `SealedChildRef` into the parent read-body and a `WriteChildRef` into the parent write-body and republishes the parent via `updateFolderMetadataAndPublish`. The new child is immediately registered into `folderTree` (via `registerFolder`) so subsequent operations (upload, rename) work without a reload round-trip. Reconciles the parent's sequence before publishing (SC#3/D-04) and triggers `performScopeExitRotation` on the parent, matching `renameItem`'s pattern.
- `collectDescendantIpnsNames(nodeReadKey, nodeChildren)` — a new shared, bounded-concurrency (`UNENROLL_COLLECT_CONCURRENCY`) DFS helper that resolves each child's `PublishedNode`, recovers its readKey via `unsealChildReadKey`, and recurses into folder/root children. An unresolvable or AEAD-failing descendant is logged and its own `ipnsName` is still returned (best-effort — never descended into further, never thrown).
- `collectRemovedItemIpnsNames(item, parentReadKey)` now resolves the removed `SealedChildRef`'s own node, recovers its readKey under the caller-supplied `parentReadKey`, and delegates to `collectDescendantIpnsNames` for folder/root items. `deleteItem`'s fire-and-forget call site now passes `folder.folderKey` as the second argument.
- `collectBinEntryIpnsNames(entry)` reads from `entry.nodeRef` / `entry.nodeReadKey` / `entry.nodeIpnsName` (the `filePointer`/`folderEntry` fields no longer exist — [62-05]) and delegates to the same shared DFS helper for folder/root entries.
- `packages/sdk/src/reencrypt.ts` deleted — content self-seal (phase 65) made re-encrypt-on-move obsolete; zero production callers.

## Decisions Made

- **`collectRemovedItemIpnsNames` gained a `parentReadKey` parameter** not present in the original stub signature. The plan's action text specified "use the caller-provided/looked-up parent folderKey to unseal the first hop" — the item's `readKeySealed` is sealed under the PARENT's readKey, which the private method otherwise has no way to obtain from a bare `SealedChildRef`. Updated `deleteItem`'s single call site to pass `folder.folderKey` (the only caller).
- **`createFolder` throws when the parent has no real writeKey** (zero-fallback legacy folder). Minting a child write-body under a parent that has never itself been write-body-published would either seal the new `WriteChildRef` under a zero key (the exact T-68.1-01-03 threat 68.1-01 structurally closed) or silently drop the write link — fail-closed instead.
- **`collectDescendantIpnsNames` is a single shared helper** used by both collectors rather than two separate DFS implementations, avoiding duplicated resolve+unseal+recurse+zero-on-exit logic.
