# Phase 68.1 Plan 12: Owned File Write + Version UI Wiring Summary

**Owner file save, in-place update, version restore/delete/download, and file download/batch-download now run end-to-end from the web UI through `client.replaceFile`/`restoreFileVersion`/`deleteFileVersion`/`downloadFromIpns` — closing the last `not implemented — phase 65` stub set in the owned-file write surface, plus a new `client.resolveFileIpnsPrivateKey` method and an sdk-core `updateFileMetadata` key-zeroing fix that were both required to make the wiring possible.**

## Accomplishments

- `file-metadata.service.ts`'s `createFileMetadata`/`updateFileMetadata` now delegate to their sdk-core counterparts (68.1-07) via `getSdkClient().getContext()`; `shouldCreateVersion`/`computeRestoreVersionUpdate`/`computeDeleteVersionUpdate` implement the pure `NodeContent.versions` transforms, ported from the pre-v3 legacy cooldown/history policy and adapted to node/v3's raw-fileKey/base64-fileIv contract.
- `useFileOperations.handleUpdateFile` resolves the file's write-chain signing key via the new `client.resolveFileIpnsPrivateKey`, unwraps `ReplaceFileDialog`'s existing ECIES-wrapped content key, and publishes via `client.replaceFile` inside `runWithFailureUx`, unpinning `prunedCids` afterward.
- `TextEditorDialog`'s owner-save branch mints a fresh fileKey/iv, encrypts the edited content, uploads to IPFS, and publishes through the same `replaceFile` path (the shared-file branch was already working via `onSaveSharedFile`).
- `useFileBrowserActions` download/batch-download wire to `downloadFileFromIpns` (68.1-04) + `triggerBrowserDownload` (raw-fileKey path, never `.buffer` for Blob).
- `useFileVersions.handleRestoreVersion`/`handleDeleteVersion` build `updates` via `computeRestoreVersionUpdate`/`computeDeleteVersionUpdate`, resolve the write-chain key, and publish via `client.restoreFileVersion`/`deleteFileVersion`, unpinning `prunedCids`/`deletedCid`.
- `VersionHistory`'s version download decrypts directly from the self-contained `VersionEntry` (no additional read-chain resolve needed — NODE-02 stores a raw fileKey per version).
- **Deviation:** added `CipherBoxClient.resolveFileIpnsPrivateKey` — a new public method required because 68.1-09's `replaceFile`/`restoreFileVersion`/`deleteFileVersion` contract expects the *caller* to pre-resolve `fileIpnsPrivateKey`, but NODE-03's frozen `SealedChildRef` schema gives the web layer no independent way to derive it (the write-chain walk needs the parent folder's `writeKey`, which lives only inside `CipherBoxClient`'s internal `FolderState`).
- **Deviation:** fixed sdk-core's `updateFileMetadata` to actually zero `fileIpnsPrivateKey` on every exit path — every call site's doc comment already claimed this happened (T-47-01) but the `.fill(0)` was missing since 68.1-07.

## Decisions Made

- `createFileMetadata`/`updateFileMetadata` delegate straight to sdk-core rather than reimplementing web-native primitives (unlike 68.1-04's read-chain choice) — write paths don't need the ROT-07 anti-rollback wrapper sdk-core's raw `resolveIpnsRecord` lacks, since a fresh forward-sequence publish carries no stale-read risk.
- `computeRestoreVersionUpdate`'s signature matches the plan's declared stub exactly (`versions`, `versionIndex` only — no `currentMetadata`), which means it cannot fold the pre-restore live content into history itself. The caller passes `createVersion: true` to `client.restoreFileVersion` so sdk-core's `updateFileMetadata` performs that fold+cap using its own `currentMetadata`/`updates` split — this reproduces the legacy non-destructive-restore behavior without duplicating `capVersions`' cap/prune logic in the web tier.
- `useFileOperations.handleUpdateFile` unwraps the existing ECIES-wrapped hex content key from `ReplaceFileDialog`'s upload pipeline (`unwrapKey` with the user's own private key) instead of changing `useDropUpload.ts`/`file-crypto.service.ts` to produce a raw key — those files are out of this plan's `files_modified` scope and the wrap/unwrap round-trip is a legitimate, minimal adaptation (the user's own public key wrapped it, so the user's own private key can unwrap it right back).
- `VersionHistory`'s pre-built `version-download-guard.ts` (`vaultKeyMissingError`, added speculatively by 68.1-02) was deliberately NOT wired into `handleDownloadVersion` — its "vault private key" gate doesn't correspond to the actual v3 data flow (each `VersionEntry` already carries a raw, self-contained `fileKey`; no vault key or additional resolve is needed). Wiring it in would have been an incorrect gate on a feature that doesn't need it. The module and its passing unit test remain untouched in the tree.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The web layer has no way to pre-resolve `fileIpnsPrivateKey` as 68.1-09's contract requires**

- **Found during:** Pre-Task-1 design pass (before writing any hook code)
- **Issue:** `client.replaceFile`/`restoreFileVersion`/`deleteFileVersion` (68.1-09) require the caller to pass a pre-resolved `fileIpnsPrivateKey` ("locked decision 2: web tier owns key/service logic"). Under the pre-v3 model this key was ECIES-wrapped directly on `FilePointer` (`ipnsPrivateKeyEncrypted`), unwrappable with only the user's vault key — confirmed by reading the retired pre-v3 `getFileIpnsPrivateKey` (git commit b24e78e90). Under node/v3, NODE-03's frozen `SealedChildRef` carries no such field: the file's own `ipnsPrivateKey` now lives inside its sealed write-body, unsealable only with the parent folder's `writeKey` — and that `writeKey` exists ONLY inside `CipherBoxClient`'s internal `FolderState` (D-03), never exposed to the web's Zustand `FolderNode`. There was no way to complete Task 2/3 as literally specified without this.
- **Fix:** Added `CipherBoxClient.resolveFileIpnsPrivateKey(parentIpnsName, fileId)` — a thin public wrapper over the existing private `resolveFileWriteChainKeys` write-chain walk, which already unseals the current file Node's write-body as a byproduct of resolving `nodeGeneration`/`originalCreatedAt`. Extended that private method's return type to include `fileIpnsPrivateKey` and updated its three existing call sites (`replaceFile`/`restoreFileVersion`/`deleteFileVersion`) to zero their own now-superfluous copy in `finally` (they already receive it from their own caller's params).
- **Files modified:** `packages/sdk/src/client.ts`
- **Verification:** `pnpm --filter @cipherbox/sdk exec tsc -b --pretty false` (client.ts itself compiles clean, zero new errors vs. pre-plan baseline); `pnpm --filter @cipherbox/sdk exec vitest run` on `client-extended.test.ts`/`client-upload-concurrency.test.ts`/`client-pinning.test.ts` — 35 passed / 2 skipped, no regressions
- **Committed in:** `0944791a8`

**2. [Rule 1 - Bug] sdk-core `updateFileMetadata` never actually zeroed `fileIpnsPrivateKey`**

- **Found during:** Same design pass as deviation #1, while confirming the "do NOT zero fileIpnsPrivateKey at the web layer — updateFileMetadata owns it (T-47-01)" constraint given for this plan
- **Issue:** Every `client.ts` call site's doc comment (`replaceFile`/`restoreFileVersion`/`deleteFileVersion`, all from 68.1-09) states "This method does NOT zero `fileIpnsPrivateKey` — sdk-core `updateFileMetadata` zeroes it in its own finally on every exit path (T-47-01)". Reading `packages/sdk-core/src/file/index.ts`'s actual `updateFileMetadata` (68.1-07) showed no such `.fill(0)` existed — its own docstring explicitly said "Does NOT zero ... fileIpnsPrivateKey". Following the given constraint literally (never zero at the web layer) would have left the key un-zeroed anywhere in the call chain — a real memory-hygiene gap (CLAUDE.md: "Clear sensitive data from memory after use").
- **Fix:** Wrapped `updateFileMetadata`'s body in try/finally, zeroing `params.fileIpnsPrivateKey` on every exit path; updated the function's docstring to match.
- **Files modified:** `packages/sdk-core/src/file/index.ts`
- **Verification:** `pnpm --filter @cipherbox/sdk-core exec vitest run src/__tests__/file/file-node.test.ts` — 14/14 passing (no test asserted the key stayed non-zero); `tsc -b --pretty false` — 50 errors, unchanged from baseline (all pre-existing, confined to unrelated quarantined test files)
- **Committed in:** `0944791a8`

**3. [Rule 1 - Bug] `computeRestoreVersionUpdate`/`computeDeleteVersionUpdate`'s `versionToRestore.fileIv`/`currentMetadata.fileIv` needed base64 decode before use as `UpdateFileContentParams.fileIv`**

- **Found during:** Task 3 (writing `useFileVersions.ts`)
- **Issue:** `VersionEntry.fileIv`/`NodeContent.fileIv` are base64-encoded strings (NODE-02 wire contract), but `sdk-core.UpdateFileContentParams.fileIv` expects raw `Uint8Array` bytes (which sdk-core then re-encodes to base64 internally). Passing the base64 string straight through would have double-encoded the IV, silently corrupting every restore/delete-version publish.
- **Fix:** Added a local `base64ToBytes` helper (matching the existing pattern already duplicated in `download.service.ts`/`file-metadata.service.ts`) and decoded before constructing `updates`/the delete-path `updates` object.
- **Files modified:** `apps/web/src/hooks/useFileVersions.ts`
- **Verification:** `pnpm --filter @cipherbox/web exec tsc -b --pretty false` clean (Uint8Array-typed field now correctly typed at the call site)
- **Committed in:** `9e5abd29e`
