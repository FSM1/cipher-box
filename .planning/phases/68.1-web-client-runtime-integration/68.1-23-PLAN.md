Fix the deterministic cross-device write-plane clobber (Round-2 Addendum root-cause, high confidence): a freshly-logged-in device that has NOT recovered a folder's `writeKey` publishes that folder with NO write-body (D-03 zero-key fallback), erasing every `WriteChildRef` from the wire; and `refreshFolderStateFromNetwork`, when it unseals a record without a `writeKey`, REPLACES `folder.metadata` wholesale — wiping a populated local `metadata.writeBody` mirror with an absent one.

  <action>
    Root-cause first, then fix. The addendum's evidence-backed chain is the working hypothesis; confirm each link against the code before changing it.

    1. refreshFolderStateFromNetwork (client.ts:1028): today it computes `realWriteKey` (undefined when folder.writeKey is zero) and calls `unsealNode(published, folder.folderKey, realWriteKey)`, then unconditionally assigns `folder.metadata = node`. When `realWriteKey` is undefined the resulting `node.writeBody` is absent, so this REPLACES a populated mirror with a write-body-less one. Change it so that when it unsealed WITHOUT a real writeKey (realWriteKey === undefined) it PRESERVES the existing `folder.metadata?.writeBody` on the newly-adopted node (assign `node.writeBody = folder.metadata?.writeBody ?? node.writeBody` before the `folder.metadata = node` write) rather than dropping it. Read-body children/sequence/nodeId/generation still adopt the fresher network view. Keep the strictly-newer anti-rollback guard (line 1032) unchanged — never adopt a record at or below the in-memory sequence (T-68-101). Never zero folder.folderKey/folder.writeKey (D-09).

    2. Cold-load write-plane recovery: confirm that the path which SEEDS the folder the editor mutates actually recovers the writeKey. dfsFindFolder (client.ts:780) already unseals child writeKeys from the parent write-body chain (WriteChildRef.writeKeySealed via unsealChildWriteKey, parent-mirror generation) and the root uses internalRootWriteKey (ensureRootFolderState:747). The defect surfaces when a folder is seeded read-only (registerFolder/loadFolder with a zeroed writeKey per client.ts:509-602) and that read-only entry SHADOWS the ensureFolderLoaded DFS recovery (ensureFolderLoaded:897 returns the existing zero-writeKey entry immediately). Determine which is happening for the conflict-detection scenario. If a read-only-seeded entry with a zeroed writeKey pre-empts DFS recovery, make the cold-load path recover the real writeKey for that entry instead of returning the write-crippled one: e.g. when `ensureFolderLoaded` / `requireFolder` finds an existing entry whose `writeKey` is zeroed (length!==32 or all-zero) AND the client can self-bootstrap (internalRootIpnsKeypair && internalRootWriteKey present), run the DFS recovery and adopt the recovered writeKey + metadata.writeBody into the existing FolderState (preserving its readKey/ipnsKeypair). Do NOT change behavior when no root write material is configured (read-only clients stay read-only).

    3. getWriteBodyParams (client.ts:669) fail-open on zero writeKey stays as-is (never seal under a zero key — T-68.1-01-03), but with (2) in place the owned-write folder now presents a real writeKey so it takes the metadata.writeBody / on-wire-unseal branch instead of `{}`.

    NO fenced code in the written file. NO plaintext key logging. Terminal-owner zeroization only (D-09): zero only navigate-minted intermediates, never caller/folderTree-owned buffers.
  </action>
