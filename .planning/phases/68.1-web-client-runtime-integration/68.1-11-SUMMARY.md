## Known Gaps

### SHARE-WRITE-KEY web-wiring gap (write-permission sharing not reachable from the UI)

**What's missing:** `ShareDialog.handleShare` (permission='write') and `handleUpgrade` (read→write) both require the shared item's own **writeKey**. Under the node/v3 write-chain, a node's writeKey is sealed inside its **parent's** write-body (`WriteChildRef.writeKeySealed`, sealed under the parent's writeKey) — there is no way to derive it from the parent's readKey alone.

**Why this plan can't close it:** `ShareDialog` is only ever passed `folderKey` = `currentFolder.folderKey` (the parent's READ key) from `FileBrowser.tsx`. The web app's own folder store (`FolderNode`, from `folder.store.ts`/`useFolderNavigation.ts`) has no `writeKey` field at all — only the SDK client's internal `FolderState.writeKey` (added in 68.1-01) carries it, and it is not currently threaded to any web UI layer. Closing this gap requires plumbing writeKey from the SDK client through `useFolderNavigation` → `folder.store` → `FileBrowser.tsx` → `ShareDialog.tsx`, a genuine cross-cutting architecture change (Rule 4) well outside this plan's 3-file scope (`key-wrapping.ts`, `ShareDialog.tsx`, `invite.service.ts`).

**Current behavior:** Both paths surface a clear, non-throwing UI error (`setError(...)`) instead of crashing or silently producing an insecure/incorrect grant. `handleUpgrade` additionally routes through `updateSharePermission` (packages/sdk/src/share/shared-write.ts:900, the thin injected-callback wrapper the plan named) so the SDK-level shape referenced by the plan is exercised, even though the write-key material to make it succeed isn't available yet.

**Also note:** there is no `PATCH /shares/:id/permission`-style backend endpoint at all — only `POST /shares` (create), `DELETE /shares/:id` (revoke, hard-delete), and `PATCH /shares/:id/grant` (rotate `readDescriptorRef` only). Even with writeKey plumbing in place, a real "upgrade" would need to be implemented as revoke + re-create with `writeDescriptorRef` set (no backend schema change required) — this is a viable path for a future gap-closure plan.

**Recommendation:** file a `68.1-*` gap-closure plan (analogous to the existing "Phase 68 ROT-07 live-wiring gap" precedent) that (1) threads `writeKey` from the SDK client through the web folder-navigation stack, and (2) implements `handleUpgrade` as revoke+recreate against the existing `POST /shares` + `DELETE /shares/:id` endpoints.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] sdk-core's grant primitives use base64, the live REST API is hex-only**

- **Found during:** Task 2 (ShareDialog wiring), confirmed during Task 3 (invite wiring)
- **Issue:** `issueReadGrant`/`claimInviteReadKey`/`claimInvite` (sdk-core/share/grant.ts) internally base64-encode the wrapped key via their own `bytesToBase64`/`base64ToBytes` helpers and expose that as `readDescriptorRef`. The live `CreateShareDto`/`ClaimInviteDto`/`CreateInviteDto`/`InviteDataResponseDto` all validate their descriptor-ref/key fields against a hex-only regex (`^(?:[0-9a-fA-F]{2})+$`). Calling `sharesControllerCreateShare`/`invitesControllerClaimInvite`/`shareInvitesControllerCreateInvite` with a base64 payload would fail server-side validation (400).
- **Fix:** Web share/invite code calls `@cipherbox/crypto`'s `wrapKey`/`unwrapKey` directly and hex-encodes via `bytesToHex`/`hexToBytes`, bypassing sdk-core's base64 wrapping entirely. Confined to the web layer per this plan's file scope (sdk-core's grant.ts was not touched).
- **Files modified:** `apps/web/src/components/file-browser/ShareDialog.tsx`, `apps/web/src/services/invite.service.ts`
