# Phase 68.1 Plan 27: GAP-7 — enumerateSharedSubtree Read/Write-Chain Rewrite Summary

**Rewrote `enumerateSharedSubtree` off the deleted `share_keys` table onto a recursive node/v3 read/write-chain DFS (mirroring `dfsFindFolder`'s generation-source rule and fail-closed AEAD semantics), and re-wired `SharedMoveDialog.tsx`'s destination picker to the new no-args signature — closing the gap where the picker always showed "No writable folders available" regardless of actual write access.**

## Accomplishments

- `enumerateSharedSubtree(shareId)` (`packages/sdk/src/client.ts`) dropped its `getShareKeysFn`/`vaultPrivateKey` args entirely and now walks the loaded `SharedFolderState`'s own read/write chain: each `SealedChildRef.readKeySealed` is unsealed via `unsealChildReadKey` under the PARENT's readKey using the parent-mirror generation (§2.6, matching `dfsFindFolder`/`navigateReadChain` — never the child's own envelope generation), and `writable: true` is set only when a `WriteChildRef` for that child's id exists in the parent's unsealed write-body AND `unsealChildWriteKey` succeeds under the parent writeKey. A structurally-unresolvable hop (missing IPNS record) is a soft skip; an AEAD auth failure on a present-but-wrong body throws (fail-closed), matching `dfsFindFolder`'s documented contract.
- The DFS is implemented as a recursive `async walk()` closure (not an iterative stack, unlike the old implementation) — this is required so a child's locally-minted `childReadKey`/`childWriteKey` stay live through that child's own recursive descent before being zeroed in a `finally` after the recursive call resolves, matching `dfsFindFolder`'s existing recursion-scoped zeroization pattern in the same file (D-09: `state.folderKey`/`state.writeKey` — sharedFolderTree-owned — are never zeroed).
- A read-only child (no `WriteChildRef` recovered under its parent) is still listed with `writable: false`, and its own children are still enumerated via the read chain — but writability never "reappears" below it: the next recursion level is walked with `parentWriteKey: null` / `parentWriteChildren: []` regardless of what that child's own write-body might independently contain.
- `SharedMoveDialog.tsx` now calls `getSdkClient().enumerateSharedSubtree(shareId)` with no args object, and the now-unused `fetchShareKeys` import and `useAuthStore`-sourced `vaultKeypair` open-guard were removed (they existed solely to source `vaultPrivateKey` for the retired signature).
- `packages/sdk/src/__tests__/enumerate-shared-subtree.test.ts` was fully rewritten onto the read-chain contract: real `@cipherbox/core` `sealNode`/`sealChildReadKey`/`sealChildWriteKey`/unseal primitives build genuine AAD-bound fixtures (mirroring the 68.1-23 `client-write-plane-recovery.test.ts` pattern), with only `sdk-core`'s `resolveIpnsRecord`/`fetchFromIpfs` mocked. Covers: a nested reachable subtree with correct writable flags and `parentId` (root → subA[writable] → subA1[writable]; root → subB[read-only] → subB1[listed, non-writable]), a file-leaf child excluded from the result, a structurally-unresolvable child skipped (not thrown), the visited-set cycle guard, a fully read-only share root (zero writeKey → every child non-writable), and the "Shared folder not loaded" throw.

## Decisions Made

See `key-decisions` in frontmatter for the full list. Summary:

- Recursive (not iterative-stack) DFS shape is load-bearing for correct zeroization ordering — an iterative stack would need to zero `childReadKey`/`childWriteKey` before they'd been consumed by a later-popped frame's unseal calls.
- Root write-body is unsealed once up front (only when the share root has a real writeKey), reusing the same zero-key detection idiom (`wk.length === 32 && !wk.every((b) => b === 0)`) already established in `getWriteBodyParams`/`refreshFolderStateFromNetwork` (68.1-23).
- Read-only subtrees remain enumerable (not silently dropped) per the plan's explicit instruction, but never regain writability at any depth below the read-only boundary.
- `SharedMoveDialog.tsx`'s `useAuthStore` guard was removed rather than left as dead code, since it existed only to source the now-retired `vaultPrivateKey` argument.
