# Phase 68.1 Plan 33: Owner Kind-Cache Race Summary

**Resolve-before-insert applied to all three owner-side folder-store projection sinks (subscribeToSdk, handleSync, resyncFolder), closing the writable-shares 10.4 kind-cache race — the last open item of Phase 68.1.**

## Performance

- **Duration:** ~15 min
- **Tasks:** 3
- **Files modified:** 4 (3 source, 1 test) + 1 evidence artifact

## Accomplishments

- Made `folder.store.ts`'s `subscribeToSdk` folder:loaded/folder:updated handler a hybrid
  resolve-before-insert projection: synchronous when every child's kind is already cached
  (or the children array is empty — 68.1-29 delete-last-item parity), await-first on any
  cache miss, with a stale-event sequence guard so an in-flight resolve never clobbers a
  newer applied state.
- Warmed the kind cache in the two direct owner-side inserters that bypass the SDK event
  entirely — `handleSync` (the reload-gating immediate initial sync on FileBrowser mount)
  and `resyncFolder` (409-conflict resync) — both now `await resolveKinds(...)` before
  `updateFolderChildren`.
- Live single-file `writable-shares.spec.ts` run: 29/29 passed. Test 10.4 ("Alice can read
  the file edited by Bob") is newly green; 10.3 ("Bob opens the write-shared file and can
  edit it") stays green; 1.1-10.2 are not regressed.

## Files Created/Modified

- `apps/web/src/stores/folder.store.ts` - `subscribeToSdk`'s post-guard projection block
  replaced with a hybrid: `allKindsCached` check (vacuously true for an empty array) gates
  a synchronous fast path vs. a guarded async IIFE that awaits `resolveKinds` before
  projecting, re-checks the folder still exists, and refuses to apply if a newer
  `sequenceNumber` has since landed. The 68.1-26 empty-over-non-empty guard block above it
  is untouched (verified byte-for-byte identical).
- `apps/web/src/stores/__tests__/folder.store.test.ts` - mocked `../../lib/kind-cache`
  (`getKind`/`resolveKinds`); extended the 5 pre-existing tests with a `markCached` helper
  so their synchronous assertions still hold, and added 6 new tests covering the sync
  fast path, empty-children fast path, the preserved 68.1-26 guard rejection, cache-miss
  deferral, resolveKinds-rejection fallback, and the stale-sequence guard.
- `apps/web/src/components/file-browser/useFileBrowserActions.ts` - `handleSync` now
  `await resolveKinds(syncChildren)` before `updateFolderChildren('root', syncChildren)`.
- `apps/web/src/hooks/folder-helpers.ts` - `resyncFolder` now
  `await resolveKinds(resyncChildren)` before `store.updateFolderChildren(...)`.

## Decisions Made

- Followed the plan's Direction 1 scope extension: fixing only `folder.store.ts` would have
  left the deterministic 10.4 reload path unfixed, since `handleSync`'s direct
  `updateFolderChildren('root', ...)` call — not the SDK event handler — is what satisfies
  the test's `waitForItemToAppear` on `page.reload()`.
- Kept the store projection a hybrid rather than unconditionally awaiting, so re-renders,
  mutation echoes, and delete-last-item/empty-children flows retain their existing
  zero-latency behavior (T-68.1-33-01 threat register disposition: mitigate via hybrid).
