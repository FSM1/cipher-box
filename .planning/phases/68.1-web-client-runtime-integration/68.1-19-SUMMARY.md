# Phase 68.1 Plan 19: SHARE-WRITE-KEY Upgrade/Downgrade Summary

**Added a mutually-exclusive `writeDescriptorRef` (set) / `clearWriteDescriptor` (clear) pair to `UpdateGrantDto` so an owner can toggle a share's write permission in place via `PATCH /shares/:id/grant` (same shareId, no revoke/recreate), and wired `ShareDialog`'s upgrade/downgrade actions through it — closing the last SHARE-WRITE-KEY web-wiring gap from 68.1-11/68.1-18.**

## Accomplishments

- `update-grant.dto.ts`: added `writeDescriptorRef?: string` (hex, mirrors `create-share.dto.ts`'s write field) and `clearWriteDescriptor?: boolean`, both `@IsOptional`.
- `shares.service.ts`'s `updateGrant` gained two new optional trailing params. Inside the row-locked transaction: `clearWriteDescriptor` truthy sets `share.writeDescriptorRef = null`; `writeDescriptorRef` truthy sets it to the decoded buffer; neither present leaves the field completely untouched (verified via `toBe` object-identity assertion, not `toEqual`). - `shares.controller.ts`'s `updateGrant` route handler passes `dto.writeDescriptorRef`/`dto.clearWriteDescriptor` through.

The throwing `updateSharePermission` import/calls are gone.

## Decisions Made

See `key-decisions` in frontmatter for the full list. Summary:

- An explicit `clearWriteDescriptor: boolean` (not an empty-string sentinel) is the downgrade clear-signal — keeps the hex validator strict and the intent unambiguous at both call sites.
- `writeDescriptorRef`/`clearWriteDescriptor` are mutually exclusive (service-level `BadRequestException`), preventing an ambiguous combined request.
- Owner-reconcile's existing read-only-rotation `updateGrant` call required zero changes — omitting both new fields is the documented "leave untouched" path.
- Upgrade/downgrade re-send the share's already-known `readDescriptorRef`/`rootGeneration` unchanged; this plan's scope is strictly the write-permission toggle.
