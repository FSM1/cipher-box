# Phase 68.1 Plan 26: Breadcrumb-Up Empty-Flash Regression Summary

**Fixed two compounding defects behind the full-workflow.spec.ts 3.9 deterministic regression: `client.ts`'s `dfsFindFolder` redundantly re-derived (and could overwrite) an already-cached, write-capable ancestor's folder state on every descent into a deeper subfolder, and `folder.store.ts` had no guard against an empty-children SDK event silently replacing a loaded ancestor's non-empty children.**

## Accomplishments

- Root-caused the regression by tracing the exact zustand/SDK data flow for `navigateIntoFolder(workspace) → navigateIntoFolder(documents) → breadcrumb-click(workspace)` against the three suspect commits (`076d74151`, `814ea642d`, `6185cc443`) and the 68.1-23 write-plane rework it depends on.
- Confirmed `useFolderNavigation.ts:183`'s `targetFolder?.isLoaded` fast path (the plan's first named suspect) is logically correct — it reads fresh `useFolderStore.getState()` synchronously right before the check, so it renders whatever the store currently holds. Left unchanged.
- Fixed `client.ts`'s `dfsFindFolder`: it previously re-resolved, re-unsealed, and overwrote EVERY intermediate ancestor's `folderTree` entry on EVERY call, even when that ancestor was already fully loaded and write-capable — contradicting the method's own documented "later calls are cheap" contract. Navigating from a loaded `workspace` into `documents` triggered a second, fully redundant DFS walk that re-derived and clobbered `workspace`'s SDK-internal state during an unrelated deeper descent. Added a cache short-circuit that reuses an already-cached, write-capable child as-is; a read-only-seeded cached entry (zero writeKey) still falls through to the full resolve+unseal+recovery path so 68.1-23's `recoverWriteKeyIfNeeded` write-chain-recovery guarantee is preserved.
- Hardened `folder.store.ts`'s `folder:loaded`/`folder:updated` handler (threat model T-68.1-26-01, the plan's second named suspect location) to reject an event carrying an empty `children` array when the store already holds a loaded, non-empty entry for that folder — logs a warning instead of silently blanking the rendered ancestor.

## Decisions Made

- The cache short-circuit in `dfsFindFolder` is gated on a REAL (non-zero, 32-byte) `writeKey` — matching the exact zero-detection predicate already used by `recoverWriteKeyIfNeeded`/`refreshFolderStateFromNetwork`/`getWriteBodyParams` elsewhere in `client.ts` — so a read-only-seeded cache entry never short-circuits past the write-chain recovery it still needs.
- The `folder.store.ts` guard is narrowly scoped to the empty-over-non-empty mismatch case only; it does not block a legitimate real-mutation event that empties a folder's children (that folder wasn't already carrying non-empty loaded children being silently discarded by a stale/mismatched event — a real deletion mutation flows through the normal store-set call sites, not this reactive SDK-event path, for the scenarios exercised by this regression).
- `useFolderNavigation.ts` was read and traced in full per the plan's `<read_first>` list but intentionally left unmodified — the fast path itself was proven correct; changing it would have been treating a symptom rather than the source.
