# Phase 68.1 Research: Web Client Runtime Integration

## Summary — what this phase is

The v2.0 refactor shipped the read-chain (Phase 63) and write-chain (Phase 65) **in `packages/sdk-core` / `packages/sdk/share/shared-write.ts`**, but deferred the **web app + `CipherBoxClient` runtime wiring** as `throw new Error('not implemented — phase 63/65 (...)')` stubs. The full `tests/web-e2e` suite has therefore never run green since Milestone 4 started — a new-user login throws at `apps/web/src/hooks/useAuth.ts:210` (root Node init), so no login-dependent spec can pass. Measured baseline on this branch: **6/208 passed, 19 failed, 183 did-not-run** (only `wallet-login.spec.ts` UI-state tests pass).

**46 runtime stubs total: 17 `phase 63` (read) + 29 `phase 65` (write).**

### Three load-bearing findings

1. **Mostly wiring, with one genuine build.** The codec (`@cipherbox/core/node`) and read/write chains exist. Owned folder read/nav, shared read nav, and all 7 shared write ops (`shared-write.ts`) are implemented — the stubs are client/web wrappers. **EXCEPTION:** owned **file** create/update (`packages/sdk-core/src/file/index.ts` `createFileMetadata:119`, `updateFileMetadata:163`) are genuinely stubbed and must be **built in sdk-core** (heavily copyable from `uploadToSharedFolder`/`updateSharedFile`). This is the largest single work item.

2. **Two open architecture decisions** (see below) — must be resolved in the plan.

3. **Internal sequencing is forced: read-chain first.** Many `phase 65`-labelled stubs actually depend on the read-chain (subtree walks, key resolution): `downloadFromIpns`, version download, `collectChildKeys`, bin subtree collect, shared move/delete childId + dest-key resolution, and owned `createFolder` (`client.ts:760`, tagged phase 63). Plan waves: read foundation → owned file write-chain → owned/shared write wiring → web-e2e enablement.

### Stale comments to ignore
Several `client.ts` comments claim `updateSharedFile`/`moveInSharedFolder` are "stubbed in shared-write.ts" — they are **fully implemented**. The stubs are the client wrappers/web handlers, not the sdk-core primitives.

### Obsolete — delete, do not implement
`packages/sdk/src/reencrypt.ts` (`reencryptFileMetadataForFolderChange`) — no callers; content self-seal removes re-encrypt-on-move.

## Open design decisions (resolve in the plan with a recommendation)

**D-1 (read): file-vs-folder kind discrimination.** `SealedChildRef` is a frozen schema with **no `kind` field** (`packages/core/src/node/types.ts`), so the file browser can't tell file from folder without a network hop per child. `isFileRef`/`isFilePointer` (`apps/web/src/utils/fileTypes.ts:137,145`) throw. Options: (a) resolve+cache kind at folder-load (only cheap if children are fetched anyway — they are on the read-chain path to a target, but a plain sibling listing does not fetch every child), (b) lazy-resolve+cache kind on demand (async icons), (c) carry kind in the in-memory `FolderState` populated at create time. Frozen read schema must not change.

**D-2 (write): owned `FolderState` model.** Owned `FolderState` (`packages/sdk/src/types.ts:164`) is **read-chain-only** — no `writeKey`, no `publishedNode`, uses `ipnsKeypair` directly. Shared `SharedFolderState` (`types.ts:205`) carries the full write-body model. Owned file write (a/b) needs either (i) extend the owned model to the write-body model like shared (clean copy of `shared-write.ts`, larger blast radius), or (ii) keep read-chain-only and thread the file `ipnsPrivateKey`/writeKey another way. This is the biggest open question and gates the owned-file-write plans.

### (b) navigation / read fan-out
- `packages/sdk/src/client.ts:478` — `ensureFolderLoaded(targetIpnsName)`: DFS from root through `folderTree`, unsealing each child readKey (and write-body for `ipnsPrivateKey`/writeKey). - `apps/web/src/utils/fileTypes.ts:137,145` — `isFileRef`/`isFilePointer` → D-1.

### (c) owned file read
- `apps/web/src/services/file-metadata.service.ts:71` — `resolveFileMetadata`: single read-chain hop (unseal child readKey → fetch file Node → `unsealContent`). Pattern: `navigate.ts:145-171`, `client.ts:892-912`.

- `apps/web/src/hooks/useFilePreview.ts:53`, `useStreamingPreview.ts:46,50`, `DetailsDialog.tsx:104` — wiring on top of the resolver.

### (d) shared-folder read nav / download
- `packages/sdk/src/client.ts:2374` — `moveInSharedFolder` wrapper → wire to implemented `shared-write.ts:772` (comment is stale).
- `apps/web/src/hooks/useSharedNavigationActions.ts:78,88,126,136,145` — `navigateToShare`/`navigateToSubfolder`/`navigateUp`/`navigateToBreadcrumb`/`downloadSharedFile` → wire to `navigateReadChain` (`sdk-core/share/navigate.ts:106`) + `enumerateSharedSubtree` (`client.ts:2394`, implemented). `navigateToRoot`/`hideSharedItem` already work.

## Reference implementations (copy these)

Canonical write-chain — `packages/sdk/src/share/shared-write.ts` (uses codec + injected `publishNodeFn`/`addToIpfsFn` seams):
- `uploadToSharedFolder:409` → template for owned file create (a).
- `createSharedSubfolder:298` → owned createFolder.
- `updateSharedFile:640` → owned update + versions (b/c); preserves `id`/`generation`/`createdAt`/`originalVersions`, publishes `seq+1`.
- `moveInSharedFolder:772` → move (publish dest before src = dup-not-orphan).
- `deleteFromSharedFolder:600` → remove read-body by ipnsName, write-body by UUID `childId`.
- Helpers: `buildChildWriteLink:155`, `walkChildWriteKey:183`, `unsealParentWriteBody:202`, `publishOrThrow:224`, `resealAndPublishParent:247`.

Read-chain — `navigateReadChain` (`sdk-core/share/navigate.ts:106`); `loadFolderMetadata` (`sdk-core/folder/load.ts:54`); child-key re-seal in `client.ts moveItem:851-923` (`unsealChildReadKey`→`sealChildReadKey`).

CAS/publish — `updateFolderMetadataAndPublish` (`sdk-core/folder/registration.ts:159`) + `publishWithCas` (`sdk-core/cas.ts`); **first publish must embed `sequenceNumber: 1n`** (strict gate). Client seam: `buildSharedWriteContextFromState` (`client.ts:2095`) routes content pins via `pinWithMode` (BYO/external) but node metadata through CipherBox.

Zeroization (D-09): mint keys as `let x: Uint8Array | null`; `.fill(0)`+null on success AND in `catch`/`finally`; **never zero caller-supplied buffers** (a derived key is zeroed by the deriver, a caller-supplied one is not — see `moveInSharedFolder` `didDeriveWriteKey:843-864`).

## Validation Architecture

The phase's exit gate is the **full `tests/web-e2e` Playwright suite** (login→browse→upload→download→share→delete→versions→rotation UX) — this is the primary, integration-tier validation and is what the user requires to prove Phases 62–68 at runtime.

- **Local/CI stack:** Postgres + Kubo (v0.42, CORS) + redis + mock-ipns-routing (`tools/mock-ipns-routing`); Playwright `webServer` auto-starts mock-ipns (:3001), API dev (:3000), web dev (:5173). Run: `pnpm test:web-e2e`. See `.github/workflows/web-e2e.yml` for the canonical recipe.
- **New sdk-core owned-file write-chain (`createFileMetadata`/`updateFileMetadata`)** is genuine new logic → cover with **Vitest** in `packages/sdk-core` (analog: existing `shared-write`/rotation suites), TDD-eligible.
- **SDK-tier round-trip:** the `tests/sdk-e2e` suite (real client→API IPNS) should stay green for any sdk-core write-chain change.
- **SC#5 doctrine:** ZERO `apps/web/src/*.spec.ts` — web behavior proven only by web-e2e; testable logic hoisted to SDK.
- **Backstop / non-inferable checks:** the `grep -rn "not implemented — phase 6"` emptiness assertion (SC#1); per-capability web-e2e specs already exist for most flows (upload, sharing, versions, recycle-bin, media, streaming, invite) — enable them by making the runtime real.
