<objective>
Fix the live, reproduced bug where an owned file moved into a subfolder becomes permanently un-editable ("File k51… is not write-capable (no WriteChildRef)"). `CipherBoxClient.moveItem` re-links the read-plane SealedChildRef and re-seals the child readKey for the destination, but leaves the moved child's WriteChildRef orphaned in the SOURCE write-body (write-link re-homing was deferred to 68.1-02 and never implemented). Implement write-link re-homing on move: unseal the moved child's WriteChildRef under the source writeKey, remove it from the source write-body, and re-seal it under the destination writeKey into the dest write-body — preserving the existing dest-before-source publish ordering for crash consistency.

Purpose: WEB-02 (owned file operations end-to-end on the write chain). Move is the last owned-write op whose write-plane link was never re-homed; without this, every owned file moved between folders loses editability in its new location.

Output: moveItem re-homing + a real-crypto RED/GREEN unit test + an e2e assertion matching the user's exact repro (edit and save AFTER moving into a subfolder, and after moving back) + a documented read-only check of the bin restore path.

Source coverage (gap-closure, single plan): closes the WEB-02 owned-move write-chain gap surfaced by the 2026-07-03 user repro. Read-plane move, per-file re-encrypt on move, and batch-upload WriteChildRef insertion are already covered (68.1-09/68.1-29); this plan adds only the missing move-time write-link re-homing.
</objective>
