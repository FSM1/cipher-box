# Phase 68.1 Plan 31: Move Write-Link Re-Homing Summary

**Fixed the live "moved file not write-capable" bug: `CipherBoxClient.moveItem` now unseals the moved child's WriteChildRef under the source writeKey, drops it from the source write-body, and re-seals it under the dest writeKey into the dest write-body — keyed strictly by node UUID, symmetric on round-trip, proven by both a real-crypto unit suite and a live single-file e2e edit-and-save repro.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2/2
- **Files modified:** 2 (`packages/sdk/src/client.ts`, `tests/web-e2e/tests/move-restore-content.spec.ts`)
- **Files created:** 1 (`packages/sdk/src/__tests__/move-write-link-rehoming.test.ts`)

## Accomplishments

- Root-caused and fixed the reported bug: an owned file moved into a subfolder read fine but permanently failed to save with "File ... is not write-capable (no WriteChildRef)" — `moveItem` re-linked the read-plane `SealedChildRef` and re-sealed the read key for the destination, but always left the moved file's `WriteChildRef` orphaned in the SOURCE write-body (this re-homing step was deferred to 68.1-02 and never implemented).
- `moveItem` now: finds the moved child's `WriteChildRef` in the source write-body by node UUID (`childPub.id`, never the ipnsName-based `childId` caller param); unseals it under the source writeKey with the SealedChildRef parent-mirror `generation`; re-seals it under the destination writeKey; threads the updated `writeChildren` lists into both the dest and source `updateFolderMetadataAndPublish` calls and their `adoptPublishedFolderState` adoptions, preserving the existing dest-before-source publish ordering for crash consistency.
- Read-plane-only moves (source or dest read-only, or the moved child has no source `WriteChildRef`) resolve without throwing and emit a `console.warn` instead — never fabricate a write link under a zero/absent key.
- The recovered child writeKey buffer is zeroed in a `finally` on every exit path (D-09); the folder-owned source/dest writeKeys are never zeroed.
- Real-crypto RED-first unit suite (6 tests) locks the contract: dest gains the re-sealed `WriteChildRef` unsealable under the dest writeKey, source loses it, round-trip move-back re-homes symmetrically, both edge cases resolve cleanly, and zeroization is proven by spying on the real `unsealChildWriteKey` return buffer.
- Live single-file e2e run against the local stack (docker + API dev + web dev server, sdk dist rebuilt) proves the user's exact repro fixed: edit-and-save an owned file immediately after moving it into a subfolder succeeds, the edit persists, and the round-trip move back to root followed by another edit-and-save also succeeds — 4/4 tests passed, exit 0, no flake re-run needed.
- Investigated (no code change) the analogous bin restore path: `deleteToBin`/`addToBin` preserve the removed child's `WriteChildRef` in the source parent's write-body verbatim (the read-body child list is filtered independently of the write-body), so restoring to the ORIGINAL parent stays write-capable. `restoreFromBin` accepts an arbitrary target and only re-links the read-plane `SealedChildRef`, preserving the target write-body verbatim with no `WriteChildRef` insertion — restoring to a DIFFERENT parent would reproduce the same bug class. Documented as a follow-up since the shipped restore flow always targets the original parent.

## Decisions Made

- **Round-trip unit test bucketing by call order, not IPNS name.** The first draft of the round-trip test keyed captured publish calls by matching a hardcoded `DEST_IPNS` constant. Against the UNMODIFIED (buggy) `moveItem`, this produced a **false pass**: the buggy code preserves both write-bodies verbatim on every move, so the moved `WriteChildRef` simply never left its original folder across either leg of the round trip — the test's assertion happened to line up with that inertness by coincidence, not because re-homing occurred. Fixed by bucketing captured publish calls by ORDER (dest publish is always call 0, source is always call 1 — the dest-before-source invariant the plan documents) and adding an explicit mid-round-trip assertion on the live `FolderState` in `folderTree` (proving the entry actually moved after leg 1, not merely survived in place). This produced a true RED (5/6 failing) before the fix and a true GREEN (6/6) after.
- **Bin restore-to-different-parent left as a documented follow-up**, not fixed in this plan — see Accomplishments. Matches the plan's explicit scope boundary.
