<objective>
Close the last open item of Phase 68.1: make writable-shares.spec.ts 10.4 pass by
eliminating the owner-side async kind-cache render race so the OWNER file browser never
presents a file as a folder to user actions.

The D-02 kind cache (`apps/web/src/lib/kind-cache.ts`) resolves each child's file-vs-folder
`kind` asynchronously (IPNS resolve + IPFS fetch per child, memoized by ipnsName). `isFileRef`
reads it synchronously with a folder-safe default on a miss. When children are projected into
the folder store BEFORE the cache is warm, a file row transiently renders and behaves as a
folder ([DIR]); `ContextMenu`'s `isFile && onEdit` guard then hides the "Edit" item. Test 10.4
reloads, waits for the row to appear, and immediately right-clicks + clicks "Edit" — inside the
same test function with no settle wait — so it hits that cold-cache window and times out.

Fix: align EVERY owner-side child-projection path with `navigateTo`'s established D-02 ordering
(await `resolveKinds` before the children land), so a row is only interactable once its kind is
resolved. This is the app-side fix the user chose; the spec is NOT weakened.

Purpose: WEB-02 exit-gate closure for Phase 68.1 — owner file browser rows are kind-correct at
first interaction.
Output: Kind-safe owner projection across `folder.store.ts`, `useFileBrowserActions.ts`,
`folder-helpers.ts`; extended `folder.store.test.ts` ordering coverage; a live single-file
writable-shares run with 10.3 AND 10.4 green.

## Code-verification finding (why scope extends beyond folder.store.ts)

The gap report (deferred-items.md "From 68.1-32") root-causes the race to
`folder.store.ts`'s `subscribeToSdk` fire-and-forget `resolveKinds`. That is a real,
documented D-02 timing gap and IS fixed here. But verifying against the reload path shows
the store handler is necessary-but-not-sufficient for 10.4:

- On `page.reload()`, `FileBrowser` mounts and `useSyncPolling(actions.handleSync)` fires an
  IMMEDIATE initial sync. `handleSync` (`useFileBrowserActions.ts:~108-147`) resolves root
  IPNS + `fetchAndDecryptMetadata` and calls `updateFolderChildren('root', metadata.children ?? [])`
  DIRECTLY — with NO `resolveKinds`, bypassing the SDK `loadFolder`/`folder:loaded` emit
  entirely. This direct insert is what satisfies the test's `waitForItemToAppear`, and it
  leaves the kind cache cold.
- `folder-helpers.ts`'s `resyncFolder` (409-conflict resync) has the same omission.

So fixing only `folder.store.ts` would leave the deterministic 10.4 reload path unfixed. Per
the planning steer ("verify against code … prefer Direction 1 unless the code contradicts"),
the code contradicts a folder.store-only scope. This plan applies Direction 1's resolve-before
-insert ordering consistently to all three owner-side projection sinks. No spec change is
needed — because a row only becomes interactable after its kind resolves, `waitForItemToAppear`
resolves after the cache is warm and the "Edit" item is present at right-click time.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SDK/network -> kind cache | `resolveKinds` performs IPNS resolve + IPFS relay fetch per child to read the child's plaintext `PublishedNode.kind`; awaiting it before projection introduces a network-latency dependency on the render path. |
| SDK events -> folder store | Multiple async folder:loaded/folder:updated events (and direct handleSync/resyncFolder inserts) can race to project children into the same store entry. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-68.1-33-01 | Denial of Service | folder.store.ts subscribeToSdk await-on-miss | medium | mitigate | Hybrid: all-cached AND empty-children events stay synchronous (no added latency, preserving 68.1-29 delete-last-item and 68.1-26 guard). Only cache-miss events await, and `resolveKinds` is bounded-concurrency + swallows per-ref failures, so a slow/failing resolve still projects folder-safe rather than hanging. |
| T-68.1-33-02 | Tampering | stale/out-of-order event clobber | medium | mitigate | The async projection re-looks-up the store after `await` and refuses to apply when `current.sequenceNumber > eventSequence` (sequence-as-clock), preventing a stale in-flight resolve from overwriting a newer applied state. |
| T-68.1-33-03 | Denial of Service | handleSync await on reload/upload | low | accept | handleSync already wraps its body in try/catch and `resolveKinds` never rejects; a failed resolve leaves rows folder-safe (same as today's fire-and-forget). The reload path gains one best-effort resolve before rows appear — the `vault-syncing` loading state already covers that window. |
| T-68.1-33-04 | Information disclosure | kind read | low | accept | `PublishedNode.kind` is plaintext top-level metadata already read by the existing kind cache; no new key material, endpoint, or unsealing is introduced. |
| T-68.1-33-SC | Tampering | npm/pip/cargo installs | n/a | accept | No new packages installed — this plan edits existing apps/web source and one test file only. No Package Legitimacy Gate applies. |
</threat_model>
