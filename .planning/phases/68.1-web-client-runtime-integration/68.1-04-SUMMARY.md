# Phase 68.1 Plan 04: Owned File Read + Kind Discrimination Summary

**Web `resolveFileMetadata`/`downloadFileFromIpns` now recover a file's readKey from its `SealedChildRef` and decrypt content with the raw fileKey (base64 iv), and `isFileRef`/`isFilePointer` are synchronous kind-cache-backed booleans (D-02 resolved) — no throwing stubs remain in any file this plan touched.**

## Accomplishments

- `apps/web/src/lib/kind-cache.ts` created: module-level `ipnsName -> 'file'|'folder'` memoization map with `getKind`/`setKind`/`resolveKinds` (bounded concurrency, best-effort) and `clearKindCache`. `resolveKinds` reads each child's plaintext `PublishedNode.kind` (no unsealing needed, NODE-03) via the web-native ROT-07-gated `resolveIpnsRecord` + ctx-free `fetchFromIpfs`.
- `isFileRef`/`isFilePointer` (fileTypes.ts) rewritten as synchronous, cache-backed booleans — no throw, folder-safe default (`false`) on a cache miss, `SealedChildRef` schema untouched.
- `resolveFileMetadata` (file-metadata.service.ts) implemented: given a file's `SealedChildRef` and the parent folder's readKey, recovers the file's own readKey via `unsealChildReadKey` (AAD built from the file's own `PublishedNode.id`, kind `'file'`, and `fileRef.generation` — the parent mirror, never the file's own envelope generation) and unseals its `NodeContent`.
- `downloadFileFromIpns` (download.service.ts) implemented: resolves `NodeContent` via `resolveFileMetadata`, fetches the CID, and decrypts with the raw (non-ECIES) fileKey — GCM or CTR per `encryptionMode`, `fileIv` decoded from base64 (v3 contract, not hex).
- `createFileMetadata`/`updateFileMetadata`/version-transform helpers remain stubs (owned by 68.1-09/68.1-12) — untouched by this plan.

## Decisions Made

- **resolveFileMetadata signature: `(fileRef: SealedChildRef, folderKey: Uint8Array)` instead of `(fileIpnsName: string, folderKey: Uint8Array)`.** The plan's stated shape (`resolveFileMetadata(fileIpnsName, folderKey)`) cannot satisfy the node/v3 read-chain: `SealedChildRef.readKeySealed` and `.generation` (both required inputs to `unsealChildReadKey`) exist ONLY on the parent's `SealedChildRef` for that child, never derivable from `ipnsName` alone (NODE-03 — `id`/`kind` are also never stored on `SealedChildRef`, requiring one extra `PublishedNode` fetch to learn the file's plaintext `id`). All 3 live call sites (TextEditorDialog, DetailsDialog, useFileSize) already had the full `SealedChildRef` in scope, so the fix was a same-shape parameter swap, not new plumbing.
- **Web-native primitives, not sdk-core's ctx-based helpers.** sdk-core's `resolveFileMetadata`/`downloadFileContent` (68.1-07) require an `SdkContext`, which the web app has no bridge to expose from its service layer (confirmed via the existing `useFileBrowserActions.ts`/`DetailsDialog.tsx` pattern — they already use `ipns.service.ts`'s own `resolveIpnsRecord`, not sdk-core's). Re-implemented the same read-chain hop using `resolveIpnsRecord` (ipns.service, ROT-07 anti-rollback gated) + `fetchFromIpfs` (lib/api/ipfs, ctx-free) + `unsealChildReadKey`/`unsealNode` (`@cipherbox/core`) + `decryptAesGcm`/`decryptAesCtr` (`@cipherbox/crypto`, the same primitives sdk-core's `downloadFileContent` uses internally) — same crypto, web-native transport. This is a strict correctness improvement over calling sdk-core directly: sdk-core's raw `resolveIpnsRecord` does NOT apply the ROT-07 durable anti-rollback floor the web's wrapper does, so calling it directly would have silently dropped tamper/rollback protection (threat T-68.1-04-02).
- **`downloadFileFromIpns` parameter shape redesigned** from `{fileMetaIpnsName, folderKey, privateKey, fileName}` to `{fileRef, folderKey, onProgress}` — `privateKey` was obsolete (v3 stores `fileKey` raw inside the sealed content, no ECIES unwrap needed) and `fileName` was unused inside the function body. Confirmed zero live callers exist yet (function is not wired into any component in this plan), so no compatibility surface to protect.
- **`clearKindCache` wired into `clear-user-stores.ts`** — the file's own header comment documents "[SECURITY: HIGH-02]" ordering and every other cache in that file (`clearFileSizeCache`, folder/vault/bin stores) is cleared on logout; the kind cache should not persist stale data across a user switch either.
