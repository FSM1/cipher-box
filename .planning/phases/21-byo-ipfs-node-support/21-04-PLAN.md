**Save handler -- encrypted IPNS entry (zero-knowledge):**

The save handler stores BYO config as a standalone encrypted IPNS entry. This preserves zero-knowledge: the server never sees the IPFS node auth tokens.

Implementation:

1. **Construct the ByoIpfsConfig object** from form state (mode, endpoint, authToken, detected protocol from testResult).

2. **Encrypt with AES-256-GCM** using the user's vault key (rootFolderKey). Follow the existing pattern from `@cipherbox/core` registry/bin encrypt functions: `JSON.stringify(config)` -> encrypt with user's key -> publish as IPNS entry.

3. **Derive a dedicated IPNS key** for BYO config. Use HKDF or a deterministic derivation from the user's vault keypair with context string `"byo-ipfs-config"`. Check if the app already stores a BYO IPNS name; if not, create one on first save and store the IPNS name in localStorage (the IPNS name is not sensitive -- it's a public identifier, the content is encrypted).

4. **Publish the encrypted blob** via the existing IPNS publish API (`sdkCore.createAndPublishIpnsRecord` or equivalent).

5. **On mount (load saved config):** resolve the BYO IPNS name, fetch the encrypted blob, decrypt with user's key, populate form state.

6. **Set BYO status on API:** Call `vaultService.setByoStatus(true)` when mode is external/dual, `setByoStatus(false)` when mode is cipherbox. This enables advisory quota on the API side.

**NOTE:** Do NOT use a server-side vaults table JSON column or `POST /vault/byo-config` endpoint as fallback. The encrypted IPNS entry is the sole storage mechanism per locked decision "Credentials stored in vault metadata on IPFS -- encrypted with user's key, decrypted client-side only. Zero-knowledge preserved."

**Save handler -- migration trigger on provider change:**

When the save handler detects that the pinning mode changed to a different provider (e.g., from 'cipherbox' to 'external', or from one external endpoint to another), and the user has existing pinned CIDs, trigger a background migration:

1. **Detect provider change:** Compare `savedConfig.mode` + `savedConfig.endpoint` with new `mode` + `endpoint`. If different and old config had pins (check quota store `usedBytes > 0`), proceed with migration.

2. **Fetch TEE public key:** The TEE public key is available from `teeKeys.currentPublicKey` (already in the app's auth context, same pattern as IPNS key enrollment). Read the existing pattern from `apps/web/src/services/folder.service.ts` or `apps/web/src/services/file-metadata.service.ts` for how teeKeys are accessed.

3. **ECIES-wrap provider configs:** Construct source and destination provider config JSON objects. Encrypt each with the TEE public key via ECIES (use `eciesjs` or the existing ECIES encrypt function from `@cipherbox/core`). The resulting encrypted strings are opaque to the server -- only the TEE can decrypt them.

```typescript
import { encrypt as eciesEncrypt } from 'eciesjs';
// Or use the pattern from packages/core/src/vault/init.ts

const sourceConfig = JSON.stringify(
  savedConfig.externalProvider ?? { endpoint: 'cipherbox', protocol: 'cipherbox' }
);
const destConfig = JSON.stringify({ endpoint, authToken, protocol: testResult?.protocol });

const teePublicKeyHex = teeKeys.currentPublicKey; // from auth context
const sourceConfigEncrypted = Buffer.from(
  eciesEncrypt(teePublicKeyHex, Buffer.from(sourceConfig))
).toString('base64');
const destConfigEncrypted = Buffer.from(
  eciesEncrypt(teePublicKeyHex, Buffer.from(destConfig))
).toString('base64');
```

4. **Call migration API:** `await migrationApi.start(sourceConfigEncrypted, destConfigEncrypted)`. This will be available from Plan 06's `apps/web/src/lib/api/migration.ts`, but define the call here. If the migration API module isn't created yet (Plan 06 depends on Plan 05), use a direct axios call as a temporary bridge -- the executor should check if Plan 05+06 have been executed.

5. **Show MigrationProgress:** After migration starts, the MigrationProgress component (Plan 06) will pick it up via polling. For now, ensure the save handler returns a flag indicating migration was triggered, so the UI can show appropriate feedback.

Discard handler: Reset all fields to `savedConfig` values, clear test result.
