# Phase 68 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

**This phase is primarily backend/client-state (rotation engine wiring, durable IndexedDB high-water state, `folderTree` reconciliation).** The UI surface is intentionally narrow — five notification/status states, all reusing the app's existing notification and header primitives. No new pages, dialogs, or layouts. This contract covers only:

1. A global rotation-progress status badge (app header) — D-02/D-03
2. Four toast-notification variants riding the existing `NotificationToast` component — D-01, D-04, D-05, D-06, D-08

If a reviewer expects more UI surface than this, they are looking at the wrong phase — see Phase 69 (FUSE/desktop) and Phase 63/65 (crypto engine, no UI).

## Copywriting Contract

All copy is plain, terse, and matches the existing `[INFO]`/`[WARN]`/`[ERR]` label convention in `NotificationToast.tsx`. No new tone — no exclamation points, no marketing language, consistent with the rest of the app's terminal aesthetic.

### Rotation status badge (D-02/D-03) — mounted in `AppHeader`'s `.header-right`, before `UserMenu`

| State | Trigger | Label | Visual |
|-------|---------|-------|--------|
| Hidden | No rotation active for this session | *(not rendered)* | — |
| Root cut in progress | `rotateReadFromNode` root step running (synchronous) | `Revoking access…` | Spinner + green (`--color-green-primary`) border, non-dismissible |
| Tail walk in progress | Background subtree walk running after root cut completes | `Finishing revocation…` | Static pill, green border, no spinner (avoid implying it's blocking) |
| Resuming after reload | Durable job record found mid-walk on page load | `Resuming revocation…` | Same pill styling as tail-walk state |

Badge is a status pill only — not a button, not focusable, no click action (D-03 explicitly deferred any interactivity; it is informational). `role="status"`, `aria-live="polite"` (never `assertive` — it is not an error).

### Toast notifications (extend `NotificationToast.tsx` / `notification.store.ts`)

| Element | Copy | Type | Notes |
|---------|------|------|-------|
| Reconcile-defer notice (D-04) | `Syncing latest state…` | `info` | Auto-retrying in background; auto-dismisses on success (no manual dismiss needed, but existing `[x]` stays available) |
| Regression rejected (D-05) | `Stale data from server rejected.` | `error` | Per-mutation toast, not a full-page block; the mutation itself did not apply |
| Defer exhausted / terminal (D-06) | `Couldn't complete securely — retry.` | `error` | Requires an action button labeled `Retry` (see Component Extension below); mutation was never applied |
| Offline/stale co-writer write failure (D-01, non-revoked) | `Write failed — access may be out of date.` | `error` | Requires an action button labeled `Refresh access` |
| Offline/stale co-writer, actually revoked (D-01, escalated) | `Write access revoked.` | `error` | No action button — refreshing cannot help; this is terminal |
| IndexedDB unavailable (D-08), shown once per session | `Secure cache unavailable — falling back to server verification.` | `warning` | One-time only; do not re-show on every subsequent mutation this session |

### Component extension required (not a new component)

`Notification` type (`apps/web/src/stores/notification.store.ts`) needs an optional action field to support D-01 (`Refresh access`) and D-06 (`Retry`):

```ts
export type Notification = {
  id: string;
  type: 'info' | 'warning' | 'error';
  message: string;
  createdAt: number;
  action?: { label: string; onClick: () => void };
};
```

`NotificationToast.tsx` renders the action as a small text button matching the existing `[x]` dismiss button's styling (same font, `--color-text-muted` default / `--color-green-primary` on hover, no background, no border-radius) — placed before the `[x]` dismiss button, e.g. `[Retry]` `[x]`. Do not use a filled/primary button style; the whole toast system is text-only chrome.

### Destructive confirmation

Not applicable — this phase adds no destructive actions. (Delete/move/rename confirmations already exist from prior phases and are unchanged here; rotation is a side effect of those existing flows, not a new user-initiated destructive action.)
