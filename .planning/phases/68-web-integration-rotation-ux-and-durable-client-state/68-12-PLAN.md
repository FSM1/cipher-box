<objective>
Close VERIFICATION Gap 2 (should-fix): `performScopeExitRotation` calls `sdkCore.rotateReadFromNode` (which re-seals + republishes the root under a NEW readKey and bumped generation/sequence) but never updates `this.folderTree`, leaving the in-memory `folderKey`/`sequenceNumber`/`nodeGeneration` at pre-rotation values. It fails safe (68-05's `reconcileFolderSequence` throws `ReconcileStaleError` on the next same-folder mutation) but is unrecoverable without a full page reload: manual Retry re-reads the same stale folderTree and fails identically.

The root cause is that `rotateReadFromNode` returns `void`, discarding the root's post-rotation state (available internally as `rootResult` from the first `rotateOne` call: `childReadKey`, `newGeneration`, `newSequenceNumber`). This plan surfaces that result and uses it to refresh the folderTree entry so a same-session retry self-heals.

Purpose: A same-session mutation on a folder that was just scope-exit-rotated must succeed without requiring a page reload.
Output: rotateReadFromNode returns the root's rotated key/generation/sequence; performScopeExitRotation writes them back into folderTree.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-memory folderTree ↔ published IPNS record | After a rotation the on-wire record advances (new readKey/generation/sequence) while the in-memory cache can lag; a mutation published against the stale cache would use a wrong key. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-68-12-01 | Tampering | mutation published against a stale post-rotation folderKey | high | mitigate | Refresh folderTree with the rotated readKey/generation/sequence immediately after rotation, so a subsequent publish uses the correct current key rather than a superseded one. The existing reconcileFolderSequence guard remains the fail-safe backstop (defer, never publish with a wrong key). |
| T-68-12-02 | Information Disclosure | zeroization of a shared/caller-owned key buffer during the folderTree swap | medium | mitigate | Zero only the OLD folderKey the folderTree entry terminally owns; store a defensive copy of the rotated readKey; never zero rootReadKey (caller-owned) or the returned RotateReadResult.readKey referenced elsewhere mid-flight (D-09 terminal-owner rule). |
| T-68-12-03 | Denial of Service | unrecoverable defer loop forcing a full page reload | medium | mitigate | Refreshing folderTree lets a same-session retry succeed, eliminating the ReconcileStaleError → bounded-retry → terminal-toast loop that previously required a reload. |

No new package-manager installs are introduced by this plan (no npm/pip/cargo additions), so no package-legitimacy checkpoint applies.
</threat_model>
