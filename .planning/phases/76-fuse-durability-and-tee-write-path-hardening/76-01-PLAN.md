<objective>
Make desktop vault initialization atomic-ish and recoverable. Today `initialize_vault` publishes the vault-key blob and the root-folder IPNS record sequentially with no preflight, so a partial failure (one record written, the other not) leaves a half-initialized vault. Critically, `root_read_key`/`root_write_key` are freshly minted random on every call (vault.rs ~127-130), so a naive "preflight, abort if exists" fix permanently strands any vault whose first attempt got partway.

This plan (SC1, closes todo:2026-06-26-vault-init-publish-ordering-preflight) adds: (1) a fail-closed preflight of BOTH IPNS names before any write, (2) a decrypt-and-resume recovery branch that ECIES-unwraps the already-published key blob to recover the original root keys rather than re-minting, and (3) a proactive unseal coherency check binding recovered keys to the existing root record.

Purpose: no vault ever ends up unregistered-but-with-published-records and permanently stuck.
Output: hardened `initialize_vault` in `apps/desktop/src-tauri/src/commands/vault.rs` with a testable network seam and extended `#[cfg(test)]` coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| desktop client -> IPNS relay (resolve) | An ambiguous resolve result crosses here; must not be interpreted optimistically |
| desktop client -> IPFS/IPNS (publish) | Publishing over an existing record would corrupt an in-flight/partial vault |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-76-01 | Tampering | initialize_vault preflight resolve | high | mitigate | Fail closed on any non-404 resolve outcome; never publish when absence is unconfirmed (Task 1/2) |
| T-76-02 | Tampering | root key coherency on retry | high | mitigate | Decrypt-and-resume recovers the ORIGINAL root keys via ECIES-unwrap; re-mint prohibited; unseal coherency check binds recovered keys to the existing root record (Task 2) |
| T-76-03 | Information Disclosure | recovered root_read_key/root_write_key | medium | mitigate | Keys stay in Zeroizing buffers; no key material in error strings or logs (Task 2) |

No package-manager installs occur in this plan (RESEARCH Package Legitimacy Audit: no new packages) — no T-76-SC supply-chain row applies.
