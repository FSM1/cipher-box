<objective>
Harden the TEE republish write-path error handling (SC3 items 1-3; closes todo:2026-07-01-tee-republish-writepath-error-handling-hardening) so real failures stop masquerading as harmless outcomes:

1. `renewIpnsRecordEol` (API) distinguishes a REAL DB error (elevate to error-level/observable) from the harmless `affected===0` CAS-miss (unchanged debug), without touching batch success accounting.
2. `decryptWithFallback` (TEE worker) rethrows a config/infra failure from `getKeypair()` via a typed `TeeKeyUnavailableError` instead of masking it as "corrupted key"; genuine epoch-mismatches still fall through to the next trial.
3. The republish route validates each batch entry is a non-null object so one malformed entry can't crash the whole batch (500).

Also resolves the RESEARCH Open Question: apps/tee-worker unit tests are wired into CI here (in-scope) so these SC3 tests are actually enforced.

Purpose: no silent write-back failure or misdiagnosed deployment misconfiguration.
Output: typed error contract across `tee-keys.ts`/`key-manager.ts`, route null-guard, API log-level fix, tests, and a small `ci.yml` wiring change.
</objective>
