<objective>
Wire the invite-claim service flow (design §3.11 / D-06), the invite half of Success Criterion 4. The crypto primitive `claimInviteReadKey` is **already fully implemented** in `packages/sdk-core/src/share/grant.ts` (lines 184–224, verified by RESEARCH) — it unwraps the share-root `readKey` with the URL-fragment ephemeral private key and re-wraps it to the claimer's public key, with no `encryptedChildKeys` fan-out. This plan adds the thin **service flow** around it: a `claimInvite` function that fetches invite data via an injected callback, calls the existing primitive, and persists a single standard grant via an injected `insertShareFn` (the Phase-64/65 D-02 mock seam).

Per D-06: one re-wrapped root `readKey` per claimer; a multi-claim invite mints one standard grant per claimer of the same `readKey`; revoke = rotate the `readKey` (Plan 06), not link invalidation. Per D-02: all transport is mocked behind injected callbacks; the apps/api `encryptedChildKeys` column/DTO drop is Phase 66. This plan only ensures the sdk-core/sdk layer has **zero** `encryptedChildKeys` consumption.

Purpose: O(recipients) grant rows instead of O(items) fan-out; eliminate the dead fan-out at the sdk layer. Output: `claimInvite`, its barrel export, and a flow test asserting a single grant and no `encryptedChildKeys`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL fragment → server | The ephemeral private key travels only in the URL fragment and never reaches the server (zero-knowledge holds) |
| invite link → reader | A v3 invite link conveys the subtree-root readKey; anyone with the link reads the granted subtree (accepted exposure, §3.11) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-65-09 | Information Disclosure | invite readKey exposure | high | accept | §3.11 accepted exposure: the link carries the subtree-root readKey by design; bounded to the granted subtree; revoke = rotate the readKey (Plan 06) |
| T-65-10 | Spoofing | replayed invite link | medium | mitigate | A replayed link re-wraps the SAME root readKey per claimer; revocation is via rotation (ADR 0002 / §3.11), not link invalidation — claimInvite adds no false revocation guarantee |
| T-65-11 | Information Disclosure | ephemeral private key handling | medium | mitigate | claimInvite does not zero the caller-owned ephemeralPrivateKey (D-09); reWrapKey zeros the intermediate readKey on success and failure |
| T-65-12 | Tampering | residual fan-out consumption | low | mitigate | Grep gate asserts zero sdk-layer encryptedChildKeys consumption — the obsoleted O(items) path cannot silently survive |

No package-manager installs in this plan (T-65-SC not applicable).
