<objective>
Implement the structured recursive write chain (WRITE-01) by rewriting the six stubbed exports in `packages/sdk/src/share/shared-write.ts` (all currently throw `"not implemented — phase 65 (write-chain)"`) on the Phase-62 write-body model, and add the explicit co-writer "cannot write until re-fetch" error (WRITE-03 / D-03).

The codec is complete (D-05): `sealNode(node, readKey, writeKey)` seals `writeBody → writeSealed` (only when `node.writeBody` is set); `unsealNode(pub, readKey, writeKey?)` returns the write-body only when a `writeKey` is supplied. Plan 01 added `sealChildWriteKey` / `unsealChildWriteKey` (role 0x04) for the write link. This plan **calls** them — it does not re-architect crypto.

Each node's write-body holds its Ed25519 signing material (`writeBody.ipnsPrivateKey`); each parent write-body seals the child `writeKey` (`writeChildren[].writeKeySealed`). The write link is NEVER in `SealedChildRef` (read-only). The defining WRITE-01 security property: a read-only holder (`readKey` only) can unseal the read-body but can never reach signing material — proven by `unsealNode(pub, readKey)` returning no `writeBody`.

Per CONTEXT discretion, deliver the **minimum that proves WRITE-01..04**: reshape `SharedWriteContext`, build the write-chain helpers, and implement the operations on the write-body model. The `addShareKeysFn` field stays in the type (Phase 68 removes it) but is never called (D-02).

WRITE-03 offline behavior: when a co-writer's write target has been rotated out (its old k51 name tombstoned/rotated — signalled here via the injected publish/resolve seam returning a tombstone/rotated indicator), the operation throws a typed `CannotWriteUntilRefetchError`. Live tombstone enforcement is Phase 66; here it is mock-tested behind the injected seam.

Output: implemented `shared-write.ts` on the write-body model, the typed offline error, and a rewritten test proving the read-only/write separation and the offline error.
</objective>
