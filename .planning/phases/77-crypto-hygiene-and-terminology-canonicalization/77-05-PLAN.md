<objective>
Make `wrapIpnsKeyForTee` bytes-in / bytes-out and move the hex boundary out to the call sites. Today it takes a hex-string TEE public key and returns a hex string; every other crypto seam in `sdk-core` works in `Uint8Array` and hex-encodes only at the API/wire boundary. Change the signature to `wrapIpnsKeyForTee(ipnsPrivateKey: Uint8Array, teePublicKey: Uint8Array): Promise<Uint8Array>` (param renamed from `currentPublicKey` to the canonical `teePublicKey`) and update its 3 current callers to hex-decode `teeKeys.currentPublicKey` before the call and hex-encode the result immediately before placing it into the `encryptedIpnsPrivateKey` wire field.

Implements Source todo `2026-07-10-wrapipnskeyfortee-bytes-in-bytes-out`. Delivers part of Success Criterion 3 (canonical `teePublicKey` naming + hex-only-at-boundary convention). This is an ATOMIC cross-file change: the signature and all 3 callers must land in the same commit or the package goes red.

SCOPE DECISION (RESEARCH Open Question 1 / Pitfall 6): This plan is NARROW — signature change + the 3 current callers of `wrapIpnsKeyForTee` ONLY. It deliberately does NOT consolidate the 3 un-consolidated inline hex->wrap->hex duplicates in `packages/sdk/src/client.ts`, `packages/sdk/src/bin/index.ts` (which has different best-effort fail-closed semantics), and `apps/web/src/services/vault-settings.service.ts`. Those are out of the literal todo scope and are left as-is to keep this change tightly scoped and green.

The `TeeKeys.currentPublicKey: string` (hex) type in `types.ts` is UNCHANGED — it stays hex at the DTO boundary; only the internal helper switches to bytes.

Purpose: Align the TEE-wrap seam with the codebase-wide bytes-internal / hex-at-boundary convention and canonical `teePublicKey` name.
Output: New `wrap.ts` signature + round-trip test + 3 updated callers.
</objective>
