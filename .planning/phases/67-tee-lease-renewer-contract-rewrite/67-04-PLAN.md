<objective>
Wire `createSubfolder`'s `teeKeys` into the published record so new subfolders enroll in TEE renewal (folded todo `2026-06-29-createsubfolder-tee-republish-wiring.md`, `resolves_phase: 67`). Today `createSubfolder` accepts `teeKeys` but never wires `encryptedIpnsPrivateKey`/`keyEpoch` into the publish, so a new subfolder's IPNS record silently expires. After the schedule collapse (67-01/67-07) `ipns_records` is the sole signing source, so the subfolder's first publish MUST carry the encrypted key.

RESEARCH Open Question 4 resolution (baked in): `createAndPublishIpnsRecord` (packages/sdk-core/src/ipns/index.ts) DOES forward `encryptedIpnsPrivateKey`/`keyEpoch` to the publish API — that wiring is complete. The gap is that `TeeKeys` (packages/sdk-core/src/types.ts) carries `currentPublicKey`/`currentEpoch`, NOT a pre-wrapped `encryptedIpnsPrivateKey`. So `createSubfolder` must ECIES-wrap the generated key itself (the established pattern in apps/web/src/services/vault-settings.service.ts and packages/sdk/src/bin/index.ts) and fail closed if `teeKeys` is present but malformed.

Purpose: Close the silent-expiry enrollment gap so subfolders created in the v2.0 model are renewable.
Output: `createSubfolder` wires + returns the TEE enrollment fields; a focused unit test proves forwarding + fail-closed.
</objective>
