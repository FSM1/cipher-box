<objective>
Rewrite the TEE republish route into the verify-in-enclave lease renewer (D-01 / TEE-01 / TEE-02 / TEE-06 / §6.4 / §6.7-2 / §7.3 tests 12, 18, 19). The relay sends the marshaled existing `signedRecord` (from `ipns_records.signed_record`) plus the encrypted IPNS key + `keyEpoch`. The TEE: (1) parses the record, (2) verifies its Ed25519 signature against `publicKeyFromIpnsName(ipnsName)`, (3) decrypts the key via the internal-epoch fallback (67-02), (4) asserts the name↔key binding, (5) re-signs the SAME CID + SAME sequence with only a later EOL (67-03's `renewIpnsRecord`), (6) zeroes the key, (7) re-encrypts to the TEE-internal current epoch when upgrading. The relay-supplied `currentEpoch`/`previousEpoch` scalars and the relay-sent CID/sequence are removed from the request contract.

Purpose: The contract "cannot originate or repoint a CID" only holds if the TEE validates the incoming signature itself — re-signing a relay-read row would relocate trust to the relay. This is the load-bearing security change of the phase.
Output: rewritten `routes/republish.ts` + extended `republish.test.ts` proving no-increment, binding rejection, verify rejection, and re-enroll surfacing.
</objective>
