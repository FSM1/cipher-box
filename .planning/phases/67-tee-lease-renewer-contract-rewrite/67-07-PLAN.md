<objective>
Reshape the relay so the canonical `ipns_records` row is the sole source of the TEE's signing inputs (D-02 / TEE-03) and the EOL-only renewal write is guarded by the same equality CAS as the Phase-66 publish path (§6.6 / TEE-04 carryover, replacing the weak `LessThanOrEqual` write-back). `getDueEntries` joins `ipns_records` (tombstone-filtered); the request body adds `signedRecord` and drops `latestCid`/`sequenceNumber`/`currentEpoch`/`previousEpoch`; the renewal write becomes a dedicated equality-CAS `renewIpnsRecordEol`; `enrollFolder` collapses to 2 args; epoch upgrades write back to `ipns_records`.

api:generate decision (stated per the project workflow): NOT required. The relay↔TEE request/response (`RepublishEntry`/`RepublishResult` in `tee.service.ts`) is an internal service-to-service HTTP call (`TeeService.republish` via `fetch`), NOT part of the public OpenAPI surface — `tee.controller.ts` exposes only `connection-test`. The schedule column drop and the new `requiresReEnroll` field do not touch any public controller/DTO. The "re-enroll required" signal's public client surface is deferred to Phase 68/69. A guard acceptance below asserts no public controller/DTO changed.

Purpose: Cut the dual-source signing state so a stale/forged schedule snapshot can never feed the signer, and harden the renewal write against forward-publish races and tombstoned names.
Output: reshaped `tee.service.ts` interface, joined `getDueEntries` + rebuilt batch, `renewIpnsRecordEol` CAS, 2-arg `enrollFolder` + updated callers, spec coverage.
</objective>
