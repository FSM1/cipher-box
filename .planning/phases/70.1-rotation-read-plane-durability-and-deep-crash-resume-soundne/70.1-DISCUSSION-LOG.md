## SC#3 — Lost-key repair

Originally framed as: an already-rotated dirty node's post-rotation readKey is unrecoverable (Phase 70 RESEARCH Pitfall 4) — what should resume do? The user asked three clarifying questions (what "typed error + top-down re-resolution" means; the trigger sequence; the window width), which established that the lost key is minted-not-derived and never persisted, and the window is network-round-trip-sized (child publish -> parent batched republish). The user then proposed persisting the key ECIES-encrypted for the rotation's duration — which reframed the whole decision from "surface a residual" to "eliminate it."

| Option | Description | Selected |
|--------|-------------|----------|
| ECIES-persist, resume | Wrap `readKeyPrime` under owner pubkey, persist ciphertext before each child publish; resume unwraps + re-seals mirror + converges. GC on mirror commit + expire abandoned jobs. Self-contained per-node recovery. | ✓ |
| Persist existing sealed key | Persist the already-computed `newReadKeySealed` (under parent key) — no new EC ops, but chained top-down recovery. | |
| Detect + surface residual | No key persisted; detect the already-rotated edge, converge the walk, raise a typed `DirtyNodeUnrecoverableError` for top-down re-resolution. | (kept as fallback) |

**User's choice:** ECIES-persist, resume.
**Notes:** The user's own proposal ("can the new key not be stored encrypted (ECIES) temporarily for the duration of the rotation to prevent this / make it resumable?") drove the outcome. Established: ECIES-under-owner-pubkey adds no net trust surface (unwrappable only with the owner key that already gates the vault) and is consistent with CLAUDE.md's ECIES rule — the never-store-keys rule is about plaintext keys / keys to the server. The "detect + surface typed error" option is retained as the fallback for the truly-expired/GC'd-key case only. Chose ECIES-wrap over persisting `newReadKeySealed` because it is self-contained per node (robust to multiple simultaneous dirty edges at depth>=2), accepting the per-node EC cost. Real cost acknowledged: the wrapped-key write must durably commit BEFORE the child publish, plus a GC lifecycle.

## SC#4 — Floor atomicity

| Option | Description | Selected |
|--------|-------------|----------|
| Single combined record | Both floors in ONE atomically-written record (Rust temp+rename; TS one IDB txn). Partial-failure divergence structurally impossible. SC#3 wrapped keys share the plane. | ✓ |
| Transactional store API | Separate stores + begin/commit transaction seam through HighWaterStore. More surface, same guarantee. | |
| Write-ahead + idempotent replay | Sequential bumps, self-heal on next resolve. Smallest change but leaves a safe-direction divergence window. | |

**User's choice:** Single combined record.
**Notes:** The fail-closed half (propagate `put`/`bump_floor` write errors instead of log-and-Ok) is mechanical, not a gray area. The combined record folds in the SC#3 ECIES wrapped-key checkpoint for one coherent durable plane; degrades to a single in-memory object on the D-08 path.

## SC#5 — Reconcile gate

Established via code read: `reconcileFolderSequence` gates generation on the cached `folderTree` value, its call sites are all write-path (not the 30s poll), and seq+signature already cover external rollback — so threading the generation is defense-in-depth against our own client equivocation.

| Option | Description | Selected |
|--------|-------------|----------|
| Thread resolved generation | Fetch resolved CID + unseal in the reconcile path; gate on the record's actual generation. Cost per write-path reconcile only. | ✓ |
| Make cached-fallback explicit + safe | Keep cached generation, document/prove the monotonic under-bump contract. Cheaper, but can't detect a gen regression in the just-resolved record. | |

**User's choice:** Thread resolved generation.
**Notes:** Chosen for completeness given this is a durability/soundness phase; the extra fetch+unseal lands on writes (two on a move), never on polls.
