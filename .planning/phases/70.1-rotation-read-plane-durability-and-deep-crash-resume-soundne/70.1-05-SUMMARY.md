# Phase 70.1 Plan 05: keyCheckpoint Seam + Persist-Before-Publish + Dirty-Item Repair Summary

**ECIES key-checkpoint seam on the TS rotation engine — `rotateOne` durably persists the minted `readKeyPrime` (wrapped under the owner's own pubkey) before the child publish, and the BFS routes any already-rotated dirty node to a checkpoint-repair path instead of crashing on the stale pre-rotation key.**

- A genuinely lost/GC'd checkpoint (`getWrappedKey` returns `undefined`) throws `DirtyNodeUnrecoverableError` instead of an opaque AEAD crash

## Decisions Made

- **Backward-compatible opt-in gating:** the new dirty-item repair path only activates when `keyCheckpointCallbacks` is supplied on `RotationParams`. This was necessary because several EXISTING tests (Plan 70-06's "safe double-rotation" Test 1, and Plan 70.1-01's SC#1/SC#2 depth>=2 dirty-resume tests) exercise dirty items with NO checkpoint callbacks wired, and must keep passing unmodified per the plan's own acceptance criteria ("existing engine tests + Plan-01 SC#1/SC#2 cases still pass"). Gating on callback presence (mirroring the file's established D-01 conditional-invocation convention for `grantCallbacks`/`reMintGrantsRootedAt`) reconciles both requirements: the new safety property is enforced whenever the checkpoint plane is wired, and pre-existing safe-double-rotation behavior is preserved when it is not.
- **`isDirtyItem` stamped only in `enqueueDirtyFrontierItem`:** rather than re-checking generation via an extra IPNS resolve/fetch at dequeue time (the plan's alternative option), the flag is set once at enqueue time. This is cheaper (no duplicate round-trip for every queue item) and correctly captures the actual production bug scope (depth>=2 dirty nodes / same-run dirty-tail merges with no competing normal-path enqueue) without altering the existing depth-1 dedup precedent.
- **Repair-path scope:** the repaired node's own children ARE enqueued this run (unsealed with the recovered key), consistent with "seeds the node's ParentTrackingState so its own children still enqueue." A childless (leaf) repaired node's recovered key is left unzeroed by the repair function itself, matching the pre-existing codebase convention that a freshly-minted/recovered "current" key for a node with zero children is never explicitly defensively zeroed elsewhere in this file (only OLD/pre-rotation keys and copies created for teardown are).
