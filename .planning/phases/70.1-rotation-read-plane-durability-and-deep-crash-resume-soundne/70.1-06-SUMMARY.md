# Phase 70.1 Plan 06: Rust Depth-Aware Dirty-Resume Consumption Summary

**Rust twin of the TS SC#1/SC#2 fix: generalized parent-tracking seed-or-find primitive + BFS requeue guard so a depth>=2 dirty-resume entry's REAL intermediate parent republishes instead of being silently dropped**

## Accomplishments

- Ported the TS engine's SC#1/SC#2 depth-aware dirty-frontier consumption fix (Plan 70.1-01) to the Rust `rotate_read_from_node` engine, on top of Plan 04's widened `DirtyFrontierEntry`/recursive `verify_subtree_clean` structural catch-up
- Fixed Bug A: the dirty-resume branch previously seeded ONE root-only `ParentTrackingState` and matched frontier entries against `root_children` only — a depth>=2 entry's real parent (any intermediate node) was never found there and got silently `continue`-dropped (no decrement, wedging `pending_child_count` forever). Now every DISTINCT real parent in the frontier gets its own `ParentTrackingState`, seeded via a new `find_node_by_ipns_name` walk-from-root primitive
- Fixed Bug B: `complete_pending_child`'s silent no-op when a parent isn't tracked is now backed by a lazy `seed_or_find_parent_tracking_state` fallback in the BFS loop (mirrors the TS reference's identical fallback), plus a requeue guard that defers a dequeued item until its own real parent has a chance to seed its tracking entry first
- The pre-rotation dirty-frontier probe (`verify_subtree_clean`) now runs UNCONDITIONALLY before `rotate_one(root)` — not only on a resume-Skip — and is folded into the normal/fresh walk too, closing the Rust structural gap the TS engine already closed
- Two new `#[tokio::test]` cases (`sc1_...`, `sc2_...`) prove depth-2 and depth-3 dirty-resume consumption end-to-end through `rotate_read_from_node`, not just `verify_subtree_clean`'s detection

## Decisions Made

- Both new tests (SC#1 single-hop `root→A→B`, SC#2 double-hop `root→A→A2→C`) exercise the resume/Skip-root branch exclusively. I deliberately did not construct a "normal-branch ordering" test that would have a frontier-fold item's real parent ALSO undergo its own natural fresh rotation in the same run — tracing that scenario by hand revealed a genuine (pre-existing, TS-shared) double-enqueue risk: a fold-based item and that same node re-discovered via its parent's own recursive children-enqueue can both land in the queue, and the second processing attempt would try to unseal a body already re-sealed under a freshly-minted key by the first. This is a latent limitation inherited from the TS reference (`engine.ts`'s own `enqueueDirtyFrontierItem` has no de-dup against a LATER natural recursion, only against items already queued at fold time), not something this plan's must-haves ask me to additionally fix. I stayed within the plan's literal scope (port SC#1/SC#2 as TS did) rather than scope-creep into hardening that edge case.
- `pre_rotation_frontier` is computed once, unconditionally, before `rotate_one(root)`, and reused as-is on the Skip branch (no second `verify_subtree_clean` call needed) — this exactly mirrors `engine.ts:1092-1094`'s `preRotationDirtyFrontier` and avoids redundant resolve/fetch work.
- `root_read_key_owned` is a single defensive `Zeroizing` clone of the caller-supplied `root_read_key`, reused by both the resume branch's proactive per-parent seeding loop and the BFS loop's lazy fallback seeding — kept distinct from `root_read_key_arr` (a separate clone) which is moved into root's own `ParentTrackingState` on the Skip branch, so the walk-primitive's copy stays available for the rest of the function.
