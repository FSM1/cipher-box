# Phase 70.1 — Learnings

Rotation read-plane durability and deep crash-resume soundness. Mined from the 13 plan
summaries, VERIFICATION/VALIDATION/SECURITY reports, the two debug records, and the
ship/review cycle (96-commit branch, first PR CI run, CodeRabbit + Greptile findings).

## Decisions

### Coalesce the shallow scope-exit publish rather than relax the assertion
A scope-root with a child inherently costs two rotation publishes (`rotate_one` +
batched `republish_parent`). Instead of weakening the D-16 "+1" assertion, we added an
additive engine primitive `rotate_read_from_node_with_root_children` that re-seals the
grant-root once with the caller-supplied post-delete child list and suppresses the plain
relink. Kept the security-meaningful invariant (exactly one authoritative publish, new
key) instead of encoding a leaky implementation detail (+2) into the test.

### Fail closed at every rotation gate, surface Err/EIO not silent no-op
Floor store fails closed on corrupt AND non-NotFound read errors; grant-scope gate fails
closed on non-authoritative cache (D-15a), incomplete ancestor walk (D-15b), and poisoned
lock (D-15c). A revocation bypass that silently no-ops is worse than an EIO — the whole
phase leans on "refuse rather than under-rotate."

### Background publish-pump backstop over upload-completion chaining
The idle-mount republish-starvation fix chose a wall-clock background thread that pokes
the mount (fresh uncacheable lookup name) over chaining the republish off upload
completion. Rationale: `fs` is moved into `fuser::mount2` and owned exclusively by the FS
thread, so the chaining option required a risky fs-sharing refactor; the pump drives the
existing drain by generating a benign FUSE op with zero new sharing.

### Scope the covered-delete fix to the shallow grant-root; defer deep intermediate keys
Fix A refreshes only the grant-root inode's in-memory key (the engine returns only the
root's `RotateReadResult`). Deep scope-exits still reseal intermediate parents under stale
keys — explicitly documented as a tracked follow-up, not silently closed. Shipping the
shallow D-16 case while naming the deep gap kept the phase bounded.

## Lessons

### Twin parity is not automatic — a fix in one engine must be checked in the other
CodeRabbit caught a real TS/Rust divergence the phase's own verification missed: the TS
rotation engine GC'd a child's ECIES key-checkpoint (`deleteWrappedKey`) BEFORE the
batched parent republish committed, while the Rust twin already deferred correctly via
`pending_checkpoint_node_ids`. When two engines are declared "twins," every substantive
fix landed in one is a parity checklist item for the other — verify it explicitly against
real code. The engine soundness fix (missing-root dirty signal on the resume convergence
check) was likewise a both-engines-together parity item.

### Open the PR earlier — branch-wide CI gates don't run locally or on the shared checkout
A 96-commit branch with no PR meant the first PR CI run surfaced two pre-existing gate
failures never seen locally or on the dispatch-gated desktop-e2e. Open the PR (or run the
gates locally) far earlier so these are found mid-flight, not at ship.

### The SC#6 single-gated-read grep gate has a ±1-line marker window
The gate flagged an unmarked `resolve_ipns_verified(` call in the production rotation
adapter. The `// sc6-allow:` marker must sit WITHIN ONE LINE of the call — a 3-line
explanatory comment block does NOT satisfy the ±1-line window. Put the marker on the line
immediately adjacent to the call.

### fuse-only test modules need feature-gating, not bare `#[cfg(test)]`
The Windows `cargo test --features winfsp` build failed E0433 because a `grant_scope` test
module using the fuse-only `crate::test_support` was gated on `#[cfg(test)]` alone. It must
be `#[cfg(all(test, feature = "fuse"))]`. A test that depends on a feature-gated support
module must carry the same feature predicate, or it breaks other feature permutations.

### Check whether CI fmt-checks before running `cargo fmt`
`cargo fmt -p <crate>` reformats the WHOLE crate, its local rustfmt version can differ from
CI's, and it stranded 8 out-of-scope files (even re-formatting already-committed code
differently). This repo's CI does NOT run `cargo fmt --check` at all, so the churn was pure
noise. Verify whether CI enforces fmt first: if it doesn't, don't run it; if it does, scope
reverts to only intentionally-edited files (`git checkout --` the drift).

### A live-stack anti-vacuous gate can't be discharged under scoped verification
SC#6's definition of done is a live docker-stack sdk-e2e run, which scoped verification is
constrained from starting — correctly landing as `human_needed` rather than a fabricated
pass. The Rust twin's identical depth-3 crash-resume + ECIES-checkpoint-repair invariant
passing at unit tier is strong indirect evidence, but not a substitute for the named gate.

## Patterns

### Adversarial reviewer verifies each finding against real code before fix-or-refute
A security-reviewer subagent verified every substantive CodeRabbit/Greptile finding against
the actual code before acting. This confirmed the real TS/Rust checkpoint-GC divergence AND
correctly REFUTED two false positives: the client key-borrow finding and the
`get_wrapped_key` double-`Zeroizing` suggestion. Fix-or-refute-with-evidence beats
blindly applying reviewer suggestions.

### Goal-backward verification — observable truths mapped to file:line + a passing test
Each ROADMAP success criterion was traced to a concrete code location and a specific
non-skipped asserting test (file:line), not to intent or documentation. Makes vacuous
coverage visible (SC#6's fixture-present-but-not-run state was caught this way).

### FakeTransport publish-count assertions pin exact publish behavior
The "+2" defect was root-caused deterministically by a `FakeTransport` test asserting
`publish_count_for(grant-root)`: childless == 1, one-child == 2, coalesced == 1. Counting
publishes against an injectable transport turned a timing-driven e2e flake into a
deterministic offline proof.

### Terminal-owner-only zeroization + refresh the in-memory inode key after rotation
The revocation-bypass fix copies the post-rotation `read_key` into the grant-root inode in
place (never zeroing the caller-owned `Zeroizing` `RotateReadResult`, never logging bytes)
so every later local relink reseals under the NEW key. Rotating the record without
refreshing the in-memory key that later publishes reference is a silent revocation bypass.

### Edge-triggered queues need a wall-clock backstop when the trigger can go silent
The publish queue drained only from inside FUSE op handlers with no timer. Any
edge-triggered drain whose event source can stop (here: the test/client stops touching the
mount) needs an independent wall-clock backstop, or queued work starves indefinitely.

### Batch CI cycles
Group gate fixes and re-runs into batched CI cycles rather than one-fix-per-push against a
slow, dispatch-gated pipeline.

## Surprises

### The "+2 sequence bump" was the rotation alone, not relink + rotation
The orchestrator's "one shared root cause" hypothesis was refuted. The +2 is
`rotate_one(root)` + batched `republish_parent(root)`, both under the NEW key, inherent to
any scope-root with a child — no relink involved. The old-key relink was a SEPARATE THIRD
publish landing LAST, inverting the assumed "old-key publish is first" attribution.

### The macOS D-16 timeout was never slowness — the second publish was never attempted
The folder's first IPNS publish (empty, seq 1) landed at mkdir; the child-add republish was
never triggered on macOS. FUSE-T defers file release ~40-47s (SMB deferred close) past the
last mount I/O, and the edge-triggered drain then never fires because the test goes silent.
No poll budget can fix work that is stuck, not slow. Raising the budget was explicitly the
wrong fix.

### Three floor-store instances share one file and one tmp path but not one lock
`CipherBoxFS` holds three `JsonSidecarFloorStore` instances pointing at the same combined
sidecar via the same deterministic `.tmp` path, but each `new()` constructs its own
`Arc<Mutex<()>>`. Concurrent writers (rotation checkpoint vs high-water bump) race the
`std::fs::rename`, and the loser hits bare ENOENT because its tmp was already consumed.
Fixed by sharing one lock per sidecar path.

### Owner-PASS-while-Bob-FAILS was a timing transient over a deterministic old-key end state
The rotation publishes synchronously inside the FUSE unlink callback; the old-key relink is
async fire-and-forget. The owner read the brief new-key window; Bob read after the old-key
relink landed. The end state (newest record old-key, via last-writer-wins CAS) is
deterministic — only the owner's transient pass was timing-sensitive.

### The API IPNS resolve is name-only, so the bypass was a genuine record replacement
The resolve path takes only the ipns name — no userId dimension, no per-principal cache.
That eliminated the "harness per-user stale cache" theory and proved the revocation bypass
was a real last-writer-wins old-key record winning, i.e. a product bug, not a test artifact.
