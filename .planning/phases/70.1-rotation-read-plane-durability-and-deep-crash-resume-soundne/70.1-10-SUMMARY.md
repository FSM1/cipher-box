- **Test 6 (multi-dirty-edge variant):** builds `root6 -> [c1_6, c2_6]` (fan-out=2, depth=2, both file children). Crashes at the 3rd `persistCallback` call (c2_6's own commit) — since a parent's batched republish only fires once `pendingChildCount` reaches zero (not incrementally per child), this leaves BOTH c1_6 and c2_6 durably dirty under the SAME still-open root6 parent simultaneously. ## Decisions Made

- **Avoided the shared `crypto.getRandomValues` spy for key recovery in the new tests:** `keyCheckpointCallbacks` makes every `rotateOne` call invoke ECIES `wrapKey` (via `eciesjs`), which internally generates an ephemeral secp256k1 keypair — very likely consuming additional `crypto.getRandomValues(32)` calls that would silently shift the spy's `capturedReadKeys[]` index positions the pre-existing Tests 1-4 rely on. Rather than risk fragile/incorrect indexing, the new tests recover any node's post-rotation `readKeyPrime` by reading that node's OWN entry from the test's `KeyCheckpointCallbacks` stub and `unwrapKey`-ing it with the owner's (Alice's) private key — a self-consistent recovery path that doesn't depend on spy call ordering at all.
- **Reused Alice's existing account keypair as the ECIES owner keypair:** `alice.publicKey`/`alice.privateKey` (from the multi-account test harness, Web3Auth-derived secp256k1) are already used elsewhere in this file as `issueReadGrant`'s `recipientPublicKey`/`navigateReadChain`'s `recipientPrivKey` for Bob — confirming they are the correct ECIES-compatible key type for `RotationParams.ownerPublicKey`/`ownerPrivateKey`. No new keypair generation was needed.
- **Multi-dirty-edge shape achieved via careful call-count arithmetic, not a new fault-injection primitive:** the plan calls for reusing "the existing counting persistCallback fault-injection mechanism" exclusively. Getting 2 SIMULTANEOUSLY dirty siblings under one crash requires understanding that a parent's batched republish (`decrementPendingAndMaybeRepublish`) only actually PUBLISHES once `pendingChildCount` reaches zero — an in-memory per-child re-seal (`parentState.children[idx] = ...`) happening before that point is entirely lost on crash. Crashing on the LAST child's own persistCallback call (before its decrement) therefore leaves ALL siblings processed so far durably dirty, since the parent's one-shot publish never fired for any of them.
- **Live e2e run explicitly deferred to the orchestrator:** per this worktree's verification-scope instructions (no docker stack / API dev server available here), verification was limited to `tsc --noEmit`, `eslint`, and `prettier --check` against the built `@cipherbox/sdk-core`/`@cipherbox/sdk` dists. The orchestrator runs `pnpm --filter sdk-e2e test -- rotation-crash-safety` (the full suite, pre-existing Tests 1-4 plus new Tests 5-6) against the shared stack after merge.
