# Phase 70.1 Plan 11: Grant-Scope Gate Fail-Closed Correctness Summary

**Three revocation-bypass / mount-wedge vectors closed in `grant_scope.rs`: cache-authoritativeness tracking, complete-path ancestor walk, and poisoned-lock handling — all fail-closed (EIO), never a silent skip.**

## Performance

- **Duration:** ~25 min
- **Started:** 2026-07-08T20:45:00Z (approx)
- **Completed:** 2026-07-08T21:06:00Z
- **Tasks:** 2 (TDD RED then GREEN)
- **Files modified:** 2 (`crates/fuse/src/write_ops/grant_scope.rs`, `crates/fuse/src/fs.rs`)

## Accomplishments

- **D-15a (CRITICAL):** `SentSharesCache` now tracks `is_authoritative` (`false` for `empty()`/`Default`, `true` only after a successful `from_sent_shares` refresh). `gate_scope_exit` returns `Err` (→EIO) while non-authoritative, closing the window where a never-refreshed or failed-refresh cache silently let a shared delete look private. A refreshed-but-genuinely-empty (authoritative) cache still allows a private delete with zero rotation — the trigger is authoritativeness, never emptiness (Pitfall 8).
- **D-15b (MAJOR):** `ancestor_ipns_chain` now returns `AncestorChain { names, reached_root }` instead of a bare `Vec<String>`. A missing inode or a cycle leaves `reached_root = false`, and `gate_scope_exit` fails closed on an incomplete walk rather than treating a partial chain as "no grant found."
- **D-15c (MAJOR):** `run_scope_exit_gate` no longer `.expect()`-panics the fuser callback thread on a poisoned `sent_shares` lock — it returns `Err(())` (→EIO). `CipherBoxFS::refresh_sent_shares` (fs.rs) recovers a poisoned lock on a successful refresh and calls `clear_poison()`, so the mount self-heals instead of permanently EIO-ing every scope-exit until remount.
- 6 new grant_scope unit tests covering D-15a (non-authoritative fail-closed + authoritative-empty succeeds), D-15b (missing-inode + cycle fail-closed), and D-15c (poisoned lock → Err, not panic).
- All 10 pre-existing grant_scope tests updated to the new `AncestorChain`/`is_authoritative` shapes and still pass.

## Decisions Made

- Reused `RotationError::RotateFailed(String)` for the two new fail-closed error paths instead of adding new SDK-crate error variants, keeping this plan's file footprint to `grant_scope.rs`/`fs.rs` only (per `files_modified`).
- Changed `ancestor_ipns_chain`'s return type from `Vec<String>` to `AncestorChain` — verified via grep that the function has no callers outside `grant_scope.rs`, so this was a safe, contained signature change rather than an architectural ripple.
- `refresh_sent_shares` actively recovers and un-poisons the lock (via `into_inner()` + `clear_poison()`) rather than merely returning an error, since a background refresh is the natural self-healing point for a transient poison — otherwise a single panicked holder would strand every future delete/rename in EIO until the mount is restarted.
