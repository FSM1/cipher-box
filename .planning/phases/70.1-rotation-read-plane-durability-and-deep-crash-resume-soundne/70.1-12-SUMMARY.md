# Phase 70.1 Plan 12: D-15d Gate Ordering + D-14 Rotation-Success Inversion Summary

**Fixed the fourth bundled gate-correctness bug (D-15d: stale-key bin refs in delete.rs, ungated rename destination, doomed-rename rotation) and inverted the shared-scope-exit unit test to prove a REAL production rotation succeeds end to end via a local mock IPNS/IPFS transport — no live network or docker dependency.**

## Accomplishments

- **delete.rs (D-15d):** `handle_unlink`/`handle_rmdir` now run the pre-gate POSIX check (EISDIR / ENOTDIR+ENOTEMPTY) first, then `run_scope_exit_gate`, and only THEN capture the parent read/write keys and build the D-07 dual `SealedChildRef`/`WriteChildRef` for the bin entry — so a shared-scope-exit rotation can never be raced by a bin ref sealed under stale pre-rotation parent state.
- **rename.rs (D-15d):** `handle_rename` now validates the destination replacement (ENOTDIR/EISDIR/ENOTEMPTY) BEFORE any scope-exit gate — a doomed rename never attempts a rotation — and additionally gates the OVERWRITTEN destination's own scope-exit (`dest_ino`), closing a silent revocation-bypass where a shared destination could be removed ungated.
- **D-14/D-15d test inversion:** `unlink_shared_scope_exit_fails_closed_until_rotation_wired` (delete.rs) now asserts SUCCESS + exactly one rotation instead of the pre-wiring EIO. Rather than settle for a spy/fake-transport proof, the test builds a real Ed25519 vault-root identity, a genuinely signed IPNS resolve envelope (`cipherbox_core::create_ipns_record`), and a minimal in-process HTTP/1.1 mock server (plain `std::net::TcpListener`, no new crate dependency) serving resolve/fetch/upload/publish — so the test drives the actual production `ApiClientTransport`/`FuseRotationDeps` code path (Plan 09) end to end, fully offline and deterministic.
- **Plan 11 handoff closed:** `unlink_private_delete_succeeds_with_zero_rotation` and `rmdir_private_delete_succeeds_with_zero_rotation` now seed an AUTHORITATIVE-but-EMPTY `SentSharesCache` (via a new `seed_authoritative_empty_cache` helper) instead of relying on the test harness's non-authoritative default, restoring the zero-rotation private-delete success path without weakening the D-15a fail-closed gate.
- **New rename.rs test coverage (previously zero tests in this file):** two tests prove the D-15d bug was real and is now fixed — a covered-source rename that should fail ENOTEMPTY previously attempted rotation (surfacing EIO instead of ENOTEMPTY); overwriting a covered destination previously removed it ungated (silently succeeding instead of failing closed).
- Full `cargo test -p cipherbox-fuse --features fuse` is green: 106 passed, 0 failed (up from 102 passed / 2 failed at the start of this plan).

## Decisions Made

- **Bin-ref reorder is a lexical/future-proofing fix, not an observable-behavior change today:** confirmed via code inspection that no code path currently writes a post-rotation `read_key`/`write_key` back into the local `InodeTable` — rotation only affects the remote IPNS record. Moving the capture after the gate matches the plan's stated invariant and the codebase's own "validate → gate → mutate" pattern, and is correct groundwork for whenever local-cache sync lands.
- **Built a real (not fake) local mock transport for the D-14 inversion test** rather than accepting the aspirational "success" assertion as untestable at the unit tier or reaching for a live docker/e2e dependency. The mock is a plain `std::net::TcpListener` background thread (no new Cargo dependency) that answers `GET /ipns/resolve`, `GET /ipfs/*`, `POST /ipfs/upload`, and `POST /ipns/publish` — enough for a single root-only (zero-children) `rotate_read_from_node` round trip. The resolve response carries a REAL signed IPNS record (`cipherbox_core::create_ipns_record` over a freshly generated Ed25519 keypair, with the vault root's `ipns_name` replaced by the actual `derive_ipns_name(pubKey)` value) so `resolve_ipns_verified`'s genuine signature/CBOR-binding check passes — this exercises the true production code path, not a stand-in.
- **The two new rename.rs tests prove gate-firing via EIO against the harness's existing unroutable-API fixture**, not via the mock server, since proving "the gate fired" only requires observing an attempted-and-failed rotation, not a full successful round trip — avoiding a second heavyweight mock-server setup for a narrower claim.
- **platform/windows/write_ops.rs left untouched**: confirmed via grep it duplicates the same `run_scope_exit_gate`/`build_child_refs` pattern and would benefit from the identical reorder, but it is outside this plan's `files_modified` and cannot even be `cargo check`ed on macOS (`winfsp-sys` requires Windows-only COM APIs — `windows_registry::LOCAL_MACHINE`, `IMarshal`). This matches the plan's own acceptance criterion ("WinFsp delete/rename handlers get the same ordering — budget a CI round-trip") and project memory ("winfsp build is CI-only on macOS").
