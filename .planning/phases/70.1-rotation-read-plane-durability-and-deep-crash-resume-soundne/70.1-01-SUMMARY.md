## Accomplishments

- **Bug A (SC#1) fixed:** the dirty-resume branch no longer does a hard-coded `rootNode.children.find(...)` lookup that only finds depth-1 children and mis-attributes every decrement to root. It now groups `preRotationDirtyFrontier` items by their real `parentIpnsName`, seeds a `ParentTrackingState` per distinct parent (root or any intermediate node) via the new `resolveParentTrackingState` helper, and enqueues every item through the existing `enqueueDirtyFrontierItem` helper (which already correctly threads `item.parentIpnsName`/`item.nodeReadKey`).
- **Bug B (SC#2) fixed:** the normal branch's BFS loop now defers (requeues) an item whose parent isn't tracked yet but is still pending elsewhere in the queue, guaranteeing a parent's `ParentTrackingState` exists before its dirty child is genuinely consumed. A defensive fallback (`resolveParentTrackingState`) covers orphaned/unreachable parent references at the re-seal gate, and the `result.skipped` (idempotency-hit) branch now also decrements an existing tracking entry so a parent's batched republish is never silently dropped a second time.
- New shared helpers: `findParentNodeByIpnsName` (module-level tree walk reusing the existing `resolveChildKeyAndEnvelope` key-chain primitive) and `resolveParentTrackingState` (resolve-or-seed an arbitrary parent's `ParentTrackingState`), both following the file's terminal-owner zeroization discipline.
- New `describe('SC#1/SC#2 depth>=2 dirty-resume consumption (Plan 70.1-01)')` block with two cases asserting concrete per-parent `publishWithCas` call counts (not subjective "works").

## Decisions Made

- **Bug A uses a full root-to-target tree walk (`resolveParentTrackingState`/`findParentNodeByIpnsName`).** This is safe in the dirty-resume branch specifically: nothing between root and any frontier item's real parent rotates identity DURING this branch's execution (by construction — `collectDirtyFrontier` only ever recurses below CLEAN edges, so every intermediate ancestor is provably not itself rotating this run), so walking with the caller-supplied `rootReadKey`/derived intermediate keys is cryptographically consistent.
- **Bug B does NOT rely on the same walk as its primary mechanism.** In the normal (fresh-walk) branch, an ancestor MAY have already minted a new identity key earlier in the SAME `rotateReadFromNode` call, and its `parentTracking` entry can already be torn down (deleted once its own `pendingChildCount` reaches zero) by the time a deeper item needs it — re-resolving via IPNS using the ORIGINAL `rootReadKey` would then fail (the currently-published body is encrypted under the NEW key). A bounded requeue guard (defer the item if its parent is untracked but still pending in the queue) sidesteps this entirely by letting the EXISTING, already-correct normal-processing pipeline create the parent's tracking naturally, with `resolveParentTrackingState` retained only as a defensive fallback for a parent that's genuinely unreachable via normal enqueue.
- **`rootParentState.pendingChildCount` in the dirty-resume branch now seeds to 0, not `frontier.length`.** The prior seed mixed every depth into root's own counter — the root of Bug A's mis-attribution. If root ends up with zero direct dirty items after grouping, its tracking entry is explicitly zeroed (`parentOldReadKey.fill(0)`) and deleted rather than left dangling for the rest of the call.
- **The `result.skipped` branch now performs a decrement (never a re-seal)** against an EXISTING `parentTracking` entry only — no lazy-create there, since a skipped result carries no real freshly-minted key (`rotateOne` returns a placeholder `Uint8Array(32)` on the idempotency-skip path), so there's nothing meaningful to re-seal with; only the pending-count bookkeeping is safe to apply.
