# Phase 70.1 Plan 08: ECIES Key-Checkpoint Seam + Dirty-Node Repair (Rust) Summary

**Rust twin of the TS keyCheckpoint seam — `rotate_one` persists a minted `read_key_prime` via `RotationDeps::persist_wrapped_key` before its own publish, and the BFS walk repairs an already-rotated dirty node from that checkpoint instead of feeding its stale parent-mirror-derived key into `rotate_one`/`unseal_node`, with a depth-3 hand-built post-crash fixture proving all 4 D-10 convergence assertions via `FakeDeps`.**

## Accomplishments

- Added `RotationDeps::persist_wrapped_key`/`get_wrapped_key`/`delete_wrapped_key` as default no-op trait methods (zero cost for a host with no checkpoint plane wired), plus `RotationError::DirtyNodeUnrecoverable` in `high_water.rs`
- `rotate_one` now persists the freshly minted `read_key_prime` (as base64 of raw key material — the engine stays key-material-free w.r.t. ECIES per RESEARCH option (b)) via the checkpoint seam BEFORE its own `seal_and_publish` call (D-03), and GCs the root's own checkpoint immediately after its commit (no parent mirror to wait on)
- The BFS walk detects an already-rotated dirty node (`QueueItem.is_dirty_item`, stamped only by `enqueue_dirty_frontier_entry`) and, when a checkpoint is found (`get_wrapped_key` returns `Some`), routes it to a new `repair_dirty_node` function that recovers the node's ACTUAL current key, re-seals only the real parent's `SealedChildRef` mirror under it, and seeds the repaired node's own `ParentTrackingState` so its children still enqueue — never calling `rotate_one`/`unseal_node` with the stale key
- When no checkpoint is found, the walk falls through unchanged to the pre-existing "safe double-rotation" path (feeding the stale key into `rotate_one`), preserving Plan 70.1-06's SC#1/SC#2 fixtures verbatim; `DirtyNodeUnrecoverable` surfaces only if that fallback also fails
- Checkpoints are GC'd (`delete_wrapped_key`) via a new `ParentTrackingState.pending_checkpoint_node_ids` list, consumed in `complete_pending_child` only AFTER the covering parent's batched republish actually lands (D-01)
- Extended `FakeDeps` with a real ECIES-backed checkpoint store (its own generated owner keypair, `cipherbox_crypto::wrap_key`/`unwrap_key`) and a new chronologically ordered `call_log` spanning both the checkpoint seam and `publish_with_cas`, used to prove cross-call ordering invariants
- Added a depth-3 hand-built post-crash convergence test (root → A → B → {C dirty, D clean sibling}) asserting all 4 D-10 points (owner navigability, revoked-reader cut, no spurious extra republish, ECIES checkpoint lifecycle), plus a multi-dirty-edge (lost-key window) variant proving two dirty children under the same parent are both repaired with exactly one batched republish

## Decisions Made

- **Repair gated on checkpoint presence, not on `is_dirty_item` alone:** the plan's grounding text described an unconditional "detect and repair" flow, but a literal read would have broken Plan 70.1-06's existing SC#1/SC#2 "safe double-rotation" tests (which hand-seed a dirty state with NO checkpoint, relying on the derived key coincidentally still being valid). Reading the TS twin's SUMMARY (Plan 70.1-05) confirmed the intended design is D-01 conditional invocation — repair only actually engages when `get_wrapped_key` returns `Some`; absent one, the walk falls through unchanged to the pre-existing behavior. This is what the shipped code implements, and it is what keeps `cargo test -p cipherbox-sdk` fully green (145/145) alongside the two new tests.
- **`DirtyNodeUnrecoverable` is a fallback-failure signal, not a hard checkpoint requirement:** it only fires when no checkpoint exists AND the stale-key fallback also fails to unseal the node's current body — replacing an opaque AEAD error with an actionable, distinctly-typed one.
- **ECIES wrap/unwrap lives inside `FakeDeps`, not inside the generic engine code:** per RESEARCH option (b) (Sharp Question 6.3, explicitly quoted in the plan's own grounding paragraph), the engine passes/receives only base64 of raw key material across the `persist_wrapped_key`/`get_wrapped_key` seam. `FakeDeps` (standing in for a production `RotationDeps` adapter) does the actual `wrap_key`/`unwrap_key` ECIES round-trip internally using its own generated owner keypair — this is a deliberate divergence from the TS twin (which threads `ownerPublicKey`/`ownerPrivateKey` directly into `RotationParams`, option (a)), chosen because the Rust plan's own frontmatter lists only the 3 checkpoint seam methods (no owner-pubkey params) as the artifact to add.
- **D-13 fixture built via a real prior `rotate_one` call, not hand-seeded ciphertext:** simulating "the crashed prior run" by directly calling `rotate_one` on the dirty node (capturing its genuinely fresh, independently minted key) — rather than hand-constructing a checkpoint — gives the persist-before-publish ordering assertion "for free" via the shared `call_log`, and proves the stale (old) key genuinely fails to unseal the node's post-rotation body (unlike the pre-existing SC#1/SC#2 fixtures' deliberate same-key simplification).

### Auto-fixed Issues

**1. [Rule 1 - Bug] Gated dirty-item repair on checkpoint presence instead of unconditional routing**

- **Found during:** Task 2 (GREEN implementation)
- **Issue:** An initial unconditional "every dirty item is repaired via checkpoint, no fallback" implementation broke two pre-existing tests (`sc1_depth2_dirty_entry_consumption_republishes_real_intermediate_parent_not_root`, `sc2_depth3_dirty_entry_decrement_is_not_dropped_across_two_intermediate_hops` from Plan 70.1-06), both of which hand-seed a dirty state with no checkpoint ever persisted and rely on the pre-existing "safe double-rotation" behavior (feeding the coincidentally-still-valid derived key into `rotate_one`).
- **Fix:** Restructured the BFS dirty-item branch to check `get_wrapped_key` first; only route to `repair_dirty_node` when it returns `Some`. When `None`, fall through to the pre-existing `rotate_one` call, mapping any resulting error to `RotationError::DirtyNodeUnrecoverable` instead of letting the raw AEAD error surface. This mirrors the already-shipped TS twin's (Plan 70.1-05) explicit "backward-compatible opt-in gating" design decision.
- **Files modified:** `crates/sdk/src/rotation/engine.rs`
