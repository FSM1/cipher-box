## RESOLVED (was CRITICAL FINDING): `sent_shares` is now refreshed from the mount lifecycle

**Discovery:** grounding the test against the live desktop binary, an exhaustive repo-wide grep (`grep -rn "\.refresh_sent_shares(" .`) found **zero** call sites invoking `CipherBoxFS::refresh_sent_shares`. `apps/desktop/src-tauri/src/fuse/mod.rs` seeded `sent_shares` to `SentSharesCache::empty()` (non-authoritative) at mount and never refreshed it. Per the D-15a fix (Plan 11), `gate_scope_exit`/`run_scope_exit_gate` fails CLOSED (`Err` -> `EIO`) while the cache is non-authoritative — **regardless of shared vs. private** — so **every** delete/rename on a real mount returned EIO unconditionally. `70.1-RESEARCH.md` (§7.3/§309) had *assumed* this wiring existed; Plan 09 added the `refresh_sent_shares` method + fields but no plan scheduled the actual call site.

**Fix (user-directed):** I initially flagged this as a Rule 4 (out-of-scope architectural) item and left it for a follow-up plan. The user then directed me to implement it in this session. The wiring:

- `crates/fuse/src/write_ops/grant_scope.rs` — added `install_sent_shares_cache` (shared D-15c poison-recovery install path) and `spawn_periodic_sent_shares_refresh` (30s cadence, `SENT_SHARES_REFRESH_INTERVAL`). `CipherBoxFS::refresh_sent_shares` now delegates to the shared install helper.
- `crates/fuse/src/fs.rs` — `sent_shares` is now `Arc<RwLock<..>>` so the background refresh task and the mounted `fs` (moved onto the mount thread) share one lock. All existing readers/writers are deref-transparent; only the field type + 3 constructor sites changed.
- `apps/desktop/src-tauri/src/fuse/mod.rs` and `.../fuse/windows/mod.rs` — at mount init, a bounded (5s, best-effort) `refresh_sent_shares` seeds the cache authoritatively; then `spawn_periodic_sent_shares_refresh` runs a 30s background loop. If the init refresh fails/times out the cache stays non-authoritative and the gate keeps failing CLOSED (safe, never a silent revocation bypass); the periodic loop recovers on its first successful tick and also covers folders shared AFTER mount (closing the stale-cache fail-open window).

**Security invariant preserved:** the fix only ever flips the gate from fail-closed to functioning when a `/shares/sent` refresh has genuinely succeeded (authoritative). It never introduces a fail-open path — a missing/failed refresh still EIOs.

## Decisions Made

- Keep Bob's grant **active through the scope-exit delete** (revoke only as cleanup afterward): the gate keys off the sent_shares cache and revoke is a hard DELETE, so revoking first would drop the covering grant and make the delete look private (no rotation). Bob is cut off by the **rotation itself** — desktop `query_grants_rooted_at` is a documented no-op (Plan 09; `crates/fuse/src/write_ops/rotation_deps.rs:137,232`), so the rotation re-mints the folder key without re-wrapping Bob's grant.
- 30s periodic refresh cadence (matches the app's IPNS-poll rhythm): short enough that a folder shared after mount is covered within one cycle, without hammering `/shares/sent`.
- Mount-init refresh is bounded (5s) and best-effort so a slow/unreachable relay can never hang the mount; the gate stays fail-closed until a refresh succeeds.
- Use IPNS sequence-number deltas and old-key-decryptability as the sole observable signals for "rotation occurred" / "exactly one rotation" / "no rotation" — avoided desktop log greps since the only rotation-adjacent log line is `log::debug!` (`rotation_deps.rs:224`), which `RUST_LOG=info` (CI default) would not surface.
- Scoped the new Step 8 to `run-all.sh` (macOS + Linux, `fuse` feature); the refresh wiring itself is applied to BOTH mod.rs and windows/mod.rs so the gate is correct on every platform.
