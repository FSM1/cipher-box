## CRITICAL FINDING: `refresh_sent_shares` is never invoked from the mount lifecycle

While grounding the test against the live desktop binary, I confirmed via exhaustive grep (`grep -rn "\.refresh_sent_shares(" .` across the whole repository) that **zero call sites** invoke `CipherBoxFS::refresh_sent_shares` anywhere in `apps/desktop/src-tauri/src/` (or anywhere else). `apps/desktop/src-tauri/src/fuse/mod.rs:346-347` seeds `sent_shares` to `SentSharesCache::empty()` (non-authoritative) at mount construction and nothing subsequently refreshes it -- not at mount init, not periodically, not via any Tauri command triggered by the frontend.

Per the D-15a fix landed in Plan 11 (`crates/fuse/src/write_ops/grant_scope.rs`), `gate_scope_exit`/`run_scope_exit_gate` fails CLOSED (returns `Err` -> `EIO`) whenever `sent_cache.is_authoritative` is `false` -- **regardless of whether the ancestry involves a shared or private node**. Because the cache can never become authoritative today, **every delete and rename on a real desktop mount currently returns EIO, unconditionally** -- not just the shared-scope-exit case this plan targets, but ordinary private deletes too.

This is a genuine scope gap, not a research artifact: `70.1-RESEARCH.md` (Sharp Question 7.3/§309) explicitly *assumes* "mount init seeds `sent_shares` via `refresh_sent_shares` (`fs.rs:101-103`) out-of-band" as an existing fact, and no plan in this phase (`01`-`12`) lists `apps/desktop/src-tauri/src/fuse/mod.rs` in its `files_modified`. Plan 09 added the `CipherBoxFS::refresh_sent_shares` method and fields to `crates/fuse/src/fs.rs`, but the actual **call site** wiring it into the mount's lifecycle (init + periodic background refresh, mirroring the existing `spawn_bin_entry_publish` pattern already present in `fuse/mod.rs:293`) was never scheduled in any plan.

**Why I did not fix this myself:** this plan's declared `files_modified` scope is `tests/desktop-e2e/` only. Wiring the fix touches `apps/desktop/src-tauri/src/fuse/mod.rs` (a different crate, outside this plan's scope) and involves genuine design choices this executor should not make unilaterally: refresh interval/backoff, whether mount init blocks on the first refresh or proceeds optimistically, and error-handling semantics on a failed periodic refresh. Per the deviation rules, an issue outside the current task's file scope that requires an architectural/design call is a Rule 4 (ask) situation, not a Rule 1-3 auto-fix -- and it is also literally "pre-existing," not caused by this plan's changes, so per the Scope Boundary it is documented here rather than silently patched.

**Recommendation:** file a new todo/gap-closure plan to wire `CipherBoxFS::refresh_sent_shares()` into `apps/desktop/src-tauri/src/fuse/mod.rs` (mount init, synchronous-or-best-effort, plus a periodic background `tokio::spawn` loop) BEFORE dispatching the real-mount desktop-e2e run for this plan's Task 2. Until that lands, expect the new acceptance leg (and, notably, ALL existing desktop-e2e delete/rename-touching legs -- recycle bin, conflict detection, move-content -- ) to fail with EIO on this branch.
