- Closed the SC#5 self-equivocation gap: `reconcileFolderSequence` now fetches the resolved CID and calls the real `unsealNode` with the folder's read key to recover the record's ACTUAL generation, feeding that (not `folderTree.get(ipnsName)?.nodeGeneration`) into `RotationHighWater.enforceResolved`. ## Decisions Made
- `keyCheckpointCallbacks`/`ownerPublicKey`/`ownerPrivateKey`/`nodeKeySource` are derived ONCE inside `performScopeExitRotation` from `this.config`/`this.folderTree`, not threaded as new parameters at each of its 5 call sites — these values never vary per call, so deriving them once avoids 5x duplication and guarantees every call site automatically inherits correct wiring (no risk of one being forgotten).
- `nodeKeySource` is backed by a REAL `folderTree` lookup (any already-loaded folder's own `ipnsKeypair` + `writeKey`) rather than a test-only fixture — genuine Phase-65 write-body-derived key material, safe for production.
- `grantCallbacks`/`innerGrants` are threaded into the `rotateReadFromNode` call as explicit fields (currently always `undefined`) since no `CipherBoxClientConfig` seam sources them yet — Phase 66 is the documented host-wiring follow-up (RESEARCH). This makes the fields structurally reachable without inventing new config surface in this plan.
- `DirtyNodeUnrecoverableError`'s catch surfaces a clear, actionable error rather than attempting the narrower "repair only the parent mirror" repair the plan's action text described — the error (as defined in `sdk-core`) carries no structured node/parent identifier to act on programmatically, so a targeted per-node repair isn't implementable without a structural change to the error type (out of scope for this plan; documented in-line as a residual, consistent with the existing `RootKeyStaleError` residual precedent).
