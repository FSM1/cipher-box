## Summary

This is a locked-decision phase (D-01..D-10 in `70.1-CONTEXT.md`) — this research does not re-litigate the approach, it grounds it against the current code and surfaces landmines. Every code claim below was re-verified this session by reading the live files, not by trusting CONTEXT.md's citations blindly.

**Two findings materially change the planner's risk picture and are not mentioned in CONTEXT.md:**

1. **A Rust twin of the ENTIRE rotation engine exists (`crates/sdk/src/rotation/engine.rs`) and is used by desktop FUSE/WinFsp.** Its module doc literally says "Rust twin of `packages/sdk-core/src/rotation/engine.ts`." It has the **exact same** depth-1-only dirty-frontier consumption bug (hard-coded `parent_ipns_name: root_ipns_name.to_string()` at lines 919/999, and a `root_children.iter().find(...)` lookup at lines 1013-1018 that only works for depth-1 children) — AND it is **further behind** than the TS engine: its `verify_subtree_clean` (lines 806-845ish) never recurses below root's immediate children (TS's `collectDirtyFrontier` already recurses the full subtree, per SC#2's Phase-70 fix), and a **missing root record returns an empty (converged) frontier**, not "dirty" (TS already returns `isDirty: true` for a missing root). CONTEXT.md's in-scope file list names only `packages/sdk-core/src/rotation/engine.ts` for the walk-mechanics fix and only `floor_store.rs`/`high_water.rs` for Rust — `crates/sdk/src/rotation/engine.rs` is not mentioned anywhere. **This is a real scope gap, not a research artifact** — flagged as Open Question 1 below; get explicit confirmation before planning whether desktop parity is in this phase or deliberately deferred.
2. **There is currently NO durable-store seam of any kind wired into either rotation engine's core walk.** `RotationHighWater`/`rotationHighWater.enforceResolved` (TS) and the Rust twin are used **exclusively** at the read-path gate inside `packages/sdk/src/client.ts` (`resolveIpnsRecord`/`reconcileFolderSequence`) and are **never passed into** `RotationParams`/`rotateReadFromNode`/`rotateOne`, nor into the Rust `RotationDeps` trait. D-01's "durably persist the ciphertext to the shared checkpoint plane" therefore requires **inventing a brand-new injectable callback seam** end-to-end (mirroring the existing `grantCallbacks`/`persistCallback` pattern) — this is a bigger lift than CONTEXT's phrasing implies and is detailed in the SC#3 section and Pitfalls below.

**Primary recommendation:** Treat this phase as five coupled but separable changes: (A) fix the two TS engine.ts consumption paths (SC#1/SC#2, mechanical, well-scoped, no new seams); (B) design and wire a brand-new `keyCheckpoint` callback seam end-to-end from `rotateOne` through `RotationParams`/`RotationClientCallbacks`/`CipherBoxClientConfig` down to a concrete web IndexedDB adapter, reusing the vault keypair already available at `CipherBoxClientConfig.vaultKeypair` (SC#3/D-01..D-05); (C) collapse the two-sidecar-file/two-object-store floor plane into one combined atomic record on both Rust and TS, and make Rust's `put` fail closed (SC#4/D-06..D-08); (D) thread the folder read key into `reconcileFolderSequence` so it can fetch+unseal for the real generation (SC#5/D-09); (E) add depth-3 e2e fault-injection reusing the existing `persistCallback`-count fault-injection mechanism (SC#6/D-10).

## Sharp Question 1 — Depth-Aware Consumption (SC#1/SC#2)

**Current `DirtyFrontierItem` shape (`engine.ts:587-597`, confirmed) — already the RICH shape, not the naive one:**
```typescript
export type DirtyFrontierItem = {
  ipnsName: string;
  nodeId: string;
  parentIpnsName: string;      // actual immediate parent, any depth
  nodeReadKey: Uint8Array;     // this node's STALE pre-rotation key (see Sharp Question 2)
  childPubKind: 'folder' | 'file';
  enqueuedGeneration: number;
};
```
`collectDirtyFrontier` (`:648-704`) recurses the FULL subtree (Phase 70's SC#2 fix already shipped) and correctly stamps each item's real `parentIpnsName` at any depth. **The frontier COLLECTION is already depth-aware.** The bug is entirely in the two CONSUMPTION paths:

**Bug A — dirty-resume branch (`:1401-1442`, confirmed):** Ignores `frontierItem.parentIpnsName` entirely. Does `(rootNode.children ?? []).find(c => c.ipnsName === frontierItem.ipnsName)` (`:1403-1405`) — only finds depth-1 children. For depth≥2, `childRef` is `undefined`, hits the fail-closed branch at `:1406-1412` which calls `decrementPendingAndMaybeRepublish(rootParentState, rootNodeIpnsName)` — **decrementing the ROOT's count for a node that isn't even root's child**, then `continue`s (drops the item, never enqueued). `rootParentState.pendingChildCount` was seeded to `frontier.length` (`:1397`) — mixing depth-2+ items into a counter that can never legitimately reach them.

**Bug B — normal-branch ordering (`:1523-1524`, `:1559`, `:1568`, confirmed):** `enqueueDirtyFrontierItem` (`:1307-1336`) DOES correctly thread `item.parentIpnsName` — this function itself is NOT buggy. The bug is queue ORDER: root's own children are enqueued first (`:1486-1515`), THEN all `preRotationDirtyFrontier` items are appended (`:1523-1524`), regardless of depth. If a depth-3 dirty node D is dequeued before its depth-2 parent P2 has been processed (P2 might itself be a fresh, not-yet-rotated node still ahead in the queue, or might not even be in the frontier/queue at all if P2's own edge is clean), `parentTracking.get(item.parentIpnsName)` (`:1568`) is `undefined`, the `if (parentState)` guard (`:1569`) skips the ENTIRE re-seal+decrement block silently, and D is still added to `completedNodeIds` via `rotateOne`'s own step 9. When P2 later rotates and enqueues D as one of ITS normal children, `rotateOne` for D returns `RotateOneSkipped` (idempotency hit), and the `if (!result.skipped)` guard (`:1559`) skips the decrement AGAIN — **P2's `pendingChildCount` for D never reaches zero, P2 never republishes.**

**Minimal fix shape (informational, not prescriptive per role boundary):** Bug A needs the dirty-resume branch to build (or reuse) real `ParentTrackingState` entries for every DISTINCT `parentIpnsName` present in the frontier (not just root), resolving+unsealing each intermediate parent to seed `children`/`baseChildrenSnapshot`/`parentNewReadKey` — mirroring what the normal branch already does for root at `:1382-1399`, generalized to arbitrary depth. Bug B needs either (a) processing order that guarantees a parent's `parentTracking` entry exists before its dirty child is dequeued (e.g., sort frontier items by depth before enqueueing, or lazily create a placeholder `parentTracking` entry using the SAME resolve+unseal machinery Bug A's fix would add), or (b) deferring a dirty item's decrement until its parent's tracking exists (a small requeue/retry). Both bugs likely share ONE underlying primitive: "given an arbitrary `parentIpnsName`, resolve+unseal it and produce/find its `ParentTrackingState`" — extracting this as a shared helper avoids duplicating the root-specific logic at `:1382-1399` a second time for Bug A.

1. 3. Recommend the new seam attach to `RotationClientCallbacks` (`packages/sdk/src/types.ts:65-74`) alongside `persistJob`, wired via a new concrete adapter in `apps/web/src/services/rotation-driver.service.ts` OR (preferred, see SC#4) as a NEW method on the SAME `HighWaterStore`-shaped seam used for the floor, since the natural storage key (nodeId) matches.

**`RootKeyStaleError` (D-05's fallback, ALREADY implemented, but ONLY for the ROOT):** `rotateReadFromNode`'s entry gate (`:1004-1018`, confirmed) already probes `unsealNode(rootProbePub, rootReadKey)` before deciding fresh-vs-dirty-tail, and throws a dedicated `RootKeyStaleError` (class defined `:302-307`) when the supplied `rootReadKey` cannot unseal the currently-published root — this is the exact "fallback for the truly-expired/GC'd-key case" pattern D-05 wants, but it currently exists **only for the walk's ROOT node**. There is no equivalent check for a mid-tree dirty CHILD. `performScopeExitRotation` (`client.ts:2016-2069`) already catches `RootKeyStaleError` specifically and falls back to a full top-down `folderTree` re-navigation — a real, working precedent to model `DirtyNodeUnrecoverableError` on for the child case, though the child case's fallback is different (repair only the parent mirror, don't re-navigate the whole tree).

**T1 confirmed exactly as the todo describes:** `collectDirtyFrontier` (`:648-704`) detects `childPub.generation > childRef.generation` (`:661`) and stores `nodeReadKey: childReadKey` (`:662-669`) where `childReadKey` was derived via `resolveChildKeyAndEnvelope(childRef, parentReadKey, ctx)` — i.e. unsealing the STALE mirror's `readKeySealed` blob under the (valid) parent key. This IS the child's PRE-rotation key, not its actual current key. Both consumption paths (the dirty-resume block's `resolveChildKeyAndEnvelope(childRef, rootReadKey, ctx)` re-derivation at `:1413`, AND `enqueueDirtyFrontierItem`'s direct reuse of `item.nodeReadKey` at `:1327`) feed this stale key as `queue[i].nodeReadKey`, which becomes `parentReadKey` in the subsequent `rotateOne` call (`:1548`). `rotateOne`'s own Step 3 (`:763`, `unsealNode(published, parentReadKey, nodeWriteKey)`) then AEAD-fails against the node's CURRENT (already-rotated) published body. **There is currently NO check anywhere in the BFS loop (`:1529-1657`) that distinguishes a "fresh" queue item from a "dirty/already-rotated" queue item before calling `rotateOne`** — this is exactly the gap D-05 requires closing: a pre-check (e.g., comparing `item.enqueuedGeneration` against a freshly-fetched envelope generation, or a boolean flag stamped at enqueue time) must route dirty items to a NEW repair function instead of `rotateOne`.

**Repair-path zeroization shape (Pitfall, not yet designed anywhere in code):** The recovered `readKeyPrime` (from `unwrapKey(wrappedCiphertext, ownerPrivateKey)`) is a FRESH buffer — its terminal-owner lifecycle differs from `rotateOne`'s own minted key: since the dirty node's OWN publish already succeeded in the lost prior run, the repair path does NOT call `rotateOne`/publish again for this node — it only needs the recovered key to (a) re-seal the PARENT's `SealedChildRef.readKeySealed` under the parent's new key (mirrors the existing D-02 re-seal at `:1568-1588`), and (b) seed a `ParentTrackingState` for this node so ITS OWN children can still be enqueued (mirrors `:1594-1617`/`:1619-1647`). The recovered key should be zeroed once that `ParentTrackingState` is torn down (mirrors `parentOldReadKey.fill(0)` at `:1292` inside `decrementPendingAndMaybeRepublish`) — do NOT zero it inside the unwrap/repair function itself if it needs to outlive that call to seed enqueue of this node's children.

## Sharp Question 3 — Combined Atomic Floor Record (SC#4 / D-06..D-08)

### Pattern 1: New injectable `keyCheckpoint` seam mirrors the existing `grantCallbacks` pattern
**What:** A new optional param on `RotateOneParams`/`RotationParams`, e.g. `keyCheckpointCallbacks?: { persistWrappedKey: (nodeId: string, wrappedKeyB64: string) => Promise<void>; getWrappedKey: (nodeId: string) => Promise<string | undefined>; deleteWrappedKey: (nodeId: string) => Promise<void> }`.

**Why this shape:** Matches the ALREADY-established `GrantRemintCallbacks`/D-04 "clean happy-path never invokes this seam when absent" contract (`reMintGrantsRootedAt:452`, `if (!callbacks) return;`) — a proven, reviewed pattern in this exact file, not a new design.

### Pattern 2: Combined per-nodeId durable record (Rust + TS)
**What:** Replace `{generation: u64}` × 2 files (Rust) / 2 IndexedDB object stores (TS) with ONE record type per `nodeId`: `{ generation: u64, seq: u64, wrappedKeyCheckpoint: Option<Vec<u8>> }` (Rust) / `{ generation: number, seq: number, wrappedKeyCheckpoint?: string }` (TS), written in ONE atomic operation.
**Rust shape:** One `JsonSidecarFloorStore` (or a renamed/generalized type) backed by ONE sidecar file, `HashMap<String, CombinedFloorRecord>` instead of `HashMap<String, u64>`; `write_map_atomic_blocking`'s existing temp+rename logic is reused unchanged (`:101-125`).
**TS shape:** ONE IndexedDB object store (not two), keyed by `nodeId`, storing the combined object; `idbPut`'s existing read-back-inside-transaction-then-max pattern (`:90-111`) is reused, extended to max each numeric field independently and to overwrite/merge the `wrappedKeyCheckpoint` field.
**Migration concern (see Pitfalls):** existing users have data in the OLD 2-store/2-file shape; a silent `DB_VERSION` bump must not lose already-persisted floors (floors are safety-critical, not cosmetic).

### Anti-Patterns to Avoid
- **Feeding a dirty `DirtyFrontierItem`'s `nodeReadKey` into `rotateOne` without a prior check** — this is the EXACT T1 crash. Any fix that doesn't add an explicit pre-`rotateOne` branch for dirty items reproduces the bug.
- **Persisting the wrapped-key checkpoint AFTER `publishWithCas` instead of before** — defeats D-03's entire purpose (the window would just move, not close).
- **Zeroing the recovered `readKeyPrime` inside the unwrap function itself** if the repair path still needs it to seed the node's own `ParentTrackingState`/enqueue its children — mirrors the exact "callee-zeroes-shared-buffer" class that broke 48/89 sdk-e2e (see Pitfalls).
- **Changing `HighWaterStore::put`'s Rust signature without a consumer sweep** — `crates/fuse/src/*` and `crates/sdk/src/{adapter,lib,listing,emit}.rs` all reference this trait; a signature change compiles-red across the workspace until every call site is updated.

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| ECIES key wrapping for the checkpoint | Custom asymmetric crypto | `wrapKey`/`unwrapKey` from `@cipherbox/crypto` (already used for grants) | Only sanctioned primitive per CLAUDE.md Rule 4; already proven correct in this exact file |

## Common Pitfalls

### Pitfall 1: Feeding a dirty node's stale key into `rotateOne` (T1, SC#3's crash)
**What goes wrong:** AEAD `unsealNode` failure inside `rotateOne`'s Step 3 (`:763`), crashing the entire walk instead of converging.
**Why it happens:** The BFS loop (`:1529-1657`) has no branch that distinguishes a dirty (already-rotated) queue item from a fresh one before calling `rotateOne`.
**How to avoid:** Add an explicit check — e.g. re-fetch the item's current published generation and compare against `item.enqueuedGeneration`, or stamp a boolean at enqueue time in both `enqueueDirtyFrontierItem` and the dirty-resume branch — and route dirty items to the NEW repair path (ECIES-unwrap + parent-mirror-only reseal) instead of `rotateOne`.
**Warning signs:** Any depth≥2 e2e test that still throws `Decryption failed`/AEAD errors after the SC#1/SC#2 consumption fix land is this pitfall, not a regression of SC#1/SC#2.

### Pitfall 2: Callee-zeroes-shared-buffer regression class (project-wide precedent, 48/89 sdk-e2e)
**What goes wrong:** Zeroing a buffer the caller still needs corrupts live application state (not a leak — a correctness/availability bug).
**Why it happens:** Easy to violate when a buffer crosses a function boundary without a defensive copy, especially when adding a NEW recovery path that reuses an EXISTING key buffer for two purposes (parent-mirror reseal AND this node's own children enqueue).
**How to avoid:** Apply the SAME terminal-owner discipline already documented throughout `engine.ts` (see `:1650-1656`'s `finally { item.nodeReadKey.fill(0); }` pattern) to the NEW recovered-key buffer: zero it exactly once, at the point where its LAST legitimate use ends (parent-tracking teardown), never inside the unwrap function itself.
**Warning signs:** Any `fill(0)` call added without a comment identifying who owns the buffer and why THIS call site is the terminal owner.

### Pitfall 3: ECIES wrapped-key persist ordering (D-03/D-07) — must precede the publish, not follow `completedNodeIds.add`
**What goes wrong:** If the persist call is placed after `publishWithCas` (Step 8, `:852-897`) or after `completedNodeIds.add` (Step 9, `:917`), the crash window is only narrowed, not closed — a crash between publish and persist still loses the key.
**Why it happens:** The natural place to "add a persistence call" when reading `rotateOne` top-to-bottom is near the end, after the publish succeeds — but D-03 explicitly requires it BEFORE the publish.
**How to avoid:** Insert the `persistWrappedKey` call immediately after Step 4 (mint, `:805`) or Step 7 (parent-mirror seal computation, `:840-846`), and `await` its durable commit before the `publishWithCas` call at Step 8 begins.
**Warning signs:** A code review that finds the new persist call anywhere after the `casResult = await publishWithCas(...)` line.

### Pitfall 4: IndexedDB/JSON-sidecar schema migration silently drops existing floors
**What goes wrong:** Collapsing 2 IndexedDB object stores (or 2 JSON sidecar files) into 1 combined store/file, without migrating already-persisted data, resets every existing user's anti-rollback floor to "unset" — safe-directionally (floors are monotonic-max, so this is under-protective, never over-protective/rollback-accepting) but still a real durability regression for existing installs.
**Why it happens:** An `onupgradeneeded`/new-file-name change is the simplest way to introduce a new schema, but it's easy to forget the OLD data needs a read-and-fold-in step.
**How to avoid:** On `onupgradeneeded` (TS) or first-read-of-the-new-file (Rust), check for the OLD two-store/two-file data and fold it into the new combined record before the old data becomes unreachable. If genuinely out of scope for this phase, document the accepted floor-reset explicitly rather than silently shipping it.
**Warning signs:** A test that seeds the OLD 2-store/2-file shape, upgrades, and asserts the floor SURVIVES is the correct regression guard; its absence is a gap.

### Pitfall 5: Desktop FUSE/WinFsp rotation engine has the SAME bugs and is NOT in CONTEXT's file scope
**What goes wrong:** If the planner scopes tasks strictly to CONTEXT's named files (`packages/sdk-core/src/rotation/engine.ts`, `crates/sdk/src/{floor_store,rotation/high_water}.rs`), the desktop FUSE/WinFsp host — which uses a COMPLETELY SEPARATE Rust rotation engine (`crates/sdk/src/rotation/engine.rs`) with the identical depth-1-only consumption bug PLUS a non-recursive `verify_subtree_clean` PLUS a missing-root-treated-as-clean bug that TS already fixed — remains unsound after this phase ships, with no disclosure that this was a deliberate scope decision.
**Why it happens:** CONTEXT.md's todo/file scope was written against the TS-only 2026-07-08 todo, which does not mention the Rust engine at all.
**How to avoid:** Surface this explicitly to the user/architect BEFORE planning tasks (see Open Question 1) — either fold `crates/sdk/src/rotation/engine.rs` into this phase's scope, or get an explicit, documented decision that desktop parity is deferred to a follow-on phase.
**Warning signs:** A ship note or SECURITY.md claiming "the rotation engine is now sound for depth≥2 crash-resume" without a qualifier scoping that claim to web/sdk-e2e only.

```typescript
function idbPut(storeName: string, nodeId: string, value: number): Promise<void> {
  return openRotationDB().then((db) => new Promise<void>((resolve, reject) => {
    const tx = db.transaction(storeName, 'readwrite');
    const store = tx.objectStore(storeName);
    const readBack = store.get(nodeId);
    readBack.onsuccess = () => {
      const existing = readBack.result as unknown;
      const floor = isValidFloorValue(existing) ? Math.max(existing, value) : value;
      store.put(floor, nodeId);
    };
    readBack.onerror = () => reject(readBack.error);
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
  }));
}
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---|---|---|
| V2 Authentication | No | Unaffected |
| V3 Session Management | No | — |
| V4 Access Control | Yes | SC#1/SC#2's fix is revocation-soundness-adjacent (a stuck/mis-attributed decrement leaves a parent mirror unpublished, delaying — not defeating — a revocation's propagation); D-01's security framing is explicit that revocation ITSELF already succeeded the moment the dirty child's own rotation committed — this phase fixes OWNER availability, not a revocation gap |
| V5 Input Validation | Yes | Rust `is_valid_floor_value`/TS `isValidFloorValue` (unchanged, already fail-closed); the SC#4 fail-closed `put` propagation is itself a V5-adjacent control (a write failure must not silently degrade to "no floor known") |
| V6 Cryptography | Yes | ECIES wrap/unwrap (`wrapKey`/`unwrapKey`, unchanged primitives, new call sites) — never hand-rolled, routes through `@cipherbox/crypto` exclusively per CLAUDE.md Rule 4; AES-256-GCM AAD-bound seals unaffected |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| A crash-interrupted rotation permanently strands a parent mirror, requiring a full top-down re-navigation the user may not know to trigger | Denial of Service (availability, self-inflicted) | SC#1/SC#2's depth-aware consumption fix (this phase) |
| A minted-but-unpublished-to-durable-storage key is permanently lost on crash, forcing the OWNER to lose navigability to their own data (revocation itself is unaffected — see security framing above) | Denial of Service (availability) | SC#3's ECIES-persist-before-publish checkpoint (D-01..D-05, this phase) |
| Cross-store floor divergence under partial write failure (generation bumped, seq write fails) | Tampering (under-protective divergence, not rollback-accepting per the TS doc's own analysis) | SC#4's combined atomic record (D-06/D-07, this phase) |
| Rust floor-store write failures silently logged and swallowed, masking a real durability defect from callers | Tampering / Repudiation (a failed durable write should be a loud, fail-closed signal, not a log line) | SC#4's fail-closed `put` (D-08, this phase) |
| A stale cached generation lets the client's OWN reconcile gate miss a self-inflicted generation regression (equivocation bug, not an external-attacker rollback — IPNS records are owner-signed) | Tampering (defense-in-depth against the client's own bugs) | SC#5's freshly-resolved-generation threading (D-09, this phase) |
| A wrapped-key checkpoint, if ever routed through the server/API instead of staying client-side durable storage, would violate the zero-knowledge boundary | Information Disclosure | CLAUDE.md Rule 6 — confirm the planner keeps the checkpoint plane entirely client-side (IndexedDB/JSON sidecar), never an API call |
