# Phase 70.1: Rotation Read-Plane Durability and Deep Crash-Resume Soundness - Context

**Gathered:** 2026-07-08
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the read-key rotation engine **sound for multi-level (depth>=2) trees under crash-resume**, and the anti-rollback floor plane **durable under write failure and concurrency**. Closes the read-plane debt disclosed at Phase 70 ship (PR #596 review: greptile P1 + CodeRabbit critical/major).

**In scope (read plane only):**

- `packages/sdk-core/src/rotation/engine.ts` — dirty-frontier consumption depth-awareness, normal-branch ordering, already-rotated-dirty-node handling, ECIES key-checkpoint on mint.
- `crates/sdk` (`floor_store.rs`, `rotation/high_water.rs`) + `packages/sdk/src/state/rotation-high-water.ts` — fail-closed write propagation, atomic cross-store bumps, shared durable plane.
- `packages/sdk/src/client.ts` `reconcileFolderSequence` — freshly-resolved generation gate.
- `tests/sdk-e2e/src/suites/rotation-crash-safety.test.ts` — depth-2/3 mid-walk-crash coverage.

**Out of scope:** the write plane (Phase 72), the API/web layers, any rotation UX beyond what the e2e asserts. No new capabilities — this hardens what Phase 70 shipped.

<decisions>
## Implementation Decisions

Two Success Criteria are **structural implementation, not gray areas** and were not discussed — they carry a precise line-level solution sketch in the depth-gap todo and go straight to research/planning:

- **SC#1** — dirty-resume consumption must be depth-aware: use each `DirtyFrontierItem.parentIpnsName` (not `rootNode.children` only), seed `parentTracking` for every intermediate parent, stop attributing decrements to the root. (`engine.ts:1401-1442`, esp. the hard-coded `parentIpnsName: rootNodeIpnsName` at `:1424`.)
- **SC#2** — normal-branch ordering: never process a dirty node before its parent has a `parentTracking` entry; close the `skipped`-result decrement drop (`engine.ts:1523-1524`, `:1559`, `:1568`).

### SC#3 — Already-rotated dirty node / lost post-rotation key

- **D-01 (approach): ECIES-persist + resume — the residual is eliminated, not documented.** When `rotateOne` mints `readKeyPrime` (`engine.ts:805`), ECIES-wrap it under the **owner's own public key** (reuse the in-engine `wrapKey` primitive already used for grants at `:465`) and **durably persist the ciphertext to the shared checkpoint plane BEFORE the child publish** (step 4, `:855`). On resume, unwrap with the owner private key (re-derived in-session via Web3Auth), re-seal the parent mirror under the correct key, and converge. Self-contained per-node recovery — robust to multiple simultaneous dirty edges at depth>=2 (chosen over persisting the already-computed `newReadKeySealed`, which would require chained top-down recovery through each parent key).
- **D-02 (defined key source):** SC#3's "repair the parent mirror from a defined key source" = the **ECIES wrapped-key checkpoint entry.** This strengthens the ROADMAP's SC#3 wording (which was written assuming the key was unrecoverable).
- **D-03 (ordering — the real cost):** the wrapped-key write must **durably commit before** the child publish, or the window is only narrowed, not closed. Critical path becomes: mint -> wrap -> await durable commit -> publish child -> ...
- **D-04 (lifecycle / GC):** delete the wrapped key once the parent mirror commits (it is then recoverable from the committed mirror), and **expire wrapped keys for abandoned jobs** so they do not linger in the durable store. Zero the unwrapped `readKeyPrime` on resume per the D-09 terminal-owner rule.
- **D-05 (fallback only):** the "detect the already-rotated edge before `rotateOne` (kill the AEAD crash) + surface a distinct typed error (e.g. `DirtyNodeUnrecoverableError`) for top-down re-resolution" behavior becomes the **fallback for the truly-expired / GC'd-key case only**, NOT the primary path. The engine must still detect `childPub.generation > childRef.generation` before `rotateOne` and never feed the stale pre-rotation key into `unsealNode`.
- **Security framing (informs planning):** an already-rotated dirty node means the **revoked reader is already cut off from it — revocation succeeded.** The only casualty is *owner* navigability. There is no revocation gap; this is an availability/durability fix, and ECIES-under-owner-pubkey adds no net trust surface (unwrappable only with the owner key that already gates the vault).

### SC#4 — Cross-store floor atomicity + fail-closed writes

- **D-06 (atomicity): single combined durable record.** Merge both floors (generation + sequence) into ONE record written atomically — Rust: write-temp + `rename` (atomic on POSIX) of one JSON sidecar; TS: one IndexedDB object in one transaction. Partial-failure divergence becomes structurally impossible (no divergence window). Chosen over a transactional `HighWaterStore` API (more surface, same guarantee) and over write-ahead + idempotent replay (leaves a safe-direction divergence window).
- **D-07 (shared plane):** the SC#3 ECIES wrapped-key checkpoint **lives in the same combined durable record / plane** — one coherent durable-write machinery for both concerns. Degrades to a single in-memory object on the D-08 in-memory degradation path.
- **D-08 (fail-closed — mechanical, no gray area):** `crates/sdk` floor store must surface write failures through `HighWaterStore::put` / `bump_floor` (fail closed on persistence failure rather than log-and-return-`Ok`). This half needs no decision.

### SC#5 — Reconcile gate generation source

- **D-09 (thread the resolved generation).** `reconcileFolderSequence` (`client.ts:1789`) must fetch the resolved CID + unseal the node inside the reconcile path so `enforceResolved` gates on the record's **actual** generation, not the cached `folderTree.get(ipnsName)?.nodeGeneration` (`:1827`). Thread the folder read key into the reconcile path. Chosen over "make the cached-fallback contract explicit" because this is a durability/soundness phase and the cost lands on **write-path reconciles only** (upload `:2276/:2500`, move `:2591-2592` — two on a move), never on the 30s poll.
- **Nuance (informs scope, not the decision):** the **sequence** floor is already gated on the freshly-resolved `sequenceNumber`, and IPNS records are owner-signed (the seq envelope binds to the body CID), so external rollback (high-seq envelope + low-gen body) is unforgeable without the IPNS key. Threading the generation is therefore **defense-in-depth against our own client equivocating** (a bug publishing a lower-gen body at a higher seq), not against an outside attacker.

### SC#6 — Depth-2/3 crash-resume e2e fixture (non-vacuous)

- **D-10 (adversarial + security fixture).** The new `rotation-crash-safety.test.ts` case must use a **depth-3 tree with fan-out >=2 at the crashed parent**, with **precise fault injection at a deep child's post-publish / pre-parent-republish point** (the exact lost-key window), plus a **multi-dirty-edge variant** (2+ siblings published, parent batch still open). After resume it must assert ALL of:
  1. owner navigates root -> deep node and unseals with the **new root key**;
  2. the revoked reader's **old key FAILS** to unseal (revocation held);
  3. the walk completes with **no spurious root `pendingChildCount` decrement** (correct per-parent accounting);
  4. the **ECIES wrapped-key checkpoint lifecycle**: persisted-before-publish, consumed on resume, GC'd after mirror commit.
- **Rationale:** Phase 70's gate passed vacuously on a childless root; a single shape / single crash point risks repeating exactly that class of miss. This fixture is the explicit anti-vacuous gate for the phase.

## Existing Code Insights

### Reusable Assets
- **`wrapKey(key, recipientPublicKey)`** (used in-engine at `engine.ts:465` for grants) — the ECIES primitive D-01 reuses to wrap `readKeyPrime` under the owner pubkey. Unwrap counterpart on resume.
- **`sealChildReadKey` / `unsealChildReadKey`** — AES-GCM AAD-bound child-key seal; the `newReadKeySealed` computed at `:840` is the "persist existing sealed key" variant we did NOT choose but which shows the mirror-repair shape.
- **`createConcurrentAddResealingMerge`** (`:1176-1249`) — precedent for re-sealing a child ref under the parent's new key with an old-then-new key probe. NOTE: it handles an *unchanged* child key; SC#3's node has a *changed* (rotated) key — do not copy it blindly.
- **`decrementPendingAndMaybeRepublish`** — the D-09 batched parent-republish tail; SC#1/SC#2 accounting hangs off this.
- **`JsonSidecarFloorStore` / `HighWaterStore` trait** (Rust) + `idbPut` max-preserving atomic (TS) — the store seam D-06/D-07 fold into a single combined record.

### Established Patterns
- **Terminal-owner zeroization (D-09):** zero only buffers you own/discard; never zero caller-owned/reused buffers (historically broke 48/89 sdk-e2e). Applies to the unwrapped `readKeyPrime` on resume and to any transient key in the mirror repair.
- **Published IPNS records are the source of truth (D-10):** the job record is advisory; the new wrapped-key checkpoint is a recovery aid, not authority.
- **`completedNodeIds.add(nodeId)` must be the last mutation** in `rotateOne` (D-07 grant-safety) — the wrapped-key persist must slot in *before* the publish, not after the completion mark.

### Integration Points
- The ECIES wrapped-key checkpoint (SC#3) and the combined floor record (SC#4) share one durable plane — build them as one durability change, not two.
- `reconcileFolderSequence` (SC#5) needs the folder read key threaded in — check how the write-path callers already hold/derive it.

<specifics>
## Specific Ideas

- D-01 explicitly overturns Phase 70 RESEARCH Pitfall 4's "no recovery" stance: the key is only unrecoverable because it was never persisted; ECIES-wrapping + durable-persist-before-publish makes the crash window fully resumable without writing plaintext keys at rest.
- The lost-key window is network-round-trip-sized (child publish -> parent batched republish), not sub-millisecond — it is a real, reproducible window, which is why the e2e fault injection (D-10) must land precisely inside it.

</specifics>
