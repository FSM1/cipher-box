# Phase 70.1 Plan 09: Production RotationDeps Adapter Summary

**Production `FuseRotationDeps` adapter (generic over an injectable `RotationTransport` seam) drives desktop FUSE shared-scope-exit read-key rotation via the real `resolve_ipns_verified`/`fetch_content`+`decode_published_node`/`upload_content`+`create_ipns_record`+`publish_ipns` primitives, replacing the hard-coded EIO stub.**

## Performance

- **Duration:** ~55 min
- **Tasks:** 3 (TDD RED, TDD GREEN, wiring)
- **Files modified:** 7 (1 new, 6 modified)

## Accomplishments

- Built `FuseRotationDeps<T: RotationTransport>`, a production `cipherbox_sdk::rotation::engine::RotationDeps` implementor, generic over an injectable transport seam so unit tests fake resolve/fetch/publish without a live `ApiClient` (mirrors `crates/sdk`'s own `FakeDeps` pattern).
- Implemented `ApiClientTransport`, the real transport backed by `resolve_ipns_verified` (fail-closed signature-checked chokepoint), `fetch_content`+`decode_published_node`, and `upload_content`+`create_ipns_record`+`marshal_ipns_record`+`publish_ipns`.
- Closed Pitfall 7 (the 409 conflict-shape landmine): on a CAS-409, `publish_with_cas` performs a follow-up `resolve`+`fetch_node` to materialize the REAL winning remote before returning `PublishAttempt::Conflict` — verified by a dedicated unit test asserting the returned `remote` came from a fetch, not a fabricated placeholder.
- Wired `persist_wrapped_key`/`get_wrapped_key`/`delete_wrapped_key` to ECIES-wrap/unwrap under the owner's own keypair (`cipherbox_crypto::wrap_key`/`unwrap_key`) and delegate ciphertext to the combined `JsonSidecarFloorStore` (Plan 70.1-03) — verified by a round-trip unit test against a real temp-dir-backed store.
- Live-wired `rotate_read_on_scope_exit`: replaced the `log::error!` + hard-coded `Err(...not yet live-wired...)` stub with a call that resolves the grant-root's stable `node_id` + current `read_key` from the locally-mounted `InodeTable`, constructs the adapter, and calls `rotate_read_from_node`.
- Added a `rotation_checkpoint_store` (`JsonSidecarFloorStore`) handle to `CipherBoxFS`, pointed at the same combined sidecar as `high_water`, and threaded it through the test fixture and both desktop mount sites (macOS/Linux FUSE + WinFsp).

## Decisions Made

- **ROT-04 desktop-grant-remint: DEFERRED** (explicitly sanctioned by this plan's `<verification>` block). `query_grants_rooted_at`/`update_grant`/`delete_grant` are left at the trait's default no-op. Consequence: an inner grant rooted at a rotated subtree node is not re-minted/deleted by the desktop client. D-16 acceptance is unaffected — the directly-revoked recipient is still cut off (server-side row deletion + rotated read keys lock them out).
- **IPNS signing-key sourcing — new scope decision, not specified by RESEARCH.** RESEARCH's "Where the adapter lives" section lists the adapter's dependencies as `api`, the owner ECIES keypair, `rt`, and the floor store — it does not address how the production adapter recovers the Ed25519 signing seed needed to actually sign+publish an arbitrary rotated node's new IPNS record (that seed lives inside `NodeWriteBody.ipns_private_key`, itself write-plane-sealed — a fully general solution would require a parallel write-key-chain walk mirroring `replay.rs::resolve_owned_parent`, which RESEARCH explicitly scopes to Phase 72). This plan resolves it pragmatically: `ApiClientTransport` sources the signing seed from the already-mounted, in-memory `InodeTable` (the same plaintext-in-memory cache `fs.rs::build_folder_metadata` already reads for local publishes) — correct for any node the FUSE mount has materialized (the common case for a scope-exit rotation, since the owner is actively mutating a locally-browsed subtree), and fails CLOSED (`Err` → EIO) for a node not yet materialized locally, rather than silently succeeding incorrectly or inventing new write-plane-walk machinery mid-plan.
- **Write-plane preservation on republish: also deferred**, for the same reason. The engine's own `seal_and_publish` (Plan 08, already landed) always emits `write_sealed: None` on a rotation republish — this adapter does not reconstruct/preserve the write body either. Both gaps are flagged here as the natural Phase-72 follow-up (mirrors the RESEARCH's own explicit "Write plane rotation remains out of scope (Phase 72)" framing).
- **`persist_job` is a no-op debug logger** (advisory per D-10 — published IPNS records are the source of truth; RESEARCH explicitly recommends this minimal form since the Rust engine has no `load_job` counterpart).

## Known Limitations (documented, not stubs)

These are NOT stubs blocking this plan's own goal (a covered scope-exit rotation completing instead of EIO) — they are narrower-than-ideal production behavior, explicitly flagged for the Phase-72 write-plane follow-up per RESEARCH's own scoping:

1. **IPNS signing-key sourcing is local-InodeTable-only.** `ApiClientTransport::publish` fails closed (`Err` → EIO) for a node that has never been materialized in the local mount. In practice this covers the common case (the owner is actively browsing/mutating the subtree being rotated) but is not a fully general solution.
2. **Write-plane (`write_sealed`) is not reconstructed on republish.** Inherited from the engine's own `seal_and_publish` (Plan 08), which always emits `write_sealed: None`. A rotated node's write-plane data (its own IPNS private key + `WriteChildRef` list, if a folder) is dropped on republish rather than re-sealed under the bumped generation.
3. **ROT-04 desktop-grant-remint** — see "Decisions Made" above; explicitly sanctioned by this plan.
