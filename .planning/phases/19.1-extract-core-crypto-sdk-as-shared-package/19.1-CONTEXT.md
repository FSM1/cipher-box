# Phase 19.1: Extract Core Crypto SDK as Shared Package - Context

**Gathered:** 2026-03-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Extract framework-agnostic vault operation logic from the web app's React services/hooks into a layered package architecture. The goal is enabling load testing, integration testing, and future CLI usage without requiring a browser context — while making the web app a thin UI layer over the SDK.

This phase covers package creation, code migration, and web app refactoring. It does NOT add new features — existing functionality is preserved and redistributed.

</domain>

<decisions>
## Implementation Decisions

### Package Architecture (five packages)

1. **`@cipherbox/crypto`** — Pure crypto primitives + key hierarchy/derivation (already exists, needs domain logic extracted out)
   - AES-GCM/CTR encrypt/decrypt
   - ECIES wrap/unwrap/reWrap
   - Ed25519 keypair generation, sign, verify
   - HKDF derivation (`deriveKey`, `deriveContextKey`, `generateFolderKey`)
   - Vault/file/registry/bin IPNS keypair derivation (`deriveVaultIpnsKeypair`, etc.)
   - Utility functions, constants

2. **`@cipherbox/api-client`** — Typed HTTP client (already exists as raw OpenAPI spec, needs orval generation moved in)
   - Move orval config + generated output from `apps/web/src/api/` into package
   - Keep axios as HTTP layer (progress events, cancel tokens needed for upload/download)
   - Both web app and SDK packages import from `@cipherbox/api-client`

3. **`@cipherbox/core`** — CipherBox domain types & metadata schemas (new, extracted from current crypto package)
   - All metadata types & schemas (FolderMetadata, FileMetadata, DeviceRegistry, RecycleBinMetadata, etc.)
   - All validators (`validateFolderMetadata`, `validateFileMetadata`, etc.)
   - Metadata encrypt/decrypt functions (`encryptFolderMetadata`, `decryptFolderMetadata`, etc.)
   - Vault init (`initializeVault`, `encryptVaultKeys`, `decryptVaultKeys`)
   - IPNS record creation and marshalling (`createIpnsRecord`, `marshalIpnsRecord`, etc.)
   - Depends on `@cipherbox/crypto` for primitives

4. **`@cipherbox/sdk-core`** — Stateless folder-aware operations (new, extracted from web services layer)
   - Folder-aware operations: `uploadFileToFolder`, `downloadAndDecrypt`, `createSubfolder`, `renameInFolder`, `moveItem`, `deleteFromFolder`
   - Each function takes everything as explicit parameters (metadata, keys, apiClient) and returns updated metadata — no internal state
   - Designed for load tests and integration tests: a test can call `uploadFileToFolder(file, metadata, folderKey, ipnsKeypair, publicKey, apiClient)` without any state management
   - Includes IPNS publish/resolve orchestration
   - Depends on `@cipherbox/crypto`, `@cipherbox/core`, `@cipherbox/api-client`

5. **`@cipherbox/sdk`** — Stateful client with full workflow orchestration (new)
   - Class-based: `new CipherBoxClient({ apiUrl, getAccessToken, vaultKeypair, onOperationStart?, onOperationEnd?, onError? })`
   - Maintains internal folder tree, key cache, IPNS sequence tracking
   - Full workflows including bin and sharing: `client.deleteFile()` handles folder metadata update + bin insertion + share cleanup
   - Emits change events for state sync with React
   - Depends on `@cipherbox/sdk-core`

### Crypto ↔ Core Split Line

- **crypto keeps:** anything that is a generic cryptographic operation or key derivation, even if CipherBox-specific derivation context strings are used. Key hierarchy functions (`deriveKey`, `generateFolderKey`, `deriveVaultIpnsKeypair`) are key management primitives and stay in crypto.
- **core gets:** anything that knows about CipherBox's data model — metadata types/schemas, validators, metadata encrypt/decrypt (which serialize domain objects then call crypto), vault initialization, IPNS record creation/marshalling.
- The dividing question: "Does this function need to know what a FolderMetadata or VaultInit looks like?" If yes → core. If it just operates on raw bytes/keys → crypto.

### SDK-Core ↔ SDK Boundary

- **sdk-core:** Folder-aware but stateless. Operations take metadata in, return updated metadata out. `deleteFromFolder()` returns `{ updatedMetadata, removedItems }` — no knowledge of bin or shares.
- **sdk:** Full workflow orchestration with state. `client.deleteFile()` calls sdk-core, then handles bin insertion and share re-wrapping internally. Bin and sharing logic lives here because the stateful SDK is the web app's orchestration layer.
- **Rationale:** Load tests drive sdk-core design — a realistic test scenario (simulate users uploading files) should be achievable with sdk-core alone, without needing the stateful SDK's overhead.

### SDK Consumer Contract

- **Auth:** Token provider callback — `getAccessToken: () => Promise<string>`. SDK calls before each request. Consumer owns refresh logic.
- **Stateless API (sdk-core):** Explicit context object per call. Every function is self-contained with all dependencies passed as parameters. Perfect for parallelized load tests.
- **Observability:** Callback hooks on the stateful client (`onOperationStart`, `onOperationEnd`, `onError`). Consumers wire up Prometheus histograms, logging, or test assertions.

### Zustand ↔ SDK State Sync

- SDK emits change events (onChange callback or EventTarget pattern)
- Existing Zustand stores (`folder.store`, `vault.store`, etc.) subscribe to SDK events and mirror state
- React components keep using the same store hooks (`useFolderStore()`, etc.) — minimal component refactoring
- Stores transition from "service callers" to "SDK event subscribers"

### Desktop Rust Parity

- Leave Rust crypto implementation as-is for v1.1
- SDK is TypeScript-only. Desktop keeps native Rust for FUSE mount performance
- Package architecture naturally supports a future wasm swap without extra design work now

### Migration Strategy

- **Bottom-up, one package at a time:** Split crypto → crypto + core first. Then create sdk-core from services. Then build sdk on top. Web app re-imports at each step.
- **Re-exports during transition:** When splitting crypto, `@cipherbox/crypto` temporarily re-exports everything from `@cipherbox/core`. Existing consumers don't break.
- **Final plan removes re-exports:** The last plan in this phase removes all transitional re-exports. All imports must point to the correct package. No lingering shims.
- **Full hook refactoring included:** Both services AND React hooks are refactored. Hooks become thin wrappers calling SDK methods. Not deferred to a follow-up.

### Package Versioning

- **Independent semver per package.** Each package versions independently — a bump to `@cipherbox/crypto` doesn't force a version bump on `@cipherbox/sdk`.
- **Caret ranges for cross-deps:** e.g., `"@cipherbox/crypto": "^1.0.0"`. Allows minor/patch updates without bumping dependents.
- **Release Please configured per-package** with independent changelogs and version tracking.

### Monorepo Structure

- All packages under `packages/` directory
- Build tooling: tsup + vitest (matching existing `@cipherbox/crypto` pattern)
- Monorepo-internal only: pnpm workspace protocol (`"workspace:*"`) for all cross-references. No npm publishing for now.

### Web-Only Services (stay in apps/web)

These services have browser-specific dependencies and do NOT move into any SDK package:

- `search-index.service` — IndexedDB dependency
- `streaming-crypto.service` — media playback / browser APIs
- Upload/download stores — UI progress tracking, cancellation
- Notification store — toast/UI feedback

### Claude's Discretion

- Internal state representation in the stateful SDK (Map vs object, immutable vs mutable)
- Change event granularity (per-operation vs batched)
- Error type hierarchy across packages
- tsup entry point configuration (separate CJS/ESM builds)
- Test organization within each package

## Specific Ideas

- Load test scenario drives sdk-core API design: "simulate 50 concurrent users each uploading 10 files" should be straightforward with sdk-core alone
- The original todo sketched a `CipherBoxClient` interface — confirmed as the stateful SDK's public API shape
- Re-exports as transitional shims with explicit removal as the final plan step — no lingering backwards-compat shims

</specifics>

<deferred>
## Deferred Ideas

- **Rust wasm-bindgen** — SDK architecture supports future wasm swap for desktop, but no wasm work in this phase. Native Rust stays.
- **Shared type definitions (JSON Schema)** for Rust ↔ TypeScript metadata parity — useful but separate scope
- **npm publishing** — packages are monorepo-internal only for now. Publishing is a future decision when external consumers exist.
- **bin/share/device-registry extraction to sdk-core** — currently these live in the stateful SDK only. If load tests need them statelessly, they can be pushed down later.

</deferred>
