<objective>
Wire the public API surface to the guarded-unpin core. Replace the unauthenticated `POST /ipfs/unpin` handler (currently `ipfsProvider.unpinFile(dto.cid)` ignoring `req.user`) with a delegation to `vaultService.guardedUnpin(req.user.id, dto.cid)` (D-01, D-02 telemetry lives inside the service), keep the response DTO opaque `{ success: true }` (D-11, no `refsRemaining`), and reroute the upload compensation path (`ipfs.controller.ts:122`) through `guardedUnpin` so the compensation cannot bypass ownership. Document the D-13 race window in a code comment at the compensation site. Finally, regenerate the api-client (mandatory per CLAUDE.md) and commit the generated files.

Purpose: This is the change that actually closes the cross-tenant unpin vulnerability at the HTTP boundary — until the controller passes `req.user.id` into the guarded path, the ownership check in 42-03 is dead code. D-11 keeps the response opaque so the wire contract is unchanged and api-client churn is limited to the regeneration check.
Output: Updated `unpin()` + compensation path in `ipfs.controller.ts`, extended controller spec, regenerated and committed api-client (openapi.json + generated client + models).
</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
| -------- | ----------- |
| authenticated client to POST /ipfs/unpin | req.user.id from verified JWT is the only authority; dto.cid is an untrusted public identifier |
| controller to VaultService.guardedUnpin | controller must forward the authenticated userId, never trust a client-supplied user field |
| upload compensation to guardedUnpin | a failed pin must be cleaned up only through the ownership-checked path, never raw Kubo |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --------- | -------- | --------- | ----------- | --------------- |
| T-42-14 | Tampering | cross-tenant unpin at the HTTP boundary | mitigate | unpin() forwards `req.user.id` to guardedUnpin; no code path reaches `ipfsProvider.unpinFile` from the controller, so CID knowledge alone cannot delete (D-01). |
| T-42-15 | Information Disclosure | CID-existence oracle via response shape | mitigate | unpin() returns the constant `{ success: true }` for every outcome; no `refsRemaining`/status field (D-11); the owned-vs-cross-user distinction lives only in service-side telemetry. |
| T-42-16 | Elevation of Privilege | compensation path bypassing ownership | mitigate | recordPin-failure compensation routes through guardedUnpin (ownership + refcount), not raw unpinFile, so a failed upload cannot unpin another user's deduped CID. |
| T-42-17 | Repudiation | quota double-decrement / double-count | mitigate | fileUnpins.inc() moved entirely into guardedUnpin (42-03); the controller no longer increments, preventing double-count on the same unpin. |
| T-42-SC | Tampering | npm installs via api:generate | accept | api:generate runs existing devDependency tooling (orval/openapi generator already in the repo); introduces no new runtime package (RESEARCH audit: zero new deps). |

</threat_model>
