<objective>
Keep the workspace `Cargo.lock` in sync with release-please's crate version bumps so `main` is never stale-on-first-cargo after a release (#13 / D-05). Use the FALLBACK path: `cargo update -p <crate> --precise <new-version>` for each bumped first-party crate, committed alongside the release, plus a `git diff --exit-code Cargo.lock` guard that fails when the lock is still stale.

Purpose: release-please bumps each crate's `Cargo.toml` `version` but does NOT update Cargo.lock's `[[package]] version` lines, so post-release `main` carries a stale lock until someone runs cargo out-of-band — a supply-chain drift hazard (T-53-03). The native `cargo-workspace` plugin (the D-05 "preferred" path) was REJECTED: research confirms open bug googleapis/release-please#2517 (March 2025) causes it to skip Cargo.lock AND `.release-please-manifest.json` updates in this repo's manifest/monorepo mode — enabling it would regress the working release pipeline. First-party crates only (the diff is just version strings; no dependency re-resolution).

Output: a post-release Cargo.lock sync step + stale-lock guard in `release-please.yml`.
</objective>
