# Plan 30-04: Logger Transport Integration and User Identity Binding

<objective>
Register a Faro transport function into Phase 28's logger transports array so that warn and error level messages are automatically forwarded to Grafana Faro. Wire user identity (publicKey only) into Faro after authentication so error reports are associated with users without leaking PII.
</objective>

## Background

Phase 28 created a logger module at `apps/web/src/lib/logger.ts` with a `transports` array hook. Each transport receives `(level, message, context)` for every log call above the configured threshold. This plan registers a single Faro transport that maps:

- `logger.error()` calls -> `faro.api.pushError()` (creates error events in Grafana)
- `logger.warn()` calls -> `faro.api.pushLog()` (creates log entries in Grafana)

This approach means the 139+ call sites from Phase 28 automatically get Faro reporting with zero code changes — they just call `logger.error('...')` and the transport handles forwarding.

## must_haves

- Faro transport registered in logger.transports array at app startup
- Transport maps `error` level to `faro.api.pushError()`
- Transport maps `warn` level to `faro.api.pushLog()`
- Transport does NOT forward `debug` or `info` (noise reduction)
- User publicKey set on Faro after successful authentication
- User cleared from Faro on logout
- No modification to any of the 139+ existing logger call sites

### Task 1: Export Faro transport registration function

<read_first>

- apps/web/src/lib/faro.ts (the module created in Plan 30-01 — to see getFaroInstance, current exports)
- apps/web/src/lib/logger.ts (Phase 28 logger — to see Transport type definition, transports array, and how transports are called)
  </read_first>

<action>
Add a `registerFaroTransport` function to `apps/web/src/lib/faro.ts`:

```typescript
import { type Transport as LoggerTransport } from './logger';

/**
 * Creates and registers a Faro transport in the Phase 28 logger.
 * Forwards warn -> pushLog, error -> pushError to Grafana Faro.
 * No-op if Faro is not initialized.
 */
export function registerFaroTransport(loggerTransports: LoggerTransport[]): void {
  const faro = getFaroInstance();
  if (!faro) return;

  const faroTransport: LoggerTransport = (level, message, context) => {
    if (level === 'error') {
      // pushError expects an Error object or a string
      const error = context?.error instanceof Error ? context.error : new Error(message);
      faro.api.pushError(error, {
        context: context as Record<string, string> | undefined,
      });
    } else if (level === 'warn') {
      faro.api.pushLog([message], {
        level: 'warn' as any, // Faro LogLevel type
        context: context as Record<string, string> | undefined,
      });
    }
    // debug and info are not forwarded — noise reduction
  };

  loggerTransports.push(faroTransport);
}
```

Key decisions:

- The transport receives already-redacted context (Phase 28 logger runs `redact()` before calling transports)
- For errors, if `context.error` is an Error instance, use it directly for better stack traces; otherwise construct a new Error from the message
- Only `warn` and `error` are forwarded — `debug` and `info` would overwhelm the free tier quota
- Check the actual Faro `pushError()` and `pushLog()` TypeScript signatures and adjust the type casts accordingly. The `as any` on level may not be needed if Faro's LogLevel type includes 'warn'.
  </action>

<action>


Find the exact location by looking for where `publicKey` is set in the auth store or returned from Web3Auth. This is typically in the `useAuth` hook's login/connect success handler.

2. In the logout path, clear the Faro user:

   ```typescript
   import { clearFaroUser } from '../lib/faro';

   // In logout handler, after clearing auth state:
   clearFaroUser();
   ```

3. Add `clearFaroUser` export to `apps/web/src/lib/faro.ts`:

   ```typescript
   export function clearFaroUser(): void {
     const faro = getFaroInstance();
     if (!faro) return;
     faro.api.setUser(null);
   }
   ```

Key decisions:

- Only `publicKey` is sent as user identity — never email (per D-13 in CONTEXT.md)
- `setFaroUser` is called after auth succeeds, not during the auth flow (to avoid sending partial state)
- `clearFaroUser` is called during logout to prevent error reports from being attributed to a logged-out user
- Both functions are no-ops when Faro is not initialized
  </action>
