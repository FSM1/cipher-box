<objective>
Validate the embedded IPNS publish sequence even when CAS (expectedSequenceNumber) is
omitted, enforcing the exact D-09 rule directly in the server's upsertFolderIpns, without
regressing any non-CAS publish path. Closes the sequence-wedge first-publish poison and
rollback/replay gap (HARD-09, D-09/D-10).

Purpose: The server's S1 sequence check is currently gated on
`expectedSequenceNumber !== undefined`, so non-CAS publishes accept ANY embedded sequence
— including a first-publish wild-jump that wedges an IPNS name forever. D-09 closes this
by gating unconditionally. D-10 ships it as a HARD reject, but ONLY after enumerating
every non-CAS publish path and proving each signs DB+1 or equal-idempotent, behind the
full SDK E2E gate (this exact class of tightening broke 48/89 SDK E2E tests before).

Output: An unconditional D-09 gate in upsertFolderIpns with an idempotent-republish
no-increment branch (TEE re-sign path), full jest coverage of the rule, and a
non-CAS-path enumeration audit recorded in the SUMMARY, validated end-to-end by the
full SDK E2E suite.
</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
| -------- | ----------- |
| Publishing client → API upsertFolderIpns | The client (or a TEE re-sign, or an attacker who obtained a signing key / replays an old signed record) submits a signedRecord with an embedded sequence. The server is the enforcement point. |
| Stored DB sequence ↔ embedded record sequence | The DB sequenceNumber is the monotonic version clock; the embedded sequence in the signed record must advance it by exactly the allowed step. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --------- | -------- | --------- | ----------- | --------------- |
| T-58-08 | Denial of Service | First publish with a wild-jump embedded sequence (e.g. u64::MAX) that wedges an IPNS name forever | mitigate | D-09 first-publish gate: embedded ∈ {0,1} only; anything higher → 400. Runs unconditionally (not CAS-gated). |
| T-58-09 | Repudiation / Replay | Replaying an old valid signed record (embedded < stored sequence) to roll back content | mitigate | D-09 `embedded < N` → 400 reject; complements the existing anti-rollback CID check. |
| T-58-10 | Tampering | Wild-jump on an existing row (embedded > N+1) skipping the version clock | mitigate | D-09 `embedded > N+1` → 400 reject. |
| T-58-11 | Denial of Service (self-inflicted regression) | The gate rejecting a legitimate non-CAS publish (vault init / per-file / bin / TEE re-sign), breaking the product | mitigate | Task 1 enumeration proves every non-CAS path signs an accepted sequence; D-10 full-SDK-E2E gate (blocking human checkpoint) catches any regression loudly before ship. Idempotent branch (embedded=N) protects the TEE 6-hour re-sign. |
| T-58-12 | Tampering | Concurrent modification masked as a sequence error (wrong status code) | accept→mitigate | CAS 409 check stays BEFORE D-09 so concurrent-modification keeps its 409 (correct client retry semantics); ordering asserted by the CAS-409 precedence test. |

## Residual Risk

D-04 legacy all-absent records and the DB-CID-authoritative trust model are unchanged.
D-09 is a Low-severity gap closure (server-side input validation, V5/V4-partial): it
hardens against wedge/rollback but the DB CID remains the trust root. The dominant risk
is a self-inflicted availability regression on a non-CAS path — fully covered by the
Task 1 enumeration + the blocking full-SDK-E2E human checkpoint (D-10). No HIGH-severity
path is introduced.
</threat_model>
