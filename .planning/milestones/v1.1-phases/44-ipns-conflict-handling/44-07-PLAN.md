<objective>
Close CR-02: in `updateFileMetadata`, after the 409 conflict merge builds `mergedMetadata`, filter the accumulated `prunedCids` against the set of CIDs the published record actually references (`mergedMetadata.cid` plus every `mergedMetadata.versions[].cid`) before returning. Today a CID pruned from the pre-conflict local list but re-added by the remote merge (e.g. remote's version list was shorter, or version deletion diverged the lists) is returned in `prunedCids` and unconditionally unpinned by `useFileOperations.ts:507-510` / `useFileVersions.ts`, permanently destroying version content the live metadata still points at.

Also folds WR-08 (file half): the existing conflict tests only assert that decrypt was called and the retry sequence — they never inspect the retry `encryptFileMetadata` payload, which is exactly where this bug hides. Add an assertion on the merged published payload.

Purpose: Data-integrity fix — restore-of-a-version must not fail because the version's content was unpinned (truth #14 / D-07 in VERIFICATION.md).
Output: a one-block reference filter before the conflict-path return; one strengthened/new file conflict test.
</objective>
