<objective>
Close CR-01: surface the merged children from `updateFolderMetadataAndPublish` and adopt them in every caller's in-memory/store state so the next write composes from the merged set, not the stale pre-merge local children. Without this, the 409 merge is published correctly but the device's NEXT write republishes the stale children with a fresh CAS sequence (no 409 fires), silently re-dropping the remote additions one write later.

This is a downstream-flowing API-contract change across three packages: sdk-core defines the return field, sdk callers (client.ts, bin, shared-write) adopt/forward it, web hooks store it. Also folds WR-08 (folder half): add a folder conflict test asserting the merged PUBLISHED children are surfaced.

Purpose: Make the lost-update fix durable across consecutive writes — the actual phase goal (truth #13 in VERIFICATION.md).
Output: publishedChildren field on the return shape; ~12 store-write sites adopting it; shared-write forwarding it; useSharedWriteOps + 2 web fire-and-forget paths adopting it; one new folder test assertion.
</objective>

## Trust Boundaries

| Boundary | Description |
| --- | --- |
| concurrent IPNS writer → same folder metadata | Two devices / a write-share recipient + owner mutate one folder; the merged-then-published children must become each caller's next base, or the next write re-drops the other writer's entries with a valid CAS sequence (no 409) |
| sdk-core public API → sdk + web consumers | The return-shape change is a contract widening; consumers must adopt publishedChildren or the fix is inert (the exact failure mode CR-01 describes) |
