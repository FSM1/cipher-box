<objective>
Close the file-record TOCTOU window (file/index.ts:225-231) and add conflict semantics. `updateFileMetadata` currently resolves a seq, builds a record, and returns it for a caller to publish — with no CAS. This plan makes it publish internally via `createAndPublishIpnsRecord` with `expectedSequenceNumber` (D-06), and on 409 apply latest-wins + loser-becomes-version (D-07): the newest write by modifiedAt is the current content pointer, the loser's content is preserved in `versions[]`, versions union-merged/deduped/capped by the user-configurable `maxVersionsPerFile`, overflow returned as `prunedCids`.

Purpose: This is the file half of the lost-update fix. Today concurrent file replaces clobber each other's content pointers and versions[] with no detection. After this, the loser's content is never destroyed — it becomes a recoverable version — and the cap honors the Phase 39 user setting instead of the hardcoded 10.
Output: Modified `updateFileMetadata` (CAS publish, conflict merge, `maxVersionsPerFile?` param, mergeVersions helper); `file.test.ts` covering CAS + loser-becomes-version + version-cap.

NOTE — contract change: `updateFileMetadata` currently returns `{ ipnsRecord, prunedCids }` for the caller to publish. Because CAS+409 detection must happen at publish time, this plan moves the publish INTO `updateFileMetadata` (via createAndPublishIpnsRecord). The return shape changes to `{ ipnsName, metadataCid, newSequenceNumber, prunedCids }` (published already). The 2 real callers (useFileOperations.ts:416, shared-write.ts:450 — which today publish the returned record via replaceFileInFolder / batchPublishIpnsRecords) are updated in Plan 04 (caller sweep). This plan owns file/index.ts only; Plan 04 owns the callers. Document the new return shape in the SUMMARY so Plan 04 wires it correctly.
</objective>

## Trust Boundaries

| client → CipherBox file IPNS publish API | CAS (expectedSequenceNumber) is the only lost-update guard for file records; previously absent (TOCTOU) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- |
| T-44-09 | Tampering (data loss) | updateFileMetadata TOCTOU | mitigate | expectedSequenceNumber CAS closes the resolve-then-publish window; on 409 the losing write's content is preserved as a VersionEntry (loser-becomes-version, D-07) — unit-tested both directions |
| T-44-10 | Denial of Service (version bloat) | versions[] growth on repeated conflicts | mitigate | versions[] capped by user-configurable maxVersionsPerFile (Phase 39 setting); overflow → prunedCids unpinned through the Phase-42 guarded endpoint — no unbounded version-history growth |
| T-44-11 | Tampering (replay) | file sequence number | accept | Same server self-increment divergence as folders — re-resolve authoritatively and re-sign; protocol fix out of scope (CONTEXT line 16) |
| T-44-12 | Tampering (wrong key) | re-encrypt merged file metadata | mitigate | Merged FileMetadata re-encrypted with `params.folderKey` via encryptFileMetadata before upload — never plaintext to IPFS (V6 crypto) |
| T-44-13 | Denial of Service (livelock) | file conflict retry | mitigate | Bounded to 2 total attempts then ConflictError — no unbounded retry |
