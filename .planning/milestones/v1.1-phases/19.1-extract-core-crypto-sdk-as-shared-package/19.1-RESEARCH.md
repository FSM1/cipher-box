# Phase 19.1: Extract Core Crypto SDK as Shared Package - Research

**Researched:** 2026-03-20
**Domain:** TypeScript monorepo package extraction, SDK architecture, build tooling
**Confidence:** HIGH

## Summary

This phase extracts framework-agnostic vault operation logic from the web app into a five-package layered architecture (`@cipherbox/crypto`, `@cipherbox/api-client`, `@cipherbox/core`, `@cipherbox/sdk-core`, `@cipherbox/sdk`). The work is primarily code reorganization -- no new features, no new crypto algorithms, no new API endpoints.

The existing `@cipherbox/crypto` package (167 LOC index, 14 submodules) already establishes the build pattern (tsup + vitest) and workspace protocol (`workspace:*`). The split creates `@cipherbox/core` by moving domain types/schemas/validators/metadata-encryption out of crypto, leaving crypto with pure primitives + key derivation. Above those, `@cipherbox/sdk-core` extracts stateless folder operations from `apps/web/src/services/` (~4,775 LOC across 15 files), and `@cipherbox/sdk` wraps them with state management and event-driven updates. The web app becomes a thin UI layer over the SDK.

**Primary recommendation:** Follow strict bottom-up order: (1) split crypto into crypto+core with re-exports, (2) move orval generation into api-client package, (3) build sdk-core from service extraction, (4) build sdk with stateful client, (5) rewire React hooks/stores, (6) remove transitional re-exports.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Package Architecture (five packages):**

1. `@cipherbox/crypto` -- Pure crypto primitives + key hierarchy/derivation (keep domain logic out)
2. `@cipherbox/api-client` -- Typed HTTP client (move orval config + generated output from apps/web)
3. `@cipherbox/core` -- CipherBox domain types & metadata schemas (extracted from crypto)
4. `@cipherbox/sdk-core` -- Stateless folder-aware operations (extracted from web services)
5. `@cipherbox/sdk` -- Stateful client with full workflow orchestration

**Crypto / Core Split Line:**

- crypto keeps: generic crypto operations, key derivation (deriveKey, generateFolderKey, deriveVaultIpnsKeypair)
- core gets: anything that knows about CipherBox data model (metadata types/schemas, validators, metadata encrypt/decrypt, vault init, IPNS record creation/marshalling)

**SDK-Core / SDK Boundary:**

- sdk-core: Folder-aware but stateless. Operations take metadata in, return updated metadata out
- sdk: Full workflow orchestration with state. Bin and sharing logic lives here

**SDK Consumer Contract:**

- Auth: Token provider callback `getAccessToken: () => Promise<string>`
- Stateless API (sdk-core): Explicit context object per call
- Observability: Callback hooks on the stateful client

**Zustand / SDK State Sync:**

- SDK emits change events
- Existing Zustand stores subscribe to SDK events and mirror state
- React components keep using the same store hooks

**Desktop Rust Parity:** Leave Rust as-is. SDK is TypeScript-only.

**Migration Strategy:**

- Bottom-up, one package at a time
- Re-exports during transition (crypto re-exports core temporarily)
- Final plan removes all re-exports
- Full hook refactoring included (not deferred)

**Package Versioning:** Independent semver per package, caret ranges for cross-deps.

**Monorepo Structure:**

- All packages under `packages/`
- Build tooling: tsup + vitest
- pnpm workspace protocol only, no npm publishing

**Web-Only Services (stay in apps/web):**

- search-index.service (IndexedDB)
- streaming-crypto.service (media playback / browser APIs)
- Upload/download stores (UI progress tracking, cancellation)
- Notification store (toast/UI feedback)

### Claude's Discretion

- Internal state representation in the stateful SDK (Map vs object, immutable vs mutable)
- Change event granularity (per-operation vs batched)
- Error type hierarchy across packages
- tsup entry point configuration (separate CJS/ESM builds)
- Test organization within each package

### Deferred Ideas (OUT OF SCOPE)

- Rust wasm-bindgen -- SDK architecture supports future wasm swap but no wasm work now
- Shared type definitions (JSON Schema) for Rust/TS metadata parity
- npm publishing -- packages are monorepo-internal only
- bin/share/device-registry extraction to sdk-core (stays in stateful SDK)

### Pattern 4: Event-Driven State Sync (SDK to Zustand)

**What:** The stateful SDK emits typed events. Zustand stores subscribe and mirror state.
**When to use:** For the `@cipherbox/sdk` to communicate state changes to the React UI.
**Example:**

```typescript

  | { type: 'folder:loaded'; folderId: string; children: FolderChild[] }
  | { type: 'folder:updated'; folderId: string; children: FolderChild[] }
  | { type: 'folder:deleted'; folderId: string }
  | { type: 'operation:start'; operation: string }
  | { type: 'operation:end'; operation: string }
  | { type: 'error'; error: Error };

// In apps/web (Zustand store subscriber):
sdk.on((event) => {
  if (event.type === 'folder:loaded') {
    useFolderStore.getState().setFolder({ ...folderNodeFromEvent(event) });
  }
});
```

### Anti-Patterns to Avoid

- **Importing Zustand stores from SDK packages:** SDK packages MUST NOT import from `apps/web/src/stores/`. All state access is via explicit parameters or the stateful SDK's internal state.
- **Using `import.meta.env` in packages:** Only `apps/web` should reference `import.meta.env`. Packages receive configuration via constructor params or context objects.
- **Using browser APIs (`Blob`, `FormData`, `document`, `URL.createObjectURL`) in sdk-core:** Use `Uint8Array` for data, pass serialization concerns to the consumer. The one exception is `crypto.randomUUID()` which is available in Node.js 19+ and all modern browsers.
- **Circular dependencies between packages:** The dependency DAG is strictly: crypto <- core <- sdk-core <- sdk. No reverse imports.
- **Moving orval react-query generation into api-client:** The api-client package should generate plain fetch/axios functions. React-query hooks stay in the web app or are a separate concern.

## Common Pitfalls

### Pitfall 1: Breaking the Build Order in pnpm

**What goes wrong:** Package B depends on package A, but `pnpm build` tries to build B before A's types are emitted.
**Why it happens:** pnpm topological sort needs explicit `dependencies` in package.json to determine build order. If `workspace:*` deps are in `devDependencies` instead of `dependencies`, the build order is non-deterministic.
**How to avoid:** Use `dependencies` (not `devDependencies`) for cross-package `workspace:*` references. Verify with `pnpm -r run build` after each new package is added.
**Warning signs:** `Cannot find module '@cipherbox/core'` errors during `pnpm build`.

### Pitfall 2: Circular Re-export During Transitional Phase

**What goes wrong:** `@cipherbox/crypto` re-exports from `@cipherbox/core`, but `@cipherbox/core` imports from `@cipherbox/crypto`. This is a valid dependency (core depends on crypto for primitives), but the re-export from crypto creates a circular module reference.
**Why it happens:** ESM module evaluation order is strict. If crypto's index.ts imports from core before core can finish evaluating its own imports from crypto, you get undefined exports.
**How to avoid:** The re-exports must be the LAST section of crypto's index.ts, after all crypto-native exports. Test with `node -e "import('@cipherbox/crypto').then(m => console.log(Object.keys(m)))"` to verify.
**Warning signs:** `undefined` when accessing re-exported symbols, or runtime errors about circular dependencies.

### Pitfall 3: `Blob` and `btoa`/`atob` in Non-Browser Contexts

**What goes wrong:** sdk-core functions use `new Blob([JSON.stringify(encrypted)])` for IPFS upload and `btoa()`/`atob()` for base64 encoding. These exist in Node.js 18+ but behave differently.
**Why it happens:** The current code was written for browser-only execution.
**How to avoid:** For base64, use a custom helper or `Buffer.from()` with fallback. For blob construction, sdk-core should accept `Uint8Array` and let the transport layer (api-client) handle serialization. The `uint8ToBase64` helper already exists in folder.service.ts and file-metadata.service.ts (duplicated!) -- consolidate into a utility in core or crypto.
**Warning signs:** `btoa is not defined` or `Blob is not defined` in Node.js test environments.

### Pitfall 4: Store Coupling in Services Being Extracted

**What goes wrong:** Services like `folder.service.ts` access `useAuthStore.getState().teeKeys` at line 189 and `useAuthStore.getState()` at line 1011 for the vault keypair. Missing these during extraction causes runtime errors.
**Why it happens:** The codebase evolved with direct store access as a convenient pattern.
**How to avoid:** Systematically audit every `useXxxStore.getState()` call in each service file before extraction. The audit results (from this research):

- `folder.service.ts`: `useAuthStore` at lines 189, 1011
- `upload.service.ts`: `useQuotaStore` (lines 89), `useUploadStore` (lines 88, 107, 108, 136)
- `file-metadata.service.ts`: `useAuthStore` at line 173
- `ipns.service.ts`: No store deps (clean)
- `download.service.ts`: `document.*` at lines 67, 70, 72 (browser-only `triggerBrowserDownload`)
- `bin.service.ts`: `useAuthStore`, `useBinStore`, `useFolderStore`, `useVaultStore`, `useQuotaStore` (heavily coupled)
- `share.service.ts`: `useShareStore` at line 27 (type import only for ReceivedShare/SentShare types)
  **Warning signs:** TypeScript errors about missing Zustand imports in package compilation.

### Pitfall 5: 53 Import Sites in Web App

**What goes wrong:** There are 53 files in `apps/web/src/` that import from `@cipherbox/crypto`. After the crypto/core split, type-only imports (like `FolderChild`, `FilePointer`, `BinEntry`) need to be redirected to `@cipherbox/core`.
**Why it happens:** Types and crypto functions are co-located in the current package.
**How to avoid:** The transitional re-exports pattern prevents immediate breakage. The final cleanup plan must systematically update all 53 import sites. Use TypeScript `paths` mapping or IDE refactoring tools.
**Warning signs:** Build succeeds with re-exports but type-checking becomes slower due to circular resolution.

### Pitfall 6: Desktop App Has One Import from @cipherbox/crypto

**What goes wrong:** `apps/desktop/src/auth.ts` imports `wrapKey, unwrapKey, hexToBytes, bytesToHex` from `@cipherbox/crypto`. These are pure crypto primitives that STAY in crypto, so this import is safe. But verify it during the final cleanup.
**Why it happens:** The desktop app's TypeScript layer (Tauri webview) uses the crypto package.
**How to avoid:** Verify this import survives the split unchanged. These functions stay in `@cipherbox/crypto`.
**Warning signs:** Desktop build failure after crypto package changes.

### Pitfall 7: orval Client Mode Change for api-client Package

**What goes wrong:** The current orval config generates `react-query` client mode (hooks). The api-client package needs plain function output (no React dependency).
**Why it happens:** orval was configured for the web app specifically.
**How to avoid:** The api-client package orval config should use `client: 'fetch'` or `client: 'axios'` mode instead of `client: 'react-query'`. The web app can then wrap the plain functions in react-query hooks if needed, or keep a separate orval config for hook generation.
**Warning signs:** The api-client package having React as a dependency.

### Pitfall 8: Release Please Configuration for Per-Package Versioning

**What goes wrong:** The current Release Please config uses a single root package with unified versioning. Adding per-package independent versioning requires careful manifest changes.
**Why it happens:** The monorepo was set up with a single version across all apps.
**How to avoid:** Add each new package to `.release-please-manifest.json` with its initial version and to `release-please-config.json` with `release-type: "node"`. Use `include-component-in-tag: true` for packages so tags are like `@cipherbox/core-v1.0.0`. Keep the root entry for app versioning.
**Warning signs:** Release Please PRs that bump all packages simultaneously when only one changed.

## Open Questions

1. **orval Client Mode for api-client Package**
   - What we know: Current orval config uses `client: 'react-query'` which generates React hooks. The api-client package needs plain functions.
   - What's unclear: Whether to use `client: 'fetch'` (no axios dependency) or `client: 'axios'` (keeps axios for progress events). The CONTEXT.md says "Keep axios as HTTP layer (progress events, cancel tokens needed for upload/download)."
   - Recommendation: Use `client: 'axios'` in the api-client orval config. The web app may keep its own orval config for react-query hook generation, or use `@tanstack/react-query` wrappers around the plain axios functions. This is a Claude's Discretion item.

2. **Base64 Encoding Strategy in Non-Browser Contexts**
   - What we know: `btoa`/`atob` are used in ipns.service.ts and file-metadata.service.ts. Both are available in Node.js 16+ but deprecated in Node.js docs in favor of `Buffer`.
   - What's unclear: Whether to add a utility abstraction or rely on global `btoa`/`atob` availability.
   - Recommendation: Use the existing `uint8ToBase64` helper (already duplicated in two files) as a consolidated utility in `@cipherbox/core`. Node.js 16+ has `btoa`/`atob` as globals, and vitest runs with Node.js. No need for a polyfill.

3. **IPFS Upload: Blob vs Uint8Array in sdk-core**
   - What we know: Current code uses `new Blob([JSON.stringify(encrypted)])` for IPFS upload and `new FormData()` with `FormData.append('file', blob)` for the axios call.
   - What's unclear: How to handle this in sdk-core without browser `Blob`/`FormData` APIs.
   - Recommendation: In sdk-core, work with `Uint8Array` throughout. The api-client's IPFS upload function should accept `Uint8Array` and handle `Blob`/`FormData` construction internally. `Blob` and `FormData` are available in Node.js 18+ as globals.
