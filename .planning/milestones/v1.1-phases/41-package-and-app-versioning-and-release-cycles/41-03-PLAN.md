**Section 4: Compute Target Versions (D-26)**

For each labeled package path:

1. Read current version from `.release-please-manifest.json`
2. Determine bump type from label: `breaking` -> major, `feat` -> minor, `fix`/`perf`/`refactor` -> patch
3. For `apps/web` and `apps/desktop` (monotonic per D-08, D-13): if bump is `patch`, upgrade to `minor`
4. Compute next version using semver rules:
   - major: `X.Y.Z` -> `(X+1).0.0`
   - minor: `X.Y.Z` -> `X.(Y+1).0`
   - patch: `X.Y.Z` -> `X.Y.(Z+1)`
   - For monotonic (major.minor only): major `X.Y` -> `(X+1).0`, minor `X.Y` -> `X.(Y+1)`

Implement semver bump without external dependencies:

```javascript
function bumpVersion(current, bumpType, isMonotonic = false) {
  const parts = current.split('.').map(Number);
  // Ensure 3-part semver (pad with 0 if needed)
  while (parts.length < 3) parts.push(0);
  const [major, minor, patch] = parts;

  switch (bumpType) {
    case 'major':
      return `${major + 1}.0.0`;
    case 'minor':
      return `${major}.${minor + 1}.0`;
    case 'patch':
      if (isMonotonic) return `${major}.${minor + 1}.0`; // patch -> minor for monotonic
      return `${major}.${minor}.${patch + 1}`;
  }
}
```

**Section 5: Handle Existing release-as (D-29)**

Read current `release-please-config.json`. For each package that already has a `release-as` entry (from a prior PR merge before RP ran):

1. Compare the existing `release-as` version with the newly computed version
2. Take the HIGHER version (the one with the bigger bump from the current manifest version)
3. This ensures multiple PRs merging in quick succession don't downgrade each other

Compare logic:

```javascript
function isHigherBump(existingReleaseAs, newReleaseAs, currentVersion) {
  // Compare both against current to determine which is a bigger bump
  const existingDelta = versionDelta(currentVersion, existingReleaseAs);
  const newDelta = versionDelta(currentVersion, newReleaseAs);
  // major > minor > patch
  return newDelta > existingDelta;
}
```

Create `.github/workflows/post-merge-release.yml`:

```yaml
name: Post-Merge Release Targets

on:
  push:
    branches:
      - main

# Serialize concurrent runs to prevent race conditions writing to config (D-29 mitigation)
concurrency:
  group: post-merge-release
  cancel-in-progress: false

permissions:
  contents: write
  pull-requests: read

jobs:
  inject-release-targets:
    name: Inject Release Targets
    runs-on: ubuntu-latest
    # Skip commits from release-please (its release PR merge) and our own release target commits
    if: "!startsWith(github.event.head_commit.message, 'chore: release') && !startsWith(github.event.head_commit.message, 'chore(release): set release targets')"
    steps:
      - uses: actions/create-github-app-token@v3
        id: app-token
        with:
          app-id: ${{ vars.RELEASE_BOT_APP_ID }}
          private-key: ${{ secrets.RELEASE_BOT_PRIVATE_KEY }}

      - uses: actions/checkout@v6
        with:
          token: ${{ steps.app-token.outputs.token }}
          ref: main

      - uses: actions/setup-node@v6
        with:
          node-version: '22'

      - name: Compute and inject release targets
        id: inject
        env:
          GITHUB_TOKEN: ${{ steps.app-token.outputs.token }}
          COMMIT_SHA: ${{ github.sha }}
        run: node .github/scripts/post-merge-release.js

      - name: Commit release targets
        if: steps.inject.outputs.packages_bumped != '[]' && steps.inject.outputs.packages_bumped != ''
        env:
          PR_NUMBER: ${{ steps.inject.outputs.pr_number }}
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add release-please-config.json
          git commit -m "chore(release): set release targets from PR #${PR_NUMBER}"
          git push
```

Key design choices per decisions:

- **D-28:** Commit message format `chore(release): set release targets from PR #N` — the `if` condition at the job level skips this commit on the next push event to prevent infinite loops.
- **Concurrency group** `post-merge-release` with `cancel-in-progress: false` — serializes runs so multiple rapid PR merges don't race on config writes. Each run reads the latest state.
- **GitHub App token** — same pattern as release-please.yml. Needed because:
  1. The commit to main must trigger the release-please workflow (GITHUB_TOKEN commits don't trigger workflows)
  2. Contents:write permission to push to main
- **checkout with token** — uses app token so `git push` authenticates correctly
- **checkout ref: main** — ensures we read the latest main, not the triggering commit (which might be stale if another merge happened)
- **Skip conditions:** Both `chore: release` (RP's commit) and `chore(release): set release targets` (our commit) are skipped to prevent loops
