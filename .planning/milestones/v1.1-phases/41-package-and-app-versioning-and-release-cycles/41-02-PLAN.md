<objective>
Create a PR-time GitHub Action that auto-analyzes individual PR commits (before squash), maps changed files to packages, determines bump level per package, detects dependency cascades, and auto-applies release labels to PRs.

Purpose: This is the core intelligence of the versioning system. Conventional commits within PRs are the source of truth for version bumps (D-01). Squash merging destroys individual commit granularity, so this action captures it before merge.
Output: pr-release-preview.yml workflow + pr-release-preview.js analysis script.
</objective>

Create `.github/scripts/pr-release-preview.js` — a Node.js script (no external dependencies, uses only `@actions/core`, `@actions/github` which are pre-installed on runners) that implements the full PR release analysis pipeline.

The script receives context from environment variables set by the workflow:

- `GITHUB_TOKEN` — for API calls
- `PR_NUMBER` — the pull request number
- `GITHUB_REPOSITORY` — owner/repo

**Section 1: File-to-Package Mapping (D-37)**

Read `release-please-config.json` from the repo root (checked out in the workflow). Extract the `packages` keys as path prefixes. Exclude the root `"."` package from enforcement per D-37.

For each changed file, find the longest matching path prefix from RP config. A file `packages/core/src/foo.ts` matches prefix `packages/core`. Files not matching any prefix are unversioned.

**Section 2: Commit Parsing**

Fetch all PR commits via `GET /repos/{owner}/{repo}/pulls/{pr_number}/commits` (handle pagination — up to 250 commits). For each commit:

1. Parse the first line of the commit message against the conventional commit regex:
   `/^(?<type>feat|fix|perf|refactor|build|test|docs|style|chore|ci|revert)(?:\((?<scope>[^)]*)\))?(?<breaking>!)?:\s*(?<description>.+)/`

2. Check for `BREAKING CHANGE:` in the commit body (also indicates major bump).

3. Fetch files changed by each commit via `GET /repos/{owner}/{repo}/commits/{sha}` and map to packages.

4. For each package touched by a commit, record the bump type:
   - `breaking` (! or BREAKING CHANGE) -> `major`
   - `feat` -> `minor`
   - `fix`, `perf`, `refactor` -> `patch`
   - `build`, `test`, `docs`, `style`, `chore`, `ci`, `revert` -> no bump (exempt per D-39)

5. Take the highest bump per package across all commits.

**Section 3: Auto-Exemptions (D-39)**

If ALL commits for a package have only exempt types (docs, test, chore, ci, style, build, revert), that package gets no label. The `release:none` label is NOT auto-applied — it is a manual escape hatch per D-39.

**Section 4: API Lock Group (D-05)**

After computing per-package bumps, check if any of `apps/api`, `packages/api-client`, `crates/api-client` has a bump. If so, take the highest bump across all three and apply it to all three. Use label prefix `api` for this group.

**Section 5: Monotonic Versioning (D-08, D-13)**

For `apps/web` and `apps/desktop`: if the computed bump is `patch`, upgrade it to `minor`. These apps use major.minor format only. The label type still reflects the commit type (e.g., `release:web:fix`), but the version computation in the post-merge action (Plan 03) handles the patch->minor upgrade.

**Section 6: Cascade Detection (D-21, D-22, D-23, D-24)**

Hardcode the dependency graph (reading it dynamically via pnpm/cargo at CI time adds complexity and fragility):

```javascript
const JS_DEPS = {
  'packages/core': ['packages/crypto'],
  'packages/sdk-core': ['packages/api-client', 'packages/core', 'packages/crypto'],
  'packages/sdk': ['packages/api-client', 'packages/core', 'packages/crypto', 'packages/sdk-core'],
  'apps/web': [
    'packages/api-client',
    'packages/core',
    'packages/crypto',
    'packages/sdk',
    'packages/sdk-core',
  ],
  'apps/desktop': ['packages/crypto'],
  'apps/tee-worker': ['packages/core', 'packages/crypto', 'packages/sdk-core'],
};

const RUST_DEPS = {
  'crates/core': ['crates/crypto'],
  'crates/fuse': ['crates/api-client', 'crates/core', 'crates/crypto'],
  'crates/sdk': ['crates/api-client', 'crates/core', 'crates/crypto'],
};
```

For each bumped package, find all packages that depend on it (reverse lookup). Apply cascade rules per D-22:

- Dependency gets `major` -> dependent gets at minimum `minor`
- Dependency gets `minor` or `patch` -> dependent gets at minimum `patch`

Cascade bumps are additive — if a package already has a higher direct bump, the cascade doesn't downgrade it.

**Section 7: Label Application (D-16, D-18)**

Map each package path to its label component name:

```javascript
const PATH_TO_LABEL = {
  'apps/api': 'api', // Lock group
  'packages/api-client': 'api', // Lock group
  'crates/api-client': 'api', // Lock group
  'apps/web': 'web',
  'apps/desktop': 'desktop',
  'apps/tee-worker': 'tee-worker',
  'packages/core': 'core',
  'packages/crypto': 'crypto',
  'packages/sdk-core': 'sdk-core',
  'packages/sdk': 'sdk',
  'crates/crypto': 'cipherbox-crypto',
  'crates/core': 'cipherbox-core',
  'crates/fuse': 'cipherbox-fuse',
  'crates/sdk': 'cipherbox-sdk',
};
```

For the highest bump type per label component, determine the label type:

- `major` from breaking -> label type `breaking`
- `minor` from feat -> label type `feat`
- `patch` from fix -> label type `fix`
- `patch` from perf -> label type `perf`
- `patch` from refactor -> label type `refactor`

Track the original commit type to use the correct label suffix. If multiple commit types contribute (e.g., both fix and perf), use the one with the higher bump, then alphabetically.

**Label format:** `release:{component}:{type}` (e.g., `release:core:feat`)

Fetch current labels on the PR. Remove any `release:*` labels that are no longer computed (in case commits were force-pushed). Add new computed labels. Do NOT remove manually-added labels that differ from computed ones unless they conflict (same component, different type) — this respects D-18 manual override.

Actually, to properly support D-18: if a label for a component was manually added (i.e., different from computed), keep the manual one. The heuristic: after computing labels, check existing PR labels. For each component, if there is already a `release:{component}:*` label AND the computed label differs, add a PR comment noting the override but do NOT remove the manual label.

**Section 8: PR Comment (D-23)**

Post or update a PR comment (use a hidden marker `<!-- release-preview -->` to find/update) with:

```markdown
## Release Preview

| Package             | Bump  | Label                  | Source               |
| ------------------- | ----- | ---------------------- | -------------------- |
| @cipherbox/core     | minor | `release:core:feat`    | Direct (feat commit) |
| @cipherbox/sdk-core | patch | `release:sdk-core:fix` | Cascade (core minor) |

### Cascade Details

- `@cipherbox/core` minor -> `@cipherbox/sdk-core` patch (direct dependency)

{If any non-conventional commits touch versioned packages:}

### Warnings

- Commit `abc1234` touches `packages/core/` but has non-conventional message: "WIP stuff"
```

**Section 9: CI Check Status (D-19)**

If any commit touches a versioned package path AND has a non-conventional commit message (doesn't match the regex), set the action as failed (`core.setFailed()`). This makes it a required CI check that blocks merge.

Exception: if `release:none` label is present on the PR, skip enforcement entirely — the PR author has explicitly opted out.

**Error handling:**

- API pagination: handle `Link` headers for >30 commits per page
- Rate limiting: catch 403/429 and retry with exponential backoff (1s, 2s, 4s)
- Missing labels: if a computed label doesn't exist in the repo, warn but don't fail (the label creation script from Plan 01 should have created them)

Create `.github/workflows/pr-release-preview.yml` that triggers on PR events and runs the analysis script.

```yaml
name: PR Release Preview

on:
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened, labeled, unlabeled]

permissions:
  contents: read
  pull-requests: write

jobs:
  release-preview:
    name: Release Preview
    runs-on: ubuntu-latest
    # Skip release-please's own PRs — they don't need release labels
    if: "!startsWith(github.head_ref, 'release-please--')"
    steps:
      - uses: actions/checkout@v6

      - uses: actions/setup-node@v6
        with:
          node-version: '22'

      - name: Analyze PR commits and apply release labels
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          PR_NUMBER: ${{ github.event.pull_request.number }}
        run: node .github/scripts/pr-release-preview.js
```

Per D-38, this runs on every PR event (open, synchronize, reopened, labeled, unlabeled). Execution is near-instant (~5-10s) as it only makes API calls and applies labels.

The `labeled` and `unlabeled` triggers ensure the preview re-evaluates when labels are manually changed (D-18).

Skip release-please's own PRs (branch prefix `release-please--`) since those are auto-generated and don't need release labeling.

Use `GITHUB_TOKEN` (not GitHub App token) for reading commits and applying labels — PR write permission is sufficient. The post-merge action (Plan 03) needs the app token for writing to main, but this PR-time action doesn't.
</action>
