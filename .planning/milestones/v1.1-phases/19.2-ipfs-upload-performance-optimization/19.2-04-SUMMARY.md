## Accomplishments

- Executed concurrency probe (Run 0) at 1/5/10/20/50/75/100 clients, establishing 50-client ceiling (zero errors up to 50; 10 errors at 75; widespread timeouts at 100)
- Collected three-point baselines at 50 clients isolating each optimization: Run 1 (sequential SDK + flatfs), Run 2 (concurrent SDK + flatfs), Run 3 (concurrent SDK + pebbleds)
- Discovered that SDK concurrent pins alone DEGRADE performance at scale (+138% p95, -26% throughput) due to doubled write load on flatfs
- Documented complete three-point comparison in post-optimization baselines with optimization attribution, concurrency probe table, and definitive SC analysis
- Updated preliminary SC analysis section with note pointing to definitive three-point analysis

## Key Finding

The two optimizations (concurrent pins + pebbleds) exhibit mandatory synergy. Concurrent pins generate more simultaneous write I/O. Only pebbleds' LSM-tree batched writes can absorb that load without contention-induced tail blow-up. Deploying concurrent pins without pebbleds would be a performance regression. Together they deliver: p50 -5.5%, p95 -13.0%, p99 -14.9%, throughput +7.0%.

## Decisions Made

- **50-client measurement point:** Highest stable client count with zero errors from concurrency probe. Also satisfies SC3's requirement to measure throughput at scale.
