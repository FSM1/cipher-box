<objective>
Tune client-side timeout and retry constants across SDK providers and API services based on Phase 18/22 baseline p99 data, using the 2-3x p99 formula to deliver sub-2s perceived latency on common operations (upload-to-visible, vault/folder load, download-to-open).

Purpose: Current timeout values are generous defaults (30-60s) set before baseline data existed. With baselines showing actual p99 values are well under 1s for most operations, reducing timeouts provides faster failure detection and retry, improving perceived UX. Faster retry base delays (500ms vs 1000ms) reduce the wall-clock penalty of transient failures.

Output: Updated timeout constants in five files across the SDK providers, API delegated routing client, and web upload service.

Update timeout and retry constants in four files. Each change is a single constant value update -- no structural code changes needed.

**1. packages/sdk-core/src/pinning/kubo-provider.ts:**
Change line 4:
```typescript
// Before:
/** Timeout for all Kubo RPC requests (30 seconds) */
const REQUEST_TIMEOUT_MS = 30_000;

// After:
/** Timeout for all Kubo RPC requests (10 seconds — ~44x client-side pin p99 of 227ms, generous for large files) */
const REQUEST_TIMEOUT_MS = 10_000;
```
Rationale: Pin p99 = 227ms client-side (Phase 18). 10s is ~44x headroom, generous enough for large file uploads while detecting failures much faster than 30s. Under load (50 clients), pin times reach ~6.4s, but that's a stress scenario -- normal operations complete well under 10s.

**2. packages/sdk-core/src/pinning/pinata-provider.ts:**
Change line 7:
```typescript
// Before:
/** Timeout for all Pinata API requests (60 seconds -- uploads can be large) */
const REQUEST_TIMEOUT_MS = 60_000;

// After:
/** Timeout for all Pinata API requests (30 seconds — external network, 15x BYO p50 of 2.0s upload) */
const REQUEST_TIMEOUT_MS = 30_000;
```
Rationale: Pinata BYO baseline shows p50=2.0s for pin (+47% vs local Kubo). 30s gives 15x headroom for tail latency and large files. External network has higher variance than local Kubo, so stays more generous.

**3. packages/sdk-core/src/pinning/psa-provider.ts:**
Change line 4:
```typescript
// Before:
/** Timeout for all PSA requests (30 seconds) */
const REQUEST_TIMEOUT_MS = 30_000;

// After:
/** Timeout for all PSA requests (15 seconds — external service, conservative reduction) */
const REQUEST_TIMEOUT_MS = 15_000;
```
Rationale: PSA profile similar to Kubo but through an external service. 15s is a conservative 50% reduction. No project-specific PSA baselines exist, but the pinning service should respond within 15s or be considered failing.

**4. apps/api/src/ipns/delegated-routing.client.ts:**
Change two readonly properties in the class declaration:
```typescript
// Before:
private readonly baseDelayMs = 1000;
private readonly requestTimeoutMs = 10_000;

// After:
private readonly baseDelayMs = 500;
private readonly requestTimeoutMs = 5_000;
```
Rationale for requestTimeoutMs: Resolve p99 = 488ms server-side (Phase 18). 5s is ~10x headroom, still very generous for DHT lookup. The old 10s was set before baselines existed.
Rationale for baseDelayMs: Faster retry start (500ms vs 1000ms) for transient failures. First retry at 500ms, second at 1000ms, third at 2000ms -- all well within reasonable range. The faster base means transient network blips resolve sooner.

- `apps/api/src/tee/tee.service.ts`: TEE timeout stays at 30_000 (batch republishing is inherently long-running)
