<objective>
Create BYO-IPFS performance benchmarking scenarios and capture baselines comparing BYO user capacity against the existing CipherBox-only baselines from Phase 19.2.

Purpose: BYO users offload IPFS pin operations to their own node, reducing CipherBox API load to IPNS publishes + CID registration (~105ms vs ~4.2s per upload). This plan quantifies the capacity gain by benchmarking: (1) pure BYO throughput, (2) PSA transient relay overhead, (3) mixed CipherBox+BYO capacity ceiling, and captures baselines for ongoing regression tracking.

Output: Three new load test scenarios, a BYO file workload module, client-pool extension for BYO-mode clients, and a baselines document with comparison to 19.2 numbers.
</objective>

Per-file operation sequence matching the BYO+Kubo external-only flow:

1. **Generate random encrypted data** — `crypto.getRandomValues(new Uint8Array(randomSize))` where `randomSize` is random between `minSize` and `maxSize`. (In the real app, data is encrypted before upload. For benchmarking we skip actual AES-GCM and use random bytes — the IPFS node doesn't care about content, and the metric we need is pin latency + API call overhead, not crypto throughput.)

2. **Pin to external provider** — `const pinResult = await client.provider.pin(data)`. Record operation `'byo-pin'` with duration and bytes.

3. **Register CID with CipherBox API** — `await client.sdkClient.axios.post('/ipfs/register-cid', { cid: pinResult.cid, sizeBytes: pinResult.size })`. Record operation `'register-cid'` with duration.

4. **Publish IPNS records** — Use the client's `sdkClient` to call the existing IPNS publish flow for the file and parent folder. Record operation `'ipns-publish'` with duration. (If this is too tightly coupled to the real upload flow, simplify: call `POST /ipns/publish-batch` directly with a mock record to measure raw IPNS API latency.)

5. **Optional: verify download** — If `verifyDownloads`, call `client.provider.get(pinResult.cid)` and verify the returned bytes match. Record operation `'byo-download'` with duration.

6. **Cleanup: unpin** — `await client.provider.unpin(pinResult.cid)` at end. Record operation `'byo-unpin'`.

Record all timings to `client.metrics` with operation names prefixed with `byo-` to distinguish from CipherBox-only metrics in mixed scenarios.

For PSA mode: step 2 changes to the transient relay flow:

1. Upload to CipherBox via `addToIpfs(ctx, data)` → get CID. Record `'psa-relay-upload'`.
2. Call `(client.provider as PsaProvider).pinByCid(cid)`. Record `'psa-pin-by-cid'`.
3. Unpin from CipherBox via `unpinFromIpfs(ctx, cid)`. Record `'psa-relay-unpin'`.
4. Register CID with API. Record `'register-cid'`.

This captures the relay overhead separately from the PSA pinning latency.

```typescript
describe('Mixed CipherBox + BYO Workload', () => {
  let cbPool: PoolClient[] = [];
  let byoPool: ByoPoolClient[] = [];

  afterAll(async () => {
    await destroyClientPool([...cbPool, ...byoPool]);
  });

  it(`${CB_CLIENTS} CB-only + ${BYO_CLIENTS} BYO clients × ${FILES_PER_CLIENT} files`, async () => {
    // Create both pools in parallel
    const [cbResult, byoResult] = await Promise.allSettled([
      createClientPool({ clientCount: CB_CLIENTS, label: 'mixed-cb' }),
      createByoClientPool({
        clientCount: BYO_CLIENTS,
        label: 'mixed-byo',
        externalProvider: { ... },
        pinningMode: 'external',
      }),
    ]);

    if (cbResult.status === 'rejected') throw cbResult.reason;
    cbPool = cbResult.value;

    if (byoResult.status === 'rejected' || byoResult.value.length === 0) {
      console.warn('BYO pool empty — running CB-only for comparison');
      byoPool = [];
    } else {
      byoPool = byoResult.value;
    }

    // Run both workloads concurrently
    const allResults = await Promise.allSettled([
      // CipherBox-only clients run standard file workload
      ...cbPool.map((pc) => {
        pc.metrics.start();
        return runFileWorkload(pc, {
          fileCount: FILES_PER_CLIENT,
          minSize: 1_024,
          maxSize: 500 * 1_024,
          verifyDownloads: false,
        }).finally(() => pc.metrics.stop());
      }),
      // BYO clients run BYO file workload
      ...byoPool.map((pc) => {
        pc.metrics.start();
        return runByoFileWorkload(pc, {
          fileCount: FILES_PER_CLIENT,
          minSize: 1_024,
          maxSize: 500 * 1_024,
          verifyDownloads: false,
        }).finally(() => pc.metrics.stop());
      }),
    ]);

    // Report separately for CB-only and BYO to compare impact
    console.log('\n=== CipherBox-Only Clients ===');
    await aggregateAndReport('Mixed (CB-only segment)', cbPool);

    if (byoPool.length > 0) {
      console.log('\n=== BYO Clients ===');
      await aggregateAndReport('Mixed (BYO segment)', byoPool);
    }

    // Key comparison: CB-only p95 in mixed vs the 19.2 baseline CB-only p95
    // If CB-only p95 degrades significantly, BYO users are competing for
    // shared resources (DB connections, HTTP connections, IPNS publish queue)
  });
});
```

The separate reporting per client type is critical. The questions answered:

1. **CB-only segment p95 vs 19.2 baseline p95:** Do BYO users' lightweight API calls (register-cid, IPNS publish) degrade CipherBox-only user experience?
2. **BYO segment register-cid + ipns-publish latency:** Does contention from CB-only heavy uploads slow down BYO API calls?
3. **Error rates per segment:** Which user type hits errors first under mixed load?

Environment variables for quick ratio sweeps:

- `LOAD_TEST_CB_CLIENTS=50 LOAD_TEST_BYO_CLIENTS=200` (default)

- `LOAD_TEST_CB_CLIENTS=200 LOAD_TEST_BYO_CLIENTS=0` (CB-only baseline for comparison)
