<objective>
Make the pending-unpin drain refcount-aware (D-02 / WR-03, HIGH). `drainPendingUnpins` currently
calls `ipfsProvider.unpinFile(row.cid)` unconditionally for every outbox CID. If a CID was re-pinned
or re-recorded (re-upload of identical ciphertext, or a pin-migration flow) while it was still sitting
in `pending_unpins`, the drain removes a LIVE pin → Kubo GC → data loss. The drain window is
≥ 5 minutes (BullMQ retry interval) and unbounded while Kubo is down, so the inline "negligible race"
argument from the upload path does NOT cover the drain.

Purpose: Close a live-pin data-loss path (HARD-01). The injected `pinnedCidRepository` already holds
the authoritative refcount; re-checking it before unpin is the complete fix.
Output: A RED-first regression test proving a re-pinned CID is NOT unpinned during drain (but its
stale outbox row is still cleaned up), then the GREEN guard.
</objective>

<threat_model>

## Trust Boundaries

| Boundary                                | Description                                                                              |
| --------------------------------------- | ---------------------------------------------------------------------------------------- |
| BullMQ drain job → Kubo (unpin)         | Background worker decides which CIDs to physically unpin; a stale decision causes data loss |
| re-upload / pin-migration → pinned_cids | A concurrent flow may re-pin a CID still queued in `pending_unpins`                       |

## STRIDE Threat Register

| Threat ID | Category          | Component                       | Disposition | Mitigation Plan                                                                                                       |
| --------- | ----------------- | ------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------- |
| T-50-03   | Denial of Service | `drainPendingUnpins` loop       | mitigate    | A non-owner share/BYO recipient re-uploading identical ciphertext could otherwise induce the drain to remove a live pin (data loss). Re-check `pinned_cids` count before unpin and skip when > 0 (D-02 / WR-03). |
| T-50-04   | Tampering         | stale outbox row after re-pin   | mitigate    | Stale `pending_unpins` rows for re-pinned CIDs are deleted so they cannot be re-attempted on a later drain.            |

</threat_model>
