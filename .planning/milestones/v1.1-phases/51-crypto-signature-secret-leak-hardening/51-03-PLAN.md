<objective>
Close finding S2 on the Rust client (D-04) and the Rust half of S3 (D-05) — combined into one plan because both touch `crates/fuse/src/lib.rs` (avoids wave-parallel write conflict).

S2/D-04: add the three optional signature fields to `IpnsResolveResponse` (`crates/api-client/src/types.rs`) and a `verify_ipns_resolve_signature` function in `crates/api-client/src/ipns.rs` (Ed25519 verify over the `ipns-signature:` prefix + pubKey→name binding), then have the FUSE resolve callers honor the result (warn on absent per D-03, error on invalid per D-02, proceed on valid).

S3/D-05 (Rust): close the raw-`Vec<u8>` key escapes — `ecies::unwrap_key` returns `Zeroizing<Vec<u8>>`, the `resolve_folder_key` BFS queue holds `Zeroizing<Vec<u8>>`, `get_folder_key` returns `Option<Zeroizing<Vec<u8>>>`, and `spawn_file_meta_reencrypt`'s folder-key copy is wrapped — auditing all call sites for the return-type changes.

Purpose: bring the Rust desktop client to signature-verification parity with web + sdk-core, and stop folder/ECIES keys from persisting in the JS-free Rust heap (BFS queue, raw `.to_vec()` copies).
Output: extended `IpnsResolveResponse`, new verify fn + Rust unit tests, `Zeroizing` key handling across ecies + fuse, FUSE callers honoring the flag.
</objective>
