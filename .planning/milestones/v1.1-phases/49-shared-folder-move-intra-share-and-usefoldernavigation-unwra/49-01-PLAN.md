<objective>
Add the SDK crypto core for intra-share file move: a stateless `moveInSharedFolder` op
in `shared-write.ts` and two `CipherBoxClient` methods (`moveInSharedFolder`,
`enumerateSharedSubtree`) in `client.ts`. The move op mirrors the owner `moveItem`
ordering (publish DEST first → re-key `FileMetadata` under the dest `folderKey` → publish
SOURCE) and re-keys via the already-shipped key-agnostic
`reencryptFileMetadataForFolderChange`. Enumeration is a lazy DFS from the share root that
unwraps each subfolder's `folderKey` from `share_keys` and flags write-capability from the
presence of a `folder-ipns` key.

This is the crypto-sensitive surface of Phase 49 (REQ-2 = re-encryption + recipient key
handling). It uses TDD because both behaviors are pure logic with a defined I/O contract.

Purpose: Make recipient-side moves preserve decryptability (the #507 / #8 bug class) and
give the web a single SDK capability to populate an anywhere-in-subtree destination picker.
Output: `moveInSharedFolder` (op + client method), `enumerateSharedSubtree` (client method),
and two green SDK unit suites.
</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
| -------- | ----------- |
| recipient web → SDK client | recipient-supplied `destFolderId`, `itemId`, `vaultPrivateKey` cross into crypto code |
| SDK → CipherBox API (`share_keys`, IPNS publish) | server is zero-knowledge; only ciphertext + IPNS records cross |
| in-memory key buffers → GC | unwrapped `folderKey`/`ipnsPrivateKey`/file-ipns key live transiently and must be zeroed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --------- | -------- | --------- | ----------- | --------------- |
| T-49-01 | Elevation of Privilege | `client.moveInSharedFolder` dest resolution | mitigate | Require a `share_keys keyType:'folder-ipns'` entry for `destFolderId` BEFORE any publish; throw "No write key for destination folder" if absent (write-capability check on the dest end; source write-cap is already proven by the loaded `sharedFolderTree` entry) |
| T-49-02 | Tampering | `shareOps.moveInSharedFolder` partial failure | mitigate | Publish DEST before SOURCE (add-before-remove); `reencryptFileMetadataForFolderChange` is idempotent (probes dest key on a source DECRYPTION_FAILED) so a retried partial move re-keys correctly rather than orphaning FileMetadata under the wrong folderKey |
| T-49-03 | Cryptographic Failure | file IPNS key source | mitigate | ALWAYS resolve the moved file's IPNS private key from `share_keys keyType:'file-ipns'` (recipient-wrapped); NEVER from `FilePointer.ipnsPrivateKeyEncrypted` (owner-wrapped — recipient cannot decrypt it) |
| T-49-04 | Information Disclosure | transient unwrapped keys | mitigate | Client method `finally`-zeroes `fileIpnsPrivateKey`, `destIpnsPrivateKey`, `destFolderKey`; the stateless op never zeroes (caller owns) so no double-free / use-after-zero |
| T-49-05 | Denial of Service | stale dest sequence | accept | CAS (`publishWithCas` via `updateFolderMetadataAndPublish`) handles a stale-sequence 409 with a 3-way merge + 4-attempt backoff; dest sequence comes from a FRESH `loadFolderMetadata` (A1), minimizing collisions |
| T-49-SC | Tampering | npm/pip/cargo installs | accept | No packages added this phase (RESEARCH.md Package Legitimacy Audit: none) |

</threat_model>
