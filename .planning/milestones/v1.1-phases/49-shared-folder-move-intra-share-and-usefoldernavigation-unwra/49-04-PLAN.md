<threat_model>

## Trust Boundaries

| Boundary | Description |
| -------- | ----------- |
| drag payload → drop handler | `dataTransfer` `application/json {items,parentId}` is attacker-influenceable in principle; parsed in the drop handler |
| batch loop → SDK | each looped `moveInSharedFolder` crosses the crypto boundary independently |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --------- | -------- | --------- | ----------- | --------------- |
| T-49-11 | Tampering | batch-loop partial failure | mitigate | `batchMoveItemsHandler` validates per item and STOPS on the first per-item failure with a clear `p.setError`, rather than swallowing — each `moveInSharedFolder` is independently atomic (publishes DEST+SOURCE) so already-moved items stay consistent; the SDK re-check (T-49-01) still guards each item |
| T-49-12 | Elevation of Privilege | drop onto non-writable folder | mitigate | The drop handler rejects drops onto folders the recipient lacks a write key for (skip move); the SDK client method re-checks `folder-ipns` regardless of UI |
| T-49-13 | Input Validation | drag JSON payload parse | mitigate | Parse `application/json` defensively (try/catch); route only the recognized `{items,parentId}` shape, fall through to the existing external-file upload path otherwise; never trust `parentId` for the write — the destination is the drop-target row's id/ipnsName, not the payload |
| T-49-SC | Tampering | npm installs | accept | No packages added this phase |

</threat_model>
