Purpose: Desktop users get the same conflict protection as web users -- when another device modifies the same folder, the desktop client re-fetches remote state, merges in the local mutation, and retries instead of silently overwriting other devices' changes.

Output: Modified Rust API client and FUSE publish logic with conflict handling and OS notifications.

       ```rust
       pub async fn publish_ipns(
           client: &ApiClient,
           request: &IpnsPublishRequest,
       ) -> Result<PublishResult, String> {
           let resp = client
               .authenticated_post("/ipns/publish", request)
               .await
               .map_err(|e| format!("IPNS publish failed: {}", e))?;

           if resp.status().as_u16() == 409 {
               // Parse conflict response body
               let body: serde_json::Value = resp.json().await.unwrap_or_default();
               let current_seq = body["currentSequenceNumber"]
                   .as_str()
                   .unwrap_or("0")
                   .to_string();
               return Ok(PublishResult::Conflict {
                   current_sequence_number: current_seq,
               });
           }

           if !resp.status().is_success() {
               let status = resp.status();
               let body = resp.text().await.unwrap_or_default();
               return Err(format!("IPNS publish failed ({}): {}", status, body));
           }

           Ok(PublishResult::Success)
       }
       ```

    1. **Modify `spawn_metadata_publish` to send `expected_sequence_number` and handle conflicts with remote re-fetch:**

       In the existing `spawn_metadata_publish` function, after the sequence is resolved and the IPNS record is created:

       a. Set `expected_sequence_number: Some(seq.to_string())` on the `IpnsPublishRequest`. The `seq` is the value from `coordinator.resolve_sequence` (the current known sequence BEFORE increment).

       b. Match on `publish_ipns` result:
       ```rust
       use crate::api::ipns::PublishResult;

       match crate::api::ipns::publish_ipns(&api, &req).await? {
           PublishResult::Success => {
               coordinator.record_publish(&ipns_name, new_seq);
               // ... existing unpin and log logic
           }
           PublishResult::Conflict { current_sequence_number } => {
               log::warn!(
                   "Conflict detected for {}: expected seq {}, server has {}. Re-syncing...",
                   ipns_name, seq, current_sequence_number
               );

               // 1. Re-fetch remote metadata to get the OTHER device's changes
               //    CRITICAL: Do NOT re-encrypt the same local metadata. If Device A added
               //    file X and Device B added file Y, using Device B's stale metadata would
               //    overwrite Device A's file X. Instead, we must:
               //    a. Resolve IPNS to get the remote CID (which includes Device A's changes)
               //    b. Fetch and decrypt the remote metadata
               //    c. Re-apply our local mutation onto the fresh children array
               let fresh_seq = coordinator.resolve_sequence(&api, &ipns_name).await?;

               // Resolve the IPNS name to get the current (remote) CID
               let remote_cid = crate::api::ipns::resolve_ipns(&api, &ipns_name).await?;

               // Fetch and decrypt the remote metadata using the folder key
               let remote_bytes = crate::api::ipfs::fetch_content(&api, &remote_cid).await?;
               let remote_metadata = crate::fuse::decrypt_metadata_from_ipfs(
                   &remote_bytes, &folder_key,
               )?;

               // Re-apply the local mutation onto the remote children.
               // `metadata` is the locally-mutated FolderMetadata that was passed to
               // spawn_metadata_publish. We need to compute the diff between the
               // pre-mutation children and the local metadata's children, then apply
               // that same diff to the remote children.
               //
               // The simplest correct approach: `spawn_metadata_publish` already receives
               // the FINAL metadata (after local mutation). The local mutation is one of:
               //   - Added child (create file/folder): child present in metadata but not in remote
               //   - Removed child (delete): child absent in metadata but present in remote
               //   - Renamed child: child with new name in metadata, old name in remote
               //
               // Strategy: Start with remote_metadata.children, then apply the diff:
               //   - For each child in metadata.children that is NOT in remote (by ipnsName): add it
               //   - For each child in remote that is NOT in metadata (by ipnsName): remove it
               //   - For each child in both: use the local version (handles rename)
               //
               // Build a map of local children by ipnsName for O(n) lookup:
               let local_by_ipns: std::collections::HashMap<&str, _> = metadata.children
                   .as_ref()
                   .map(|c| c.iter().map(|child| (child.ipns_name.as_str(), child)).collect())
                   .unwrap_or_default();
               let remote_by_ipns: std::collections::HashMap<&str, _> = remote_metadata.children
                   .as_ref()
                   .map(|c| c.iter().map(|child| (child.ipns_name.as_str(), child)).collect())
                   .unwrap_or_default();

               let mut merged_children = Vec::new();

               // Keep all remote children, but use local version if locally modified
               for (ipns, remote_child) in &remote_by_ipns {
                   if let Some(local_child) = local_by_ipns.get(ipns) {
                       merged_children.push((*local_child).clone()); // local version (handles rename)
                   } else if local_by_ipns.is_empty() || metadata.children.as_ref().map(|c| c.iter().any(|_| true)).unwrap_or(false) {
                       // Child exists remotely but not locally -- this is a local DELETE
                       // Only omit it if local metadata had children (wasn't empty/None)
                       // If local had no children array, keep remote (safety)
                       if metadata.children.is_some() {
                           // Local intentionally removed this child -- skip it
                       } else {
                           merged_children.push((*remote_child).clone());
                       }
                   } else {
                       merged_children.push((*remote_child).clone());
                   }
               }
               // Add any locally-added children that don't exist in remote
               for (ipns, local_child) in &local_by_ipns {
                   if !remote_by_ipns.contains_key(ipns) {
                       merged_children.push((*local_child).clone());
                   }
               }

               let mut merged_metadata = remote_metadata;
               merged_metadata.children = Some(merged_children);

               // 2. Small random jitter to break symmetry with other devices
               let jitter = std::time::Duration::from_millis(100 + (rand::random::<u64>() % 400));
               tokio::time::sleep(jitter).await;

               // 3. Re-encrypt the MERGED metadata (not the stale local metadata)
               let retry_json = encrypt_metadata_to_json(&merged_metadata, &folder_key)?;
               let retry_cid = crate::api::ipfs::upload_content(&api, &retry_json).await?;

               // 4. Create new IPNS record with fresh sequence
               let retry_seq = fresh_seq + 1;
               let retry_value = format!("/ipfs/{}", retry_cid);
               let retry_record = crate::crypto::ipns::create_ipns_record(
                   &ipns_key_arr, &retry_value, retry_seq, 86_400_000,
               ).map_err(|e| format!("IPNS retry record creation failed: {}", e))?;
               let retry_marshaled = crate::crypto::ipns::marshal_ipns_record(&retry_record)
                   .map_err(|e| format!("IPNS retry record marshal failed: {}", e))?;
               let retry_b64 = base64::engine::general_purpose::STANDARD.encode(&retry_marshaled);

               let retry_req = crate::api::ipns::IpnsPublishRequest {
                   ipns_name: ipns_name.clone(),
                   record: retry_b64,
                   metadata_cid: retry_cid.clone(),
                   encrypted_ipns_private_key: None,
                   key_epoch: None,
                   expected_sequence_number: Some(fresh_seq.to_string()),
               };

               match crate::api::ipns::publish_ipns(&api, &retry_req).await? {
                   PublishResult::Success => {
                       coordinator.record_publish(&ipns_name, retry_seq);
                       log::info!("Conflict resolved for {} after retry (seq {})", ipns_name, retry_seq);
                   }
                   PublishResult::Conflict { .. } => {
                       log::error!(
                           "Persistent conflict for {} after retry. User should re-sync manually.",
                           ipns_name
                       );
                       // Do NOT retry again -- surface the error
                       return Err(format!("Persistent conflict for {}. Another device is actively modifying this folder.", ipns_name));
                   }
               }
           }
       }
       ```

       **IMPORTANT -- Why re-fetch remote metadata instead of re-encrypting the same local metadata:**
       If Device A added file X and Device B added file Y concurrently:
       - Device A publishes successfully (children now contains X)
       - Device B tries to publish its metadata (containing only Y, not X) and gets 409
       - If Device B retries with its SAME metadata, it would overwrite Device A's file X
       - Instead, Device B must: fetch the remote metadata (which now contains X), then add Y to it, producing [X, Y]
       - This is the correct conflict resolution behavior that preserves all devices' changes

       **Note on merge complexity:** The merge logic above handles the common cases (add, delete, rename). For edge cases where both devices modify the SAME child entry, the local version wins (last-writer-wins per child). This is acceptable for v1 and matches the web client behavior.
