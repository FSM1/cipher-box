    **1. Create `tests/e2e/utils/conflict-helpers.ts`:**

    This helper simulates a concurrent publish from another device by directly calling the API's publish endpoint to bump the server-side sequence number for a specific folder.

    ```typescript
    /**
     * Conflict detection test helpers.
     *
     * Simulates concurrent device publishes by calling the API publish endpoint
     * directly to increment a folder's server-side sequence number, making the
     * web client's local sequence stale.
     */
    ```

    **`bumpServerSequence` function:**
    - Accepts: `apiBaseUrl: string`, `accessToken: string`, `rootIpnsName: string`
    - Steps:
      1. Resolve the root folder's current IPNS record via `GET /ipns/resolve?ipnsName={rootIpnsName}` (using the Playwright APIRequestContext or raw fetch) to get the current `sequenceNumber` and `cid`
      2. Call `POST /ipns/publish` with `{ ipnsName: rootIpnsName, record: <any valid base64 string>, metadataCid: <the current cid from resolve>, expectedSequenceNumber: <current sequence number as string> }` -- this publishes with the correct expected sequence, so it succeeds, incrementing the server-side sequence number by 1
      3. The web client's local sequence is now stale (it still has the old value)
      4. Return the new server sequence number for assertions

    **IMPORTANT considerations for the publish call:**
    - The `record` field must be a valid base64 string. Since we're just bumping the sequence (not actually creating a valid IPNS record for resolution), we can pass the same record data or a dummy base64 string. The API accepts any base64 string in the record field.
    - Use the **same** `metadataCid` that was already resolved. This makes the bump a no-op in terms of content (same CID), but the sequence number still increments.
    - The function needs an authenticated `APIRequestContext` or raw `fetch` with bearer token. Follow the pattern from `web3auth-helpers.ts` where `page.request` is used for API calls.
    - **Expected warning:** The dummy base64 record string will cause the API's delegated routing publish to log a warning (invalid IPNS record format). This is expected and harmless in tests -- the API still bumps the DB sequence number. Add a JSDoc comment on `bumpServerSequence` noting: `// NOTE: Uses a dummy base64 record which generates a delegated routing warning in API logs. This is expected -- we only need the DB sequence bump, not a valid IPNS record for DHT propagation.`

    **Alternative simpler approach:** If directly calling publish is complex (need valid IPNS record), consider this approach instead:
    - Call `POST /ipns/publish` **without** `expectedSequenceNumber` (backward-compatible unconditional publish) with the existing CID. This will increment the sequence unconditionally. Then the web client's next folder mutation will send its (now stale) expectedSequenceNumber and get a 409.
    - This is simpler because it doesn't require matching the expected sequence on the bump call itself.

    Provide both approaches in the helper, with the simpler one as default. The function signature:
    ```typescript
    export async function bumpServerSequence(params: {
      page: Page;  // For page.request API calls
      apiBaseUrl: string;
      accessToken: string;
      rootIpnsName: string;
    }): Promise<{ newSequenceNumber: string }>;
    ```

    - Extract auth state for API calls (accessToken from `TestAuthState` or from Zustand store via `page.evaluate`)

    **Test 1: "Upload file to folder with stale sequence -> conflict -> re-sync -> retry succeeds"**
    1. Extract current auth state: `accessToken` and `rootIpnsName` from Zustand stores via `page.evaluate`
    2. Call `bumpServerSequence({ page, apiBaseUrl, accessToken, rootIpnsName })` to make the client's local sequence stale
    3. Upload a test file via `UploadZonePage.uploadFile()`
    4. **Expected behavior:** The upload triggers a folder publish with the stale sequence, gets 409, the client re-syncs (SyncIndicator may briefly show conflict state), retries, and the file appears in the file list
    5. Assert: `FileListPage.waitForItemToAppear(fileName, { timeout: 30000 })` -- file appears despite the conflict
    6. Assert: No error toast is persistent (the conflict was auto-resolved). Check that there is no visible error state after the operation completes.
    7. Cleanup: Delete the uploaded file via context menu if desired (or leave for next test)

    **Test 2: "Create folder when parent has stale sequence -> conflict -> re-sync -> retry succeeds"**
    1. Bump server sequence again via `bumpServerSequence`
    2. Create a folder via context menu right-click empty area (or keyboard shortcut) -> CreateFolderDialog -> enter name -> create
    3. **Expected behavior:** Same as Test 1 -- folder creation publishes parent folder IPNS, gets 409, re-syncs, retries, folder appears
    4. Assert: `FileListPage.waitForItemToAppear(folderName, { timeout: 30000 })`
    5. Cleanup: Delete the created folder

    **Test 3 (negative): "Per-file IPNS publish does NOT trigger conflict"**
    1. This test verifies that file content updates (which publish only the file's IPNS record, not the folder's) do NOT get conflict errors even when the folder sequence is stale.
    2. Upload a test file (this resets the sequence as a side effect of the successful retry from the folder publish)
    3. Bump the folder's server sequence via `bumpServerSequence`
    4. Edit/update the file content: navigate to file, open text editor dialog, modify content, save. Or: upload a file with the same name (triggers file update, not folder publish).
    5. **Expected behavior:** The file update succeeds without any conflict because it publishes only the file's per-file IPNS record, not the folder's.
    6. Assert: The file content is updated successfully (no error state visible)

    **Note on Test 3 feasibility:** Test 3 requires a way to update file content that triggers only a per-file IPNS publish. The `TextEditorDialog` save flow should do this (it updates the file content via `handleUpdateFile` which publishes only the file's IPNS record per Phase 12.6 design). If this is too complex to test reliably, this test can verify that the file update does not show a persistent error rather than asserting no 409 was sent.
