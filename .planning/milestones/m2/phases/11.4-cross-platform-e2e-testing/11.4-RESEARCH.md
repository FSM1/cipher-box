# Phase 11.4: Cross-Platform E2E Testing - Research

**Researched:** 2026-02-28
**Domain:** CI/CD infrastructure, cross-platform desktop testing, FUSE filesystem testing, cryptographic interop validation
**Confidence:** HIGH (mostly based on existing project code and CI patterns)

## Summary

This phase creates a new CI workflow (`e2e-desktop.yml`) that validates the desktop client (Tauri binary) on all three platforms (macOS, Windows, Linux) against a locally-running backend stack. The core challenge is installing Postgres, IPFS (Kubo), Redis, FUSE drivers, and Xvfb natively on each platform's CI runner since Docker service containers are only available on Linux runners.

The existing project already has all the building blocks: a `--dev-key` auth bypass for headless authentication, a `POST /auth/test-login` endpoint, cross-language crypto test vectors in `apps/desktop/src-tauri/src/crypto/tests.rs`, and per-platform build jobs in `ci.yml`. The main work is (1) adding artifact upload to existing build jobs, (2) creating a new E2E workflow that downloads those artifacts and runs FUSE-level integration tests, and (3) writing shell/Rust test scripts that exercise file operations through the mounted filesystem.

**Primary recommendation:** Build the E2E workflow as a separate `e2e-desktop.yml` triggered by `workflow_run` (after CI completes). Use `ikalnytskyi/action-setup-postgres@v8` for cross-platform Postgres, install Kubo v0.34.0 from prebuilt binary, and run the Tauri binary with `--dev-key` for headless auth. Tests are shell scripts (bash/PowerShell) that perform file I/O on the FUSE mount point and verify results. Crypto interop tests are `cargo test` with shared fixture files.

## Architecture Patterns

### Workflow Architecture

```
ci.yml (existing, modified)
  build-desktop-{windows,macos,linux}
    + upload-artifact step (NEW)

e2e-desktop.yml (NEW)
  trigger: workflow_run (after ci.yml), workflow_dispatch

  jobs:
    e2e-desktop:
      strategy:
        matrix:
          include:
            - os: macos-latest
              artifact: desktop-macos
              fuse-feature: fuse
            - os: windows-latest
              artifact: desktop-windows
              fuse-feature: winfsp
            - os: ubuntu-22.04
              artifact: desktop-linux
              fuse-feature: fuse
      steps:
        1. Download desktop binary artifact
        2. Install Postgres (action-setup-postgres)
        3. Install Kubo (prebuilt binary)
        4. Install Redis
        5. Install FUSE driver (platform-specific)
        6. Setup Node.js + pnpm
        7. Install monorepo deps + build API
        8. Create .env files
        9. Start API + IPFS daemon + mock-ipns-routing
        10. Run migrations
        11. Run desktop E2E tests (with Xvfb on Linux)
        12. Upload test artifacts on failure
```

### Test Execution Model

The desktop binary is launched with `--dev-key` which triggers headless auth:

1. Binary starts, creates webview (hidden), detects `--dev-key`
2. Webview JS calls `POST /auth/test-login` -> gets tokens + keypair
3. Calls `handle_test_login_complete` Tauri command
4. `complete_auth_setup` stores keys, inits/fetches vault, registers device, mounts FUSE
5. FUSE mount appears at `~/CipherBox` (macOS/Linux) or `C:\CipherBox` (Windows)
6. Test scripts perform file I/O on mount point
7. Test scripts call API to verify data was encrypted/uploaded correctly
8. Binary is killed, mount is cleaned up

### Pattern: Headless Desktop Launch in CI

```bash
# macOS/Linux
export CIPHERBOX_API_URL=http://localhost:3000
export VITE_API_URL=http://localhost:3000
export VITE_TEST_LOGIN_SECRET=e2e-test-secret-ci-only
export RUST_LOG=info

# Generate a dev key
DEV_KEY=$(openssl rand -hex 32)

# Launch binary in background (debug build for --dev-key support)
./target/debug/cipherbox-desktop --dev-key $DEV_KEY &
DESKTOP_PID=$!

# Wait for FUSE mount to appear
for i in $(seq 1 60); do
  if mount | grep -q "CipherBox"; then
    echo "Mount detected"
    break
  fi
  sleep 1
done

# Run tests...

# Cleanup
kill $DESKTOP_PID 2>/dev/null
# Force unmount on macOS
diskutil unmount force ~/CipherBox 2>/dev/null || true
# Force unmount on Linux
fusermount3 -u ~/CipherBox 2>/dev/null || true
```

```powershell
# Windows
$env:CIPHERBOX_API_URL = "http://localhost:3000"
$env:VITE_API_URL = "http://localhost:3000"
$env:VITE_TEST_LOGIN_SECRET = "e2e-test-secret-ci-only"
$env:RUST_LOG = "info"

# Generate a dev key
$DEV_KEY = -join ((1..32) | ForEach-Object { '{0:x2}' -f (Get-Random -Max 256) })

# Launch binary in background
$proc = Start-Process -FilePath ".\target\debug\cipherbox-desktop.exe" `
  -ArgumentList "--dev-key",$DEV_KEY -PassThru -NoNewWindow

# Wait for mount (WinFsp mounts as drive letter or folder)
$timeout = 60
for ($i = 0; $i -lt $timeout; $i++) {
  if (Test-Path "C:\CipherBox") {
    Write-Host "Mount detected"
    break
  }
  Start-Sleep -Seconds 1
}

# Run tests...

# Cleanup
Stop-Process -Id $proc.Id -Force -ErrorAction SilentlyContinue
```

### Pattern: FUSE File I/O Test

```bash
#!/bin/bash
set -euo pipefail
MOUNT_POINT=~/CipherBox

echo "=== Test: Create and read file ==="
echo "Hello from CI" > "$MOUNT_POINT/test-file.txt"
sleep 2  # Wait for debounced IPNS publish
CONTENT=$(cat "$MOUNT_POINT/test-file.txt")
[ "$CONTENT" = "Hello from CI" ] || { echo "FAIL: content mismatch"; exit 1; }
echo "PASS: file create/read"

echo "=== Test: Create directory ==="
mkdir -p "$MOUNT_POINT/test-folder"
[ -d "$MOUNT_POINT/test-folder" ] || { echo "FAIL: directory not created"; exit 1; }
echo "PASS: mkdir"

echo "=== Test: Write file in subdirectory ==="
echo "Nested content" > "$MOUNT_POINT/test-folder/nested.txt"
sleep 2
NESTED=$(cat "$MOUNT_POINT/test-folder/nested.txt")
[ "$NESTED" = "Nested content" ] || { echo "FAIL: nested content mismatch"; exit 1; }
echo "PASS: nested file"

echo "=== Test: Delete file ==="
rm "$MOUNT_POINT/test-file.txt"
sleep 2
[ ! -f "$MOUNT_POINT/test-file.txt" ] || { echo "FAIL: file not deleted"; exit 1; }
echo "PASS: delete"

echo "=== Test: Binary file round-trip ==="
dd if=/dev/urandom of=/tmp/test-binary.bin bs=1024 count=512 2>/dev/null
cp /tmp/test-binary.bin "$MOUNT_POINT/test-binary.bin"
sleep 3  # Larger file needs more time for upload
CHECKSUM_ORIG=$(shasum -a 256 /tmp/test-binary.bin | cut -d' ' -f1)
CHECKSUM_MOUNT=$(shasum -a 256 "$MOUNT_POINT/test-binary.bin" | cut -d' ' -f1)
[ "$CHECKSUM_ORIG" = "$CHECKSUM_MOUNT" ] || { echo "FAIL: binary checksum mismatch"; exit 1; }
echo "PASS: binary round-trip"

echo "All FUSE tests passed!"
```

### Pattern: API Round-Trip Verification

After desktop writes a file via FUSE, verify the API can see the encrypted data:

```bash
#!/bin/bash
set -euo pipefail
API_URL=http://localhost:3000
TEST_SECRET=e2e-test-secret-ci-only
TEST_EMAIL="e2e-desktop-$(date +%s)@test.local"

# 1. Authenticate via test-login
AUTH_RESPONSE=$(curl -s -X POST "$API_URL/auth/test-login" \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"$TEST_EMAIL\",\"secret\":\"$TEST_SECRET\"}")
ACCESS_TOKEN=$(echo "$AUTH_RESPONSE" | jq -r '.accessToken')

# 2. After desktop writes "test-file.txt" via FUSE, check vault API
# The API should show the file in the root folder metadata
VAULT_RESPONSE=$(curl -s -H "Authorization: Bearer $ACCESS_TOKEN" \
  "$API_URL/vault")
ROOT_IPNS=$(echo "$VAULT_RESPONSE" | jq -r '.rootIpnsName')

# 3. Verify IPNS resolve returns valid encrypted metadata
IPNS_RESPONSE=$(curl -s -H "Authorization: Bearer $ACCESS_TOKEN" \
  "$API_URL/ipns/$ROOT_IPNS/resolve")
# Should return a CID pointing to encrypted folder metadata
echo "IPNS resolved: $IPNS_RESPONSE"
```

### Anti-Patterns to Avoid

- **Don't rebuild Rust from source in E2E jobs:** Cargo builds take 10-20 minutes per platform. Download the binary artifact from the build job instead.
- **Don't use Docker service containers on macOS/Windows runners:** Only `ubuntu-*` runners support `services:` blocks. Everything must be natively installed.
- **Don't use release builds for E2E:** The `--dev-key` flag is `#[cfg(debug_assertions)]` only. Must use debug builds.
- **Don't assume the mount is instant:** FUSE mount requires auth -> vault fetch -> metadata decrypt -> FUSE init. Budget 30-60 seconds for mount readiness.
- **Don't skip Redis:** The API's `BullModule` (BullMQ) requires Redis. The app will fail to start without it.
- **Don't hardcode mount paths:** macOS/Linux use `~/CipherBox`, Windows may use `C:\CipherBox` or a drive letter. Parameterize.

## Don't Hand-Roll

| Problem                     | Don't Build                 | Use Instead                                                        | Why                                                                      |
| --------------------------- | --------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Cross-platform Postgres     | Shell scripts per OS        | `ikalnytskyi/action-setup-postgres@v8`                             | Handles brew/choco/apt + service startup + createdb + connection URI     |
| Cross-platform IPFS         | Complex conditional install | Kubo prebuilt binary from dist.ipfs.tech                           | Official distribution, no build required, same approach on all platforms |
| Headless GUI on Linux       | Manual Xvfb setup           | `GabrielBB/xvfb-action@v1`                                         | Handles install, startup, cleanup; no-op on non-Linux (safe in matrix)   |
| Cross-platform test runner  | Custom test framework       | Shell scripts (bash + PowerShell)                                  | FUSE tests are file I/O -- shell is the natural tool                     |
| Crypto interop test vectors | Generate at runtime         | Checked-in JSON fixtures from existing `generate-test-vectors.mjs` | Deterministic, version-controlled, already proven                        |

## Common Pitfalls

### Pitfall 1: Docker Services Only Work on Linux Runners

**What goes wrong:** Using `services:` block in a job that runs on `macos-latest` or `windows-latest` fails silently or errors.
**Why it happens:** GitHub Actions only supports Docker service containers on Linux runners.
**How to avoid:** Install all dependencies (Postgres, IPFS, Redis) natively on macOS and Windows using brew/choco/actions.
**Warning signs:** `services:` in a job with `matrix.os` that includes non-Linux.

### Pitfall 2: Existing Build Jobs Don't Upload Artifacts

**What goes wrong:** The E2E job can't download the desktop binary because it was never uploaded.
**Why it happens:** Current `build-desktop-*` jobs in `ci.yml` use `tauri-action` but don't have `upload-artifact` steps.
**How to avoid:** Add `actions/upload-artifact@v4` to each `build-desktop-*` job. The binary is at `apps/desktop/src-tauri/target/debug/cipherbox-desktop` (debug build for `--dev-key` support). Note: `tauri-action` builds a release binary by default, so we either need a separate debug build step or adjust the approach.
**Warning signs:** "Artifact not found" errors in the E2E workflow.

### Pitfall 3: Debug vs Release Build for --dev-key

**What goes wrong:** The `--dev-key` flag and `handle_test_login_complete` command are gated behind `#[cfg(debug_assertions)]`. Release builds strip them.
**Why it happens:** Security measure to prevent dev auth bypass in production.
**How to avoid:** The E2E workflow must build or use debug binaries, not the release binaries from `tauri-action`. Options: (a) add a separate `cargo build --debug` step in the build job and upload that artifact, (b) add a Cargo feature flag like `e2e-testing` that enables test-login support in release builds, or (c) build debug in the E2E job itself (slow but simple).
**Warning signs:** "Unknown argument --dev-key" when launching the binary.

### Pitfall 4: Redis Requirement

**What goes wrong:** NestJS API fails to start because BullMQ can't connect to Redis.
**Why it happens:** `app.module.ts` imports `BullModule.forRootAsync()` which requires Redis.
**How to avoid:** Install Redis on each platform: `brew install redis && brew services start redis` (macOS), `choco install redis-64` (Windows), `sudo apt install redis-server && sudo systemctl start redis` (Linux).
**Warning signs:** API startup errors mentioning `ECONNREFUSED :6379`.

### Pitfall 5: FUSE-T Requires Reboot on macOS (WRONG -- it doesn't)

**What goes wrong:** Confusion between FUSE-T and macFUSE/osxfuse.
**Why it happens:** Old macFUSE required kernel extension + reboot. FUSE-T uses userspace NFS/SMB server, no kext, no reboot.
**How to avoid:** Use `brew install --cask fuse-t` (already done in existing CI). This is a non-issue.
**Warning signs:** N/A -- just documenting to prevent future confusion.

### Pitfall 6: Kubo Daemon Startup Race

**What goes wrong:** Tests start before IPFS daemon is fully ready.
**Why it happens:** `ipfs daemon &` backgrounds the process but the API is not immediately available.
**How to avoid:** Poll `curl -s http://localhost:5001/api/v0/id` until it returns HTTP 200 before proceeding.
**Warning signs:** API IPFS operations fail with connection refused.

### Pitfall 7: macOS Finder Interference with FUSE Mount

**What goes wrong:** macOS creates `.DS_Store` files in the mount point, which pollute tests.
**Why it happens:** Finder automatically indexes directories.
**How to avoid:** The desktop app already filters `.DS_Store` in FUSE operations. But test scripts should ignore/filter these files in directory listings. Also, CI runners run headless so Finder interference is minimal.
**Warning signs:** Unexpected `.DS_Store` files in test assertions.

### Pitfall 8: Windows Path Differences

**What goes wrong:** Tests use Unix path separators or `~` which don't work on Windows.
**Why it happens:** Different path conventions across platforms.
**How to avoid:** Use separate shell scripts for Windows (PowerShell `.ps1`) and Unix (bash `.sh`). Don't try to make one script work everywhere.
**Warning signs:** "File not found" errors on Windows.

### Pitfall 9: Cross-Workflow Artifact Download Requires Token Permissions

**What goes wrong:** `actions/download-artifact` can't find artifacts from the CI workflow.
**Why it happens:** v4 requires explicit `run-id` for cross-workflow downloads, or `workflow_run` trigger provides the run context.
**How to avoid:** Use `workflow_run` trigger which provides `github.event.workflow_run.id` for artifact lookups. Or use `dawidd6/action-download-artifact` which searches by workflow name.
**Warning signs:** "Unable to find any artifacts" errors.

### Cross-Platform Kubo Install

```yaml
# Linux/macOS
- name: Install Kubo (IPFS)
  if: runner.os != 'Windows'
  run: |
    KUBO_VERSION="v0.34.0"
    if [ "$(uname)" = "Darwin" ]; then
      ARCH="darwin-$(uname -m | sed 's/arm64/arm64/' | sed 's/x86_64/amd64/')"
    else
      ARCH="linux-amd64"
    fi
    wget -q "https://dist.ipfs.tech/kubo/${KUBO_VERSION}/kubo_${KUBO_VERSION}_${ARCH}.tar.gz"
    tar -xzf "kubo_${KUBO_VERSION}_${ARCH}.tar.gz"
    sudo ./kubo/install.sh
    ipfs init
    ipfs daemon &
    # Wait for daemon
    for i in $(seq 1 30); do
      if curl -s http://localhost:5001/api/v0/id > /dev/null 2>&1; then
        echo "IPFS daemon ready"
        break
      fi
      sleep 1
    done

# Windows
- name: Install Kubo (IPFS)
  if: runner.os == 'Windows'
  shell: powershell
  run: |
    $version = "v0.34.0"
    Invoke-WebRequest -Uri "https://dist.ipfs.tech/kubo/$version/kubo_${version}_windows-amd64.zip" -OutFile kubo.zip
    Expand-Archive -Path kubo.zip -DestinationPath .
    $env:PATH = "$PWD\kubo;$env:PATH"
    [Environment]::SetEnvironmentVariable("PATH", "$PWD\kubo;$env:PATH", "Process")
    ipfs init
    Start-Process -FilePath "ipfs" -ArgumentList "daemon" -NoNewWindow
    # Wait for daemon
    for ($i = 0; $i -lt 30; $i++) {
      try {
        $null = Invoke-WebRequest -Uri "http://localhost:5001/api/v0/id" -ErrorAction Stop
        Write-Host "IPFS daemon ready"
        break
      } catch { Start-Sleep -Seconds 1 }
    }
```

## State of the Art

| Old Approach                                        | Current Approach                        | When Changed         | Impact                                       |
| --------------------------------------------------- | --------------------------------------- | -------------------- | -------------------------------------------- |
| Docker services for all CI                          | Native installs on macOS/Windows        | Always been required | No Docker on non-Linux runners               |
| `actions/download-artifact` v3 (same workflow only) | v4 supports cross-workflow via `run-id` | 2024                 | Can download from build workflow             |

**Deprecated/outdated:**

- macFUSE/osxfuse: Requires kernel extension + reboot. Replaced by FUSE-T for CI.
- `dawidd6/action-download-artifact`: Was needed when official action didn't support cross-workflow. Official v4 now handles this with `run-id`.

## Key Decisions for Planning

### Debug Build Strategy

The biggest architectural decision: how to get a debug binary for E2E testing.

**Option A: Build debug binary in existing build jobs (RECOMMENDED)**

- Add `cargo build` (debug) step to each `build-desktop-*` job in `ci.yml`
- Upload as artifact alongside the release build
- Pros: Leverages existing Cargo cache, runs in parallel with release build
- Cons: Adds ~5-8 min to build jobs (but cached target dir helps)

**Option B: Build debug binary in E2E workflow**

- Full Rust build in the E2E job itself
- Pros: Self-contained workflow
- Cons: No Cargo cache (cold build), adds 15-20 min per platform, duplicates existing build infra

**Option C: Add `e2e-testing` Cargo feature**

- Enable `--dev-key` and `handle_test_login_complete` in release builds when feature is active
- Pros: Can use the release binary from `tauri-action`
- Cons: Requires code changes to `main.rs`, less clean separation

**Recommendation:** Option A. The existing build jobs already have Cargo caches. Adding a debug build step is minimal overhead.

### Workflow Trigger Strategy

**`workflow_run` trigger (RECOMMENDED):**

```yaml
on:
  workflow_run:
    workflows: ['CI']
    types: [completed]
    branches: [main]
  workflow_dispatch:
```

- Runs after CI completes on main (or manual dispatch)
- Can access CI workflow's artifacts via `github.event.workflow_run.id`
- Does NOT run on PRs by default (saves CI minutes)

**For PR testing, add path-filtered trigger:**

```yaml
on:
  pull_request:
    branches: [main]
    paths:
      - 'apps/desktop/**'
      - 'packages/crypto/**'
      - 'tests/e2e-desktop/**'
      - '.github/workflows/e2e-desktop.yml'
```

## Open Questions

1. **Windows mount point location:**
   - macOS/Linux mount at `~/CipherBox`
   - Windows: Is it `C:\CipherBox` or a drive letter? Need to check `fuse/windows/mod.rs` mount function
   - Recommendation: Read the code to determine mount path, parameterize in test scripts

2. **macOS runner architecture:**
   - `macos-latest` now runs on Apple Silicon (arm64)
   - The existing `build-desktop-macos` job works on `macos-latest`, so this should be fine
   - But Kubo binary download needs `darwin-arm64` not `darwin-amd64`
   - Recommendation: Auto-detect architecture in install script

3. **Tauri webview on CI:**
   - The binary creates a hidden webview for auth even in `--dev-key` mode
   - On Linux, this requires Xvfb for WebKitGTK
   - On macOS, the runner may have a display; if not, need to set `LSUIElement` or similar
   - On Windows, WebView2 should work headless
   - Recommendation: Use `GabrielBB/xvfb-action` on Linux; test macOS/Windows without Xvfb first

4. **IPNS publish timing in tests:**
   - FUSE write triggers debounced IPNS publish (1.5s debounce, 10s safety valve)
   - Test scripts need adequate `sleep` between write and verification
   - Recommendation: Use generous waits (5-10s) in CI tests; speed is not critical

5. **Concurrent test isolation:**
   - Each platform run uses a unique test email (timestamp-based)
   - But all share the same Postgres DB on the same runner
   - Recommendation: This is fine since each runner has its own stack; no cross-runner sharing

6. **Windows Redis availability:**
   - `choco install redis-64` may not provide the latest version or may be unreliable
   - Alternative: Use `memurai` (Redis-compatible Windows server) or skip BullMQ in test mode
   - Recommendation: Try chocolatey first; if unreliable, use `tporadowski/redis` releases directly
