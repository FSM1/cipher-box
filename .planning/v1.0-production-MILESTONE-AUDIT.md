### NEW Integration Gaps

#### GAP-1 (CRITICAL): Bin permanent delete cannot unpin file CIDs

**File:** `apps/web/src/services/bin.service.ts` lines 648-668

**Problem:** `unpinFileCids()` fetches file metadata from IPFS and parses it as plain JSON, expecting `{ cid, size }`. However, file metadata is AES-256-GCM encrypted via `encryptFileMetadata()` -- the IPFS blob is `{ iv: "hex...", data: "base64..." }`, not a plain FileMetadata object.

**Impact:** When permanently deleting from bin, CIDs are **never unpinned**. `removeUsage()` never executes because `fileMeta.cid` is always undefined. Affects `permanentlyDelete`, `emptyBin`, and `purgeExpired` -- all three permanent-delete paths.

**Root cause:** The bin stores `FilePointer` (which has `fileMetaIpnsName`) but NOT the `folderKey` needed to decrypt the file metadata. At permanent-delete time, the parent folder may already be deleted.

**Fix options:**

- (a) Store `folderKey` (ECIES-wrapped) in `BinEntry` at soft-delete time
- (b) Store plaintext CID + size in `BinEntry` at soft-delete time (simpler, lower risk)
- (c) Walk folder tree to recover `folderKey` if parent exists

#### GAP-2 (MODERATE): Windows desktop delete skips recycle bin

**File:** `apps/desktop/src-tauri/src/fuse/windows/write_ops.rs` line 480+

**Problem:** macOS/Linux FUSE `handle_unlink`/`handle_rmdir` call `spawn_bin_entry_publish()` to create bin entries on delete. The Windows WinFsp `handle_cleanup` with `FspCleanupDelete` flag does NOT call `spawn_bin_entry_publish()`.

**Impact:** Files deleted via Windows desktop go straight to permanent deletion without bin protection. macOS/Linux users get recycle bin; Windows users do not.

**Evidence:** `grep -r "bin_entry\|spawn_bin_entry_publish" apps/desktop/src-tauri/src/fuse/windows/` returns no matches.
