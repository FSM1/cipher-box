## Problem

Non-blocking hardening findings from the Phase 68.2 ship-review (CodeRabbit).
None observed in the passing e2e/unit suites; deferred rather than changing
cache/freshness semantics late in a verified-green phase. Grouped here:

## Items

1. **Owned `listingCache` invalidation on file-only mutations** (`client.ts`
   ~`resolveListingChildren`/`3613`). The shared path already invalidates
   `listingCache` on a file-only publish (`client.ts:5028`); the OWNED path
   (`replaceFile` / `restoreFileVersion` / `deleteFileVersion`) does not, so a
   cached `ResolvedChild[]` could serve stale size/modifiedAt/version. **Masked
   today** because the web forces resolve after these mutations (68.2-14/16
   `forceResolve` + `invalidateOpenFolder`), bypassing the cache — but the SDK
   cache staying stale is latent for any non-forcing consumer. Mirror the
   shared-path `listingCache.delete(ipnsName)`.

2. **`toResolvedChildView` unresolved default** (`FileList.tsx:23-36`). Falls
   back to `kind: 'folder'` when a raw child has no paired `ResolvedChild`
   (matches the historical folder-safe default; e2e nav passes because the
   store sets `children`/`rawChildren` atomically). Harden by threading an
   explicit "unresolved" state and disabling double-click nav / drag until the
   item resolves, instead of defaulting to a navigable folder.

3. **`invalidateOpenFolder` monotonicity** (`useSyncPolling.ts:39-47`). The
   poll-leg writeback re-checks folder identity but not sequence monotonicity —
   a slow await racing a newer nav re-resolve could apply older (still
   above-floor) children over newer. Add a stored-vs-resolved `sequenceNumber`
   guard before `updateFolderChildren`.

4. **`refreshSharedFolder` stale write envelope** (`client.ts:5229`). Refresh
   adopts children+sequence but leaves the write-body `publishedNode` stale, so
   a later shared write may republish an outdated write-body. Pass the freshly
   resolved `PublishedNode` into `adoptSharedFolderResult` as `publishedParent`.
   **IMPLEMENTED in Phase 73 (73-05).** Residual follow-up (Phase 73
   crypto/security review, LOW, defense-in-depth): the resolve that seeds
   `publishedParent` is a raw `resolvePublishedNode` (`client.ts:5674`), not the
   ROT-07-gated variant the sibling read facades now use (SC3) — a
   validly-signed but rolled-back parent envelope could seed a stale write base
   (ROT-07's deleted-child-resurrection threat). Mitigated today by the
   in-memory `state.sequenceNumber >= result.sequenceNumber` monotonicity guard
   just above (`client.ts:5647`) plus server-side CAS on publish; a bare
   `signatureVerified` assert would NOT catch it (the rollback is validly
   signed), and the share root has no parent mirror to source
   `generation`/`versionFloor` from, so proper floor-gating is a non-trivial
   SDK-side change. Defer to a future SDK write-plane hardening pass.

5. **`ResolvedChild.sequence` safe-integer narrowing** (`folder-listing.ts:115`).
   `Number(sequenceNumber)` isn't range-checked at this site (the upstream
   gated resolve guards `MAX_SAFE_INTEGER` only when `rotationHighWater` is
   configured). Validate/handle out-of-range explicitly before conversion.

6. **Shared empty-state grid a11y** (`SharedFileBrowser.tsx:810-822`). The
   empty-state div sits directly under a `rowgroup`, breaking grid semantics;
   wrap it in a `role="row"` (with a cell) or move it out of the grid.

7. **SDK test hardening** — stronger/added assertions CodeRabbit requested:
   fail-closed (`signatureVerified: false`) cases for the gated facades
   (`resolve-child-identity.test.ts`, `descend-shared-child.test.ts` — see the
   companion gating todo), assert trusted-vs-envelope generation in
   `folder-reresolve.test.ts`, and tighten the `selectEncryptionMode` assertion
   in `folder-metadata-facade.test.ts`.

8. **Double forced re-resolve on cold navigation** (`useFolderNavigation.ts`
   ~`refreshFolderListing`:68-73). The D-03 belt-and-suspenders leg runs
   `listFolder({ forceResolve })` and `ensureFolderLoaded({ forceResolve })`
   concurrently; `listFolder` also drives `ensureFolderLoaded` internally, so a
   cold nav can pay for two back-to-back IPNS resolves. **Deferred, not fixed:**
   both legs are `forceResolve` on the freshness-critical path we just hardened
   for Regression B (68.2-16) and return different shapes (`ResolvedChild[]` vs
   raw `children` + `sequenceNumber`). The clean fix is an SDK API change —
   expose the raw state + sequence from `listFolder` (or dedup the two forced
   resolves in-SDK via `reresolveInFlight`) so the web needs one call. Do NOT
   just drop `forceResolve` on the second leg — that reintroduces the stale
   `rawChildren`/`sequence` staleness Regression B fixed. Verify against
   writable-shares + shared-folder-desync e2e.

9. **Shared resolved-listing projection may fire before the SDK seed**
   (`useSharedNavigation.ts`:355-375). The display projection effect calls
   `listSharedFolder(currentShareId, [])`, which reads `sharedFolderTree`, but
   `setFolderChildren`/`setCurrentView` run before `seedActiveSharedFolder`, so
   an intermediate render could hit the "Shared folder not loaded" path and
   leave `resolvedChildren` empty. **Masked today** — the effect deps include
   `folderChildren`/`currentSequenceNumber`, which change on seed completion and
   re-fire the projection (writable-shares 29/29 + shared-folder-desync green).
   Harden by gating the effect on seed completion (or moving the seed earlier)
   so the projection only runs against a seeded tree; the reorder touches the
   delicate shared-nav seeding sequence, so validate with the shared e2e suites.

10. **Parallelize `resolveChildren`** (`folder-listing.ts`:87-127). Per-child
    resolution (`gatedResolve` + `unsealChildReadKey` + `unsealNode`) is
    sequential, so a listing over an N-child folder blocks on N serial
    IPNS+IPFS round-trips (a rename in a 100-file folder pays 100 sequential
    resolves before the mutation promise resolves). Bound with the existing
    `p-limit` (already a dep, used for `UPLOAD_CONCURRENCY`) at 3-5 concurrent,
    threaded in from `resolveListingChildren`. Preserve result ordering by input
    index, the skip-on-failure semantics, the `resolved.length < children.length`
    partial-cache guard (Greptile P1), and per-child `childReadKey` zeroing.
