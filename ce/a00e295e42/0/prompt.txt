**SC4 — WRITE-03 refreshWriteAccess supplier corrupts write state on retry**

The `refreshWriteAccess` supplier (`refreshCurrentDepthWriteKey` in `apps/web/src/hooks/useSharedNavigationActions.ts:783-844`) reseeds the SDK's `sharedFolderTree` state via `seedActiveSharedFolder` **without passing `publishedNode`** (line 824-834) — unlike the other three call sites in the same file (`navigateToShare` line 268, `navigateToSubfolder` line 410, `restoreToBreadcrumbIndex` line 540), all of which correctly pass a real `publishedNode` after plan 73-07's own fix for this exact bug class.

Every shared-write op reads this state with **no network re-resolve** (`buildSharedWriteContextFromState` → `unsealNode` first thing). Since `seedSharedFolder` falls back to `PLACEHOLDER_PUBLISHED_NODE` (empty `readSealed`) when `publishedNode` is omitted, `unsealNode` throws a GCM/decrypt error immediately — before the retried write can ever reach `publishNodeFn`'s tombstone/success classification.

Concretely: after "Refresh access" is clicked (D-01/WRITE-03), `useMutationFailureUx.ts`'s `retryAfterRefresh` calls the supplier, then retries the same write — which now throws an unclassified crypto error instead of either succeeding or reaching the intended "Write access revoked." terminal toast.

This was never caught because the one e2e case that exercises this retry live (`tests/web-e2e/tests/rotation-ux.spec.ts:444`, WRITE-03) was, per 73-08-SUMMARY.md's own admission, never actually run against a live stack (documented as a remaining step due to parallel-worktree port contention). Static tracing of the real call graph shows the retry path would not reach the classified outcome the test asserts.

**Suggested fix:** capture the active depth's live `publishedNode` before reseeding (e.g. `getSdkClient().getSharedFolderState(currentShareId)?.publishedNode`, mirroring `navigateToSubfolder`'s existing pattern) and pass it through in `refreshCurrentDepthWriteKey`'s `seedActiveSharedFolder` call. Then run the WRITE-03 e2e live to confirm.
