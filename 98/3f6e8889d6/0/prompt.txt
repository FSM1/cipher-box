## 2. Does the read-chain RUNTIME already exist in sdk-core? (verdicts)

The **low-level Node codec is complete** in `packages/core/src/node/`: `sealNode`/`unsealNode`, `sealChildReadKey`/`unsealChildReadKey`, `sealChildWriteKey`/`unsealChildWriteKey`, `sealContent`/`unsealContent` (`seal.ts:96-331`), plus encode/decode. Types in `types.ts` (`Node`, `SealedChildRef`, `NodeContent`, `NodeWriteBody`, `PublishedNode`).

### (a) auth/root-Node-init — **PARTIAL**
- EXISTS: `initializeVault` (`packages/core/src/vault/init.ts:43`) mints rootReadKey/rootWriteKey/rootIpnsKeypair; `publishVaultKeyBlob`/`loadVaultKeyBlob` (`packages/sdk-core/src/vault/index.ts:30,74`); login unwrap path fully works.
- MISSING: a primitive that **publishes an empty `kind:'root'` Node to the deterministic root IPNS keypair**. `createSubfolder` (`folder/registration.ts:49`) is ~90% the template but mints a *fresh* Ed25519 keypair and uses `kind:'folder'` with no write-body. A root variant (accept the vault's root keypair + `kind:'root'` + `writeBody{ipnsPrivateKey, writeChildren:[]}`) must be added (or inlined in `useAuth`). ~40 lines composing existing `sealNode`+`addToIpfs`+`createAndPublishIpnsRecord`+`deriveIpnsName`.

### (b) navigation / read fan-out — **EXISTS (primitives)** → wiring
- `loadFolderMetadata` (`folder/load.ts:54`) and `fetchAndDecryptMetadata` (:29) resolve IPNS→fetch→`unsealNode`. `client.loadFolder` (`client.ts:393`) **already works** and builds `FolderState`.
- The DFS/BFS walk pattern (`ensureFolderLoaded`) exists twice as reference: `rotateReadFromNode` (`engine.ts:990-1014`, resolveAndFetch + `unsealChildReadKey`) and `navigateReadChain`. **Caveat:** owned `ensureFolderLoaded` must also recover each folder's `ipnsPrivateKey`/writeKey from the **write-body** (`unsealChildWriteKey` walk) to populate `FolderState.ipnsKeypair` for later writes — primitives exist (`shared-write.ts` `unsealParentWriteBody`/`walkChildWriteKey`).
- `createFolder`: `createSharedSubfolder` (`shared-write.ts:288`) is the near-exact template (builds child node w/ write-body + parent `SealedChildRef` + `WriteChildRef`, publishes both).

### (c) file read — **PARTIAL** (primitives exist, thin composition + one adapter missing)
- Metadata resolution: no dedicated owned-file resolver, but it is a **single read-chain hop** composing existing `resolveIpnsRecord`+`fetchFromIpfs`+`unsealChildReadKey`+`unsealNode` → `node.content`. Exact pattern lives in `navigate.ts:145-171` and `client.ts:892-912`.
- Download: `downloadAndDecrypt` (`download/index.ts:29`) **uses the legacy ECIES model** (`fileKeyEncrypted` hex + `userPrivateKey` unwrap). v3 stores the **raw** `fileKey` inside `NodeContent`. Need a raw-key variant: `fetchFromIpfs(content.cid)` + `decryptAesGcm`/`decryptAesCtr(ct, content.fileKey, iv)`. Note `NodeContent.fileIv` is **base64** (see `shared-write.ts:448,703`), not hex — format detail to get right.
- `isFileRef` kind discrimination: **MISSING cheap primitive.** `SealedChildRef` has no `kind` (schema frozen, `types.ts:83-104`); kind lives only on the child's `PublishedNode.kind`, requiring a network hop per child. Genuine design decision (resolve+cache kind at folder-load time, or carry kind in `FolderState`).

### (d) shared-folder navigation/download — **EXISTS** → pure wiring
- `navigateReadChain` (`share/navigate.ts:106`) is the canonical multi-hop walk root→file leaf returning `NodeContent` (with `behind-retry`/`revoked` states).
- `client.enumerateSharedSubtree` (`client.ts:2394`) **already implemented** (uses `loadFolderMetadata`).
- sdk-core `moveInSharedFolder` (`shared-write.ts:772`) **fully implemented**; the `client.ts:2360` wrapper just needs to build src/dest `SharedWriteContext` and call it.
