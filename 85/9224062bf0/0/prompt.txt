## Test 1 — `full-workflow.spec.ts:1314 › 6.6.2 Restore a past version` (run 29061952925)

**Exact failure** (job 86265524185 log line 35035):
```
Error: expect(received).toBe(expected)   // line 1355
Expected: "Updated content after edit - version 2"
Received: "Edited in-browser via text editor modal - version 3"
```
The trace shows: restore-confirm clicked → details closed → editor opened → textarea read immediately. The editor showed the **pre-restore** current content (version 3).

**Root cause — missing synchronization (not stale cache).** The only "wait" between confirming the restore and reading the editor is (lines 1476-1478):
```ts
await expect(async () =&gt; {
  expect(await detailsDialog.getVersionCount()).toBe(1);
}).toPass({ timeout: 30000 });
```
Restore **swaps** current↔v1, so the past-version count is `1` **both before and after** restore. This gate passes instantly and provides **zero** wait for the restore's IPNS republish to land. I confirmed via a sub-agent that the text editor re-resolves the file **fresh from the live API on every open** (`downloadFromIpns` → `resolveIpnsRecord` → `resolveFileMetadata` → `downloadFileContent`, none cached — `packages/sdk/src/client.ts:4169`, `packages/sdk-core/src/ipns/index.ts:196`, `.../file/index.ts:373`). So there is no in-memory current-CID for restore to invalidate; the editor simply raced the just-committed/in-flight restore publish and read the old record. Given more time it reads version 2.

**Classification: (A) fixable test-timing race.**

**Fix** — full-workflow.spec.ts tail of 6.6.2 (~lines 1483-1495). The trivial `getVersionCount()===1` gate is a no-op; replace the single open→read→assert with a poll of the real end-state:
```ts
await expect
  .poll(async () =&gt; {
    await fileList.rightClickItem(editableFileName);
    await contextMenu.waitForOpen();
    await contextMenu.clickEdit();
    await textEditorDialog.waitForOpen({ timeout: 10000 });
    await textEditorDialog.waitForContentLoaded({ timeout: 30000 });
    const c = await textEditorDialog.getContent();
    await textEditorDialog.clickCancel();
    await textEditorDialog.waitForClose();
    return c;
  }, { timeout: 30000 })
  .toBe(editableFileUpdatedContent);
```
Note `textEditorDialog.waitForContentLoaded` (`text-editor-dialog.page.ts:100`) only waits for the textarea to be *visible*, not for correct content — so a single read is inherently racy.

**Latent product gap to flag separately (not what broke this test):** `useFileVersions.handleRestoreVersion` (`apps/web/src/hooks/useFileVersions.ts:58`) never refreshes the open folder listing after restore — only quota + the details dialog's own version list (`DetailsDialog.tsx:178` just bumps `metadataRefresh`). The file list won't show restored size/mtime until the 30s sync poll. Worth a ticket, but orthogonal to this flake.

## Test 2 — `writable-shares.spec.ts:533 › 8.1 Owner can navigate into subfolder created by recipient` (run 29061952925)

**Exact failure** (log line 35065):
```
TimeoutError: locator.waitFor: Timeout 30000ms exceeded.   // line 544
&gt; 544 | await bobSharedBrowser.getFolderItem(securitySubfolder).waitFor({ state: 'visible', timeout: 30000 })
```

## Suite-level: should CI add `retries: 1`?

**Primary recommendation: fix all three at source first — do not reach for retries.** All three are fully diagnosable; none is Web3Auth/irreducible jitter. Two are pure timeout calibration (add the missing CI floor / raise the budget or bulk the operation), one is a genuinely absent wait. Papering these with retries would hide exactly the kind of fixable timing bug the `retries:0` philosophy is meant to surface.

**Secondary (defensible backstop, optional):** the substrate *is* a shared 2-vCPU stack whose IPNS publish/resolve latency has a fat tail under 3-worker load — that tail will keep producing occasional cumulative/timeout blips on other multi-mutation paths. A **CI-only `retries: 1`** (not 2) is a reasonable safety net *because Playwright reports retried tests as "flaky" in the run summary* — visible, not hidden. A genuinely-broken test still fails both attempts and reds the build; a transient live-stack blip passes on retry and lands in the flaky list for triage. That preserves the fix-at-source signal while cutting spurious red builds. If you adopt it: `retries: process.env.CI ? 1 : 0`, keep local at 0, and make "any test in the flaky report is a must-fix" a standing rule. I'd gate this on fixing the current three first and only add it if residual flakiness remains.

**Recommended order:** (1) land the three source fixes above; (2) re-run the dispatched suite twice; (3) add `retries:1` CI-only *only if* still flaky, with the flaky-report-triage rule.</result>

## Findings

### [HIGH] `moveItem` never threads `baseWriteChildren` — its own source-folder WriteChildRef drop can be resurrected by a concurrent writer

**Location:** `packages/sdk/src/client.ts:2916-2932` (source-folder publish inside `moveItem`), merge logic at `packages/sdk-core/src/folder/registration.ts:332-367`

**Code:**
```typescript
// client.ts moveItem — SOURCE folder publish (drops the moved child's WriteChildRef)
const { newSequenceNumber: srcSeq, publishedChildren: srcChildren, publishedWriteChildren: srcPublishedWriteChildren } =
  await sdkCore.updateFolderMetadataAndPublish({
    children: updatedSource,
    baseChildren: baseSourceChildren,
    readKey: sourceFolder.folderKey,
    writeKey: sourceWriteBodyParams.writeKey,
    writeChildren: rehomedSourceWriteChildren,   // &lt;- has the moved child's ref REMOVED
    // no baseWriteChildren passed here
    ...
  });
```

**Issue:**
`moveItem` drops the moved child's `WriteChildRef` from the source folder's write-body (`rehomedSourceWriteChildren = sourceWriteBodyParams.writeChildren.filter(wc =&gt; wc.childId !== childPub.id)`, `client.ts:2859-2861`) — structurally the same operation `deleteItem` performs. But unlike `deleteItem` (which this same phase fixed), `moveItem` never passes `baseWriteChildren` to `updateFolderMetadataAndPublish`. Per `registration.ts:340-367`, when `params.baseWriteChildren` is `undefined` the merge falls back to the "legacy naive union" (`byChildId.set` for local then remote, remote entries always win/are always included) — the exact premise the phase's own research doc (`72-RESEARCH.md` "Critical Finding 2") states will resurrect a dropped `WriteChildRef` under a concurrent-write race.

If a CAS-409 occurs on the source-folder publish (a racing writer — another collaborator or another device of the same user in a shared folder — republishes the source folder from a snapshot that predates the move), the retry's naive union re-adds the racing writer's stale `WriteChildRef` for the moved child back into the source folder's write-body, even though `moveItem` explicitly intended to drop it.

This is not a newly-introduced bug in the sense of being unknown — the phase's own `72-03-SUMMARY.md:33,120` explicitly documents it: *"other write-chain callers (`moveItem`, `restoreFromBin`) do not yet pass it and continue to get the pre-existing naive-union behavior... SC#3 (restoreFromBin re-homing, deferred to Plan 05) is the next candidate to thread it through."* Plan 05 threaded it through for `restoreFromBin`/`permanentDeleteFromBin`, but no subsequent plan in this phase (checked 72-01 through 72-10 PLAN/SUMMARY docs) revisited `moveItem`. `72-VERIFICATION.md:31` marks SC#1 "VERIFIED" citing only `deleteItem`, with no mention of the residual `moveItem` exposure. There is no pending todo tracking it (`.planning/todos/pending` has nothing referencing `moveItem` + the naive-union gap). There is also no regression test for it (`move-in-shared-folder.test.ts` has no concurrent/409/resurrection test).

**Impact:**
In a shared folder with multiple writers (or a single user with multiple devices holding a real writeKey for the same folder), after Alice moves file/folder F out of source folder S into destination D, a concurrent stale republish of S can resurrect F's `WriteChildRef` in S. F then becomes write-capable via **two** independent write scopes simultaneously — the new destination D (intended) and the old source S (unintended). Anyone who retains write access to S (which may include a collaborator whose access to F was specifically supposed to end when it was moved out of the folder they can write to) can still mutate F using S's writeKey, even though F no longer appears in S's read-plane children — a live, silently-restored write capability outside the intended sharing/authorization boundary. This is exactly the class of write-chain-resurrection attack the phase's SC#1 fix targets, just via a different write-chain-mutating operation that was left out of the fix's rollout.

**Recommendation:**
Thread `baseWriteChildren: baseSourceWriteBodyParams.writeChildren` (captured before the drop, mirroring `deleteItem`'s pattern) into the `moveItem` source-folder `updateFolderMetadataAndPublish` call at `client.ts:2916-2932`. The destination-side publish is add-only and does not need it (a naive union there cannot resurrect anything, since nothing was dropped from the destination). Add a regression test analogous to `registration.test.ts`'s "Test C — resurrection guard" but driven through `moveItem` (or extend `move-in-shared-folder.test.ts`) to close this before it ships. If deliberately deferred, it should be an explicit, documented decision (as Plan 03's research doc demanded for SC#1 generally) rather than a silent gap.

**References:** `packages/sdk-core/src/__tests__/folder/registration.test.ts:274-420` (the base-aware merge tests that prove the *primitive* works — this finding is that `moveItem` never invokes it); `.planning/phases/72-sdk-write-plane-durability-and-correctness/72-RESEARCH.md` "Critical Finding 2" and `72-03-SUMMARY.md:33,120`.
