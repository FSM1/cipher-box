**Code:**


**Issue:**
This is the one production-shaped surface that still filters on the bookmark's superseded copy of the permission. The doc comment above it states that no production caller takes this half yet, and the sweep runs over the owner's own scopes alone. A grep of the engine confirms that claim: the only other bookmark reads are `accept.rs:971` (the idempotent ack short-circuit, which reports the accept's own outcome and not a live standing) and `received_status.rs:390` (`carried`, which is the correct carry-forward seed value).

## Detailed Analysis

### Trust boundary: can a forged, replayed, or lagged record raise the reported permission?

No. The raise path has exactly one entrance, at `received_status.rs:401-408`:

```rust
if class == ResolutionClass::Granted {
    if let Some((candidate, floors)) = &amp;resolved {
        if let Some(committed) = self.committed_permission(candidate, share, contact) {
            permission = committed;
        }
```

Four gates stand in front of that assignment.

1. **Record authenticity.** `resolved` (line 570) reads the sharer-scoped epoch and cut-epoch floors, resolves the name, runs `fanout_get_verify`, then applies `floor::check_sequence` at `Strictness::AtOrAboveFloor`. A replay below the durable sequence floor returns `None` and reports a refusal on `events`. A floor the pass cannot read also returns `None`, because with no floor neither bar can fire.

2. **Owner authenticity and cut freshness.** `facts_from` (line 784) binds `candidate.envelope.scope` to `share.scope_id`, then runs `verify_commitment_in_force` against the **contact-anchored** identity and the durable cut-epoch floor. The identity and the encryption subkey both come from the contact book, never from the resolved record. A record cannot vouch for itself.

3. **Commitment membership.** `blob_present` (line 815) requires both a commitment entry at the recipient-blinded tag **and** a signed blob at that tag. A blob at an uncommitted tag counts as removal.

4. **Epoch floor.** `classify` returns `EpochLag` when `record_epoch &lt; epoch_floor`, and `EpochLag` is not `Granted`, so it reaches no raise.

`committed_permission` (line 470) derives the tag from the identical inputs that `facts_from` uses: `self.enc_secret`, `contact.enc_subkey()`, and `share.scope_root_name`. Because `Granted` implies a commitment entry at that tag, the `None` arm of `committed_permission` is unreachable from the `Granted` branch. I verified that the two tag derivations cannot diverge, since both take the same three arguments in the same pass with the same `contact`.

I also checked the `find` against `any` asymmetry between the two functions. A duplicate-tag commitment would let `find` pick a different entry than `any` matched. `crates/core/src/seal/grant.rs:986` rejects a duplicate tag at decode with `TrustViolation::DuplicateGrantTag`, and `grant.rs:1011` enforces the same invariant at encode with a release-active `Err`. Encode and decode stay symmetric per AGENTS.md rule 8. The asymmetry is therefore not reachable. **No finding.**

### Trust boundary: what does a non-`Granted` verdict carry?

| Class | Permission written | Write seed |
| --- | --- | --- |
| `Granted` | The committed value from the owner-signed entry | Deposited only when the value is `Write` (`open`, line 735) |
| `RevocationSignal` | Forced to `Read` (line 425), when grafted | Removed (line 432) |
| `Unresolvable` | `carried` | Removed when carried is not `Write` |
| `EpochLag` | `carried` | Removed when carried is not `Write` |
| No contact in the book | `carried`, class `Unresolvable` (line 396) | Removed when carried is not `Write` |
| Budget exhausted or damper not due | The held verdict, unchanged | Untouched |

A stale `Write` cannot survive a `Cut`. An owner cut raises the recipient's durable cut-epoch floor, so a replayed pre-cut set fails `verify_commitment_in_force`, `owner_signed_record` reads false, and `classify` returns `Unresolvable`. The post-cut set that does verify holds no blob at the cut recipient's tag, so `classify` returns `RevocationSignal`, and line 425 forces `Read`. Both arms remove the write seed at line 432.

A stale `Write` also cannot survive a `RevocationSignal`, by the explicit demote at line 424-426. The demote is correctly scoped to `grafted`, so a stripped row in a sharer's own set cannot clear material on a scope this vault owns.

### Fail-closed: the no-verdict fallback

`live_permission` returns `share.permission` when the map holds no verdict. That happens before the first pass, after a restart, when the contact-store read fails, and when the `MAX_RESOLVES_PER_PASS` budget of 16 runs out on a vault that holds more bookmarks than that.

The fallback is acceptable, for three reasons.

1. **The bookmark copy is not attacker-controlled.** `accept.rs:907-913` takes the permission from `candidate.grant_section.commitment.entries`, at the tag the verified contact's subkey locates, and returns `AcceptError::UncommittedTag` when no entry exists. The comment at line 905 states the rule: the untrusted pointer's word is not authority. `reconcile` runs only after `adopt_deferred` succeeds (line 986), so the stored value always passed the gate once.

2. **It is a display value, not a capability.** The write affordance is gated separately and twice over, at `facade.rs:11354`:

```rust
permissions.get(&amp;root.0) == Some(&amp;CommittedPermission::Write)
    &amp;&amp; seeds.contains_key(&amp;root.0)
```

`scope_write_seeds` lives in memory only, and the module comment at `received_status.rs:427` states the rule. A restart therefore admits no write until a tick re-proves the pass, whatever the row says. This satisfies the blueprint's position that a grant blob the pass opened is the whole of the capability.

3. **It degrades toward staleness, not toward forgery.** The fallback is the last owner-signed value this device verified. The failure mode is a row that lags an undelivered downgrade, which is the same residual the whole "revocation is discovered, not delivered" model accepts by design.

I record one honest limitation. A host that renders the permission badge without the standing badge would show `write` with no hint that no pass has resolved the share. The engine gives the host both fields, and `resolution: None` is explicitly documented at `revocation.rs:24` as "not yet known" rather than `Granted`. The obligation sits with the host, and `apps/web/src/routes/SharedPage.tsx` meets it.
