<result>## Root cause found — it is not provisioning. It is the read accelerator's new session bearer + browser CORS.

I reproduced it live in Chrome against the still-running local stack (web preview :4173, mock routing :3001, Kubo :8080) and traced it to the byte.

### The mechanism (proven, not inferred)

`892ca9981` (in your range) changed the accelerator's credential from *host-configured* to *the live session JWT*:

- `crates/engine/src/facade.rs:1664` — `gateway: gateway.into_gateway(accelerator_bearer.clone())`, and `:1735` `.with_session_bearer(...)`, so `api.login_identity` at `:1739` fills the same cell.
- `crates/engine/src/content/read.rs:219-230` — `into_gateway` attaches that bearer to the accelerator leg **if `carries_credentials_safely`**, and `:176-188` returns `true` for `localhost | 127.0.0.1 | [::1]` — the comment even says "a loopback host for local development (`apps/web/.env.example` ships a `http://localhost` Kubo)".
- `crates/engine/src/content/read.rs:382-387` — every block fetch then carries `Authorization: Bearer &lt;jwt&gt;`.

At the base commit that bearer was `Option&lt;Zeroizing&lt;String&gt;&gt;` supplied by the host (`git show 4128ccc:crates/engine/src/content/read.rs:68`), and `apps/web/src/engine/config.ts:103-104` never supplied one — so the request went out unauthenticated.

An `Authorization` header makes the cross-origin GET non-simple. Kubo's gateway advertises `Access-Control-Allow-Headers: Content-Type, Range, User-Agent, X-Requested-With` — **no `Authorization`**. Measured in the page itself:

```
Accept: application/vnd.ipld.raw               -&gt; 200, 1052 bytes
Accept + Authorization: Bearer x               -&gt; FAIL "Failed to fetch"   (preflight rejected)
```

`VITE_PUBLIC_GATEWAYS` is unset in `apps/web/.env`, so the accelerator is the only source (`read.rs:166`, `:315-319` rotates on transport failure — there is nothing to rotate to). Every block read in the browser now fails.

### Answers

1. **No new provisioning gate is failing.** The real gates are: the resolve-tick loop spawns only with a root name (`facade.rs:2192`), and the drain leg runs only when *both* scope seeds are cached (`facade.rs:2388-2390`). Both were satisfied in my repro. What blocks the publish is one step later: `Drain::load_scope_root` (`crates/engine/src/sync/drain.rs:838-852`) needs the root's head block through the gateway (`assemble_head_envelope`) and returns `Halt::UploadAttempt` when it cannot — silently, no dead letter. The same gateway failure makes `RootAdopter` fail, which the tick maps to `RefreshVerdict::Unreachable` → the exact string you saw (`facade.rs:2640`).

2. **All-zero root id is legitimate.** `facade.rs:1669` seeds `Snapshot::new(NodeId([0u8; 16]))`, and `facade.rs:2227`: "The vault's own root scope and root node are the anchored all-zero id16". It is not an unprovisioned tell.

3. **`handOffLoginSecret` is identical on both paths and the hook is missing no facade call.** Both `packages/login/src/flow.ts` (`handOff`) and `apps/web/src/engine/introspection.ts` call `handOffLoginSecret(facade, exporter)` → `facade.start(secret)` (`packages/login/src/secret.ts:63-73`). Provisioning lives *inside* `start` (`facade.rs:1779`). Live proof: the hook login minted the vault — no `vaultUnprovisioned` event was emitted (the event does cross the bridge: `crates/wasm/src/lib.rs:748`), and the mock routing log shows the mint's two PUTs (root record then vault pointer, both 200) followed by the tick loop GETting the root name 200/310 bytes every cadence. The app's own path only adds the API identity exchange before Core Kit; the engine does its own `api.login_identity` either way.

4. **No test can see this.** `crates/engine/tests/write_plane.rs:578` builds engines on `ApiBaseUrl::offline()` (which skips provisioning by design, `facade.rs:1776-1779`) and plants records, so "first-run mint → queued write drains" is never composed. The gateway tests use a scripted HTTP fake and assert only that the header is *present* (`read.rs:506` "accelerator request carries the member bearer token"). CORS is browser-only, and the wasm suite's new test just proves a host-supplied bearer is refused (`crates/wasm/src/host.rs`). Your web-e2e write-path specs are the first thing in the repo that could catch it.

5. **Root cause, one sentence:** since `892ca9981` the engine stamps the session JWT onto every read-accelerator request — including a loopback Kubo, which `carries_credentials_safely` explicitly permits — and the browser's CORS preflight for `Authorization` is rejected by that gateway, so no block can be read, the root never adopts, and the drain halts in `load_scope_root` before it publishes.

**Smallest fix — it is main's regression, and the one-liner belongs in `crates/engine`:** in `crates/engine/src/content/read.rs:176-188`, stop treating a loopback accelerator as credential-safe (fall to `GatewaySource::public(base_url)`, `read.rs:227`). No browser will ever deliver an `Authorization` header to a plain local gateway, so the loopback exemption can only ever break reads — and it also stops shipping the session token to a gateway that isn't CipherBox's. Staging/prod are `https://` and unaffected.

Caller-side alternatives if you want the loopback exemption kept: move the Kubo URL from `VITE_READ_ACCELERATOR_URL` to `VITE_PUBLIC_GATEWAYS` in `apps/web/.env`(+`.env.example`, + the web-e2e CI env), or add `Authorization` to Kubo's `Gateway.HTTPHeaders` CORS allowlist in the compose file. Either unblocks the specs, but neither protects the next host that points the accelerator at a gateway it doesn't control.

One thing to check separately: whatever real accelerator staging uses must allowlist `Authorization` in its CORS response, or the web app will fail there the same way.</result>

<result>## Review: `5dfc33553` — accelerator bearer narrowed to `https://`

Verdict: the narrowing is sound and I found **no path where the session token reaches plaintext transport**. Three real gaps, none of them a token-disclosure bug; the most important one is that the fix does not cover the deployed configuration.

### 1. Downgrade paths — clean

- **Redirects are closed at both seams**, so a `https://` → `http://` hop cannot replay the header: `crates/desktop-seams/src/http.rs:38` (`redirect::Policy::none()`), `packages/client/src/seams/http.ts:29` (`redirect: 'error'`). Covered by `crates/desktop-seams/tests/conformance.rs:476` and `packages/client/src/seams/http.test.ts:125`. The one escape hatch, `ReqwestHttp::with_client` (`crates/desktop-seams/src/http.rs:46`), has a single caller and it sets `Policy::none()` (`crates/load/src/seams.rs:24`).
- **Casing / whitespace / scheme-relative all fail closed.** `HTTPS://`, `" https://…"`, `//gw`, `https:/gw` all miss the prefix at `crates/engine/src/content/read.rs:178` → the leg is rebuilt via `GatewaySource::public` (`read.rs:218`) and never armed. Both host config edges also trim first: `apps/web/src/engine/config.ts:56-58`, `apps/desktop/src-tauri/src/engine/config.rs:89`.
- **Denial is permanent.** `GatewaySource::public` mints a *fresh* cell (`read.rs:146-151`); `SessionBearer::set` is `pub(crate)` and only `ApiClient::with_session_bearer` (`crates/engine/src/facade.rs:1735`) ever writes, into the clone the facade holds (`facade.rs:1651-1665`). A denied leg has no path to being armed by a later login.

### 2. Prefix vs. parse

The prefix is the **right** primitive here, and a URL parse would be strictly *worse*: RFC 3986 schemes are case-insensitive, so a parser would accept `HTTPS://gw.test` and hand it the token, where the prefix denies it. Every parser-vs-prefix divergence I can construct lands on the fail-closed side.

The one input that gets through and probably should not: `REDACTED` passes `read.rs:178` and is handed the bearer. Not a downgrade (still TLS to `gw.cipherbox.test`), and the browser `Request` constructor throws `TypeError` on a credentialed URL so it bricks rather than leaks — but reqwest will send it as Basic auth alongside the JWT. Worth an explicit reject on `@` in the authority, or accept it deliberately and pin it in the test.

### 3. Credential leakage in the read path — clean

`SessionBearer`'s hand-written `Debug` redacts (`read.rs:122-130`); `HttpRequest`'s `Debug` renders header *names* only (`crates/engine/src/seams/http.rs:57-67`); `InvalidBearer` carries nothing (`http.rs:31-33`); the `fetch` refusal string is a static literal (`read.rs:375-377`). Headers are rebuilt per source inside `fetch` (`read.rs:371`), so nothing is retained across a rotation, and `GatewaySource::public` fallbacks hold an unarmable cell. `HttpCredentials::Omit` is pinned on the gateway leg (`read.rs:385`).

### 4. Privacy

An unauthenticated accelerator read exposes **strictly less**: without the JWT the operator sees CIDs + IP + SNI, with it they also get account linkage plus a token that authorizes the whole API. The delta runs the other way — see gap B.

Standing risk this change does not touch: the accelerator is CipherBox's own token-authed Kubo (`CONTEXT.md:81`), and it receives the *full-API* session JWT. A gateway compromise is a session takeover for every online member. TLS is not the mitigation for that; an audience-scoped gateway token is.

### Gap A (highest value) — the fix does not cover staging

The commit's stated root cause is CORS, which is **scheme-independent**, but the fix keys on scheme. The read accelerator in staging is a token-authed Kubo behind TLS. If it ships the same stock `Access-Control-Allow-Headers` allow-list, `Authorization` is still attached (`read.rs:212-216`), the preflight is still rejected, and staging bricks in exactly the way the commit message describes — with `Drain::load_scope_root` halting and the chrome still reading `synced`. Confirm the deployed gateway explicitly allows `Authorization` (and that `vars.VITE_READ_ACCELERATOR_URL`, `.github/workflows/deploy-staging.yml:98`, points at that gateway and not a stock one).

### Gap B — the downgrade is silent, and it can widen the CID audience

`into_gateway` (`read.rs:209-221`) emits no event when it denies the token. If the configured accelerator *requires* auth, every block read now 401s and rotates to `public_fallbacks` — handing the member's read CID set to a third-party gateway that previously never saw it, with no event and no dead letter. That is the same fail-quiet shape the commit message calls out on the write path. Harmless in the shipped local config (`VITE_PUBLIC_GATEWAYS` empty) but not in a real deployment. Recommend surfacing the denial once at construction.

### Gap C — the invariant lives at a call site, not in a constructor

`GatewaySource.bearer` is `pub` (`read.rs:141`) and `Gateway.accelerator` is `pub`, so `carries_credentials_safely` guards exactly one call site. Any future in-crate `GatewaySource { base_url, bearer }` bypasses it silently. Make it structural:

```rust
impl GatewaySource {
    /// The only way to attach a credential: TLS or no token.
    pub fn accelerator(base_url: impl Into&lt;String&gt;, bearer: SessionBearer) -&gt; Self {
        let base_url = base_url.into();
        if carries_credentials_safely(&amp;base_url) { Self { base_url, bearer } }
        else { Self::public(base_url) }
    }
}
```
