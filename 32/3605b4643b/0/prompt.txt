<result>## Decision brief — #1355 (core: how a carried field declares itself uncuttable, before the v2.0 wire freeze)

### (a) The question

`crates/core/src/seal/envelope.rs:111` protects exactly two carried fields from the produce-side cut by hard-coded name — `const UNCUTTABLE: &amp;[&amp;str] = &amp;[GRANT_SECTION_KEY, WRITE_SEALED_KEY]` — and that list is frozen the moment each binary ships, so no v2.0 reader can ever learn that a v2.1 additive field is protocol-bearing and will silently drop it under size pressure. **Decide now whether the wire reserves a way for a future field to declare itself uncuttable (a key-name marker or a reserved sub-map), or whether we write down that no additive envelope field will ever be protocol-bearing** — retrofitting is impossible once v2.0 binaries exist, because an old binary cannot be taught a new key name.

### Ground truth I confirmed

| Fact | Evidence |
|---|---|
| The cut is unconditional and one-pass, ranked largest-first | `envelope.rs:138-197`; ranking at `:171-175` |
| `epochTag` names are deliberately **not** protected — protecting a name there would hand a padder an uncuttable name | `envelope.rs:105-111`, test `envelope.rs:588` |
| Map keys are unconstrained UTF-8 text; ordering is length-first then bytewise | `codec/decode.rs:215-240`, `codec/value.rs:190-194`. `!` (0x21) sorts before every letter/digit at equal length. **A one-byte prefix is representable today and no reserved key uses it.** |
| Envelope carried unknowns survive rotation verbatim — they are **not** cleared like the grant section is | `net/rotation.rs:865`, `:994`, `:1611`, `:1789`, `:2667`. Contrast `rotation/reseal.rs` building the section with `PreservedFields::new()` (cited in #1356). **So envelope-level bloat is relieved only by the cut; nothing else ever reclaims it.** |
| A cut is reported, not silent | `net/author.rs:274-289` → `sync/drain.rs:2021,2435` (rotation paths still don't report — that is open issue **#1362**) |
| The grant section is bounded only by **counts**, never bytes | `seal/section.rs:282` (`MAX_HISTORY_LINKS=256`), `:289` (`MAX_GRANT_BLOBS=1024`), checks at `:330,349,383` — this is exactly #1356 |

| A forward `v` is refused for re-seal, not gracefully handled | `net/rotation.rs:721`, `:1212` — `if envelope.v != ENVELOPE_V { return Err(ResolveFailure::Rejected) }` |

**The load-bearing consequence nobody has written down yet:** any self-declared uncuttable marker is declared *by the publisher*, so a hostile publisher marks their padding critical and resurrects the exact wedge the truncation was built to close — and because rotation carries envelope unknowns verbatim, that bloat would be permanent rather than rotation-clearable. **A marker is only sound if it ships with a release-active byte budget enforced symmetrically at `decode_envelope` and `encode_envelope`** (AGENTS.md rule 8), so an over-budget record never enters anyone's carried set in the first place.

---

### (b) Options

**Option A — reserved key-name prefix (`!`), plus a frozen critical-bytes budget.** The shape #1355's body sketches.

- Pros: `canonical_key_cmp` is length-first (`value.rs:190`), so a one-byte prefix perturbs no ordering semantics; costs 1 byte per critical field. Works uniformly at top level *and* inside `epochTag` — the budget is what makes that safe, closing the `envelope.rs:105-111` objection rather than dodging it. Composes: the grant section and write body can adopt the same convention later with no second reservation. `UNCUTTABLE` becomes "the two grandfathered names **or** the marker test" — a predicate swap at `envelope.rs:171`.
- Cons: requires a budget constant and two new symmetric checks; the budget is only meaningful if `grantSection` is itself byte-bounded, so **this option makes #1356 a hard prerequisite, not a sibling**. Grandfathering is permanently visible (two names that can't carry the marker without a wire break).
- Cost: ~40 lines in `envelope.rs`, one constant + `manifest.json` key (mirroring `writeBodyMaxBytes`), 2-3 unit tests, envelope reject vectors + count bump, one blueprint paragraph.

**Option B — reserved sub-map key (`"critical": {...}`) added to `UNCUTTABLE`.**

- Pros: smallest code delta — one more string in the `envelope.rs:111` array plus a single `as_bytes().len()` budget check; no predicate, no scan.
- Cons: the reservation is per-map, so `epochTag` and every nested map needs its own future reservation; ~11 bytes of key+framing overhead per record forever vs. A's 1 byte per field; all-or-nothing granularity — a v2.0 client cannot reason about individual entries inside a map it does not type. Same budget requirement, same #1356 dependency.

**Option C — declare that no additive envelope field will ever be protocol-bearing; write down the reasoning; change nothing on the wire.**

- Pros: zero wire bytes, zero code, zero freeze risk, no dependency on #1356. Consistent with today's `envelope.rs:105-111` reasoning taken to its conclusion.
- Cons: this is the expensive one, and the cost is invisible today. Interior (non-scope-root) envelopes have **no** uncuttable field at all — `grantSection` and `writeSealed` exist only on scope roots — so under C an interior node can never gain a protocol-bearing additive field, ever. The only escape is a typed field with an envelope `v` bump, and `rotation.rs:721/1212` reject a foreign `v` outright, so a `v` bump is a hard per-node fork, not graceful evolution. The `revocationPin` example in #1355 is precisely the thing C forbids.

**Ranking sub-decision (#1355 checkbox 3), orthogonal to A/B/C.** Largest-first (`envelope.rs:175`) bounds the *count* of fields destroyed; smallest-first bounds the *bytes* a single cut destroys but never relieves the pressure, so every later edit cuts again. Under A or B the adversary that largest-first leaves in scope — aiming the first cut at the one honest protocol-bearing field — is closed by the marker, so **largest-first should be kept**. Under C that adversary stays live and the argument for revisiting is stronger, but only marginally: under C nothing cuttable is trust-bearing by declaration, which is the same defense stated as policy instead of as bytes.

---

### (c) Recommendation

**Option A, paired with #1356, largest-first retained.**

The deciding argument is not elegance, it is that C's cost lands on interior nodes and is unrecoverable. Every other bound in this codec chose reservation over prohibition — `MAX_WRITE_BODY_BYTES` (`write_body.rs:365`) exists because per-field bounds were a treadmill, and the same reasoning says a per-name uncuttable list is a treadmill that stops moving the day we ship. A costs one byte per future critical field and buys a graceful additive path that C spends a `v` bump on. B is A with a worse footprint and a per-map reservation debt.

The non-negotiable rider: the marker ships **with** the budget, symmetric across `decode_envelope` and `encode_envelope`, release-active, in the `assert_within_bound` style (`write_body.rs:414`/`:529`), frozen in `manifest.json` beside `writeBodyMaxBytes`. Without it, A hands every publisher an uncuttable pad that rotation never clears — strictly worse than today.

# Decision brief — #1399, the recycle bin as vault-level engine behavior

**Grounding:** `main` @ `3d3ac0fc1`. The existing proposal comment on #1399 was grounded at `243c6ce74` (5 commits back); its claims verify but many line numbers have drifted — corrected numbers are used throughout.

## (a) The question

The bin does not exist anywhere in `crates/engine`, `crates/core`, `packages/client`, or `apps/web`, yet `blueprint/web-client.md:266` commits `/bin` with "restore/purge ops via facade" and `blueprint/desktop.md:192-194` calls the bin "vault-level engine behavior." The decision is where a deleted node's *state* lives between delete and purge, and what rebase, rotation, and reclamation rules that placement inherits.

**No frozen decision constrains this.** The blueprint cites `FSM1/cipher-box-next#5` for recycle-bin semantics, but #5 is the v1 feature keep/cut list and never mentions the bin — the citation only carries "nothing shipped in v1 was cut except vault import." This is open design.

## Four findings that reshape the problem

**F1 — Today's delete is already half a bin, and a revocation hole.** `publish_delete` (`crates/engine/src/sync/drain.rs:1330-1356`) drops one `ChildRef` and republishes the parent. The child's record is never retired (the only `retire(...)` sites in drain.rs are `2615`/`2636`/`2663`, none on the delete path), its `HeldRecords` entry is never evicted (`drain.rs:2578` is the *only* mutation of `held` in the whole crate), and content is never unpinned (`release_staged_blocks`, `drain.rs:2329-2334`, early-returns because a `Delete` op yields no content root, `op.rs:434-446`). That is #1434. **The unstated consequence: an unlinked-but-live node is unreachable from the tree, so it is in no eager set (`CONTEXT.md:21`) and no sweep. A revoked grantee holding the old scope seed keeps reading every deleted node forever.** That is a fail-open revocation residual on `main` today, and it is the decisive argument in D1 below.

**F2 — The rebase rule collides, and nobody has noticed.** `Delete` today rebases under *conditional delete* — dropped if the target advanced, edit wins, "a rebased edit resurrects a concurrently deleted node" (`blueprint/engine.md:400`, `CONTEXT.md:60`, code at `sync/rebase.rs:503`). `Move` rebases under a different rule entirely — dest-first publish, presence-conditional source-remove, race loser compensates (`blueprint/engine.md:404`, `publish_ref_move` at `drain.rs:1363`, source check at `drain.rs:1387-1389`). Repointing `Delete` at a relink-into-bin silently swaps one blueprint-locked rebase rule for another, and `blueprint/desktop.md:199` explicitly promises the FS core renders "edit-wins deletes." This needs an explicit decision (D5), not a side effect.

**F3 — A repointed `Delete` fills the bin with `.DS_Store`.** FUSE `rmdir` refuses a non-empty folder (`crates/fuse/src/ops.rs:1137-1155`) but treats platform junk as invisible, then `delete_descendants` issues **one `Command::Delete` per junk descendant** (`crates/fuse/src/ops.rs:1027-1046`). Repoint `Delete` and every hidden junk file the mount sweeps becomes a user-visible bin entry.

**F4 — v1's bin was not a folder at all**, which is a fourth model the proposal never weighed: a standalone per-user JSON blob, ECIES-sealed, published at an IPNS name HKDF-derived from the login secret (`v1:packages/core/src/bin/derive-ipns.ts:19-21`), holding `BinEntry` records with `originalParentIpnsName`, `originalPath`, `deletedAt`, `descendantCids`, and `originalFolderKeyEncrypted` (`v1:packages/core/src/bin/types.ts:19-73`). v2 has the exact structural precedent for it — the vault settings record (`crates/engine/src/settings.rs`, 1719 lines; core framing at `crates/core/src/seal/settings_record.rs`, body opaque to core) and the owner-local store family (`crates/core/src/seal/owner_local.rs`, `OwnerLocalKind::{ReceivedShares, ContactBook, InviteRecords}`). It is a real option, and F1 is what kills it.

## (b) Sub-decisions

### D1 — Where deleted entries live

| Option | Mechanism | Pro | Con |
|---|---|---|---|
| **A. Bin root per scope** (reserved `NodeId`, ordinary folder child of the scope root; trash = intra-scope relink) | `OpKind::Move`/`Relink` under `ScopeCrossing::Intra` already exists and is the only crossing that publishes (`facade.rs:3685`, `:3713`; `drain.rs:1228` halts every other) | Node seeds are id-derived and location-independent (`CONTEXT.md:7`), so trash and restore are **pure relinks — no re-seal, no epoch change, no new KDF edge**. Binned nodes stay in the scope subtree, so they ride the lazy wave and re-seal on revocation — **this is the only option that closes F1.** `/bin` gets a per-scope listing free from `snapshot(binRoot)`; only the cross-scope union is new | Binned items are visible to that scope's grantees — deleting a shared file moves it to a shared trash. "Vault-level" becomes a facade aggregation, not a storage property. Needs a reserved-id mint guard and origin metadata (D2) |
| **B. Owner-sealed bin index; node stays unlinked-but-live** (v1's model, over the settings-record or owner-local pattern) | `settings.rs` / `received_share_store.rs` are working templates; delete path unchanged | Literally vault-level, one flat list. Owner-only by construction — no grantee disclosure. **Zero change to `publish_delete`, to the conditional-delete rebase rule, and no F3 regression.** Core cost near zero (both structures seal an engine-encoded body core never interprets) | **Fatal on F1**: a node absent from the tree is in no eager set and no sweep, so revocation never cuts access to anything binned. Also: the owner-local family rides the *per-device* `StagingStore` (`received_share_store.rs:1-10`), so it needs the published settings-record machinery instead — and that reintroduces v1's worst flaw, a whole-list rewrite with no CAS (`v1:packages/sdk/src/bin/index.ts:336-356` documents the resulting data-loss bug at length). Restore also needs a relink of a node absent from `Snapshot`, which no op supports. A grantee's delete lands in the grantee's private bin — the owner loses the file with no way to see it |
| **C. Tombstone on `ChildRef` in place** | New `deleted` field in the read-body | Restore trivial; origin metadata structurally free | Every read path must filter, and one that forgets is a **fail-open disclosure**. `/bin` has no index, so the vault-level listing is structurally incomplete. Adds a semantic field to the most-read structure in the wire format |
| **D. One vault-level bin scope** | — | Matches the words in the blueprint exactly | Unbuildable in v2.0. Every delete becomes a cross-scope move — refused at journal time (`refuse_scope_exit`, `facade.rs:1675-1686`, `ScopeExitRefused` at `:1152`) and at publish time (`drain.rs:1228`) — and per `CONTEXT.md:11`/`:21` a scope exit out of a granted scope is **a rotation per delete**. `consume_scope_exit_triggers` (`rotation/trigger.rs:106`) has zero production callers; `ReplayReport::scope_exit_triggers` (`rebase.rs:183`) is populated and dropped |

### D2 — Where origin metadata lives (only live under A)

| Option | Pro | Con |
|---|---|---|
| **Optional `origin` on `ChildRef`** `{parentId, name, deletedAt}` | Sealed inside the read-body, so it discloses nothing; renders in the listing with no resolve. `Map::insert` is canonically ordered by construction (`crates/core/src/codec/value.rs:224-233`), so ordering is free | One core wire change: accept + reject vectors, `manifest.json:207`/`:211` count bumps against the drift assert (`kat_manifest.rs:2165-2169`, `:2210-2213`), a reject `check` string pinned by `every_crate_check_is_pinned_by_a_vault_family` (`kat_manifest.rs:1704-1711`), and an AGENTS.md rule-8 release-active encode check matching `assert_children_unique` (`core/src/seal/body.rs:397-412`). Core gates engine, so it serializes the slices |
| **Ride `ChildRef.unknown` (`PreservedFields`)** | Genuinely zero-core — `collect_unknown`/`merge_unknown` (`body.rs:505-525`) round-trip byte-stably and typed fields always win | It *is* a wire format, with no schema, no acceptance domain, no reject vectors. Abuses the forward-compat channel. Same objection as encoding origin into the name string |
| **Owner-local side index for origin only** | No core change | Per-device (`StagingStore`), so origin is lost on the other device; and unreadable to a grantee restoring from a shared bin |

### D3 — Retention and what triggers a purge

The AC sketch on #1399 says "retention expiry is driven by the injected clock seam." That contradicts #1094's recorded decision (count-based keep-latest-N, no clock, declined age-based rules for replay determinism) and needs reconciling.

The engine reads its clock seam (`trait Scheduler`, `crates/engine/src/seams/scheduler.rs:50`) **exactly once per command**, at `facade.rs:3651`, journaled onto the op (`op.rs:43`), and every downstream publish reuses `applied.op.authored_at.0` (`drain.rs:1276, 1302, 1317, 1350, 1394, 1627, 2169`). So `deletedAt` is *data* and the UI may freely display "deleted 12 days ago"; the question is only whether the engine may **branch** on `now()` to destroy data.

| Option | Pro | Con |
|---|---|---|
| **User-initiated purge only** | Matches the existing blueprint rule verbatim — `blueprint/engine.md:796-797`: "Retention default: keep all versions within quota, with an explicit **user-initiated prune op**." No determinism question. No data destroyed without a gesture | The bin grows against quota until emptied |
| **Count/byte budget on `VaultSettings`, actuated at trash time** (pure function of bin contents, so replay is deterministic) | Bounded bin; each emitted purge carries its own journaled `authored_at` | **Verified precedent warning: `VaultSettings.retention` is plumbed end-to-end and never actuated.** Its only non-test read repo-wide is the encode arm at `settings.rs:925`; `Op::prune` (`op.rs:419-430`) has zero production callers; there is no `Command::Prune` (`facade.rs:807` is the unrelated `PruneInviteLinks`). `plan_prune` is called only from `publish_prune` (`drain.rs:1779`), which no production op reaches. A bin budget added the same way is the second dead setting — it ships with its actuation or not at all |
| **Time-based auto-purge via the clock seam** | What #1399's AC asks for; what v1 did (`recycleBinRetentionDays`, default 30, `v1:packages/core/src/vault/types.ts:73-84`) | v1's was an **opportunistic sweep on bin load** (`v1:apps/web/src/hooks/useBin.ts:45-52`) — if the user never opened the bin, nothing ever expired. Retention was advisory, not enforced. A clock branch inside a replayed decision makes two devices reach different bins, and it destroys data with no undo, hardest on the device offline longest — exactly the rule #1094 declined |

### D4 — Reclamation, and how purge settles (composes #1434 and #1094)

Purge is not "the bin's hard-delete path" — **purge is the reclamation the engine does not have at all**, bin or no bin (F1). `publish_prune` (`drain.rs:1751-1845`) is the template: it owes every doomed root to the `RetireLedger` (`drain.rs:1806-1809`, `seams/retire_ledger.rs:14-30`/`:69-80`) **before** publishing (`:1810-1839`), and refuses the whole op if a doomed CID is also named by a survivor (`drain.rs:1786-1801`).

**Refcounted unpin needs no new counter** — the safety property #1399's AC asks for is already implemented and tested: a target the live record still names retires nothing (`net/retire.rs:318-321`, test `:845-854`); a pass that cannot establish the live set stands down (`net/retire.rs:310-313`, test `:858-871`); register and retire derive their CID sets through one function with an equality invariant (`content/retention.rs:188-200`, test `:499-525`). Cross-*node* sharing is the registry's job (`CONTEXT.md:78` union liveness).

**The settlement hazard is real and confirmed with a sharper mechanism than the proposal stated.** `live_node_cids` (`drain.rs:1920-1942`) resolves the owing node by its *own derived write name* (`drain.rs:1925`) with `ResolveMode::NoCache`; a `None` skips the entry (`net/retire.rs:310-313`) and the ledger is never-discard by contract (`seams/retire_ledger.rs:62-65` — "There is no attempt budget, no expiry, and no sweep"). A plain `Delete` does *not* strand debt today, precisely because the record is never retired and keeps resolving. **Any purge that removes the record produces a permanently unsettleable debt: pinned bytes charged forever.**

| Option | Pro | Con |
|---|---|---|
| **New `OwedRetire` "no live record by construction" class** the pass treats as an empty live set | Cheapest; keeps the deliberate leak-not-loss polarity (`drain.rs:1918-1919`, `blueprint/engine.md:145-146`) | A new trust-shaped class in the ledger; needs its own test that a mislabeled entry cannot unpin a live record |
| **Retire the `ipnsName` only after content debt settles** | No ledger change | Leaves a resolvable record for an item the user was told is gone |
| **Never retire the name** (status quo) | Zero work | The #1434 leak stands: quota spent forever, republisher effort forever, and the F1 revocation hole stands |

**#1094 composes cleanly, not awkwardly:** a purge owes every version root through `version_cids` — the same channel `plan_prune` uses — so keep-latest-N and bin purge feed one ledger with no interaction beyond it. Note also that v2's location-independent node seeds delete an entire v1 problem class: v1 had to stash `originalFolderKeyEncrypted` on every bin entry and re-encrypt the record on restore (`v1:packages/core/src/bin/types.ts:60-72`); under D1-A there is nothing to re-encrypt.

### D5 — Command shape and the rebase rule (this is the one the proposal misses)

| Option | Pro | Con |
|---|---|---|
| **Repoint `Delete` at trash; `Purge` is the hard delete** | Every existing caller becomes recoverable by default, FUSE `unlink` included (`blueprint/desktop.md:192`); `delete` already has a wasm builder (`crates/wasm/src/lib.rs:991`) whereas **`Command::Move` has none** — so trash must reach web through `delete` regardless | Swaps the conditional-delete rebase rule for the Move rule (F2), amending `blueprint/engine.md:400` and contradicting `desktop.md:199`. Hits F3 — the FUSE junk sweep fills the bin |
| **Repoint `Delete`, but keep it rebasing under the *delete* rule** (relink mechanics, delete semantics: a concurrent edit drops the trash and the node stays put) | Preserves both blueprint rules unamended; the user-visible outcome ("edit wins") is identical to today | A relink that rebases like a delete is a new hybrid — needs its own rebase arm and tests. Still needs an F3 carve-out: an explicit hard-delete path for the junk sweep |
| **New `Trash` command; `Delete` unchanged** | No rebase-rule question at all | FUSE `unlink` stays a permanent delete unless separately rewired, so desktop deletes are unrecoverable — against `desktop.md:192` |

### D6 — What #1400 actually needs from the engine

Not a design choice so much as a cost the plan must carry. `snapshot()` refuses non-folders (`facade.rs:5634-5637`) and listing is strictly parent-keyed (`Snapshot::children`, `sync/model.rs:266-281`) — there is no predicate, no flat scan. The only flat facade read is `received_shares()` (`facade.rs:5690`), landed three days ago in `3d3ac0fc1`, which is the precedent to copy.

- **A new command** is a mechanical 5-file change: `facade.rs` (enum `:610` + `Debug` label `:794` + handler `:3663`) → `crates/wasm/src/lib.rs` builder → `packages/client/src/worker/protocol.ts:213` union → `commandCodec.ts:233` case (a missing case is a compile error via the `descriptor: never` bound at `:224-226`) → `packages/client/src/facade.ts` one-liner.
- **A new flat read is ~9 files**, because reads bypass the command envelope and every transport implements them individually (`engineHost` → `serve` → `transport` → `correlatedTransport` → `broadcast` → `broadcastTransport` → `leaderRelay` → `engineClient` → `facade`, plus `testkit`). Budget the read as the dominant client cost.
- Web side: `/bin` currently falls through the `*` catch-all (`apps/web/src/App.tsx:10-23`); `AppSidebar.tsx:13` is the `comingSoon` stub, `NavItem.tsx:77-88` discards `to` entirely when stubbed, and the `bin` icon already exists. `apps/web/src/stores/sharing.store.ts` is the right store shape (a projection with no independent writers); `useVaultActions.ts:1-6` states the law the page must obey — "the UI never patches its own listing," so a restore must re-read rather than optimistically remove the row.

## (c) Recommended package

1. **D1 → A, bin root per scope**, aggregated into one listing at the facade. The decisive reason is F1, and it is not the reason the proposal gave: only Option A keeps binned nodes inside the scope subtree, so they ride the lazy wave and a revocation actually cuts access to them. Options B and C leave a revoked grantee reading everything ever deleted. Accept the consequence: a scope's grantees see that scope's bin, and a grantee's delete lands in the shared bin (the only intra-scope option, and it matches "shared folder trash").
2. **D2 → the `ChildRef.origin` field.** Pay the one core wire change with real accept/reject vectors rather than smuggling a schema-less format through `unknown` or through the name string. This makes core gate engine, so slice core first.
3. **D5 → repoint `Delete`, keep the delete rebase rule** (option 2). It preserves `blueprint/engine.md:400` and `desktop.md:199` unamended, and it keeps `delete`'s existing wasm builder as the path to web — which matters, since `Command::Move` has no builder. Add an explicit hard-delete path for the FUSE junk sweep (`crates/fuse/src/ops.rs:1027-1046`) so `.DS_Store` never reaches the bin.
4. **D3 → no clock, no auto-purge in v2.0.** Purge is user-initiated, matching the standing rule at `blueprint/engine.md:796-797`. Display age from the journaled `deletedAt`; never branch on it. Surface bin bytes beside the quota rather than enforcing a budget — `pending_reclaim_bytes()` (`facade.rs:5614`) is the existing shape for exactly that kind of vault-level figure. Do not add a budget knob to `VaultSettings` unless its actuation ships in the same slice; `retention` is the cautionary precedent and it is verified dead. This requires amending #1399's own AC sketch, which currently asks for clock-driven expiry.
5. **D4 → land the reclamation first, separately, with the ledger class.** #1434 is a standing leak *and* a revocation hole on `main` today; it is landable on its own merits before any bin exists, and nothing about the bin should gate fixing it.

The package's coherence: every piece leans on machinery that already exists and is tested — intra-scope relink, the add/add auto-suffix comparator (`blueprint/engine.md:403`, not v1's `" (restored)"` scheme at `v1:packages/sdk/src/bin/index.ts:599-609`), the retire ledger's survivor check, union liveness at the registry. The only genuinely new primitives are a reserved node id, one optional wire field, and one ledger class.

Two v1 laws worth porting verbatim regardless of the picks: **fail-closed subtree enumeration** — an unenumerable descendant folder aborts the whole operation rather than half-reclaiming, with per-file CID capture staying best-effort (`v1:packages/sdk/src/bin/index.ts:219-234`, cycle-guard at `:244-247` against attacker-influenceable metadata) — and **restore's add-before-remove ordering**, so the item is listed at the destination while still recorded in the bin and is never lost mid-restore (`v1:packages/sdk/src/bin/index.ts:651-652`).
